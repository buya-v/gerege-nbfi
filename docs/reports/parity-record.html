aggregation order
Fineract reserves per loan, rounds each to the minor unit, then sums. A port that sums the balances first and applies the percentage once lands on 74234.31 — one minor unit out, on every provisioning run, with no rounding error to point at.
enum ordinals
Client status ACTIVE is 300, not 2. DAYS_360 stores 360 — the value, not a sequential index. A port that assumes ordinals count upward uses the wrong day-count basis on every interest calculation and never raises an error.
step order
The six COB business steps are pinned in sequence. Run add-periodic-accrual-entries before loan-delinquency-classification and the money differs, with the arithmetic correct throughout.
publication
DEC-2 §4.4.2 is operative. The bar stays red by recorded decision while the finding set matches its baseline exactly — and refuses in both directions, so silencing a finding blocks publication as hard as introducing one.

why 11 are benign
Not because they port a Fineract column — that argument alone is worthless. The Go side was proved: the loan slice owns no persistence (no postgres.go, no database/sql import) and AmountOutstanding has no reader outside its own file and test. So no derived balance reaches a persistence boundary. Verified against LoanCharge.java:152-156 and the amount_outstanding_derived column at :108-109.
why 10 are real
investor/postgres.go does own a persistence boundary — the exact condition the other eleven relied on, and it is absent here. Insert (:108-120) writes the loan-outstanding snapshot into five *_outstanding_derived columns; loadDetails (:187-215) SELECTs them back as authoritative. The write and the read-back close the loop I-3 exists to refuse.
the principle
Stated better by the adjudication than by the brief that commissioned it: “adopting the schema is not adopting the write paths.” The value originates as loan.getSummary().getTotalPrincipalOutstanding() — a balance Fineract derives and this port stored instead.

Repairing the INSERT alone leaves a decoded balance still trusted; repairing the SELECT alone leaves the write path. G-19 — ratified 9 September

Fineract accepts money finer than MNT's minor unit. This port refuses it. That refusal is now a ratified deliberate departure, not an open question — and the same rule now covers three contexts rather than the one seam where it was first seen.

no rule changed
DEC-2 predicate G-08 already said it: "Refuse residue; do not truncate and do not round." Truncating invents money one way, rounding the other, and either makes a parity comparison pass while the systems disagree by a fraction that accumulates. What the ratification added is scope.
what it forbids
No parity vector may ever be derived from a residue value. No int64 of MNT minor units equals 100.125, 40000.245 or 0.005, so such a vector would have to invent a number neither system produced. The oracle's characters are recorded; the port's refusal is the graded answer.
the oracle does generate it
Every earlier instance had its extra digit supplied by a prober, and the open question was whether Fineract's own arithmetic could produce one. It can: a 1% charge on 1162502.50 yields periods[0].feeChargesDue = 11625.025. But the persisted charge is 11625.03 — clean, and rounded HALF_UP. So the hazard is narrower than feared: it lives in projection cells, not stored money. That distinction belongs in the parallel-run assessment, which stays a user gate.

What is not covered

  • savings — three vectors against 1,862 lines. Status ordinals (200/300) and the daily-accrual tie are pinned behind a permanent red-drive; submit, approve, activate and deposit are not.
  • investor — the purchase price, 97.25% of an outstanding balance, appears in no capture. That is an oracle gap, not a promotion gap: no amount of transcription reaches it, only a new capture pass against an endpoint that exposes a settled transfer amount — if one exists.
  • workingcapital — two vectors, including the balance decomposition. The stored balance is observable after all, through the detail endpoint rather than the list; the remaining draw and repayment paths are not.
  • collateral — the ScaledInt valuation has no observable oracle counterpart. That claim was false and is now retracted. GET /clients/{id}/collaterals/{id} computes total = base_price × quantity and totalCollateral = total × pct_to_base/100 on the read path. The proof is that the values cannot be stored: the table carries four columns — id, quantity, client_id, collateral_id — and no total column exists. Pinned as CL-04; the seam is graded.
  • loanproduct · DAYS_360 — the value with the largest money impact is the least corroborated. It is published by the template and exercised by no product in the tenant, so the persistence side is unconfirmed.
  • six roll-forward writes — the only sites that returned UNDECIDABLE, and the most useful result of the adjudication. They name precisely what would settle them: a type-checked forward reachability analysis that fails closed on unresolved value flow. Clearing them on hand-walked evidence would repeat the error the original heuristic already made, so they stay open.
  • the remaining findings — 31 under 12 baseline pairs, each carrying its argument and a stated removal condition. Every one now has a site-level verdict; what is left is remedy, not triage.

Scale, in proportion

The reference implementation is roughly 544,000 lines of main Java across 5,317 files. The Go port stands at 57,626 non-test lines. That ratio is not a completion percentage — the port deliberately excludes Spring Batch, the API layer and much else — but nobody should read 15 of 15 contexts as the migration is done.

The conformance harness is 45,369 lines, roughly 79% the size of the port it grades. That is the cost of proving behaviour against a live oracle rather than asserting it, and it is why extracting a shared core mattered more than the sixteen lines it saved on the day.
