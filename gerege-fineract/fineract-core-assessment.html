Run Fineract as Gerege’s core, and extend it for Mongolia?

Today the program ports Fineract to Go context by context, and a running Fineract serves only as the reference every port must match. The alternative is to run Fineract itself in production, configured for Mongolia, and build what Gerege needs as extensions. This is an exploration, not a decision.

Short answer

It is the faster and cheaper road to a licensed, operating NBFI, and worth exploring seriously. Keep it on two conditions:

  1. A 1–2 week spike proves the Mongolia-specific needs fit as out-of-tree extensions, with no fork of Fineract.
  2. You re-ratify three project rules Fineract cannot meet as written.

What we would gain and what we would pay

Gains

  • Time to a pilot: weeks of configuration and extensions instead of months of porting.
  • Maturity: years of production use at other institutions, and 908 of 938 of its own scenarios pass in MNT on our rig.
  • Cost: Apache 2.0, no licence fee; model credit goes to extensions and tests, not re-implementation.

Costs and risks

  • Two stacks: a Java service to operate, patch and upgrade next to Gerege Nexus in Go.
  • Upgrade discipline: extensions must stay out of Fineract’s core; a fork makes every upgrade a merge.
  • Less control: Fineract’s model decides naming fields, stored balances and the single tenant time zone.
  • Regulatory: FRC acceptance and a parallel run are still needed, as on the Go road.

What carries over from the work already done

  • The reference environment (the standing Fineract, the MNT tenant set-up, the throwaway replay rig) becomes the development and acceptance environment.
  • 322 golden vectors and 938 replayed scenarios become the regression suite for the configured Fineract, for every extension, and for each Fineract upgrade.
  • The Go ports (about 25,600 lines of graded postings and schedule code) can run as an independent shadow ledger: fed by Fineract’s events, they recompute each posting and flag any disagreement. That is a strong control to show FRC and auditors.
  • Gerege Nexus becomes the channel, identity and integration layer in front of Fineract, behind the same adapter contract. The contract stays; only what sits behind it changes.

A spike to decide it

One to two weeks, all of it inside gerege-fineract/, before any commitment.

  1. Configure a Gerege tenant on a throwaway Fineract: MNT, HALF_UP, Asia/Ulaanbaatar, two representative loan products, no savings products.
  2. Build three out-of-tree extensions: national ID validation, the three-part name held in a data table behind a small API, and an event consumer that drives a stub payment-rail service, with the RTGS / ACH+ threshold in config.
  3. Run acceptance: replay the existing golden vectors and Fineract scenarios against the tenant; nothing may regress.
  4. Prove the constraints: no savings endpoint can be enabled, Idempotency-Key can be required on money requests, and a Fineract version bump leaves the extensions untouched.
  5. Decide with evidence: effort per extension, anything that needed a core change (target: none), and a firm pilot estimate.

Decisions for you

  1. Whether to run the spike, with the Go port staying suspended meanwhile.
  2. Whether to re-ratify the three rules Fineract cannot meet as written: whole-minor-unit storage, stored balances, and the name fields.
  3. Whether Ulaanbaatar time is acceptable as Hovd’s business date.
  4. Who operates a Java service in production.

Cutover, FRC sign-off and licence facts stay yours on either road.
