THE FIRST ACCEPTING-SIDE OPENING-BALANCE OBSERVATION THIS PROGRAM HAS EVER TAKEN, AND IT WAS NOT TAKEN ON TENANT `gerege`. It could not be: :812's fall-through requires findNonContraTransactionIds to be EMPTY and `gerege` carries 26 non-contra transaction ids, so the one tenant this corpus grades against is structurally incapable of producing this observation and always will be. T305 measured both registered tenants of the standing reference oracle and NEITHER qualifies -- `gerege` has the ledger; `default` has an empty ledger but runs rounding-mode 6 (HALF_EVEN) at Asia/Kolkata, which CLAUDE.md's own rule makes a DISCRIMINATION PROBE rather than a parity vector, and it has no financial-activity-300 mapping and no GL accounts at all, so :708 would throw first and the answer would be a different refusal. ***** WHERE IT WAS TAKEN, AND WHY THAT IS ADMISSIBLE. ***** On a THROWAWAY Fineract instance stood up from the SAME DOCKER IMAGE the standing reference oracle runs -- sha256:e596339626bf..., verified with `docker inspect -f '{{.Image}}' fineract-fineract-1` -- with tenant `t305` SEEDED at Asia/Ulaanbaatar and rounding-mode 4 (HALF_UP) from the environment variables the pinned source binds into the tenant liquibase seed (application.properties:60-61, 77, 499-501, 514 -> db/changelog/tenant-store/parts/0002_initial_data.xml:41 and db/changelog/tenant/parts/0002_initial_data.xml:219-220). Four things make a capture admissible in this store and the throwaway satisfies all four: (a) THE CODE IS THE SAME BYTES, not merely the same version; (b) THE TENANT ARITHMETIC IS THE RATIFIED ONE -- HALF_UP, and MoneyHelper.PRECISION is a compile-time 19 so the mode is the only tenant-scoped term; (c) THE BYTE PROVENANCE IS THE USUAL ONE -- request bytes, response bytes, status, sha256 of each, captured-at-utc, all committed; (d) THE RECIPE IS COMMITTED AND DETERMINISTIC -- `bash run-all.sh` rebuilds the instance, replays the setup campaign and re-fires the same body. The instance was DESTROYED in the same run (`docker compose down -v`, no named volume declared) and the standing oracle's four ledger counters were re-read BEFORE the POST, AFTER the POST and AFTER the teardown, all three equal to the baseline: 60/64 journal entries, 0 closures, 26 distinct transaction ids, 352 command-source rows. THE TENANT IS CALLED `t305` AND NOT `gerege` ON PURPOSE: a capture whose provenance said `gerege` while it was taken elsewhere would be indistinguishable from one taken on the graded tenant. WHAT IS NOT CLAIMED: this vector says nothing about `gerege`'s accumulated state -- its chart, its products, its 60 entries -- and no capture taken this way could. That is not a workaround here, because THE ACCEPTING SIDE IS ONLY OBSERVABLE ON A TENANT WITH NO ACCUMULATED STATE; for this one observation a disposable instance is not a second-best surface, it is the only possible one. ***** WHAT IT GRADES THAT NOTHING ELSE DID. ***** T296 mutated the port in four arms and measured that ARM A -- refuse whenever req.Command == 'defineOpeningBalance', never reading the posted-id list -- SURVIVED THE ENTIRE CORPUS, because every refusal capture in this store AGREES with it. It is registered as `ledger-wrong-openingbalance-always-refusing` and this vector kills it: it returns a refusal where the oracle returned HTTP 200 and six journal entries. That is the headerRefusingPoster class -- THE REASONABLE THING TO DO, WHICH THE ORACLE DOES NOT DO -- and LDG-04 exists for exactly the same reason. ***** THE SIX LEGS, AND WHY THE BODY CARRIES THREE. ***** saveAllDebitOrCreditOpeningBalanceEntries (:759-797) calls helper.persistJournalEntry TWICE INSIDE THE PER-LEG LOOP: the leg's own entry at :791 and its CONTRA on the financial-activity-300 account at :796, with the opposite side. THE CONTRA IS PER LEG AND NOT SUMMED, and a one-debit-one-credit body cannot tell those two answers apart -- so this request carries THREE legs of THREE DIFFERENT amounts and the readback carries six entries. `ledger-wrong-openingbalance-no-contra` is the port that writes only what the caller sent, and this vector kills that too. ***** A CORRECTION THIS CAPTURE FORCES ON THE REST OF THE STORE. ***** LDG-REFUSE-03's title, this port's STEP 1.5 comment and the oracle's own message at :814 all say that opening balances are refused 'after journal entries posted'. THAT IS FALSE AS STATED. findNonContraTransactionIds EXCLUDES every transaction that touches the contra account, and every entry an opening balance writes touches it -- so OPENING BALANCES DO NOT BLOCK EACH OTHER. OB-ACCEPT-02 re-sent THE BYTE-IDENTICAL REQUEST while six opening-balance entries existed and got HTTP 200 again, with the previous opening balance REVERSED first (:726-735: six reversal entries on their own transaction id, the originals flagged reversed=t with reversal_id set). Only after a PLAIN manual entry (MJE-ACCEPT-01, HTTP 200 -- itself the shape T296's arm B refuses) did the SAME bytes finally draw HTTP 403, with errors[0].args carrying exactly that one transaction id. Three answers, one request body, one tenant, in sequence: ACCEPT, ACCEPT-with-reversal, REFUSE. The predicate is the LEDGER'S CONTENT, not the command and not the tenant. ***** WHAT THIS VECTOR DOES NOT GRADE, stated rather than left to be assumed. ***** (1) glAccountType is EXCLUDED on every leg (expect.legs[].excluded_fields carries gl_account_type), for the reason LDG-04 records at length: glAccountType in a /journalentries response projects the ACCOUNT'S CURRENT classification and not the entry's, so A2-26 observed the identical row rendering ASSET in A2-088 and INCOME in A2-320 with every other cell byte-identical and NO entry edited. Grading it would make this vector go red on a GL-account retype that touched no journal entry. The classification the capture rendered is recorded here and graded by nothing: GL 2 and GL 3 ASSET, GL 4 LIABILITY, GL 1 EQUITY. (2) The REVERSAL behaviour OB-ACCEPT-02 observed is committed but is graded by NOTHING -- no port in this store reverses anything, and promoting it needs a schema that can express 'this POST also modified earlier entries'. It is named in the capability row as the next thing to promote, not left here. (3) The transaction id is server-assigned and is not a graded cell; the rerun invariant is over the LEGS. (4) NO BALANCE IS GRADED: acc_gl_journal_entry's office_running_balance and organization_running_balance are GATE G-12 and this schema has no field for either. (5) The ORDER of the six legs follows the source (:742 debits before :745 credits); OB-ACCEPT-01's request happened to list its legs debits-first, so THE CAPTURE CANNOT SEPARATE 'source order' from 'request order' and this vector does not claim it does.
