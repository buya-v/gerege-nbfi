## THE HEADLINE IS A PROCESS DEFECT: TWO ORCHESTRATORS RAN OVER THIS REPO AT ONCE, AND THE LOCK PERMITTED IT

The cloud fire read `.softhouse/LOCK`, found `started_at: 2026-08-22T06:00:08Z` — **6 h 07 m old**, past the
6-hour staleness threshold — and `HEAD` (`2871f17`) reading *"fire 20260822-140002 closed clean … zero live at
exit."* Both signals said the holder was gone. **It was not.** The local fire had started a **second session**
that reused the **same fire id and the same `started_at`**, so a live holder wore a six-hour-old timestamp.

**The rule is unsound as written, and the defect is in the FRESHNESS SIGNAL, not the threshold.** A lock whose
`started_at` is stamped once at fire start cannot distinguish *"holder died five hours ago"* from *"holder has
been working for five hours."* Raising the threshold trades one failure for the other. **A lock needs a
heartbeat the holder refreshes, and the staleness test must read the heartbeat, not the start time.** Filed
below as the first thing the next fire should fix.

Both fires then independently ran **T251** and **T241** and **reached the same conclusions** — which is
corroboration, not waste, but it is corroboration nobody paid for on purpose.
