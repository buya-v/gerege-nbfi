## 1. THE FORMULATION

> **An `errors[0].args` cell is gradeable iff the wire value is a SCALAR that the vector can
> name as a DECLARED INPUT whose provenance is INDEPENDENT of the response body being graded.**

Mechanised as a **selector**, never a literal:

```
expect.refusal.arg_echo : "transaction_date" | "latest_closing_date"     CLOSED vocabulary
graded cell             : refusal.arg0_value                              (via cmpStr)
want                    : ResolveArgEcho(arg_echo, v.Request)             resolved at grading time
got                     : the implementation's Refusal.Arg0Value
```

**Four properties make it hold rather than merely read well.**

1. **The store cannot write a date literal, even deliberately.** `Refusal.Arg0Value` carries
   `json:"-"`. This package decodes with `DisallowUnknownFields` [`vector.go:920`], so a vector
   file containing `"arg0_value": "2026-01-31"` dies at load with **unknown field**. The rule
   "grade the relation, never the calendar" is enforced by the *type*, not by a reviewer noticing.
   Driven: `TestArgEchoIsASelectorAndNotADate/the_store_cannot_express_a_graded_DATE_LITERAL`.
2. **Each selector is BOUND TO THE CODE its throw site pairs it with**, in both directions, and
   the binding is source-derived rather than conventional
   [VERIFIED: `JournalEntryWritePlatformServiceJpaRepositoryImpl.java:631, 637-638`, pinned
   `426a23544`]:

   | line | refusal | constructed with |
   |---|---|---|
   | `:631` | `FUTURE_DATE` | `transactionDate` |
   | `:637-638` | `ACCOUNTING_CLOSED` | `latestGLClosure.getClosingDate()` |

   **THE SAME WIRE FIELD MEANS DIFFERENT THINGS IN THE TWO REFUSALS.** A vector pairing them the
   other way round is refused.
3. **It is REQUIRED on those two codes and FORBIDDEN on every other**, and on every non-refusal
   vector. An optional cell is one an author drops the day it becomes inconvenient — the
   deflation direction this store pins everything against.
4. **The vocabulary is CLOSED to two names.** Not "closed to what is scalar today": closed in
   source, so widening it is a diff a reviewer sees.

### Why the wire itself carries the discriminator, and it is not an accident of formatting

`ApiParameterError`'s constructor walks the vararg and special-cases **exactly one type**:

```java
if (object instanceof LocalDate) {
    final DateTimeFormatter dateFormatter = new DateTimeFormatterBuilder().appendPattern("yyyy-MM-dd").toFormatter();
    messageArgs.add(ApiErrorMessageArg.from(dateFormatter.format((LocalDate) object)));
} else {
    messageArgs.add(ApiErrorMessageArg.from(object));
}
```

[VERIFIED: `fineract-core/.../infrastructure/core/data/ApiParameterError.java:95-105`, block
duplicated at `:118-128`.]

So "`args[0].value` is a JSON **string**" ≡ "the oracle put a `LocalDate` there" — a **source**
property of the throw site. On OB-01 it is a JSON **array**, because `:815` passes a
`List<String>` as one vararg `Object` [T294 handoff §3 item 1, and the wire].

Observed, verbatim, from the committed bytes:

```

A1-02-future-boundary+1   "args":[{"value":"2026-08-24"},{},{}]   transactionDate 2026-08-24
A2-01-preclosure-on-date  "args":[{"value":"2026-01-31"},{},{}]   transactionDate 2026-01-31
```

## 3. THE PER-CELL ZONE/CLOCK DETERMINATION — made BEFORE the cell was wired

T329's finding is directly in this path: two Fineract fields spelled `createdDate` are
**different quantities on different clocks**, and grading a wall-clock-derived date as a literal
bakes an up-to-8-hour window into a parity vector.

**3a. The render itself reads no clock.** `DateTimeFormatter("yyyy-MM-dd").format(LocalDate)`
[VERIFIED: `ApiParameterError.java:97-99`]. A `java.time.LocalDate` has no instant and no zone;
a date-only pattern over it is a pure field render. The serialisation step **adds nothing and
can shift nothing.**

**3b. `FUTURE_DATE` → `command.getTransactionDate()`.** Reaches `:631` from the request body via
`JsonParserHelper.convertDateTimeFrom` → `LocalDateTime.parse(s, formatter).toLocalDate()`
[VERIFIED: `JsonParserHelper.java:544-547, 558-586`]. **No `ZoneId`, no `Instant`.** On a
`yyyy-MM-dd` body with `dateFormat: yyyy-MM-dd` the whole path is the identity on the caller's
characters. **CLOCK: none. ZONE: none.**

**3c. `ACCOUNTING_CLOSED` → `latestGLClosure.getClosingDate()`.** `GLClosure.closingDate` is a
`LocalDate` on `@Column(name = "closing_date")`, assigned in `fromJson` from
`command.localDateValueOfParameterNamed(CLOSING_DATE)` — the same zone-free parse
[VERIFIED: `GLClosure.java:53-54, 59-62, 70-72`]. **CLOCK: none. ZONE: none.**

**3d. THE FINDING: the two clock-derived dates in this arm are NOT in `args` at all.**

| quantity | clock | zone | echoed into `args`? |
|---|---|---|---|
| `request.transaction_date` | none | none | **YES** (`:631`) |
| `request.latest_closing_date` | none | none | **YES** (`:637-638`) |
| `request.business_date` — `DateUtils.getLocalDateOfTenant()` | **wall clock** | tenant, `Asia/Ulaanbaatar` | **NO** |
| `glclosures.createdDate` — audit insert [T329] | **wall clock** | **JVM** | **NO** |

`:631` constructs `FUTURE_DATE` with `transactionDate` and **not** with the business date it has
just compared against. **So the guard that READS the wall clock does not ECHO it**, and that is
checkable at `:631` rather than merely true today. `GLClosure extends AbstractAuditableCustom`
[VERIFIED: `GLClosure.java:44`], so a `createdDate` exists on that row — it is simply not what
`:637` passes. T328 excluded `createdDate` structurally; nothing here re-admits it.
