## The rule, as shipped (four independent conditions, all must hold)

A worktree is pruned only if **all four** hold:
1. its branch is **merged** into `main` — `git merge-base --is-ancestor <branch> main`,
   read by exit status alone (0 = merged, 1 = not merged, anything else = error, and
   error is **not** folded into "not merged" — it is logged as its own case, but both
   resolve to KEEP).
2. `git -C <worktree> status --porcelain -- :(top)` **succeeds** (exit 0) **and** is
   empty. Exit status is captured on its own line, immediately after the command
   substitution, so it cannot be swallowed by `pipefail` or defaulted by a
   `wc`-on-empty-input trick — the exact class of bug T190/T202 closed at this same
   file's `:224`/`:262`.
3. the worktree is **not** reported `locked` by `git worktree list --porcelain`.
4. its branch is **not** the harness's own auto-generated default per-worktree branch
   (`worktree-<basename of the worktree dir>`, e.g. `worktree-agent-a341e70251b2e0209`).

Conditions 1–2 are the two the task specified. Conditions 3–4 are additions I found
necessary by testing the shipped conditions 1–2 against the **live** repo (below) —
without them, the two specified conditions alone are not sufficient, and I could not
in good conscience report "my own worktree and every live sibling classify NOT
prunable" without adding them, because as shipped-with-only-1-and-2 that claim was
**false** for a discoverable, non-hypothetical case.

## What I found testing conditions 1–2 alone, before adding 3–4

`git merge-base --is-ancestor B main` is **true** both when B's work is finished and
fast-forward-merged, **and** when B has simply never diverged from `main` yet — a
worktree just created, before its agent has made a single commit. The two are
topologically identical: `tip(B)` is an ancestor of `main` either way.

Live-repo evidence [VERIFIED, live gerege-nbfi repo, run from inside my own worktree,
2026-08-22, `git worktree list --porcelain` captured to `/tmp/live-wt-porcelain.txt`]:
my own currently-running worktree's own branch, `worktree-agent-a341e70251b2e0209`,
evaluated **MERGED** by condition 1 alone — trivially, because it had made zero commits
beyond `main` at measurement time, not because its work was finished. Only my
uncommitted edits (condition 2, the clean check) kept it from a **false PRUNE verdict**,
and that was a matter of timing (I happened to have uncommitted edits at that instant),
not of the merge rule being correct. Of the 43 live linked worktrees, **7** carried this
exact default-branch pattern; a merge-status-only scan (script run from my own worktree,
no `-C` into any other worktree — see below) found:

## Why editing the live file mid-fire is safe (repeating the instruction's own point,
verified against how git actually works)

This worktree's edit to `fire-program.sh` lives only on branch
`softhouse/T213-worktree-pruning`, in this worktree's working directory. The live
`.softhouse/bin/fire-program.sh` in the main checkout (`/Users/buv/gerege-nbfi`) is
untouched — I never wrote to it (the harness itself refused a `Write` attempt aimed at
that path earlier in this session, redirecting me to the worktree copy, which is
correct). When this branch is merged, `git merge`/`git checkout` on the main checkout
**replaces the file via a new inode** (effectively a rename onto the working tree path),
so a `fire-program.sh` process already running with the old file open by path keeps
executing the bytes it opened — a running fire is not affected mid-flight by a merge
landing under it. The new pruning logic only takes effect starting the *next* fire that
execs this script fresh.
