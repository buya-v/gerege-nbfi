### The seven findings worth carrying forward

1. **`hierarchy` omits the root's own id.** A child of root id 1 stores `.2.`, **not**
   `.1.2.`; a grandchild stores `.3.4.`. The REST API never returns `hierarchy` at all — it
   returns `nameDecorated`, 4 dots per depth level. **Fineract has no test for this
   anywhere**, so a port that writes the intuitive `.1.2.` would ship green.
   → `out/A2-019-db-glaccount-rows.txt`

2. **A duplicate mapping is accepted at create and detonates at resolution.** Two
   `paymentChannelToFundSourceMappings` for the same payment type → HTTP 200, both rows
   persisted; every later disbursement fails **permanently** with 403
   `"More than one result was returned from Query.getSingleResult()"`. The
   `@UniqueConstraint(name="financial_action")` is JPA-only and **absent from the deployed
   DDL** (confirmed by `\d acc_product_mapping`). The oracle can create a product that can
   never disburse. → `out/A2-prod-067-*`, `out/A2-086-disburse-loan3-dupchannel.json`

3. **Resolution order, observed rather than inferred.** Same product, same amount: payment
   type 1 (override present) credits **GL 16**; payment type 2 (no override) credits
   **GL 2**. The payment-type-specific row wins; absence falls back to the generic
   (`payment_type` NULL) row. → `out/A2-087`, `out/A2-088`

4. **The MISS message renders the enum with spaces**, not the constant name:
   `"…does not exist for an account of type CHARGE OFF EXPENSE"`, `args: ["LOAN", 22,
   "CHARGE OFF EXPENSE"]`. → `out/A2-092-chargeoff-loan1-unmapped.json`

5. **A fourth delete guard is missing.** Children / product-mapping / journal-entry guards
   all fire, and with three live at once the **journal-entry** guard wins. But a GL account
   referenced *only* by a financial activity has **no application guard** — it falls through
   to the raw PostgreSQL FK and leaks `violates RESTRICT setting of foreign key constraint
   "FK_office_mapping_acc_gl_account"` to the caller. → `out/A2-120` … `out/A2-124`

6. **`usage` / `manualEntriesAllowed` are updatable but do not count as "a parameter."**
   Sent alone → 400 "No parameters passed for update." Sent alongside `name` → 200, and the
   `changes` map contains them. Confirmed at source: `GLAccountCommand.validateForUpdate`
   calls `anyOfNotNull(name, glCode, parentId, type, description, disabled)` — omitting all
   three of `usage`, `manualEntriesAllowed`, `tagId`. → `out/A2-141`, `A2-142`, `A2-131`, `A2-132`

7. **Type rules are checked at mapping time and never re-checked.** GL 2 was retyped
   ASSET → INCOME (HTTP 200) while mapped to four products, carrying journal entries posted
   as ASSET, and while being the `ASSET_TRANSFER(100)` target — an activity the oracle
   *refuses to create* against a non-ASSET account. End state in
   `out/A2-150-db-final-state.txt` shows activity 100 → GL 2 with `classification_enum = 4`.
   The oracle holds a state it would refuse to let you create. → `out/A2-111`, `A2-fin-103`

Also worth flagging for the contract: **the duplicate-glCode refusal returns the raw
PostgreSQL text** (`duplicate key value violates unique constraint
"acc_gl_account_gl_code_key"`) straight through the API, and **omitting `usage` is not
caught by the validator** — it reaches the database and returns 403 with the failing row
inlined. Both are wire-visible strings a port cannot reproduce without the same engine and
constraint names.

## Guard driven RED

`manifest.py verify` is the only guard shipped, and it is demonstrably failable.
`prove-manifest-red.py` proves it, and restores the tree:

```
baseline: GREEN (exit 0)
  mutate  -> exit 1 CAUGHT      (one byte changed in a captured observation)
  delete  -> exit 1 CAUGHT      (an observation removed)
  add     -> exit 1 CAUGHT      (a file no recorded recipe produced)
restored: GREEN (exit 0)

RESULT: guard is demonstrably failable
```

It refuses to draw a conclusion if the baseline is already red (exit 2), so it cannot
"prove" anything from a broken starting tree.

## Money handling

Every JSON parse in this directory uses `json.load(..., parse_float=Decimal)` (obligation
**T145**) — see `show.py` and `manifest.py`. All monetary literals in `req/` are bare
integers. Observed journal-entry amounts are reported exactly as the oracle returned them
(`1200000.000000`) and were never routed through a binary double. For the record,
`acc_gl_journal_entry.amount` is `numeric(19,6)` — not a float — read from
`information_schema` and recorded in `out/A2-150-db-final-state.txt`.
