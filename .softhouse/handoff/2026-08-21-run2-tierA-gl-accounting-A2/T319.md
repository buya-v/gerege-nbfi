## Changes Made

### F5 — CRITICAL. The in-session discriminator, re-derived

**The defect.** T309 asked one question: *"was this id `in_progress` in the tasks.json
committed when this fire took the lock?"* — arguing that at that instant the fire has
dispatched nothing. The first half is true; the inference *"therefore nothing in that set
will ever be this fire's own dispatch"* is false, and the counter-example is the incident
T309 was written about. Fire `20260823-140001` took its lock at 14:00:08 with 8 inherited
`in_progress` claims and at 14:05:01 **dispatched 8 workers onto seven of those same ids**
[VERIFIED: `.softhouse/reviews/T302/a2/out-f5-cell.txt`, cell B′ — 7 demotable, every one
a live worker].

**Why the argument, not just the patch.** The broken inference is *"state at instant t₀
settles ownership for all t > t₀"*. It is the same inference in both T309 attempts; only
the evidence source changed (a field, then a git blob). Re-dispatch is not an exotic case
here — it is the documented reason the driver opens on inherited `in_progress` tasks at
all, and this program re-offers parked and `needs_retry` tasks constantly.

**What replaces it: three conjunctive terms, each fail-closed on its own.**

| term | question | why it is there |
|---|---|---|
| **1** inherited | was the id `in_progress` at this fire's lock commit? | T309's term. Necessary, no longer sufficient, no longer asked alone. |
| **2** untouched since | is the task's record byte-identical to its record at the lock commit? | **The F5 fix.** A dispatch is a write — the driver's own commits say *"record PUSHED BEFORE SPAWN (P-85)"* — so a rewritten record reads as a re-dispatch by the fire holding the lock. |
| **3** positively named | did the caller pass `--corpse <id>` for it? | The P-91 burden inversion. Terms 1 and 2 are derivations; if a future edit gets a derivation wrong, term 3 caps the blast radius at what a human enumerated. |

**Term 2 is measured, not reasoned.** `.softhouse/capture/t319-reconciler-f5/probe-objdiff.py`
compares the eight real task records at `5428c0a4` against `5964ab54`, key by key. All
seven re-dispatched ids differ in `attempts` (0→1), `fire` and `note`; **zero survive term
2**, which is the correct answer [VERIFIED: `out-objdiff.txt`].

**Why a whole-record comparison and not a field.** Reading a named field is the shape that
has failed three times: `task["fire"]` (T309 attempt 1, six live workers), `dispatched_at`
(four days stale where present, absent on batch-2 tasks), `task["branch"]` (stale after a
rename — T302 F9). Each needs someone to remember to refresh it, which is **P-45** —
*"a guard that only works when someone remembers to run it enforces nothing"* [VERIFIED:
`.softhouse/patterns.md`, P-45] — with the verb changed. Term 2 interprets no field at all.

**Alternatives rejected, with reasons.** (a) *Detect the `in_progress` transition in the
range `lock..HEAD`* — gives the WRONG answer on the real incident: the seven ids were
already `in_progress` at the lock and stayed so, so there is no transition to find. It is
term 1 wearing a walk. (b) *Per-task process liveness* — there is no process per task; a
subagent is in-process. (c) *Branch WIP* — inverted for the case that matters (a live
worker in its first minutes has no commits).

**Residual risk, stated.** Term 2 detects a re-dispatch because a re-dispatch writes the
record. A fire that spawned a worker onto an already-`in_progress` task while writing
nothing would be invisible to it. That would violate P-85, it is not a shape this repo has
recorded, and term 3 is the backstop for exactly it.

### F6 — HIGH. The anchor is no longer a commit-message search

T309 used `git log -1 --fixed-strings --grep "<subject>"`. `--grep` matches the whole
message, subject **and body**, and `-1` takes the newest — so the anchor was *"the most
recent commit mentioning that string anywhere"*, and a review commit quoting the subject
moves 7 demotions to 8 [VERIFIED: T302 `out-f6-grep.txt`, cells 2 and 3]. T309's docstring
reasoned only about *absence* and called it safe; multiplicity fails the other way.

**The replacement asks for something a message cannot imitate**: the anchor is the newest
commit that **actually touched `.softhouse/LOCK`**, and its **subject** (`%s`, not the
message) must be the lock-take form. Taking the lock *is* writing that file. A release
commit touches the path but has a different subject and is refused; an unparseable subject
is refused; a LOCK whose `fire` disagrees with the anchor's is refused.

**It also removes a second dependence.** The fire id is read off the anchor commit's
subject, so `LOCK["fire"]` is now only a cross-check. That closes **F10** as a functional
matter: the live lock of `20260827-230001` carries no `fire` key, which made T309's
in-session mode **100% inert on the machine it shipped to**. Matrix cell I covers it.

Measured against the five real fire ids: exactly one exact-subject match each, and each is
in the set of commits that touched `.softhouse/LOCK`
[VERIFIED: `.softhouse/capture/t319-reconciler-f5/out-anchor.txt`].

### F7 — HIGH. A missing LOCK now REFUSES instead of granting demote-everything

`caller_is_lock_holder()` returned `"wrapper"` — the authority that demotes every
`in_progress` task — to any caller the moment `.softhouse/LOCK` was not on disk, justified
by a liveness probe that lives in `fire-program.sh` and is run by exactly one caller.
`ready-tasks.py` has **no liveness check of its own** (its six `/bin/ps` references are all
`ps_ancestors()`, which answers *"who am I"*). T302 drove it: no LOCK, 8 live workers,
`mode: wrapper`, *"8 task(s) WOULD be demoted"*.

Now: absent LOCK → `refused`, unless the caller passes
`--no-live-session-established-out-of-band`. The flag is deliberately long, deliberately
not spelled `--force`: it is not permission to override a check, it is the caller
*supplying a fact this module cannot measure*. `fire-program.sh` passes it at the one call
site reachable only after `foreign_live_session_in_repo()` returned 1.

Also closed, same function: a LOCK naming **pid 1** passed the ancestry test for every
process on the host (`ps_ancestors` walks up to and including pid 1). Now refused, and pid
1 is excluded from the accepted ancestor set.

### F1 — HIGH, confirmed on real data. `merged` vs `never-committed`

`rev-list --count main..B` is zero when B has been **merged**, because the work landed;
`branch_wip` read that as *"nothing was ever committed to it"* and demoted to
`needs_retry`, the status that offers a task for re-dispatch. T302 drove it against a clone
with all 528 real heads: **3 of the 8 real corpses (T297, T298, T308) are merged into main
and got that sentence.**

Now `git merge-base --is-ancestor <sha> main` runs before the count and returns a distinct
kind `merged`, whose text says the work landed and that `needs_retry` here means *somebody
must adjudicate*, not *do it again*; the demotion note leads with that clause. When
`--is-ancestor` cannot answer, the verdict is `unverified`, never `absent`. The pruned leg
no longer asserts *"no WIP was found"* — it names merged-and-pruned and renamed as
indistinguishable-from-here.

**Rejected: a new `needs_adjudication` status.** It is not in `fire-program.sh`'s chain
terminal list nor in `ready-tasks.py`'s `NOT_RUNNABLE`, so a task carrying it would appear
in neither READY, BLOCKED nor IN PROGRESS — a silent disappearance, which is worse than a
loud `needs_retry`.

### F4 — MEDIUM. The STEP-0 promise is conditional and names what it cannot promise

The four unconditional lines telling every driver that *"the wrapper repairs it on the way
out"* now name the three paths on which it does not: a signal with too little budget, a
REFUSE from `foreign_live_session_in_repo()` (which returns 0 = REFUSE while **any**
`claude` sits in the repo root — the documented interactive entry point), and a REFUSE from

### F2 — HIGH. The worktree rescue no longer claims a rescue it did not perform

Three git commands, three discarded return codes, and `log "rescued …"` printed
unconditionally — then T288 promoted that claim into a **durable note in `tasks.json`**.
T302 drove it against the population it serves (a SIGKILLed worker's stale
`.git/worktrees/<name>/index.lock`): 128 / 128 / 128, branch absent, worktree still dirty,
log line says rescued.

All three rcs are read; any failure logs *"NOTHING was rescued"* naming each rc and
`continue`s **before** `RESCUE_PAIRS+=`, so an unverified rescue never becomes evidence.
This mirrors T202's fix at `:783-797` — the twin's twin, finally applied to both branches
of the same function.

### F3a — MEDIUM. `examined=0` is no longer spelled like "nobody"

`[[ "${first:t}" == claude ]] || continue` was a one-way filter: an unrecognised process
incremented neither `checked` nor `unknown`, so it could never reach
`(( unknown )) && return 2`, and with nothing recognised the function fell through to
`return 1` — **the value that authorises rewriting `tasks.json`**.

**Two obvious repairs were rejected, and the direction is why.**
- *"`examined=0` ⇒ `return 2`"* — wrong. Zero `claude` processes is a perfectly
  establishable "nobody" and it is the **normal** state on the wrapper's exit path after
  its own driver has been waited on. Returning 2 there refuses every normal-tail reconcile
  and makes T288's whole repair inert — replacing a fail-OPEN with a permanent fail-CLOSED,
  which is the failure T288 exists to remove.
- *"lsof every live process, decide on cwd alone"* — right in principle, unaffordable:
  hundreds of rows inside a ~7 s signal budget, and it would REFUSE on any shell or editor
  in the repo, which is F3b made worse.

So **recognition** is widened instead: basename is `claude`, **or** a path *segment* of the
command line is `claude`. That catches `/Applications/Claude Code/claude` (T302's CASE 1)
and `node /opt/claude/cli.js`. The first draft was a bare `*claude*` substring test and its
own harness caught it matching `notaclaude` — recorded in the code, because over-matching
here drifts toward F3b's inertness. The evidence string now reports how many candidates
matched only by mention.

### F8b — LOW. The two budget layers no longer collapse into one

`RECONCILE_DEADLINE_SECS=$budget` and `reconcile_bounded "$budget"` were the same number,
so the inner (graceful: evidence degrades, demotion still lands) layer only *began*
degrading at the instant the outer (brutal: subtree killed, nothing written) kill was due.
Inner is now `budget - RECONCILE_TAIL_RESERVE_SECS`, default 1 s against a tail T302
measured at 0.106 s, floored at 1 s, and both numbers are logged.

Neither weakens the F5 fix: term 2 compares whole records and interprets nothing, so

### The matrix — item 2, and the part that generalises

`.softhouse/capture/t319-reconciler-f5/run-ownership-matrix.py`, 13 cells.

**Why T309's matrix could not see F5.** Its cell B passes **one commit as both the lock and
the state under test**, so the clock is frozen at the lock instant; cell A, the only
clock-advancing cell, is a fire that dispatched only fresh ids. *A matrix that cannot move
the clock cannot see a re-dispatch.*

**Cell B′ is the fix to the test**, and it is not a cell somebody has to remember to keep:
`_assert_matrix_can_see_a_redispatch()` raises and fails the whole run if no cell in the
table advances the clock across a re-dispatch. Delete B′ and you get a red run, not a
smaller green one.

**RED/GREEN in the same invocation.** `--selftest` plants T309's shipped single-term
predicate into a *copy* of `ready-tasks.py` (by locating the term-2/term-3 markers; if it
cannot plant, it refuses to report anything) and **requires cell B′ to fail against it**.
It does: **7 demotions, matching T302's measurement exactly**, against 0 on the shipped
tool.

**Mode determinism, which T309's matrix left to the ambient process tree.** `in_session`
vs `wrapper` turns on whether any ancestor is named `claude` — so from inside an agent
every cell is `in_session`, from a plain shell every cell is `wrapper`, and the same table
means different things in different hands. Each cell now **constructs** its ancestry:
double-fork (reparent to pid 1, dropping the ambient `claude`), then exec a four-line C
shim installed as `claude` or `wrapperzsh`. Each cell asserts the **mode** as well as the
count. argv[0] spoofing was tried first and does not work here — macOS `ps` prints the
kernel's executable path and the python framework launcher re-execs with its real path;
copying `/bin/zsh` is SIGKILLed on exec (rc 137, code signature); `/bin` and `/tmp` are
different volumes so no hard link. Without a compiler the rig **fails** rather than running
every cell in whatever mode it happens to get.
