## Q8 — blast radius. **CONFIRMED, and the inode argument is more load-bearing than T190 argued.**

T190 says the change takes effect on the **next** fire because the running zsh keeps reading its
original inode. The prompt is right that this deserves a check rather than a nod, and the check is
interesting:

**(a) Does a git merge/checkout replace the inode?** **Yes** [VERIFIED: `/tmp/t200/q8.zsh`]:
inode `7946942` → `7946950` across the merge. Git writes a temp file and renames, so the path gets a
**new inode** and any already-open fd keeps the old content.

**(b) Does a running zsh re-read a mutated script?** This is where the nod would have been wrong.
[VERIFIED: `/tmp/t200/q8b.zsh`, `/tmp/t200/q8c.zsh`]

| script size | **in-place** truncate+rewrite (same inode) | **rename** replace (new inode) |
|---|---|---|
| 1.6 KB | not re-read | not re-read |
| 7.5 KB | not re-read | not re-read |
| **15.0 KB** | **HIJACKED — ran the new bytes** | not re-read |
| 30–33 KB | **HIJACKED** | **not re-read** |

zsh reads large scripts **incrementally**, and the hijack threshold on this host sits between 7.5 KB
and 15 KB. **The real `fire-program.sh` is 16,438 bytes — above the threshold**
[VERIFIED: `wc -c`, live inode 7913849].

So: had anyone edited the live wrapper *in place* while a fire was running, the running fire **would**
have started executing the new bytes mid-flight. It is specifically because git uses rename, and
because T190 edited the **worktree copy** at
`/Users/buv/gerege-nbfi/.claude/worktrees/agent-a73424a6001f745ae/.softhouse/bin/fire-program.sh`
rather than the live path, that the running fire is untouched. **T190's reasoning is correct and its
caution was warranted, not ceremonial.** I did not modify the live wrapper or the live LOCK.

**Carrying forward T190's own top follow-up.** `:250`'s `git add -A -- . ':!.softhouse/LOCK'` is
still cwd-relative — both the `.` and the unanchored `:!` exclude. **Yes, this should be a task**,
and the diff makes the case stronger rather than weaker: after T190 the guard is *asymmetric* — the
`git status` above it is `:(top)`-anchored and sees the whole repo, while the `git add` below it sees
only cwd. If cwd ever ceased to be the repo root, the guard would report a dirty path, stage nothing,
and still log `rescued: committed the leftovers` — reinstating precisely the false-rescue class T190
removed in Q3/Q4. It is latent today because cwd is pinned twice over (plist `WorkingDirectory` +
`cd "$REPO"` at :49, and nothing between them and :250 changes cwd — the worktree sweep uses

## Pattern candidate

**A probe that ends where the claim ends cannot see what happens next.** T190's lock-release proof
asked "is the LOCK file gone?" and got a true answer on all four paths — while missing that on INT
and TERM the shell **resumes** and runs on unlocked. The claim "released on every exit path" quietly
assumes the signal *is* an exit path; under zsh it is not. This is P-55's lesson in a new costume:
the probe inherited the claim's own framing. **When verifying a cleanup handler, always run the
subject past the handler and observe whether it is still alive.**
