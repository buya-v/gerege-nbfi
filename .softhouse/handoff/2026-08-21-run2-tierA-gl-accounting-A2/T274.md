## The four routes, each measured

A numbering note first, because it will otherwise look like a discrepancy in the record:
**`tasks.json` and `REVIEW.md` swap F-6 and F-7.** `REVIEW.md` §4 has F-6 = *the response is
unattested* and F-7 = *`known_keys` is an exemption list*; the T274 task text has them the
other way round [VERIFIED: `.softhouse/reviews/t261-tenant-attestation/REVIEW.md:260,276` vs
the T274 `description` in `.softhouse/tasks.json`]. I identify the routes **by shape**, never
by number, and give each its own RED case.

### R1 — an ABSENT assertion was an UNCHECKED assertion  (T261 F-4, HIGH)

`cmd_verify` required exactly two things: the `attestation-derivation:` tag and a
`request-headers-sha256:` line. Every other assertion was matched with
`for line in side_lines: if line.startswith("body-sha256: ")` — **delete the line and the
loop body never runs.** Deleting `body-sha256:` from the sidecar and replacing the committed
request body with different bytes *of the same length* left `body-bytes`, `Content-Length`
and the header record all agreeing → `VERIFIED`, rc=0. The committed request body was a
forgery and the module said the artefact set was sound — inside a module whose docstring
says *absence of evidence is not evidence*.
**MEASURED on the shipped rig: rc=0** [VERIFIED: `evidence/10-four-routes-red-green.txt`, arm
`red R1`].

### R2 — headers were compared as a SET, so order and multiplicity were unverifiable  (F-5)

Both directions of check (2) were membership tests (`if line not in side_lines`,
`if line not in rec_lines`). Two distinct shapes, both driven:

* **R2a** two wire header lines reordered in the sidecar → rc=0.
* **R2b** the same header sent TWICE (curl does not de-duplicate — T250's own red-drive C
  measured *both* values reaching the server, which is the discovery that makes this
  material), one copy deleted from the sidecar → rc=0. The sidecar then says one tenant
  header went out where two did.

**MEASURED on the shipped rig: rc=0 for both** [VERIFIED: same transcript, arms `red R2a`,
`red R2b`].

### R3 — `known_keys` was an EXEMPTION LIST, so a recognised key was never validated  (F-7 in REVIEW.md)

`if key in known_keys: continue` skipped the "asserts a line that was not sent" check for any
of ten keys. Default-**allow** in an evidence verifier. Two shapes:

* **R3a** append an invented `content-length-crosscheck: MATCH (99999 bytes)` → rc=0.
* **R3b** *alter* the real crosscheck line to the same fiction → rc=0. R3b is the sharper
  one: nothing was added, an existing assertion was simply made false, and the verifier had
  no code path that could ever look at its value.

**MEASURED on the shipped rig: rc=0 for both** [VERIFIED: arms `red R3a`, `red R3b`].

Worth recording, because it bounds the route rather than overstating it: an invented line
under an **unknown** key *was* caught by the old rig (it fell through to
`if line not in rec_lines`). The route is precisely "a key the verifier recognised was
exempted from validation", not "anything could be added".

### R4 — the RESPONSE leg was entirely unattested, and that limit was stated NOWHERE  (F-6 in REVIEW.md)

`verify` never opened `NAME.json` or `NAME.status`; `oracle_send` computed no response
digest. Swapping the response body for another real capture's response → rc=0. For a

**MEASURED on the shipped rig: rc=0** [VERIFIED: arm `red R4`, which swaps `probe.json`
(468 bytes) for a different real oracle response (264 bytes)].

## Changes Made

### 1. `.softhouse/capture/lib/wire_attestation.py` — rewritten around one rule

`verify` no longer inspects assertions one at a time. It **re-derives the entire sidecar**
from the wire records and the committed artefacts using **the same function `derive` uses**
(`build_sidecar()`), and compares the two texts exactly, line by line, in order.

There is no list of "things we check", so there is nothing to fall outside of. R1 (a missing
line changes the text), R2a/R2b (order and multiplicity are part of the text), R3a/R3b (a
value that is not the derived value changes the text) and R4 (a swapped response changes
`response-sha256:`) all die at the same root, and so do shapes nobody has thought of yet.

Supporting decisions, each of which is itself a default-deny:

* **The obligation is set by the WIRE, not by the sidecar and not by the caller.**
  `Content-Length` in the request record ⇒ a body was sent ⇒ the body assertions are REQUIRED
  and the artefact must be supplied; no `Content-Length` ⇒ they are FORBIDDEN and
  `body: <none>` is required. Withholding `--req` from a capture whose wire shows a body is a
  REFUSAL (exit 2), not a skipped check [VERIFIED: control `P4`].
* **The required assertion set is derived, enumerable and PRINTED on every run**, pass or
  fail, with the number of verbatim wire lines required in order.
* **The response leg is attested.** `derive` now writes `NAME.resphdr` from the trace's
  `<= Recv header` blocks and puts the response headers digest, the final status line, the
  response body digest and byte count, a response `Content-Length` cross-check and a
  cross-check of `NAME.status` against the wire status line into the sidecar.
  *Decision and argument:* the alternative — declare the response out of scope and say so in
  the module — was available and is what T261 offered as the minimum. I rejected it because
  the response is the half a vector is graded on; a rig that attests only the request and
  says so is honest but nearly useless for the purpose this rig exists for. The residual
  limits (TLS parameters, timing, redirect-hop bodies, and `captured-at-utc`, which is not
  derivable) are stated **in the module docstring**, where a reader meets them.
* **A schema version, and it is not a downgrade route.** `derive` writes
  `attestation-schema: 2`. Sidecars written before T274 carry no schema line, are schema 1,
  attest the request only, and are **not retro-edited** (T114). Presenting a response
  artefact against a schema 1 sidecar is REFUSED (exit 2), so deleting the schema line to
  escape the response checks buys a refusal, not a pass [VERIFIED: control `P2`]. An unknown
  schema value is refused. A schema 2 sidecar with any attested artefact withheld is refused
  [VERIFIED: control `P3`].
* **Two smaller fail-opens repaired in passing**, both found while reading rather than
  reported by T261: T250's `content_length()` returned `None` on a non-integer
  `Content-Length`, which made the sidecar assert `ABSENT (no Content-Length was sent)` about
  a request that plainly sent one — a false statement manufactured out of a parse failure.
  Two `Content-Length` headers were silently read as the first. Both now REFUSE.
  [UNVERIFIED: I did not drive either red against the live oracle — curl does not readily
  emit them and I did not build a synthetic trace. They are reasoned repairs, not measured
  ones, and I am flagging them as such rather than counting them as fixes.]
* **Failure reporting is the MINIMAL EDIT**, via `difflib` opcodes. My first version walked
  positions and turned one deleted line into a cascade of 13 findings, one of which
  (`REQUIRED assertion ABSENT: request-headers-artefact:`) was **false** — the assertion was
  present, the tail boundary had shifted. Assertion-level diagnostics are now computed only
  when the verbatim wire block matched, and the module says so when it withholds them. A
  diagnostic that is confidently wrong is worse than one that is withheld.

**THE LINE.** In `.softhouse/conformance.sh`, in `run_guards()`, immediately after

**AND the function it calls**, defined next to `guard_no_fail_open_instruments` (which ends

```sh
guard_attestation_population() {
  local out rc=0
  out="$(mktemp "${TMPDIR:-/tmp}/attestpop.XXXXXX")" || return 1
  python3 "$REPO_ROOT/.softhouse/capture/lib/attest_population.py" >"$out" 2>&1 || rc=$?
  LC_ALL=C sed 's/^/conformance: /' "$out"
  rm -f "$out"
  if [ "$rc" -eq 0 ]; then return 0; fi
  if [ "$rc" -eq 2 ]; then
    warn "conformance: the sidecar-population ratchet REFUSED (exit 2): no verdict is"
    warn "conformance: available about the attestation population. This is NOT a pass."
    return 1
  fi
  warn "conformance: the sidecar-population ratchet FAILED (exit $rc). A capture sidecar"
  warn "conformance: was committed with no derivation line, or the pin needs to move in"
  warn "conformance: the same commit. The pin is"
  warn "conformance:   .softhouse/capture/lib/attest_population_pin.json"
  return 1
}
```

**HARD or SOFT — my recommendation, and the hazard in it.** HARD (join the `failed=1` tally,
as written above). The ratchet answers a question about the repository, not about the oracle,
and it is cheap and deterministic. **THE HAZARD, stated because P-83 exists:** a HARD guard
failure exits 2 **before** the `reference oracle (…) probe = up|down` line is printed, and
this program has already had to correct a rule that read that silence as an ORACLE OUTAGE.
**What a reader must check to tell them apart:** a ratchet failure prints
`conformance: attest-population: FAIL` (or `attest-population REFUSING:`) followed by the
named cause, and the census lines above it. An oracle outage prints the probe line with
`down`, or, if the harness died earlier still, prints neither the census nor the probe. If
you see census lines and no probe line, a guard failed; if you see neither, the harness never
got that far. T269 owns this decision and may overrule it — but it must state the
discriminator, whichever way it goes.

**The ratchet is already driven red**, four rot-routes plus two refusal modes plus two
