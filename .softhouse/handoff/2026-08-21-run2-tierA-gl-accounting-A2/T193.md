### 1. `.softhouse/capture/lib/check_wire_float_roundtrip.py` — a second arm

**Derivation is the vector store's own citation, never a directory name and never a
`capture-prod3*` glob.** For every `*.json` under `.softhouse/vectors` carrying a non-empty
`provenance.capture_ref`, the referenced file is opened and every numeric token inside a
**recorded-request block** is held to the same byte-preservation predicate the first arm uses.
A recorded-request block is the value of a key named `inputs` or `request`, found at **any
depth** by walking the **parsed** document. Cite a capture from a rig that does not exist yet
and it is inspected the day it lands; rename `out/` and nothing moves.

New machinery: `Tok` (a numeric token carrying its **source text**, returned in place of the
parsed number so the document can be walked structurally), `parse_tokens`, `split_tokens`
(recursion, splitting tokens into graded / not-graded and collecting block paths),
`cited_captures` (the store walk).

**Refusals added, each with its own diagnostic:**

- a numeric token in a recorded request that a binary-double round trip rewrites — names the
  file, line, JSON path (`$.captures[9].inputs.disbursementAmount`), token and rendering;
- a citation this guard cannot follow (dangling, absolute, or `..`-escaping) — **named before**
  the population checks, deliberately, because a dangling ref drops out of the derived set and
  would otherwise arrive at the zero-population branch wearing the costume of an empty store;
- a cited capture record that does not parse as JSON;
- a vector store that is present and cites **nothing** — ERROR, not a pass (P-35);
- cited records that yield **zero** recorded-request blocks — this is exactly what a renamed
  `inputs` key looks like from the outside: the arm keeps running and grades nothing. Refused.

**Applied T186's ratified boundary, and did not widen it.** (a) The oracle-facing wire admits
major-unit decimal and is bound by **byte fidelity** — that is the predicate, unchanged;
value-preservation was never substituted for it. (b) and (c) are Zones B and C and are other
guards' populations. T186 §7 **A2** — "no float-shaped token in a request body" is WRONG and
must be rejected in review — is **not** reopened: the second arm enforces byte preservation,
never a blanket ban, even though the float-shaped count inside recorded-request blocks happens
to be zero today.

**Docstring** also records T186 §2.4 / FU-7: the property is not the defensible weaker choice,
it is the **exact survival condition** across `ChargeRequest.amount`'s `double` — the one
genuine Java `double` on a Fineract request path.

**Selftest** grew 5 cases → 13 (10 RED, 3 GREEN). The eight new ones are listed in the
RED/GREEN file; (g) and (m) are the anti-over-breadth pair, (k) is the anti-vacuity one.

## Unverified

- **`BigDecimal.valueOf(7.0)` in `Capture3*.java` is harmless — REASONED, NOT EXECUTED.**
  28 `BigDecimal.valueOf` sites across the `Capture3*` family; the money ones are
  `valueOf(100)`, which I read as resolving to `valueOf(long)` (int→long is more specific than
  int→double under JLS 15.12.2.5), and the rate ones are `valueOf(7.0)` → `valueOf(double)` →
  `new BigDecimal(Double.toString(7.0))` = `"7.0"`, exact. **I did not run a Java program to
  confirm either overload resolution or the resulting scale.** The *recorded* output is
  `"annualNominalInterestRate": "7.0"`, which is consistent with that reading
  `[VERIFIED: capture-prod3b-raw.json]`, but consistency is not proof of the mechanism.
- **I did not re-verify the transcription of any vector.** This task is about representation
  and transit fidelity of the request record. It re-derives no money figure and makes no claim
  that any `expect` cell is right.
- **I did not establish whether anything actually re-serialises a cited capture record.** The
  59 non-preserved cells in `T149-TIE-P9-raw.json` are a property of the file; whether a
  promotion or analysis script ever `json.load`s it without `parse_float` is not something I
  measured. The vector's `*_major_text` cross-check fields and `admit.go`'s digest pin both
  argue against live damage, but I did not audit `.softhouse/capture/pathb/t149/`'s scripts
  (out of scope this fire).
- **The `new BigDecimal(<x>)` census is NOT a usable lint and I am not claiming it is clean.**
  A regex over tracked `*.java` for `new BigDecimal(` with a non-quoted first argument returns
  well over a hundred hits, and the ones I sampled are `new BigDecimal(principal)` where
  `principal` is a **`String`** parameter — the safe constructor
  `[VERIFIED: .softhouse/capture/actualactual/src/CaptureActualActual.java:153-156, the
  signature reads `String principal, int n, String rate`]`. Distinguishing the dangerous
  `new BigDecimal(double)` from the safe `new BigDecimal(String)` needs type resolution, which
  a text lint does not have. I therefore did **not** ship one, and no claim about that surface
  should be read into this task's green run.
- **`float-shaped tokens PRESENT 278`** on the first census line is the pre-existing arm's
  figure and I did not re-derive it; the docstring's "221 of 320 bodies" is T173's file count,
  a different quantity from a token count, and the two are not in conflict.

## Follow-ups

- **FU-T193-1 — the request *generation* half of T186 §8 item 6 is still uninspected, and I am
  saying so rather than implying coverage.** This task closed the **recorded** request. The

  `new BigDecimal(` followed by a **numeric literal** (`new BigDecimal(1200000.0)`), which needs

  should be registered as such.
