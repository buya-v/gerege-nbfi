# T336 — the post-checkout push-before-spawn hook: what is actually available, and what I installed

**Branch** `softhouse/T336-post-checkout-decision`. **Role** coder.
**Task shape:** the driver filed this as *"install the hook"*; T280's F-C refuted that before

## HEADLINE — F-C reproduced, and then superseded by a bigger measurement

**F-C reproduced.** [VERIFIED: `.softhouse/capture/t336-post-checkout-decision/out/fc-reproduce.txt`]
On `/usr/bin/git 2.50.1 (Apple Git-155)`, with T279's hook installed and `SOFTHOUSE_PUSH_GATE=enforce`,
`git worktree add` returns **rc=1** and: branch ref created, files checked out, admin dir
registered, `git status` works in it — and case 5 goes further than T280 did: I switched that
"refused" worktree to `softhouse/T999-slug`, committed in it, and **the commit is visible from
the spawning repo**. It is a fully functional worker worktree. T280 is right; the hook cannot
refuse. Same result when spawning from a **linked worktree** (case 4).

**But F-C understates the problem, and the understatement is this task's real finding:**

> **The agent harness creates worker worktrees WITHOUT RUNNING GIT HOOKS AT ALL.**

[VERIFIED: `out/real-route-POSTCHECKOUT-FIRED.log`, `out/real-route-REFTXN-FIRED.log`]
I installed an always-`exit 0` logging `post-checkout` and a logging wrapper around T312's
`reference-transaction` in the live `/Users/buv/gerege-nbfi/.git/hooks/`, then spawned **five
real workers through the real route** (`Agent` tool, `isolation: worktree`) between 11:57 and
12:03. **Zero hook invocations for any of the five spawns**, by any of three independent write
targets (`/tmp`, the git common dir, and a marker file dropped in the new worktree itself — so
a sandbox denying one path cannot explain it).

**The control that makes this a measurement and not a broken instrument** (P-22): in the same
minute, from the same hooks directory, **both hooks fired for ordinary worker git commands** —
`reference-transaction` at 12:01:38 for `refs/heads/softhouse/T323-wire-unwired-guards`, and
`post-checkout` at 12:03:18 with `$3=1` for `git checkout -b softhouse/T270-superseded-trap`.
The harness spawn at 12:03:00 sits *between* those two log lines and wrote nothing.
`core.hooksPath` is unset at every origin and no `GIT_*` hook variable is set [VERIFIED: worker
probe running `git config --list --show-origin`]. Yet git demonstrably ran: the branch got a
real `branch: Created from origin/main` reflog entry and the worktree's `logs/HEAD` is
shape-identical to `git worktree add -b <br> <path> origin/main`
[VERIFIED: `out/reflog-signature.txt`]. So git ran with its hooks suppressed.

## THE ANSWER TO THE OPEN QUESTION (what a hook can observe at hook time)

Measured, not reasoned [VERIFIED: `out/fc-reproduce.txt` case 7]: at `post-checkout` time
`pwd` is the **new** worktree, `HEAD` is the auto-generated `worktree-agent-<id>`, and every
ref in the shared repo is visible. T279's hook never asks about "this branch" — it asks about
the **main worktree's** branch versus its upstream, which is the right question and is immune
to the driver's worry. The worry was well-founded for a *different* design and is now moot,
because the hook does not run.

**Corollary that matters for the audit I did ship:** the worktree→task mapping can only be
recovered *after the fact*, from the worktree's own `logs/HEAD` (`checkout: moving from
worktree-agent-… to softhouse/T336-…`). No hook at spawn time could ever have checked it.

## THE DECISION

**Chosen: (c), narrowly and with its weakness stated. Rejected: (a), (b), (d).**

**(a) install it warn-only — REJECTED, and not on judgement.** Its premise is
false: "a loud warning lands in the WORKER's own output at the instant the worktree is
created" — the hook does not run at that instant, so no warning lands anywhere. A reshaped
variant *is* available (warn at the worker's own first `git checkout -b softhouse/…`, which
does fire, guaranteed, on a command every worker must run). I rejected that too, on two
grounds: it warns the wrong actor after the violation window has already opened, and the
worker cannot fix it — it cannot push the driver's LOCK; and the hook's dirty-tree arm
(`git status --porcelain -- .softhouse/`) would fire on every worker branch-switch while the
driver is mid-edit, which is most of a fire. A banner that mostly cries wolf is P-22.

**(b) move the check to something that CAN veto — REJECTED, after finding one that can.**
`reference-transaction` in the `prepared` state **genuinely vetoes** `git worktree add`:
`fatal: ref updates aborted by hook`, rc 255, **no branch, no directory, no admin dir, nothing
to work in** [VERIFIED: `out/refuse-candidates.txt` B1a and B1d, with B1c/B1e as the permitting
controls and B1f showing the blast radius is scoped to the `worktree-agent-*` glob]. It is a
true precondition — and it is useless here, because the harness does not invoke it for the
spawn. I also measured that `pre-receive` on a local remote never fires, since `git worktree
add` pushes nothing (B2). The driver's own wrapper cannot intercept either: `fire-program.sh`
launches `claude -p /softhouse-program` once per fire; the `git worktree add` is issued by the
harness inside that session, per batch, out of the wrapper's reach.

**(d) nothing is worth it — REJECTED, but it was close.** The case for (d) is real: (c) cannot
prevent anything, and see the blind spot below. I rejected it because (c) costs ~250 lines,
**cannot brick a fire**, and turns a miss that is currently found only when someone thinks to
look into one that a machine reports. That is a smaller claim than enforcement and I have not
dressed it up.

## Blockers

**None blocking this task. One limitation you must read before citing the audit.**

**The detector I shipped would have MISSED the violation this very fire committed.** Its
spawn times come from `.git/worktrees/<id>/`, and those directories are **destroyed by the
exit protocol's own prune sweep**. Iteration 1 batch 5 spawned at 10:44:04 and pushed 135 s
late; those four worktrees are already gone, and the live run today reports only iteration 2
[VERIFIED: `out/audit-live-repo.txt`, spawn list starts 11:34:58]. So wiring this into the
exit protocol **after** the prune sweep would produce a permanent, silent green. The follow-up
patch below therefore places the call **before** the sweep, and the audit prints its
under-reporting blind spot on every run rather than in a comment.

The honest summary in one sentence, using the word the task asked for: **push-before-spawn
remains a CONVENTION.** Nothing in this repo can prevent a violation of it; after the
follow-up below is applied, a violation that is still on disk will be *reported*.

## Follow-ups

**FU-1 (the patch I was forbidden to apply this batch — `fire-program.sh` is held by T342,
T343 serialised behind it).** Assign to **T343**, or to whichever task holds
`.softhouse/bin/fire-program.sh` after T342 lands. Insert **immediately after line 2126**
(`local WT_PRUNED=0 WT_KEPT=0`) and therefore **BEFORE** the `for` loop that calls
`git worktree remove` — placement is the whole point; after the loop the evidence is gone.

```zsh
# T336: push-before-spawn AUDIT. A DETECTOR, NOT A GUARD -- it cannot prevent anything,
# and the obligation it audits remains a CONVENTION (P-45). It runs HERE, before the
# prune sweep below, because that sweep deletes `.git/worktrees/<id>` and with it the
# only record of when each worker was spawned. Run after the sweep it would be blind to
# exactly the worktrees the sweep removes, i.e. permanently and silently green.
# It NEVER fails the fire: a violation is recorded, loudly, and the fire still closes.
if [[ -x /usr/bin/python3 && -f "$REPO/.softhouse/hooks/push-before-spawn-audit.py" ]]; then
  local PBS_OUT PBS_RC
  PBS_OUT=$(/usr/bin/python3 "$REPO/.softhouse/hooks/push-before-spawn-audit.py" \
              --repo "$REPO" --min-spawns 1 2>&1)
  PBS_RC=$?
  print -r -- "$PBS_OUT" | while IFS= read -r L; do log "push-before-spawn: $L"; done
  case $PBS_RC in
    0) log "push-before-spawn: no violation among the spawns still on disk (NOT enforcement)" ;;
    1) log "ERROR: push-before-spawn: VIOLATION recorded above (P-85). The fire is NOT failed on this; record it in RESUME.md and in the exit note." ;;
    *) log "WARN: push-before-spawn: audit could not run (rc=$PBS_RC) — this is NOT a pass" ;;
  esac
fi
```
Whoever applies it must re-drive it: temporarily point `--repo` at
`.softhouse/capture/t336-post-checkout-decision/probe/drive-audit-red-green.zsh`'s RED scratch
repo and confirm the `ERROR:` line is emitted (P-22 — do not ship it having only seen it green).
