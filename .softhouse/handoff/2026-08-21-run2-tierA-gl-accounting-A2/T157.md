## The red probe — or an honest statement that the failure mode is unreachable, with evidence

**Apparatus (P-33).** `/usr/bin/grep (BSD grep, GNU compatible) 2.6.0-FreeBSD` — the same binary and
version T108/T154 used. Locale: this shell's `LC_CTYPE=C.UTF-8`, `LANG` unset — and I confirmed this is
also the **production** locale for the actual launchd fire: the plist (`.softhouse/launchd/mn.gerege.nbfi.softhouse-program.plist`)
invokes `/bin/zsh -lc "…fire-program.sh"` — a **login shell**, which reads `/etc/zprofile`
(`export LANG=C.UTF-8`, line 7, [VERIFIED: `/etc/zprofile:7`]) since neither the plist's
`EnvironmentVariables` (only `PATH`, `HOME`) nor `~/.zprofile` (absent, [VERIFIED: `test -f ~/.zprofile` →
absent]) override it. So the UTF-8-locale precondition for BSD grep's invalid-byte behaviour is genuinely
present in the real fire, not just in my sandbox.

### First: the specific defeat T154 hardened the other 24 greps against does not reach this line

T154's leg-1 defeat (v2/v4 in `drive-leg1.sh`) is: an invalid byte **before** the target match, **on the
same line**, makes BSD grep go blind to everything from that byte rightward on that line — so a positive
`grep -Eq` check silently returns "not found."

That shape cannot occur here. The pattern is `^?? \.softhouse/LOCK`, anchored at column 0 — there is no
"before the match" position on the matched line, because the match starts at the first byte. And the
matched literal itself (`.softhouse/LOCK`) is a fixed ASCII path this same script creates
(`LOCK="$REPO/.softhouse/LOCK"`, line 23) — it can never itself carry an invalid byte in production. I also
tried to construct a real file whose *name* contains an invalid UTF-8 byte, to see if such a byte could
even reach a `git status --porcelain` line at all:

```
$ python3 -c "open(b'/tmp/t157-realrepo/' + b'poison_\xe2_file.go', 'wb')"
OSError(92, 'Illegal byte sequence')
```

APFS refuses to create the file outright (`EILSEQ`). So on this filesystem, the T154-leg-1 shape is
**structurally unreachable** for this specific grep, for two independent reasons: the anchor gives it no
"before the match" position, and the filesystem won't produce the poisoned byte in the first place.

### Second: I found a different, more severe failure — and drove it red

Testing systematically across invocation shapes (P-33's "invocation" axis), I found BSD grep 2.6.0-FreeBSD
behaves completely differently for this pattern depending on whether the input is a **seekable source**
(a regular file, by argument or `<` redirection) or an **anonymous pipe**:

```
$ printf 'zzz clean line before\n M poison_\xe2_after.go\n?? another_after.go\n' > order1.txt

$ grep -v '^?? \.softhouse/LOCK' order1.txt        # FILE ARGUMENT
rc=1                                                 # ZERO lines printed — total blindness
$ grep -v '^?? \.softhouse/LOCK' < order1.txt       # '<' REDIRECTION (still seekable)
rc=1                                                 # same — total blindness

$ printf 'zzz clean line before\n M poison_\xe2_after.go\n?? another_after.go\n' | grep -v '^?? \.softhouse/LOCK'   # ANONYMOUS PIPE
zzz clean line before
 M poison_�_after.go
?? another_after.go
rc=0                                                 # correct — all 3 lines pass, poison notwithstanding
```

Reproduced across poison **first**, **middle**, and **last** line, and — to test T154's specific claim
directly — with the poison appended **directly onto the LOCK-matching line itself** (a shape that cannot
occur in production, since the LOCK path is fixed ASCII, but worth checking since it is exactly what T154
described):

```
$ printf '?? .softhouse/LOCK\xe2\n M real_change.go\n' > poison-on-lock-line.txt
$ grep -v '^?? \.softhouse/LOCK' poison-on-lock-line.txt   # FILE ARGUMENT
rc=1                                                          # ZERO output — NOT "the line is kept"
```

**This contradicts T154's own Blockers note**, which said: *"It is also fail-closed under BSD grep: a
blind `grep -v` fails to match, so the line is kept, `DIRTY` is non-empty, and the rescue path runs rather
than being skipped."* Driven directly, that is not what happens. Under a seekable input, one invalid byte
anywhere makes the whole `grep -v` pipeline print **nothing at all** — not "the poisoned line survives,"
but every line, poisoned or clean, vanishes. `DIRTY` would come back **empty**, and `run_exit_guard` would
conclude there is nothing to rescue — the opposite of fail-closed. This is exactly the class of claim P-46
warns about: T154 reasoned about the mechanism by analogy to the other guards rather than driving it, and
the analogy does not hold for this input source.

### Third: the real invocation is a pipe, so the catastrophic case is not reachable today

`fire-program.sh:224` is `git status --porcelain | grep -v …` — an **anonymous pipe**, never a file
argument or redirection. I re-ran every poison placement above through the identical pipe shape and none
of them reproduce the failure — pipe-fed `grep -v` handles every position correctly, matching the "PIPE"
row above. So: **the specific defeat is not reachable through the code as written today.** It would only
detonate if a future edit changed this line from a pipe to a file read (e.g. capturing
`git status --porcelain` to a temp file for debugging, or piping through an intermediate `tee`+`<` before
grep) — a plausible, easy-to-introduce refactor, and one that would fail **silently and catastrophically**
(the whole rescue path going blind) rather than obviously.

### Fourth: the fix is verified correct across every case above, and the normal path is unchanged

`LC_ALL=C grep -av` fixes the file-argument and `<`-redirection cases (all now `rc=0`, correct
line-for-line output, including the "poison on the match line" case correctly filtering only the true LOCK
line). And on the two REAL, non-synthetic scenarios that matter for ordinary operation — captured with a
real git repo, real `git status --porcelain`, no injected bytes at all:

| scenario | pre-fix output | post-fix output |
|---|---|---|
| only `.softhouse/LOCK` untracked (clean) | *(empty)*, rc=1 | *(empty)*, rc=1 — **identical** |
| `.softhouse/LOCK` untracked + ` M .softhouse/conformance.sh` + `?? new_deliverable.go` | ` M .softhouse/conformance.sh`<br>`?? new_deliverable.go` | ` M .softhouse/conformance.sh`<br>`?? new_deliverable.go` — **byte-identical** |

No false positive, no behaviour drift in ordinary operation.

### What "fail-closed" buys here, stated plainly

Contrary to how T154 described it, the pre-fix line was **not** a live fail-closed guard today — it was
never actually exposed to the invalid-byte defeat, because (a) it's fed by a pipe, and (b) APFS won't
create the poisoned filename in the first place. So this fix does not close a currently-live hole. What it
**does** buy: it forecloses a **latent, currently-unreached, and far more severe** failure than the one
T154 named — a future change to a seekable input source would previously have made `run_exit_guard` go
**completely blind** (not "noisy but safe"), silently reintroducing exactly the failure this function's own
comment says was **already observed in production on 2026-08-18** ("driver exiting rc=0 mid-run with
deliverables uncommitted … invisible to the next fire"). It also closes the P-26 sweep so no future auditor
has to special-case this one site. It buys nothing against the unrelated bug noted below (Follow-ups).
