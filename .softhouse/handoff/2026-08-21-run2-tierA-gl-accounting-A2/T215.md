Both live inside `run_exit_guard()` (`.softhouse/bin/fire-program.sh:561` onward), the driver's
exit-protocol rescue for a fire that ends with uncommitted deliverables (skill STEP 5.5). **They are not
duplicates — they do two different jobs on two different halves of the same rescue:**

- **Line 581, the DETECT site.** `DIRTY=$(git status --porcelain -- ':(top)' ':(top,exclude).softhouse/LOCK')`
  computes what the rescue considers "dirty" in the first place — the read that decides whether the rescue
  fires at all, and what it logs to the operator (`log "WARN: exit-protocol violation..."`, up to 20 lines
  printed). A broken DETECT site makes the guard **noisy or blind at detection time**: it either fails to
  notice real dirt, or (as T172 originally fixed) it wrongly reports `.softhouse/LOCK`-prefixed siblings as
  dirty when they were already excluded correctly elsewhere.
- **Line 602, the STAGE site.** `git add -A -- ':(top)' ':(top,exclude).softhouse/LOCK' >/dev/null 2>&1`
  is the actual write: it stages what DETECT found dirty, immediately followed by the commit that rescues
  it (`git commit -q -m "softhouse: rescue uncommitted deliverables..."`). A broken STAGE site is the
  **quiet failure mode** the T215 task brief names: if this pathspec is widened, `git add -A` silently
  skips every LOCK-prefixed sibling (e.g. `.softhouse/LOCKED_STATE.md`) at commit time, the commit still
  succeeds (on whatever it *did* stage), and the guard logs `"rescued: committed the leftovers"` — a false
  success, because the actual deliverable never made it into the commit. This is the exact "work destroyed
  because it was never committed" hazard skill STEP 5.5 exists to prevent, and the precedent for it
  (2026-08-18 17:22, 4,482 insertions stranded) is cited directly in the guard's own comments at line 592.

**Line numbers re-derived, not trusted from `tasks.json` (P-63).** `.softhouse/tasks.json`'s own text for

**Before (T210, inherited):** `ANCHOR_PATTERN='DIRTY=\$\(git status --porcelain'` — a single hard-coded

**Reproduced the driver's original measurement exactly** [VERIFIED: ran directly, not asserted] — the
old probe is genuinely blind to a broken STAGE site, confirming the T215 premise before trusting it, per
the brief's instruction (1).

**Now:** `check-lock-exclusion-anchor.sh` enumerates every line containing the literal fixed-string
fragment `:(top,exclude).softhouse/LOCK` (this exact fragment appears nowhere else in the file — measured
`grep -Fc` = 2, both at the two known guard sites, before any change). For each occurrence it:

1. Classifies it by the git subcommand on the line — `git status --porcelain` → **DETECT**, `git add -A` →
   **STAGE**, anything else → refuses with a named error rather than silently skipping it (a 3rd site in
   an unrecognised shape now FAILS the run instead of passing it by omission).
2. Checks it is paired with the top-anchor pathspec `':(top)'` (T190's cwd-relative-pathspec fix).
3. Checks the pathspec argument closes **exactly** at `':(top,exclude).softhouse/LOCK'` — see the
   population-shrinkage bug found and fixed below.
4. Evaluates the extracted line **verbatim** against a fresh scratch git fixture per site (never a shared
   one — a STAGE site's `git add` mutates the index and must not leak into the next site's read) and
   checks the property specific to its type (DETECT: `.softhouse/LOCKED_STATE.md` present, `.softhouse/
   LOCK` absent, in `$DIRTY`; STAGE: same two facts, read from `git diff --cached --name-only` after the
   `git add -A` line runs).
5. After the loop, requires **at least one DETECT-classified and at least one STAGE-classified site** —
   this is a categorical floor, not a hard-coded count, so a 3rd DETECT or 3rd STAGE site is absorbed
   automatically, but an entire category silently dropping to zero (one guard deleted outright while its
   sibling survives) still fails the run instead of passing on the remaining site. See the dedicated test
   for this below.

**Population rule chosen over a second hard-coded anchor, per the brief's instruction (3).** Rejected
alternative: add a second `ANCHOR_PATTERN2` for `git add -A`. Rejected because it only buys back to
"two hard-coded anchors, N sites" — a future third exit-guard call site sharing this pathspec (plausible:
the same rescue pattern already appears, unrelated to LOCK, at a different pathspec on line 230 for
releasing the lock file itself) would again need a new task to add a third anchor. The population form
instead asks "does every occurrence of this exclusion fragment look right", which needs no code change
when the guard grows a third call site of a known type.

### A gap found and closed during this task, not shipped

The first working draft used one fragment (`':(top,exclude).softhouse/LOCK'`, WITH the closing quote) as
both the population census and the well-formedness check. Running `run-red-demo-site1.sh` against that
draft produced an **inconclusive** result, not a red one: the DETECT mutation (`...LOCK*'`) no longer
contained the closing-quote fragment at all, so the site **vanished from the population count** (2 → 1)
instead of failing — the probe reported `VERDICT: PASS` on the one remaining (STAGE) site. This is the
same P-22 class the task exists to fix, just one level deeper: a census that a defect can shrink out of is
as vacuous as a guard that cannot fail. The demo script's own P-64 precondition check (below) caught this
automatically — it refused to call the run red because it could not observe both sites classified — rather
than accepting the accidental pass. Fixed by splitting the fragment into a **loose** `CENSUS_FRAGMENT` (no
closing quote — still matches the widened mutant as a substring) used only to find candidate lines, and a
**strict** `WELLFORMED_FRAGMENT` (closing quote required) checked per-site, so a corrupted pathspec stays
in the population and is failed BY NAME rather than disappearing from the count. Re-ran `run-red-demo-site1.sh`
after the fix: now reports the named `FAIL ... it appears WIDENED or otherwise corrupted` line and passes
its own P-64 precondition check. This same split is also why the categorical DETECT/STAGE floor (item 5
above) exists — it was added and tested after finding that a wholesale deletion of one site (not a
corruption, an outright removal) would otherwise pass on the surviving site's population of one:

```
$ (delete the STAGE line entirely from a scratch copy, run the probe against it)
population scan: ... found 1 time(s) ...
--- site 1: line 581 --- classified: DETECT, CHECK 1 PASS, CHECK 2 PASS
category counts: DETECT=1 STAGE=0
FAIL: zero STAGE-classified sites found -- the 'git add -A' LOCK-exclusion guard appears to have been
removed entirely, not merely mutated.
VERDICT: FAIL ...
exit code: 1
```

## Preconditions checked before believing a red (P-64)

Both `run-red-demo-site1.sh` and `run-red-demo-site2.sh` capture the probe's stdout+stderr and, before
interpreting the exit code, mechanically assert:

1. **Both sites were classified** (`"classified: DETECT"` and `"classified: STAGE"` both present in the
   transcript) — if either is missing, the demo reports `PRECONDITION FAILED (P-64): ... an inconclusive
   run, not a red one` and exits 2, distinct from both PASS (0) and a confirmed RED (0-with-message, since
   the demo's own exit reports success at *demonstrating* red). This is what caught the population-shrinkage
   bug above, on the first run of `run-red-demo-site1.sh` against the pre-fix probe draft.
2. **The failure names the correct site's category** (the `", DETECT) matched the LOCK-exclusion
   census but ... WIDENED"` / `", STAGE) ..."` message) — not merely "exit nonzero somewhere".
3. **The untouched site reports fully clean** (`CHECK 1S PASS` + `CHECK 2S PASS`, or `CHECK 1 PASS` +
   `CHECK 2 PASS`) — a run that goes red on both mutations without distinguishing them would still satisfy
   (1) and (2) partially but fails this check, which is the brief's own bar: "a probe that goes red for
   both mutations but cannot say which is weaker than one that names the site."

`check-lock-exclusion-anchor.sh` itself also has its own precondition checks carried over from T210 and
extended: `GREP=/usr/bin/grep` existence/executability is checked before any matching begins (P-58 — the
interactive `grep` shell function re-execs as ugrep, and this script refuses that path entirely); the
target file's existence is checked before reading; `grep -c` vs `grep -n` counts are cross-checked for
consistency before iterating; and each site's scratch fixture is rebuilt fresh (`setup-scratch-repo.sh`
re-run) immediately before that site's `eval`, so a STAGE site's index mutation from a prior iteration
cannot leak into the next site's read.

  extension local and additive.
