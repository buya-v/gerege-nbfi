# T211 — SIGTERM can now promptly stop a fire

**Branch:** `softhouse/T211-sigterm-prompt-stop`
**Target:** `.softhouse/bin/fire-program.sh` (worktree copy only — the live file was never touched)
**Probe artefacts:** `.softhouse/handoff/2026-08-21-run2-tierA-gl-accounting-A2/T211-probe/`

Every measurement below was taken under **zsh 5.9 (arm64-apple-darwin25.0)** on
**macOS 26.5.1 (25F80)**, through the real launchd invocation shape
`/bin/zsh -lc <script>`, spawned by `T211-probe/spawn.py` with
`start_new_session=True` (setsid) and `restore_signals=True` (INT/QUIT/PIPE
reset to `SIG_DFL`). The default-disposition control is the P-55 guard the
brief demanded: T202's first probe backgrounded its subject from a
non-job-control zsh, which `SIG_IGN`s INT/QUIT in the child, and so concluded
"zsh ignores SIGINT" — an artefact of the harness. This harness does not have
that defect, and S6 below re-derives the real mechanism from the other side.

`bash -n` / `zsh -n` are **not** offered as evidence anywhere in this handoff.

## Changes Made

One file, `.softhouse/bin/fire-program.sh`, +196 / −13.

### 1. `run_driver` — the driver is backgrounded in a subshell and `wait`ed on

Before (foreground pipeline):

```
"${CAFFEINATE[@]}" "$CLAUDE_BIN" … | tee "$RAW" | /usr/bin/jq … 
RC=${pipestatus[1]}
```

After (backgrounded subshell + `wait`, rc carried through a file):

```
( { "${CAFFEINATE[@]}" "$CLAUDE_BIN" … 
    print -r -- $? > "$DRIVER_RC_FILE" } \
  | tee "$RAW" \
  | /usr/bin/jq -r --unbuffered "$DIGEST" 2>/dev/null ) &
DRIVER_JOB_PID=$!
wait "$DRIVER_JOB_PID"
DRIVER_WAIT_RC=$?
DRIVER_JOB_PID=0
```

Both branches (jq present / absent) got the same treatment.

### 2. `stop_driver()` + `driver_tree()` — new, in the trap block

`on_signal` now calls `stop_driver` **before** `release_lock`. `driver_tree`
builds the descendant closure of the job from **one** `/bin/ps -Ao pid=,ppid=`
snapshot; `stop_driver` SIGTERMs the whole closure, waits
`DRIVER_STOP_GRACE_SECS` (default 3), then SIGKILLs anything still present and
not a zombie.

### 3. `RC` recovery is fail-closed

`${pipestatus[1]}` no longer works after `wait` (S4/S5 below). The driver's own
status is written to `$LOG_DIR/fire-$STAMP.driver-rc` by the `{ … }` group and
read back. If the file is missing/unparseable **and** the job reported success,
`RC=70` and the wrapper says so loudly — because the chain loop below stops on
non-zero and chains a fresh driver on zero, so "we could not read the driver's
status" must never be spelled the same way as "the driver succeeded".

### 4. Deliberately NOT changed

`trap release_lock EXIT` keeps T202's exact bytes and its re-entrancy
reasoning. `stop_driver` is reached only through `on_signal`, because on every
non-signal path `run_driver` has already `wait`ed the job to completion.

Same subject harness, same scratch repo, same signal, the **real bytes** of each
version lifted verbatim by anchor (`T211-probe/extract.py`) — pre-fix from
`git show cc33f7f:.softhouse/bin/fire-program.sh`
(sha256 `b1c6f7fb…073a`), post-fix from this worktree (sha256 `80f3390a…dbc9`).

| bytes | signal | handler entry | wrapper exit | trap ran? | LOCK | driver child |
|---|---|---|---|---|---|---|
| **PRE-FIX** | TERM | **never** | **45.199 s — HUNG, harness had to SIGKILL** | **NO** | **STRANDED** | **ORPHANED** |
| **POST-FIX** | TERM | **0.0104 s** | **3.619 s** | YES | released | killed |
| POST-FIX | INT | 0.0103 s | 3.601 s | YES | released | killed |
| POST-FIX | HUP | 0.0054 s | 3.692 s | YES | released | killed |
| POST-FIX | QUIT | 0.0097 s | 3.716 s | YES | released | killed |
| POST-FIX | KILL | n/a — untrappable | 0.196 s | NO | STRANDED | ORPHANED |

[VERIFIED: `T211-probe/matrix.txt`; handler-entry figures are
`(handler log epoch) − (spawner's printed signal epoch)`, e.g. TERM
`1787362365.119050 − 1787362365.108691`.]

**The 45.199 s is a floor, not the deferral.** It is the harness's own timeout;
the wrapper was still alive when the harness gave up. The true pre-fix deferral
is the **remaining life of the foreground child** — 300 s in the probe, and
*hours* in a real fire, since the foreground child is `claude`. T202 measured the
same property as 29.88 s behind a 30 s child [`.softhouse/reviews/t202-probe/
zsh-trap-deferral.txt`]; this probe reproduces it against a child long enough
that no bounded observation can name the endpoint.

**Of the post-fix ~3.6 s, 3.0 s is the deliberate `DRIVER_STOP_GRACE_SECS`**
(give `claude` a chance to shut down cleanly before SIGKILL) and ~0.3 s is
`release_lock`'s git round trip. The trap itself runs in ~10 ms. launchd's
SIGTERM→SIGKILL grace is far larger than 3.6 s, so the handler now completes.

**SIGKILL is unchanged and still strands, by construction** — nothing in-process
can help. It remains handled out of process by T202's `lock_holder_is_dead()`,
which is verified intact below.

### The four things `wait` alone does NOT give you

The brief asked me to verify the shape against zsh's real semantics rather than
assume it. `wait` alone is **insufficient**; here is what I measured and what I
did instead. All from `T211-probe/semantics.txt`, `semantics2.txt`,
`waittrap-matrix.txt`, `treewalk.txt`.

**(a) The handler must `exit`; `wait` is RESTARTED otherwise.**
`waittrap-matrix.txt`, the fg/bg × exit/return matrix:

| shape | handler | exit latency | trap ran? |
|---|---|---|---|
| fg | exit | 20.094 s HUNG | NO |
| fg | return | 20.189 s HUNG | NO |
| **bg** | **exit** | **0.130 s** | YES |
| bg | return | 20.194 s HUNG | YES, at +1.35 s — then the shell went straight back to waiting |

The bg/return cell is the finding: the handler ran promptly and the shell
resumed `wait` anyway. T202's rule that every handler must terminate is now
load-bearing for *this* fix too, not only for the lock.

**(b) `background + wait + exit` still ORPHANS the child.**
The bg/exit cell exits in 0.130 s and leaves `/bin/sleep 300` running,
reparented to pid 1. On its own the named fix would have traded a stranded LOCK
for an *unlocked `claude` still writing to the repo* — strictly worse. That is
why `stop_driver` exists and why `on_signal` calls it **before** `release_lock`.

**(c) There is no process-group shortcut.** `setopt monitor` is **REFUSED** in
this shape — zsh 5.9 answers `can't change option: monitor` with no controlling
terminal [`semantics.txt` S5b]. So there is no job control, so a background job
does **not** get its own process group: every descendant shares the *wrapper's*
pgid [`semantics2.txt` S4b, and the live fire above]. `kill -- -$$` would
therefore signal the wrapper itself. Hence the explicit tree walk.

Also measured: `$!` of a bare background **pipeline** is its **last** member
(`jq`), not the driver [`semantics2.txt` S4-clean: `$!`=26997 = the third
`/bin/cat`, while the driver was 26995]. `$!` of `( … ) &` is the **subshell**,
the parent of every member [S4b] — which is why the fix uses the subshell form.

The tree the handler must actually stop is **three levels deep**, because
`/usr/bin/caffeinate` execs the utility in place and leaves its assertion-holder
as a *child* of it [`semantics.txt` S7, `treewalk.txt`]:

```
$!  /bin/zsh          ( … ) & subshell
 ├─ /bin/zsh          the { … } group == pipeline member 1
 │   └─ claude        caffeinate exec'd it in place   <-- the one that matters
 │       └─ caffeinate  assertion holder
 ├─ tee
 └─ jq
```

`treewalk.txt` drives the exact `driver_tree` bytes against that shape: 6 pids
found, the long child at index 3, `-> IN the tree … (a single kill on $! would
have MISSED it)`, and after the TERM sweep `no stray sleep -- the tree kill
reached the long child`.

**(d) SIGTERM, never SIGINT, is what the handler must forward.** An asynchronous
child of a non-job-control shell has SIGINT set to `SIG_IGN` (the POSIX rule
that produced T202's P-55 false reading). Measured directly: `SIGINT did NOT
kill the background child`, then `SIGTERM DID kill it` [`semantics.txt` S6]. A
handler that forwarded SIGINT would have been a dead letter.

**(e) `${pipestatus[1]}` dies.** After `wait`, `$pipestatus` holds **one**
element, not the pipeline's three [`semantics.txt` S4/S5:
`$pipestatus AFTER wait = (0)`]. `semantics2.txt` S9 shows the replacement
working: a `{ exit 37 } | cat | cat` job waits rc=0 while the rc file correctly
holds 37.

## Anchor for a regression probe (for T210)

I did not touch `.softhouse/reviews/`. Here is the durable target T210's
re-point should bind to.

**Bind by CONTENT, never by line number.** T211 moved `run_driver` from lines
237–291 to 356–474 and the trap block from 159–206 to 159–325; any line-number
binding is already stale.

**The extraction contract that works against BOTH pre- and post-fix bytes**
(this is exactly what `T211-probe/extract.py` does, and it is proven against
both — see the `extracted from …` headers in `red-TERM.txt` and `matrix.txt`):

- **trap block** — first line whose text *starts with* `LOCK_RELEASED=0`,
  through the first following line whose stripped text *is exactly*
  `trap release_lock EXIT`.
- **`run_driver`** — first line *starting with* `run_driver() {`, through the
  first following line whose stripped text *is exactly* `}`.

I deliberately placed `DRIVER_JOB_PID`, `driver_tree()` and `stop_driver()`
**inside** that trap-block range (after `release_lock()`, before the T202
`on_signal` comment) so a probe that extracts the trap block gets the whole
shutdown machinery in one piece and `on_signal` is not left calling an undefined
function.

**The three anchor lines a regression must not lose** (each appears verbatim in
`run_driver` / the trap block; patterns are given for BSD `/usr/bin/grep -E`,
naming the binary per P-58 — note the Bash tool's `grep` is a function
re-execing as ugrep with `-I`, so it is a *different program* and may answer
differently):

| # | anchor line (verbatim) | pattern | occurrences |
|---|---|---|---|
| 1 | `  DRIVER_JOB_PID=$!` | `^[[:space:]]*DRIVER_JOB_PID=\$!$` | 2 (jq / no-jq branch) |
| 2 | `  wait "$DRIVER_JOB_PID"` | `^[[:space:]]*wait "\$DRIVER_JOB_PID"$` | 2 |
| 3 | `  stop_driver` (inside `on_signal`) | `^[[:space:]]*stop_driver$` | 1 |

**Anchor 2 is the one to bind to if only one is wanted.** It is the fix: it is
what puts the shell in `wait` instead of in a foreground child, and no
regression that reintroduces the defect can keep it.

**Better than any text anchor, a behavioural binding is already committed and
re-runnable:**

```
/bin/zsh .softhouse/handoff/2026-08-21-run2-tierA-gl-accounting-A2/T211-probe/run-case.zsh \
         <path-to-fire-program.sh> TERM <label>
```

It rebuilds a scratch repo, drives the given bytes through `/bin/zsh -lc` with
default dispositions, and prints the three verdict lines the probe should assert
on — `EXIT LATENCY`, `LOCK = released|PRESENT-STRANDED`, and
`DRIVER CHILD = reaped|ORPHANED`. Pre-fix bytes make it fail; post-fix bytes
make it pass. It never touches the live repo or the live `.softhouse/LOCK`.

## Unverified

- **Whether launchd's own `AbandonProcessGroup` default would clean up an
  orphaned `claude` after a SIGKILL strand.** [UNVERIFIED] Testing it would mean
  stopping the live launchd job, which I would not do while a fire is running.
  The fix does not depend on it: `stop_driver` cleans up in process, and SIGKILL
  remains covered by `lock_holder_is_dead()`.
- **`release_lock`'s `git push -q origin main` latency against the real
  remote.** [UNVERIFIED] The scratch repo has no `origin`, so the measured
  ~0.3 s is the *failure* path. A slow or hanging push would extend the handler
  past launchd's grace. It is not a correctness risk for the lock: `rm -f
  "$LOCK"` is the first statement in `release_lock`, so the local lock — the one
  STEP 0 reads — is gone before any git call. Raised as a follow-up.
- **The exact real-world value of `DRIVER_STOP_GRACE_SECS` needed for `claude`
  to shut down cleanly on SIGTERM.** [UNVERIFIED] 3 s is a chosen default; the
  probe's stand-in dies instantly, so the probe cannot calibrate it. It is
  overridable by environment without editing the script.
- **Behaviour when the wrapper is NOT its process group's leader** (e.g. run by
  hand inside an interactive pipeline). [UNVERIFIED] The fix does not use a
  negative-pgid kill, so it should be unaffected, but I did not measure it.

   instead of from a guess.
