## 4. The design decision — REFUSE AT ADMISSION

**Chosen: at admission.** An unknown `context` makes the vector INADMISSIBLE, sitting immediately
below the two checks it repairs, alongside the class/directory/provenance lock that is already
there. The refusal is a property of the file, so it belongs where the other properties of the file
are judged.

**Rejected: at classification** — "a `parity` class whose comparator does not exist cannot be
graded."

**Why rejected, and it is a measurement, not a preference.** A `contract-refusal` vector consults
**no comparator at all**: its expectation is derived from the frozen contract's own doc comments,
its `oracle.seam` is required to be `"none"` (*"nothing was captured"*), and it is graded by
matching a sentinel. A rule phrased "the comparator for this class/context does not exist" is
vacuous for that class — and **RED-2 above shows that form of the attack is live**: admitted, PASS,
exit 0, contract-refusal 4→5, cells 5664→5665. A classification-level fix closes the parity door
and leaves the refusal door open. Three further reasons:

1. **Wrong outcome.** "Cannot be graded" reads naturally as a *skip*, and a skip is exit 0 with a
   quieter report. The measured defect is a corpus defect: the file should never have been in the
   store. `Admit`'s own doc comment already says an inadmissible vector is *"never a FAIL and never
   a skip … a defect in the corpus [that] makes the whole run untrustworthy"* — exit 2. That is the
   correct verdict here and it is the one admission already produces.
2. **Wrong time.** Classification happens per-vector during grading; admission happens before any
   number is computed. The thing that had to stop happening is a **number being printed**.
3. **Wrong message.** A classification refusal says "I could not grade this"; the reader's repair is
   to supply a comparator. The true statement is "this file claims coverage of a context this schema
   knows nothing about", and the repair is to build the second schema.

**Third alternative also rejected: a store-level context registry** (e.g. a list in
`capabilities.json` or `PIN.json`). It would put the constraint one level above the schema, so a
second schema would have to be threaded through a shared file that both comparators read — exactly
the "edit in five places" outcome the task warns against, and it would give the `ledger` builder a
`user`-gate-adjacent file to modify before writing a line of comparator.

### How a future context gets added under this design — **it is not added here**

The set lives in **one function**, `SchemaContexts()` in `vector.go`, within twenty lines of the
schema string it is a property of:

```go
const LoanScheduleContext = "loanschedule"
func SchemaContexts() []string { return []string{SelfTestDir, LoanScheduleContext} }
func IsSchemaContext(ctx string) bool { … }
```

It is a property of **`gerege.loanschedule.vector/v1`**, not a global registry. DEC-2 §5.2 has
already **decided** that `ledger` arrives as a *second schema* — `gerege.ledger.vector/v1` with its
own `Request`, `Expect`, comparator and cell whitelist, sharing only the store root, the file
census, the duplicate-case-id check, the raw-token float scan and the capability registry. Under
that decision the `ledger` builder declares `SchemaContexts()` **next to its own comparator**, in
its own package, and **does not edit this function or this list at all**.

The two checks then read as one statement in opposite directions:

- `admit.go:109-110` (pre-existing): a file whose `schema` is not `gerege.loanschedule.vector/v1`
  is not this harness's to grade — that is what routes a ledger vector *away* from loanschedule's
  rules.
- `admit.go:139` (new): a file whose `context` is not one this schema grades is not this harness's
  to grade — that is what stops a loanschedule vector wandering *into* ledger's directory.

Together: **a vector's schema, its directory and the comparator that grades it name ONE context.**
Neither is an allowlist the second context has to be threaded through. The `ledger` extension is no
harder to build than it was before this commit; the one thing it can no longer do is be faked with
`cp`.

The test's four sub-tests, and why each exists:

1. `a_parity_vector_copied_into_an_unknown_context_is_refused` — the driver's exact probe, asserted
   through `Run` (not `Admit`) because *the defect was the headline number moving*, and a unit
   assertion on `Admit` cannot see 44. Asserts exit 2, exactly 1 inadmissible, and **parity count
   and graded-cell count equal to the control's** — derived from the store, never hard-coded, so
   promoting a 44th real vector does not turn this red.
2. `the_same_bytes_in_the_right_context_are_admitted` — **the anti-vacuity control.** The same
   bytes filed under `loanschedule/` grade as a 44th parity vector at exit 0, so sub-test (1)'s
   refusal is attributable to the *context* and not to a harness that refuses every planted file.
3. `a_contract_refusal_vector_in_an_unknown_context_is_refused_too` — RED-2, permanently. This is
   the sub-test that would go red if somebody later moved the check to the comparator.
4. `an_empty_context_reports_one_defect_not_two` — an empty context reports *"context is empty"* and
   **not also** the unknown-context message. A refusal that lists two problems for one cause trains
   its reader to discount refusals.

Every fixture is anti-vacuity checked with `countDifferingLines`: if a future edit to
`P-00-baseline-6x7pct.json` makes the probe differ in more than the two intended lines, the test
**fails loudly** rather than quietly testing something else.
