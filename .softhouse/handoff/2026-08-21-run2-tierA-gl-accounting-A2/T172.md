other regex metacharacters worth keeping, but `$` is the minimal diff and keeps the existing `-a`/`LC_ALL=C`

## What I did NOT fix and why

- **`awk '/^worktree/{print $2}'` (line 238).** Reviewed above — not an unambiguous defect (no reachable
  false-match input against git's own fixed vocabulary), so leaving it matches requirement 4's instruction
  to fix only the unambiguous cases, not to over-fix.

- **Two other fail-open-shaped constructs found and deliberately left alone, because requirement 5
  explicitly forbids changing this file's control flow, locking protocol, or exit codes, and both of these
  sit inside exactly that:**
  - **Line 97:** `LOCK_EPOCH=$(/usr/bin/stat -f %m "$LOCK" 2>/dev/null || print 0)`. If `stat` fails on a
    race (e.g. the lock file vanishes between the `[[ -f "$LOCK" ]]` check and the `stat` call),
    `LOCK_EPOCH` silently defaults to `0`, `AGE` becomes enormous, and the lock is treated as stale and
    taken over — a fail-*open* result in the locking protocol. Fixing this would mean changing what happens
    on a lock-acquisition race, which is precisely the locking protocol requirement 5 says not to touch. Not
    fixed; flagged as a follow-up instead.
  - **Lines 283–295:** the `python3` heredoc deciding whether the chain loop stops. `except Exception:
    sys.exit(1)` catches every error (missing file, malformed JSON, missing key) the same way it treats "live
    tasks remain" — both mean "keep chaining." This is the shape P-40 names ("an enumerator with a bare
    `except: continue` is a silent-skip guard"), but changing what an exception does here changes the chain
    loop's control flow and exit behaviour, which requirement 5 forbids me from touching. Not fixed; flagged
    as a follow-up instead. (Note: unlike a rescue guard that silently *drops* work, this one silently
    *continues working* on error, which is the less dangerous direction — but it is still an unstated
    assumption worth a human decision, not mine to make inside this task's scope.)

  I did **not** treat these as "unambiguous" fixes in the P-37/P-40 sense, because unlike the LOCK anchor —
  where the pattern's own text and the guard's stated intent make the correct fix a one-character, drivable
  change with no other consequence — both of these sit inside logic requirement 5 names by name
  (`git pull`/lock-taking sequence; the chain loop's stop condition) and a fix to either is a control-flow
  change I was told not to make in this task.

- **The remaining `2>/dev/null` / `>/dev/null 2>&1` sites** (network probes at lines 57/66/67/71/79, and
  git/docker plumbing at 118/119/120/126/128/129/205/228/230/245/246/250/263) were reviewed and are not the
  same shape: each either (a) is an expected-to-sometimes-fail reachability probe whose caller already
  branches on the result (`if nc -z ...; then ... else ...`), or (b) suppresses *output* while the caller
  still checks `||` and logs a `WARN` on failure (e.g. line 120, 129, 263). None of these silently converts
  a real failure into an empty/clean result the way the pre-fix line 224 did. I did not find a fifth
  fail-open site beyond the two named above.

## Follow-ups

- **F-1 (new, mine).** `fire-program.sh:97`'s `stat`-failure fallback (`LOCK_EPOCH=... || print 0`) is
  fail-open in the locking protocol: a `stat` race on a vanishing lock file causes the lock to read as
  infinitely stale and be silently taken over. Requirement 5 forbids me from touching the locking protocol
  in this task; worth a dedicated task if this race is judged plausible enough to matter (the lock file's
  own lifecycle — created, committed, pushed, deleted on trap — means the race window is narrow, but it
  exists).
- **F-2 (new, mine).** `fire-program.sh:283–295`'s chain-stop check swallows every exception
  (`except Exception: sys.exit(1)`) the same way it treats "live work remains" — both mean "keep chaining."
  This is the P-40 shape (an enumerator that can't distinguish "nothing to do" from "couldn't tell"). Not
  touched here because fixing it changes the chain loop's control flow, which requirement 5 forbids. Worth a
  task, scoped narrowly to distinguishing "stop, program complete/all-gated" from "stop, couldn't read
  state" from "continue, work remains" as three outcomes rather than two.
