## 1. The headline — the corpus was never blind to HALF_EVEN

The brief said:

> *"0 of 46 vectors carry either tie answer — so **nothing in the parity corpus would
> notice a port that inherited Fineract's stock HALF_EVEN default**. That is a hole in the
> first ratified tenant parameter."*

The first clause is true of the literal **characters** `20925.05` and `20925.04`. **The
inference is false, and it is false by three vectors.** `T61-HE-A`, `T61-HE-B` and
`T61-HE-C` — promoted by task T61 — are exact ties at the same quantization on other
principals, and their named counterfactual is `MONEY-QUANTIZATION-HALF-EVEN`, the same
one this task was sent to create coverage for. `T61-HE-A`'s own title says so: *"kills a
port that applies banker's rounding at Money.java:52 by 6 minor units."*

Measured, not read. Mutating the port to banker's rounding at that one site — the
already-named `M7` of `.softhouse/handoff/T61-mutations.py` — over the **42**-vector store
as it stood before this task:

```

```

`.softhouse/capture/pathb/t149/redgreen/premise-refuted-42-vector-store.txt`.

**Where the brief's number came from, and why it misled.** It is T136's, and T136 stated
it correctly — *"the graded corpus is **not** blind to the parameter: 0 of 46 vector files
contain either tie answer, **but** `REFUSE-02` makes HALF_EVEN a contract refusal"*. Two
things then happened to it. T136 offered `REFUSE-02` as the defence and did not notice
`T61-HE-*`, which is the stronger one; and the brief kept the count and replaced T136's
"but" with a "so". The count survived; the qualification did not.

**The generalisable lesson, and I would put it in `patterns.md`:** *grepping the store for
a **value** does not answer what the store **kills**.* A corpus of 43 vectors is a set of
functions, not a set of literals; the only sound way to ask whether it notices a defect is
to build the defect and run it. This store already has that instrument (`T61-mutations.py`,
13 named mutations) and the brief's claim would have taken one command to check.

## 4. Admissibility — how a Path B capture got past T76's `PROMOTE NOTHING`

T76 refused to promote any of `B-01..B-04` and its reasoning had to be answered, not
sidestepped. Its four tests, against this capture:

| test | this capture |
|---|---|
| 1. seam status `exercised` | `schedule.core` is `exercised` on `path_b_server` — unchanged data |
| 2. capability `in_graded_domain` | `schedule.core` is `true` — unchanged data |
| 3. **truthfully expressible in the frozen shape** | the hard one; see below |
| 4. `graded_against` non-empty | kills `MONEY-QUANTIZATION-HALF-EVEN`, margin 1 minor unit, both arms observed |

**Test 3 had two limbs.**

*Day count.* T76's B-01 is refused because its product is `days_in_year_enum = 1` /
`days_in_month_enum = 1`, i.e. **ACTUAL/ACTUAL**, which the graded domain excludes — and
writing `FIXED_30_360` anyway *"would state a product setting the oracle did not have; the
numbers would match and the provenance would be a lie."* That is right, and it is why this
capture was **not** taken on the canary's own product 11 (also ACT/ACT). It was taken on
product **9**, `T22 probe p09-sarp-360-30`, whose row is `days_in_month_enum = 30` /
`days_in_year_enum = 360`. `FIXED_30_360` is what the oracle ran.

That the two products answer **byte-identically** (`39f56dc2…` at the tie principal,
`713a3560…` at 1.2M) is a measurement recorded in the vector, not the justification: the
justification is that the transcription is true.

*`interestCalculationPeriodMethod`.* DEC-1 pins it **unset**; the running server always
populates it, and every Path B request here carries `SAME_AS_REPAYMENT_PERIOD`. T76 left
this `[UNVERIFIED]` — it could not test it, because B-01's ACT/ACT product confounds the
day count with it. **Closed by measurement, on this shape only:**

* `T149-CTRL-P9-1M2` (product 9, SARP + 30/360, MNT 1,200,000) is **byte-identical** to the
  committed `B-01-baseline-raw.json` taken by T36 in a different fire (`713a3560…`);
* and it agrees with the promoted Path A vector `P-MNT-1M2` — ICPM **unset**, same fixed
  30/360 — in all 12 rows across principal, interest, outstanding balance and row total,
  and in total interest (`14,498,847` minor units).
  `redgreen/crosscheck-vs-patha.txt`.

With the day count controlled, ICPM is the only remaining difference and it moves nothing.
The mechanism is visible in source and agrees: its only reader on this path is
`ProgressiveEMICalculator.addDisbursement` (`:127-132`), which resolves `effectiveDueDate`
to the from-date of the first repayment period whose due date is **after** the disbursement
— which *is* the disbursement date when the loan is disbursed on the schedule start date.

**This closure is scoped and I want it read that way.** It licenses nothing about a daily
interest calculation, where the setting is live; it is not an amendment to the pin; and it
does not reopen `B-01..B-04`, each of which still fails a different test. Recorded as an
amendment appended to `t76/PROMOTION-DECISION.md` rather than by editing T76's verdict.

**One transcription consequence of the seam.** Path B's disbursement row has **no
`fromDate` field at all**, where the Path A pass-3b rig records one. So this vector
withdraws a **third** cell — `from_date` — beside the two every other vector withdraws. It
is not covered by the "the contract already fixes it at 0" exemption: the contract fixes a
disbursement row's `InterestMinor` and `InstallmentNumber`, and fixes nothing about its
`FromDate`. Filling it from the due date would be deriving a cell and storing it as an
observation. `vectors/README.md` now records this as the seam deciding which cells exist.
