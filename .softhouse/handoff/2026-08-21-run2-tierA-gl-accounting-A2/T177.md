## Findings — what the throw depends on

The task named four candidate hypotheses. Taking them in order:

**(a) Pure per-request nondeterminism — REFUTED.** 33 cold starts, 33 throws, 0 observations; and
inside a JVM the outcome is a deterministic step function, `XXXXoooo`, in 7 of 7 JVMs that asked the
cell more than four times. In 107 trials no `observed` was ever followed by a `threw` in the same
process. A coin would not do that.

**(b) Order / warm-up dependence — CONFIRMED, and it is the dominant factor.** Attempts 1–4 threw in
7/7 JVMs; attempt 5 was observed in 7/7. And the warming need not be the disputed cell: **50 prior
calls on a different, never-throwing cell (same principal, n = 200) flip it (3/3), while 1 prior call
(0/3) and 10 prior calls (0/3) do not.** It is generic exercise of the shared code path.

**(c) Fresh-JVM vs warmed-JVM — CONFIRMED, and the warming agent is the OPTIMISING COMPILER.** With
C2 switched off (`-XX:TieredStopAtLevel=1`) the transition **never happens**: 8 attempts, 8 throws,
and a flat ~6.1 s elapsed on every one. With C2 on, the **true stack depth reached at overflow rises
within a single JVM** — with HotSpot's 1024-frame recording cap lifted, attempts 1–4 reached
`5119, 4683, 4683, 8400` frames and attempt 5 did not overflow at all.
`[VERIFIED: out/matrixC/raw/depth-uncapped-0.stdout]`

> Consequence for every capture in this program: **`errorStackDepthTotal: 1024` is HotSpot's default
> `MaxJavaStackTraceDepth`, not a depth.** T169's two throwing cells, and T159's, all record 1024
> for that reason. No depth conclusion may be drawn from them.

**(d) Thread / connection dependence — thread REFUTED as the locus; connection NOT APPLICABLE.** This
seam is called in-process, so there is no connection and no request. Varying *thread identity* — a
**freshly spawned thread with a brand-new stack for every probe** — leaves the pattern exactly
unchanged (`XXXXoooo`), so the state that changes is **JVM-wide compiled code, not per-thread stack
state**. A single probe on a fresh thread from a cold JVM throws 3/3, like the main thread.

**(e) Stack size — CONFIRMED as the other half of the mechanism.** Cold JVM, first seam call, inputs
held fixed: `-Xss` 512k / 1m / 2m / 4m all throw (2 JVMs each); **8m and 16m are observed** (2 JVMs
each). The image's measured default is `ThreadStackSize = 2040` KB on OpenJDK 21.0.11 Zulu21.50+19-CA
`[VERIFIED: out/jvm-defaults.txt]`. **A cell whose outcome moves with `-Xss` is not a cell whose
outcome is a property of its inputs.**

## Impact on T116 and G-8 option (a)

**1. A single-shot boundary probe measures the JVM, not the oracle.** T159's follow-up 5 ("bound the
`StackOverflowError` region") and any design that asks each cell **once** is measuring where the
sweep's own warm-up curve crossed that cell, and would produce a "boundary" that moves with case
order and case count. **There is no input-only throwing region to map.** This is the concrete answer
to the question T177 was raised to settle, and it should re-scope that follow-up before any oracle
time is spent on it.

**2. A vector must never be promoted from a cell whose outcome depends on where it sat in the run.**
Two designs are reproducible; both are `ENGINEERING` decisions for the driver, and T177 decides
neither:

* **(i) Cold-start capture** — one JVM per cell, the graded cell as its *first* seam call. Maximally
  reproducible and trivially attestable; costs one JVM start per cell. T177 measured **33/33
  reproducibility** for the disputed cell and **9/9** for the headline cell under this discipline.
* **(ii) Declared warm-up protocol** — a fixed, recorded number of prior seam calls, with the count,
  the `-Xss` and the JIT flags written into the vector's attestation, so a re-capture can reproduce
  the state. Cheaper; requires the attestation to gain three fields it does not have today.

**3. What T116 (option (a), the family-B promotion) needs before it captures.** T116's target cell is
untouched by this finding *arithmetically* — the money never varied. What changes is the
**reproducibility argument**: the capture that promotes it must state the JVM state it was taken in.
T177 gives one directly usable datum — **G-8's headline cell (B = 1001 minor units, n = 3000) is
observed 9/9 from cold** — and **no** datum about the other family-B cells' cold behaviour, because
T177 only ever asked them at non-zero positions inside the `t159prefix` replay. **Those must be
re-asked cold before anyone claims they are cold-safe.** `[NOT MEASURED for family-B cells other
than B = 1001 at n = 3000]`

**4. G-8's write-up carries one sentence that is now unsupported**, and T170 owns the rebuild (T177
edited nothing):

> `gates.md` — *"It is not monotone: `(B=10001, n=2000)` dies while `(B=10001, n=3000)` succeeds, so
> this is not a simple size limit and cannot be excluded by bounding the inputs."*

The **premise** is refuted: the two cells differ in run position, not in behaviour. The
**conclusion** ("cannot be excluded by bounding the inputs") may still hold — T177 did not test it —
but it no longer rests on that evidence. G-8's finding #1, "**THE REFERENCE ORACLE THROWS**", stands
and is if anything strengthened: option (b)'s graded domain still needs a way to express "no answer",
because a rig at the default `-Xss` will keep producing them.

**5. A cheap, non-invasive mitigation exists and is worth the driver's attention.** At `-Xss8m` the
disputed cell is observed on the **first** call of a cold JVM (2/2), as is the same cell at 16m
(2/2). Raising the capture rigs' `-Xss` would remove most of this class of throw from future sweeps.
**T177 does not adopt it** — it changes the measurement conditions of every capture in the corpus and
that is a decision, not a worker's edit.

**6. For the Go port.** These cells have a defined answer that the reference implementation can
produce when given enough stack; the throw is an environmental limit of the JVM, not a semantic the
Go port must reproduce. **Stated as a reasoned inference from (e), not as a measurement**, and it
does **not** generalise to cells T177 never asked. `[REASONED, not verified as a general rule]`

## Follow-ups

1. **Re-scope T159's follow-up 5 before spending oracle time.** There is no input-only throwing
   region to bound. If a boundary is still wanted, it must be defined *at a stated JVM state* — e.g.
   "the set of cells that throw as the first seam call of a cold JVM at the default `-Xss`" — and
   every cell must be asked from its own fresh JVM.
2. **Give the capture attestation three fields**: the cell's `seq` within its JVM process, the JVM's
   `-Xss` (or measured `ThreadStackSize`), and the JIT flags. Without them a throw is not
   attributable and a non-throw is not reproducible. This is the smallest change that would have
   prevented the T159/T169 disagreement from being a mystery.
3. **Decide the capture discipline for gradeable cells** — cold-start-per-cell, or a declared warm-up
   protocol recorded in the attestation. `ENGINEERING`, driver's call; T177 recommends cold-start for
   anything promoted, because it needs no new protocol to be reproduced.
4. **Consider raising the rigs' `-Xss`.** 8m removes the throw for the disputed cell on the first
   cold call (2/2). It changes the measurement conditions of the whole corpus, so it is a decision,
   not an edit.
5. **`errorStackDepthTotal: 1024` in every existing capture is a recording cap, not a depth.** Any
   future rig that cares about depth must set `-XX:MaxJavaStackTraceDepth=0`. Worth a line in
   `patterns.md` — **another worker holds that file, so T177 did not touch it.**
6. **T170 owns G-8's rebuild.** The "not monotone" sentence's premise is refuted (see above); the
   headline cell is cold-safe; and the disputed cell is **not** the headline cell, which the current
   framing conflates. T177 edited `gates.md` not at all.
7. **Family-B cells other than B = 1001 at n = 3000 have no cold-start measurement.** If T116
   promotes one, ask it cold first.
