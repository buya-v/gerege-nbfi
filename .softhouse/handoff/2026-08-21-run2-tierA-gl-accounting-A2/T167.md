## Changes Made

One file changed: `.softhouse/reviews/t47-probe/t47_edit_1.py`.

**The edit the script performs is byte-for-byte unchanged.** Every anchor string and every
replacement string is exactly T47's; only the write mechanism, a content gate and an
authorisation gate were added. This is checked, not asserted: an authorised run on a
scratch copy of the revision-9 document produces sha256
`4f2387c821a01953503c77c2c70730bf72657c994491110c5ae3bc27a866dc37`, which is
`git show bf67a85:docs/adr/DEC-1-schedule-generator-adapter.md` exactly
[VERIFIED: transcript §6 R8, `reproduces bf67a85:… exactly: True`].

1. **Atomic write.** `tempfile.mkstemp(dir=<the target's own directory>)` → write → `flush`
   → `fsync` → `os.replace()` → `fsync` of the directory. The target is **never opened for
   writing**. The same-directory requirement is met *by construction* — a directory cannot
   span filesystems — and is *additionally asserted at runtime* by comparing
   `os.stat(tmp).st_dev` with `os.stat(target).st_dev` and refusing (exit 5) if they differ.
2. **sha256 content gate, both ends.** The target must hash to `32539607…` (the pre-edit
   blob) or the run refuses having written nothing (exit 3). The *candidate* text is hashed
   **before** anything is moved into place and must equal `4f2387c8…` (exit 4), so a wrong
   write cannot occur even transiently. A post-write read-back is checked too (exit 6).
3. **Default-deny authorisation** — see its own section below.
4. **`assert` → real check.** The revision-9 anchor test at the old line 66 was an `assert`,
   which `python3 -O` strips; the `.replace` would then have silently done nothing and the
   file would have been rewritten with unmodified content. Now a `die(1, …)`.
   [VERIFIED: transcript §6 R10 — an authorised run under `python3 -O` still produces the
   correct blob.]

**What T114's standing ruling permits here, reasoned rather than assumed.** T114 held that
*editing a script that produced committed evidence invalidates the evidence*. `t47_edit_1.py`
did produce a committed artefact: it and the ADR diff it made landed in the **same commit**,
`bf67a85` [VERIFIED: `git show --stat bf67a85` — 2 files, the script and the ADR]. Three facts
decide it:

- The evidence is a **document diff already immutable in git**, not a measurement that has to
  be re-derivable by re-running the script. Nothing I do to the working-tree copy can alter
  `bf67a85`, and `git show bf67a85:…` still returns the original bytes (sha256
  `04cc3f4c4fee44e02ae57a863ed01ad660214bb7cdff91e8de736e96cf4fe39d`).
- The script was **already dead as a recipe before I touched it**: DEC-1 revisions 11 and 12
  rewrote §4.1.1, so neither anchor exists in the ratified document
  [VERIFIED: `grep -c 'A port must implement the packed rule WITH the '` over the current ADR
  → `0`]. Editing it therefore destroyed no reproduction capability that existed.
- The hardening makes it **more** faithful to the committed evidence, not less: the sha gate
  pins it to exactly the input it was written for and to exactly the output it produced, so
  it is now a *checkable* reproduction recipe where before it was an unpinned rewriter.

The ruling's purpose — never let a later edit make a committed number unreproducible — is
served, so the hardening is in scope. The pre-fix bytes are used throughout the red probe by
their **immutable commit** `bf67a85`, never via `main:` (P-24).

### The misclassification, reproduced first (transcript §0b)

Over the **pre-fix** bytes: the driver's regex `^\s*(try:|finally:|except)|atexit|signal\.`
matches **0**; T156's `GUARD` (verbatim from `t156-sweep-unguarded-mutators.py:58`), run the way
T156 ran it — Python `re` — returns **3 matches → GUARDED = True**; `trap` appears on lines
**55, 145, 151** and the AST says **3 of 3 occurrences are inside string literals**, the prose the
script writes into the ADR. `ast.Try` nodes: **0**. The file was scored safe by the text it was
writing.

**A second, independent P-33 finding fell out of reproducing it.** The *same pattern text* piped
through `grep -E` returns **0**. Neither is a typo: in Python `re` a bracket expression honours
the `\n` escape, so `[^#\n]` means *not `#` and not newline*; in POSIX ERE it does not, so
`[^#\n]` means *not `#`, not backslash, not the letter `n`* — and each of the three `trap`
occurrences has a letter `n` earlier on its line (`One trap worth`), which the anchored
`[^#\n]*` cannot cross. **Same characters, opposite verdict, depending on the engine.** Any
follow-up that ports this classifier between Python and shell will silently change its answers.
[VERIFIED: transcript §0b, both engines run side by side on the same bytes.]

### Pre-fix — the document is destroyed

- **§1, deterministic, no timing at all.** Under `ulimit -f 64` the run dies with
  `OSError: [Errno 27] File too large` and leaves the scratch ADR at **65,536 bytes** of
  328,439, sha `cfd3abb8…` — neither the old document nor the new one.
- **§3b, the real 328,439-byte size, the signal *aimed* at the window** (fire the moment the
  target's size drops below its starting size), retried until the kill lands inside it:

  | signal | attempt | scratch ADR afterwards |
  |---|---|---|
  | SIGINT | 7 | **DAMAGED — 0 of 335,644 bytes** |
  | SIGTERM | 1 | **DAMAGED — 0 of 335,644 bytes** |
  | SIGHUP | 1 | **DAMAGED — 0 of 335,644 bytes** |
  | SIGKILL | 2 | **DAMAGED — 0 of 335,644 bytes** |

  Every byte gone. `io.open(path, "w")` opens with `O_TRUNC`, so the document is emptied
  *before* the first byte of replacement text is written; there is no state in which a
  fraction of the old document survives.
- **§2** repeats it on a 62,729,207-byte padded copy (padding appended after both anchors, so
  `rep()` still finds exactly one of each) — all four signals **EMPTIED**. Padding changes the
  *duration* of the window, never its existence.
- **§3, randomized-delay sampling, N=40 per signal** — reported because it is what a naive
  test would do, and it is the **wrong instrument**: at the real size ~167 ms of the run is the
  two string replaces and the unprotected window is well under a millisecond, so a uniform
  delay lands in it rarely (this run: **1 DAMAGED in 160 trials**, on the SIGHUP leg; an earlier
  run of the same probe with a narrower delay range got 5 in 160). A rate here measures the
  sampler, not the defect — which is why §3b aims at the window instead.

### Post-fix — the same interruptions leave the target untouched

- **§4A, aimed at the pre-`os.replace` window** (kill the instant a `.t47-edit1-*.tmp`
  appears), retried until the kill lands before the rename:

  | signal | attempt | target afterwards | temp residue |
  |---|---|---|---|
  | SIGINT | 2 | **UNTOUCHED, 328,439 bytes** | none — `finally` ran |
  | SIGTERM | 6 | **UNTOUCHED, 328,439 bytes** | `.t47-edit1-dyrb7jyf.tmp` |
  | SIGHUP | 3 | **UNTOUCHED, 328,439 bytes** | `.t47-edit1-46nodc0s.tmp` |
  | SIGKILL | 2 | **UNTOUCHED, 328,439 bytes** | `.t47-edit1-6jn5skx8.tmp` |

  Byte-identical to its starting state, i.e. sha `32539607…`, on all four paths.
- **§4B, randomized delays straddling completion, N=40 per signal, 160 trials.** Outcome is
  always exactly `UNTOUCHED` or exactly `COMPLETED`; **`DAMAGED`/`MISSING`: 0 of 160.**
  (untouched/completed: SIGINT 16/24, SIGTERM 15/25, SIGHUP 10/30, SIGKILL 14/26 — the split
  confirms the trials really did straddle completion rather than all landing on one side.)

### Which signals `os.replace` makes moot, and why — stated, not staged (§4b)

For the **target**, all four, for one reason: the hardened script never opens it for writing,
so no signal can catch it half-written. The four differ only in the fate of the **temp file**:
SIGINT raises `KeyboardInterrupt`, the ordinary `finally` in `atomic_write()` runs and unlinks
it; SIGTERM and SIGHUP terminate with no Python code running, leaving it; SIGKILL cannot be
caught at all — **a trap-based fix would be defeated by SIGKILL and `os.replace` is not**,
because atomicity is a property of `rename(2)` in the kernel rather than of any handler the
process gets to run. I did not stage a "recovery" for these paths, because there is nothing to
recover: the residue is a temp file that is not the ADR, that nothing reads, and that the next
run replaces. It is reported rather than hidden.

### One structural proof with no timing in it at all (§5)

Set the target's mode to `0444`. The **pre-fix** script dies with `PermissionError [Errno 13]`;
the **post-fix** script **succeeds** and produces the correct blob, because renaming over a file
needs permission on the *directory*, not on the file. That is a direct observation that the
target is never opened for writing, and it does not depend on winning a race.

## The refusal: default-deny for a ratified DEC-n

This is the part of the finding that matters most. A script that can silently rewrite a
ratified DEC-n is a `user`-gate bypass wearing a probe's clothes, and the pre-fix file was
exactly that: `DOC` was **hard-wired** to `docs/adr/DEC-1-schedule-generator-adapter.md`, there
was no argument to pass, no confirmation, and no way to run it *other* than against the
ratified document.

The design now is: **there is no default target, and there is no override that reaches the real
ADR.** A run must clear four independent barriers.

1. `--target=PATH` must be given explicitly. No argument, no default, no environment fallback.
2. The resolved real path must not be the repo ADR, must not lie anywhere inside the repository
   working tree, must not sit under any directory named `adr`, and must not carry the ADR's own
   basename. Each is checked on `os.path.realpath`, so a symlink does not evade it. **No flag
   lifts any of these** — the only legitimate remaining use of this script is reproducing a
   historical edit on a scratch copy, and that use never needs to write inside the repo.
3. `--authorise=I-AM-REPRODUCING-T47-EDIT-1-ON-A-SCRATCH-COPY-NOT-THE-RATIFIED-DEC-1`, matched
   literally. **Deliberately an argv word and not an environment variable**, and the brief was
   right to call that out: an env var is exported once in a wrapper, inherited by every child
   process and then forgotten, so it authorises runs nobody is thinking about. An argv token
   must be retyped at every single invocation, states in its own text what it is authorising
   (it is not `--force`; it says *"a scratch copy, not the ratified DEC-1"*), and is recorded
   by construction in the process table and the shell transcript. The script also writes a
   loud `edit1: AUTHORISED run on scratch target … (sha256 …)` line to stderr.
4. The target's sha256 must be the exact pre-edit blob. This is **content-addressed
   authorisation** and it is the barrier that cannot be argued with: the ratified ADR today
   hashes `49dc8923…`, not `32539607…`, so even with every other check removed the script
   could not touch it.

Measured refusal matrix (transcript §6). The "watched file unchanged" column is a sha256
comparison taken immediately before and after each run:

| # | invocation | exit | outcome |
|---|---|---|---|
| R1 | no arguments | 2 | usage; refuses, names the `user` gate |
| R2 | `--target` only, no token | 2 | usage; refuses |
| R3 | valid target, `--authorise=yes` | 2 | token mismatch, nothing written |
| R4 | **the real ratified ADR** + valid token | 2 | `target IS the ratified DEC-1 ADR … no override`; **real ADR unchanged: True** |
| R5 | scratch file whose **content would pass the sha gate**, under a dir named `adr`, ADR's basename | 2 | refused on path policy; unchanged: True — this isolates the authorisation barrier from the content barrier |

| R7 | authorised, exact revision-9 bytes, `--dry-run` | 0 | prints before→after, **unchanged: True** |

| R10 | authorised run under `python3 -O` | 0 | correct blob; the ex-`assert` still guards |

### Should T156's GUARD regex be replaced by a parser-based check?

**Yes, and as a separate task** — recommending it with evidence rather than doing it here.
Evidence from this task, all measured:

- **The regex is wrong in the risk-hiding direction on 4 of 19 files**, and the AST re-audit
  reproduces that independently: of the four, three have 0 guards *and* their guard-words are
  100 % inside string literals (`prove-exit-trap.py` 8/8, `t156-sweep…py` 14/14,
  `t47_edit_1.py` 5/5 for `trap`); the fourth's are inside shell `echo`s.
- **The regex is also wrong in the other direction**, and my own fix demonstrates it: the
  hardened `t47_edit_1.py` now carries a docstring quoting the old
  `io.open(DOC, "w", encoding="utf-8").write(s)` line, so a *source-text* sweep for unguarded
  writers will now match a file that is atomic. Only an AST walk distinguishes the two.
  I kept the quotation because a fix that deletes the record of what it fixed is worth less
  than a false positive in the safe direction — but it makes the case for the parser concrete.
- The mechanics are cheap for Python (`ast.walk`, ~60 lines — `t167-reaudit-guards.py` is a
  working prototype) and **genuinely hard for shell**, where the stdlib has no parser. That
  asymmetry is the design question the follow-up has to answer, and it should not be resolved
  by silently applying a Python-shaped answer to `.sh` files.
