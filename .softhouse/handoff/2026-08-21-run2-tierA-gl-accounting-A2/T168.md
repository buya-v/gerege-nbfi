**A note on how this was driven, given P-55 (T202's harness-artefact false
conclusion).** T202 recorded a false "SIGINT/SIGQUIT ignored" finding because its probe
backgrounded the subject from a non-job-control shell, which `SIG_IGN`s `INT`/`QUIT` in
the child. This prover does **not** do that: `run_case()` uses
`subprocess.Popen(["bash", dst], …, start_new_session=True)` — a direct `exec` of
`bash` into its own new session, never a shell `&` background job — so no job-control
`SIG_IGN` is imposed on the child. The signal itself is delivered by `os.kill(ppid,
signal.SIGQUIT)` from a stub process, a direct signal to a specific pid, not a
terminal keystroke through job control. [VERIFIED: reading `prove-exit-trap.py:163-187`
before adding the new case; this shape and reasoning pre-date T168 — T158 already relied
on it for the other three signals it drove]

## The :94 vs :98 claim correction

T158 found: the empty-census refusal (`[ "$CENSUS_N" -gt 0 ] || fail …`, now at
`prove-redgreen.sh:112-113` after this task's edits shifted line numbers — was `:98` at
T156's HEAD) is **pre-empted** by `[ -f "$VEC" ] || fail …` (now `:108`, was `:94`) on
every realistic state: `$VEC` is one `*.json` file under `$STORE`, so a store empty
enough to make the whole-store census empty already implies `$VEC` is missing, which the
earlier `-f` check has already refused before `store_census()` is even called. T158
reached the census-empty message only via a contrived symlink construction (`$VEC` a
symlink so `-f` follows it while `find -type f` does not) — not a state an operator or a
crash produces.

**This task corrected the comment, not the code.** The `-f` check and the census-empty
check are both still present, unchanged in behavior — I did not delete, reorder, or
"improve" a working guard to match a wrong description of it, per the explicit
instruction. I added:
* a rewritten block comment above `store_census()` explaining the correction and citing
  T158's finding directly (previously it said, in effect, "an EMPTY census is a refusal"
  as if that were the protection);
* a one-line comment on the `-f` check itself marking it as the line that actually
  supplies the protection;
* a one-line comment on the census check marking it as defense-in-depth for a state the
  `-f` check does not cover (e.g. `$VEC` present but every *other* `*.json` under
  `$STORE` gone), not as reachable via "the store went empty."

I did not change `README.md`'s or any other file's prose to add a NEW claim about this —
