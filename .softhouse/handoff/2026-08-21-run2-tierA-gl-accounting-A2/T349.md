## 1. Q1 — does the deny stop the AGENT spawn, or only a `Bash git worktree add`?

**It stops the Agent spawn.** These are different call paths and both are deniable, and the answer to
the sub-question the task called the most important one is: *not only Bash.*

| drive | expect | got |
|---|---|---|
| `R1` CONTROL: log-only hook, real Agent spawn | hook fires; worktree created | fires with `tool_name=Agent`; worktree + branch created | PASS |
| `R2` RED: deny `Agent` | refused, nothing created | `deny`; **branch diff empty, worktree diff empty**; refusal text reached the model verbatim | PASS |
| `R3` RED: deny `Bash` whose command matches `worktree add` | refused | `deny`; nothing created | PASS |
| `R4` deny `Agent` ONLY, prompt permits a fallback | — | **the model issued `git worktree add` from Bash on the very next turn and got its worktree** | see below |

[VERIFIED: `out/R{1,2,3,4}-*.report.txt` and the matching `*.hook.jsonl`]

**R4 is the load-bearing negative result.** Nobody told that session to route around the gate; it was
told only "you are free to accomplish the same end state by whatever other means the tools allow", and
it went to `git worktree add` immediately. So a gate on `Agent` alone is not a gate. **Both paths must
be matched.** (Cross-check for a future harness: in stock Claude Code the spawn tool is named `Task`;
in this build the payload says `Agent`. Match both names.)

## 2. Q2 — what the hook has at decision time, and what it costs

**Payload.** `tool_name`, the **entire `tool_input` including the full worker prompt**, `cwd`,
`session_id`, `transcript_path`, `permission_mode`, `tool_use_id`, `prompt_id`, `effort` — and the one
that decides whether this is safe: **`agent_id` and `agent_type` are present ONLY on a SUBAGENT's tool
call, and absent from the driver's own.** [VERIFIED: `out/R1-control-log.hook.jsonl` — the `Agent`
record has `payload_keys` without `agent_id`; the subagent's `Write` record has it, same `session_id`.]

That single field is what stops the hook bricking a fire: workers are forbidden to push, so a
push-gate applied to a *worker's* own sub-spawn would deny it forever. With the exemption, it never
sees them — **16 live subagent tool calls were exempted during one drive** [VERIFIED:
`out/candidate.gate.jsonl`].

**The prompt is enough to identify the task.** Three shapes the `softhouse` worker-prompt template
guarantees all yield the id: the handoff path `.softhouse/handoff/<run>/<Tnnn>.md`
(`.claude/skills/softhouse/SKILL.md:122`), the `softhouse/<taskid>-<slug>` branch line (`:119`), and
the `=== TASK Tnnn ===` header this very prompt carries. All three drive green [VERIFIED:
`out/unit-drive.txt`].

**Cost, measured, not estimated** [VERIFIED: `out/cost.txt`, `out/fetch-cost.txt`,
`out/unit-drive.txt`]:

| thing | median | note |
|---|---|---|
| hook process, no network (`python3` start + parse + log) | **122 ms** | the floor on every gated tool call |
| `git ls-remote origin refs/heads/main` → real GitHub over SSH | **4180 ms** | 10 samples |
| `git fetch --quiet origin main` → same origin | **4330 ms** | 8 samples; the gate needs CONTENT, so it must fetch |
| candidate gate, full decision, local origin | 375–450 ms | 14 unit cases |
| candidate gate, subagent fast path | **121 ms** | exempt, no network |
| `git ls-remote` to an unroutable host, no client timeout | **75.1 s** | this number decides §3 |

The SSH handshake dominates: fetching content is no dearer than asking for a sha. **~4.3 s is added
to each DRIVER spawn** — about 22 s per five-worker batch, against a multi-hour fire. That is
affordable.

**The 122 ms floor is the real cost driver, and it is avoidable.** `"matcher": "*"` runs the hook on
*every tool call of every session in the repo, workers included*. Scoping it works: with
`"matcher": "Agent|Task|Bash"` the subagent's `Write` produced no invocation at all [VERIFIED:
`out/M1-matcher-scoped.report.txt`]. **I did not measure how many tool calls a real fire makes**, so I
will not put a number on the `"*"` tax — [UNVERIFIED] — but one 3.5-minute worker made 16, and a fire
runs five workers for hours, so the scoped matcher is the only sane configuration.

## 3. Q3 — the failure mode when it cannot decide, and which answer is less bad

Three separate "cannot decide" shapes, all measured, and **all three of the accidental ones fail OPEN**:

| shape | harness behaviour | evidence |
|---|---|---|
| hook exceeds its `settings.json` `timeout` | **FAILS OPEN** — hook killed, tool ran, worktree created | `out/H1-hook-timeout-5s-hang20s.report.txt`: 5 s timeout, hook slept 20 s, logged `hang-start` and never got to emit its deny; the spawn succeeded |
| hook script raises / exits 1 | **FAILS OPEN** | `out/B1-hook-crashes.report.txt` |
| hook script missing entirely | **FAILS OPEN** | `out/B2-hook-missing.report.txt` |
| origin unreachable, hook decides | **the hook's own choice** | `out/P3-offline-FAILOPEN.report.txt` (allowed) vs `out/P4-offline-FAILCLOSED.report.txt` (denied), same unroutable origin |

Two consequences, and they pull in opposite directions.

**(a) The hook must own its network timeout, or it cannot fail closed at all.** `git` will sit on an
unroutable host for **75 s**; any sane `settings.json` timeout is shorter; a timeout is an ALLOW. So a
hook that leaves the deadline to the harness fails open in exactly the offline case it was written for.
The candidate therefore sets its own 12 s deadline (`SOFTHOUSE_SPAWN_GATE_NET_TIMEOUT`) and it must
stay **strictly below** the `settings.json` timeout (30 s). Measured at a 4 s internal deadline the
denial lands in 4.13 s [VERIFIED: `out/unit-drive.txt`].

**(b) Which direction is less bad: FAIL CLOSED.** *Reasoning, recorded as required:* a fire that cannot
reach `origin` **cannot satisfy the obligation at all** — it cannot push the LOCK, the dispatch record
or `RESUME.md` — so every worker it spawns lands in precisely the P-85 state the obligation exists to
prevent: origin saying *"no fire is running"* while workers are live. Refusing to dispatch loses one
scheduled fire; the scheduler fires daily and the LOCK/RESUME protocol resumes. Failing open loses the
guard in the only condition where the violation is *guaranteed* rather than merely possible.
The cost I am accepting, stated plainly: a transient GitHub slowdown past 12 s denies a legitimate
spawn and idles a fire until the next run. I judge a lost fire cheaper than a duplicate dispatch,
because the program has already paid for a duplicate dispatch twice and has never paid for an idle fire.

**(c) And the sting in the tail.** Because crash, missing file and timeout all fail open, **this guard
is fail-open by construction**: any accident that stops it working produces a permanent silent green.
That is P-22's shape exactly ("a guard, a canary or a control that cannot fail is worse than none"). So
adopting it **requires a liveness check** — see condition C2 in §6. Without one, a typo in
`settings.json` disables enforcement forever and nothing in the transcript says so.

## 4. Q4 — the escape hatch, and why it cannot quietly become the default path

The candidate has three hatches: `SOFTHOUSE_SPAWN_GATE=off`, `=warn`, and
`SOFTHOUSE_SPAWN_GATE_FAIL=open`. All three drive green as designed [VERIFIED: `out/unit-drive.txt`].

**The structural finding is that a running session cannot reach them.** A session was told to
`export SOFTHOUSE_SPAWN_GATE=off` from a Bash tool call and then spawn; **the spawn was still refused**
[VERIFIED: `out/E1-escape-hatch-from-inside.report.txt`, `out/hatch.gate.jsonl`]. Each `Bash` tool call
is a fresh shell; the hook inherits the **`claude` process's** environment, not the tool shell's. So the
hatch is settable only by:

1. editing `.softhouse/bin/fire-program.sh` to export it before `claude` launches — a **tracked file**, diff visible to a reviewer;
2. editing `.claude/settings.json` or the hook script — **tracked files**, same;
3. the human's own shell or the launchd plist — outside any agent.

That is as close to un-defaultable as this program can get: **using the hatch costs a commit.** It is
not proof against a determined driver (it could commit that change, and R4 shows a model will route
around an obstacle without being asked), but it does mean the hatch cannot be taken silently from
inside the fire that wants it. I do **not** claim more than that.

## 5. Would it have got the four REAL dispatch events right?

The task named three; there are four measured, and I replayed all of them from the recorded inputs —
the reflog of `refs/remotes/origin/main` for what origin said at each spawn instant, and the dispatch
commit's own diff for which task ids the batch carried. [VERIFIED: `out/replay.txt`,
`probe/replay-real-dispatches.py`]

| event | recorded | margin | ancestry gate | **content gate** |
|---|---|---|---|---|
| E1 2026-08-22, first spawn 21:58:42 | VIOLATION | **+101 s late** | **ALLOW — WRONG** | **DENY — right** |
| E2 2026-08-28 08:00 fire batch 5, first spawn 10:44:04 | VIOLATION | **+135 s late** | DENY — *by luck* | **DENY — right** |
| E3 2026-08-28 14:00 fire batch 1, first spawn 14:06:52 | COMPLIANT | −66 s | ALLOW — right | **ALLOW — right** |
| E4 2026-08-28 16:46 wave 1a (the fire running me), first spawn 16:47:13 | COMPLIANT | −54 s | ALLOW — right | **ALLOW — right** |

**Answer to the question as asked: yes — the content gate correctly ALLOWS both compliant dispatches
and correctly REFUSES both violating ones, 4/4, on real recorded inputs.**

**And the replay killed the obvious design, which is the more valuable half.** The natural hook is
*"is local `HEAD` on `origin/main`?"*. It fails, because at both violations **the dispatch record had
not been COMMITTED yet**: `fb371fdf` was committed 22:00:18 against a 21:58:42 spawn, `59fc41b4` at
10:46:13 against a 10:44:04 spawn [VERIFIED: `git log -1 --format=%cI`]. At E1 local `main` was
`fe244198` — clean, already pushed — so an ancestry gate waves the spawn through while the record does
not exist at all. At E2 it happened to deny only because an unrelated merge `4246ce63` (committed
10:42:53) was sitting unpushed on `main`; that is luck, not a guard.

**So the gate must ask a CONTENT question of `origin/main`** — *for the task id named in this spawn's
prompt, does published `tasks.json` already carry it non-`pending` with a `branch`, and does
`origin/main` carry a `LOCK` and an in-flight `RESUME.md`?* That is what the obligation actually says,
and it is what the candidate implements. Its denial messages on the real inputs are specific:
`T264…T275 read status='pending' on origin` for E1, and for E2 `T332`/`T334` were **absent from
origin's `tasks.json` entirely**.

## 6. RECOMMENDATION — ADOPT, subject to four conditions

Not one of the four sink-questions came back badly, and it is the only mechanism the program has ever
found that fires on the spawn route. But it is worth having only with all four of these:

* **C1 — match BOTH call paths, and exempt subagents by `agent_id`.** `Agent|Task` and `Bash` whose
  command matches `worktree\s+add`; `agent_id` present ⇒ allow. Without the first, R4. Without the
  second, every worker's own sub-spawn is denied forever, and *that* is the brick the driver feared.
* **C2 — ship a LIVENESS CHECK with it, or do not ship it.** Crash, missing file and timeout all fail
  open (§3c), so a dead gate is indistinguishable from a clean fire. The check must be a positive
  assertion — feed the hook a synthetic *unpushed* payload and require a `deny` — run from
  `fire-program.sh` at fire start and/or from the bar, and it must be loud when it cannot run (P-22:
  never let "could not check" read as "checked"). **This is the condition I would not trade.**
* **C3 — fail CLOSED with the hook's own 12 s network deadline, strictly under the `settings.json`
  30 s timeout.** §3a/§3b.
* **C4 — scope the matcher to `Agent|Task|Bash`.** §2. `"*"` taxes every tool call of every worker at
  122 ms for no benefit.

**Installation is NOT this task's to do and should not be a worker's.** It writes
`.claude/settings.json`, which is harness configuration. Under CLAUDE.md's "Answering gates" it is
**ENGINEERING**, not RESERVED — it spends no money, exposes no endpoint, binds no third party — so the
driver may decide it; but file it as its own task with that grant, C1–C4 in the brief, and **a
mandatory RED drive in the live repo before any prose calls it enforcement** (P-22, and P-45's lesson
that this task family is entirely about).

**The non-hook alternative, since the task asked.** T336's `push-before-spawn-audit.py` detector plus
its FU-1 wiring is the backstop, not a substitute: it detects, cannot prevent, and is blind to
worktrees the prune sweep has already removed. Keep it. It is what covers the window in which the hook
is not yet installed, and it is the thing that would notice if the hook silently died. I did **not**
find a non-hook mechanism that prevents anything: the harness issues the `git worktree add` itself, git
hooks are suppressed on that route (T336), and the wrapper is outside the loop. If the driver rejects
C2 as too much work, then the honest answer reverts to T336's: *push-before-spawn stays a convention,
and we stop pretending otherwise.*
