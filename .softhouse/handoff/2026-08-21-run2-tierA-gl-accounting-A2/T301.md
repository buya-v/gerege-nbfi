# T301 — the wrapper edits itself while running

**Branch** `softhouse/T301-wrapper-self-modification`
**Sole-writer scope** `.softhouse/bin/fire-program.sh`, `.softhouse/capture/t301-wrapper-self-modification/`, this handoff. Nothing else touched.

---

## VERDICT

**IMPLEMENTED — but the brief's hazard did NOT reproduce against the shipped wrapper, and that has to be said first.**

The re-exec-from-snapshot fix is in. It is **not** a bug fix. Driven end to end against the real
`fire-program.sh` with the snapshot switched off, an in-place rewrite during the driver's run **did not
reach the running fire** [VERIFIED: `capture/t301-wrapper-self-modification/drive-snapshot.txt`, ARM RED,
`MARKER REACHED THE RUNNING FIRE: no (count=0)`]. The reason is measurable and has nothing to do with git:

> `lsof` on the fire while it sat in `wait` reported the offset of its own script fd as **`o0t131779`**
> against a **131,779-byte** file — it had read **100 %** of itself before blocking.
> [VERIFIED: `drive-fragility.txt`, ARM OFFSET]

zsh must parse a compound command in full before running any of it, and `fire-program.sh` invokes the driver
from inside its final `while (( CHAIN_N < CHAIN_MAX ))` loop. Reaching the multi-hour `wait` therefore forces
a read through the loop's `done`, and the ~500 bytes after `done` sit inside the ~7.6 KB read-ahead.

**So why ship the fix?** Because that immunity is **layout, not design, and one ordinary edit removes it.**
Appending 15 KB of top-level content after the chain loop — literally "add a step at the end of the fire" —
brings the hazard straight back:

| arm | shape | snapshot | marker reached the running fire? |
|---|---|---|---|
| RED | wrapper as shipped | off | **no** |
| GREEN | wrapper as shipped | on | no |
| CONTROL | sleep at top level | n/a | **YES** (proves the harness can detect a reach) |
| FRAGILE | top-level code after the chain loop | off | **YES** |
| FRAGILE-SNAP | same shape | on | **no** |

[VERIFIED: `drive-snapshot.txt` and `drive-fragility.txt`]

Today's safety rests on **three contingent facts**, none of which is tested by anything: git renames rather
than truncates; the driver call happens to be nested inside the last compound command; and the read-ahead
happens to be larger than the bytes after `done`. The snapshot replaces all three with one unconditional
fact. That is the whole argument, and it is a defence-in-depth argument, not a "there is a live bug" one.

**Honest counter, recorded because it is the strongest one against shipping:** the hazard does not reproduce
today, and the fix adds a new failure surface. That surface is bounded and was driven (three COST arms
below), and every one of its failures is visible at second zero of the log rather than silently hours in —
which is the asymmetry that decided it.

## WHAT WAS MEASURED

### 1. Which writers can reach a running shell at all
`probe-writer-inode.zsh` → `probe-writer-inode.txt`. 12 shell writers + 5 git operations, each leg asserting
the content actually changed (T309's first draft passed vacuously; this one refuses to score a NOOP).

**ISOLATED — new inode, cannot reach a running fire:**
`git merge` / `checkout -- <path>` / `pull --ff-only` (T309) · `git reset --hard` · `git stash pop` ·
`git apply` · `git checkout-index -f -a` · `git restore` · `sed -i ''` (BSD) · `mv` · `install` · `patch` ·
**Claude Code `Write` tool** (inode 15730695 → 15730699) · **Claude Code `Edit` tool** (15730698 → 15730702).

**IN PLACE — same inode, CAN reach a running fire:**
`cat > file` · `python open(path,"w")` · `>> append` · `tee file` · `dd conv=notrunc` · **`cp src dst`** · `ex -s`.

Two corrections to the comment block T309 left in the wrapper, both now fixed in it:
* it named **`sed -i ''`** as dangerous — on this host BSD sed renames and is isolated;
* it did **not** name **`cp`**, `tee`, `>>` or `ex`, and all four are in place. `cp` is the one that bites:
  "copy the fixed wrapper over the live one" is what a human types, and it is the dangerous half of cp/mv.

### 2. The two residual-exposure candidates the brief named
* **`lib-worktree-prune.zsh` (sourced) — NOT an exposure.** Edited after `source` returns and before its
  functions are called, by BOTH shapes: in-place kept `LIB: ORIGINAL`, rename kept `LIB: ORIGINAL`. A sourced
  file is consumed whole by `source`. [VERIFIED: `probe-source-and-shift.txt` PART 1]
* **A non-git in-place edit — real, and the only residual.** See the writer table. Note that agents in this
  pipeline run under instructions that PREFER `cat > file` heredocs to the (isolated) `Write` tool, so the
  dangerous writer is the one currently being encouraged.

### 3. The mechanism, sharper than the brief stated it
The brief predicted a **misparse** at a shifted byte offset. What actually happens on this zsh is a **SPLICE
at the read-buffer boundary**, and it needs no shift at all. PART 3b swapped `ORIG`→`MARK`, four characters
for four, nothing moved — and the row straddling the boundary executed as:

```
ROW 0290 ORIG
ROW 0291 ORIK      <-- three bytes from the old file, the rest from the new
ROW 0292 MARK
```

[VERIFIED: `probe-source-and-shift.txt` PART 3b, verbatim rows; copy in `ladder-boundary.out`]

Here the splice landed inside a quoted string and printed harmlessly. Inside a command name, a variable, an
`if`/`fi` or a heredoc delimiter it is a syntax error or a **different command**. Insert and delete shapes
were also driven (PARTS 2, 2b, 2c) and all executed foreign bytes cleanly on line boundaries — the
"misparse" half of the brief's premise is **not confirmed**; the "executes bytes it never started with"
half is confirmed several ways.

**Read point R = ~7.6 KB** (bracketed between 7,260 B and 8,740 B by PART 3, read off directly as row 291 of
a 26-byte ladder by PART 3b). Everything more than ~7.6 KB past the currently-executing command is exposed.

### 4. The stakes, for the record
Were the layout immunity ever lost, the exposed region of this file is not filler. `run_exit_guard`,
`reconcile_tasks_json`, `wt_prune_blindspot_check` and the prune sweep that calls **`git worktree remove`**
all live past the driver's `wait`. The failure mode is not "the fire crashes", it is "the classifier that
decides what to DELETE was rewritten under us".

### 5. The T309 identity instrument — still alive, and discriminating
`probe-identity-instrument.zsh` → `.txt`, remove-and-observe per P-95 (*"a fallback and a fail-open are
indistinguishable by reading, and they have opposite severities"* — `patterns.md:3115`):

| arm | result |
|---|---|
| green | one `wrapper identity:` line, real inode/sha/bytes |
| **red-excise** (identity block deleted, `zsh -n` still parses) | **0** `wrapper identity` lines |
| mutated (one comment byte appended) | sha moved `cf39bea9…` → `7504cd2a…`, matching the file on disk |

So the line is produced by that code and its sha tracks the bytes. Updated for T301: it now also logs
`wrapper snapshot: …` naming the **repo copy** (path, inode, sha, bytes) alongside the snapshot it is
actually running, because after the re-exec `${0:A}` names a file under `$TMPDIR` and would otherwise lose
the answer to "which commit is that".

## THE FIX, AND WHAT IT COSTS

`fire-program.sh`, immediately after arg parsing and before the log redirection: copy `$0` to
`$TMPDIR/fire-wrapper-snap.XXXXXX/fire-program.sh` and `exec` it.

* **`SCRIPT_DIR` — the cost the brief flagged, paid explicitly.** `SCRIPT_DIR="${0:A:h}"` located four
  siblings (`lib-worktree-prune.zsh`, `branch_sweep.py`, `ready-tasks.py`, `../guards/repo-state-attest.sh`)
  and running from `/tmp` would have broken all four. The original directory is pinned into
  **`FIRE_SCRIPT_DIR`** before the exec and read back as `SCRIPT_DIR="${FIRE_SCRIPT_DIR:-${0:A:h}}"`, so a
  non-snapshot run is byte-identical to pre-T301 behaviour. Driven: ARM COST-SCRIPT-DIR shows the lib
  sourced (no FATAL), `refguard|` + `sweep|` lines from `branch_sweep.py`, and `attest-preflight|` lines
  from the guard, all under a snapshot run. Those four are not exposed to the hazard anyway — sourced zsh
  and compiled python are both read whole.
* **Re-exec loop** — guarded by `FIRE_SNAPSHOT_OF`, which only the exec'd copy sees. Driven:
  `'fire start —' lines: 1`, `'RUNNING FROM A SNAPSHOT' lines: 1`.
* **Snapshot failure — FAIL-OPEN, deliberately.** `TMPDIR` made unwritable: the fire logs
  `SNAPSHOT FAILED (mktemp/cp under …) — running directly from the repo copy, which an IN-PLACE writer
  (cat >, cp, tee, >>, python open(w)) could still reach mid-fire` on stderr AND in the log, then runs
  normally (rc=0). A fire that refuses to start because `/tmp` is full would be a worse bug than the one
  being fixed. Fail-open is named in the log rather than left silent, per P-95.
* **Escape hatch** `FIRE_NO_SNAPSHOT=1` restores pre-T301 behaviour and says so in the log. It is what the
  RED arm uses.
* **Disk** — one ~130 KB dir per fire under `$TMPDIR`; the wrapper sweeps `fire-wrapper-snap.*` older than
  a day at start.

**Alternative rejected — "forbid landing bin/ changes from inside a fire".** It is both *unnecessary* (every
git write path renames; measured) and *unenforceable* (nothing calls it). It would also have blocked this
fire's own T324 and T325 wrapper landings, which were correct. Recorded rather than assumed, as the brief
asked.

## HARNESS DEFECTS FOUND IN MY OWN RIG (fixed, and the fixes are the evidence)
1. Probe B v1 inserted **comment** lines, so "already buffered" and "re-read at a shifted offset" predicted
   identical output. Kept as `probe-source-and-shift-v1-NONDISCRIMINATING.txt` with the reason.
2. PART 2b claimed to force a mid-token resume and could not: with `I > R` the resume point is still in
   original bytes. PART 2c (`I < R`) is the only configuration that can.
3. Three git legs measured vacuously (dirtied and restored inside the window). Split into `pre` + `op`.
4. `ex` leg never ran — macOS `/bin/echo` ignores `-e`.
5. `mkclone`'s `local arm="$1" c="$WORK/clone-$arm"` — zsh expands the whole line before assigning, so
   `$arm` resolved to the **caller's** `arm` under dynamic scoping. Right by accident inside a function,
   empty at top level, so two arms silently shared one clone.
6. `fire rc=$?` printed after a `grep -c` assignment reported the *grep's* exit code; the arm that PASSED
   looked like `rc=1`.
7. `grep -c 'fire start'` also matched "…before this fire started", reporting 2 re-execs where there was 1.
