### C.6 Verdict

**SECOND SOURCE OF TRUTH.** A cache can be dropped and rebuilt from the source of truth at any moment with
no change in behaviour. This one cannot: its own writer reads it back to compute the next value, two code
paths write overlapping subsets of it, its correctness depends on a mutable foreign attribute read at
recompute time and never versioned against the entries it already signed, and the flag that claims to
describe its freshness was observed `true` on rows wrong by MNT 2,000,000.00 through four recomputes and two
REST endpoints.

## The adopted-schema tension, stated

Both `CLAUDE.md` instructions meet here and I am not resolving one silently:

- *"The ledger is double-entry and append-only. **Balances are derived, never written.**"*
- *"Contract-first, schema-first, strangler … **adopt Fineract's PostgreSQL schema**."*

The measurement narrows the collision without dissolving it. **Fineract's own implementation does not treat
this column as the ledger's balance**: the GL report derives with `SUM`; the field is absent from
`/journalentries` unless explicitly requested; the JPA entity does not carry it; the list endpoint that
serves it has never run on PostgreSQL. It is a denormalised report accelerator bolted on outside the domain
model — and one this measurement showed can be, and already was, wrong.

So "adopt Fineract's schema" is about the **storage shape** the two systems share so a shadow-parity diff is
meaningful; it is not a licence to reproduce a defect. "Balances are derived, never written" is about where a
**number the business relies on** comes from. A column Fineract itself neither trusts nor derives from is a
storage-shape question, not a source-of-truth question — **provided nothing in the Go port ever reads it back.**

**What the tension still costs, named:** if the port keeps the column and writes `0` while the reference
oracle writes a computed number, a row-level table diff between the two systems differs on that column on
**every entry**, for the whole shadow-parity window. Whoever runs the parity diff must exclude those columns
explicitly, and that exclusion is itself a narrowing that has to be written down. I am not writing it down as
settled — I am naming it as the price of the recommendation below.

## Recommendation, and what it depends on

**Recommend (a) + a narrowed (b). Recommend AGAINST (c).** The driver decides; `A2-29` takes nothing.

- **(a) for BEHAVIOUR, without qualification.** The Go port derives every balance from the append-only
  entries and **never reads** `office_running_balance`, `organization_running_balance` or
  `is_running_balance_calculated` — not to serve a response, not to seed an incremental computation, not in a
  report predicate. The measurement makes this the load-bearing half: reading the column back is exactly the
  mechanism by which the oracle poisoned a freshly computed row (§C.3, entry 62). This is the
  non-negotiable and needs no gate.
- **(b), narrowed, for STORAGE: keep the columns, write the DDL default, never recompute.** Keep
  `NOT NULL DEFAULT 0.000000` / `DEFAULT false` exactly as `0001_initial_schema.xml:163-171` declares, so
  Fineract's own DDL is unchanged and a Fineract process pointed at the same database still starts. Ship no
  equivalent of `ACCOUNTING_RUNNING_BALANCE_UPDATE`. This is cheap and faithful: the columns are already
  default-populated on Fineract's own ORM path (§a), so "written by the default and nothing else" is exactly
  what Fineract does between recomputes.
  **Rejected alternative, recorded:** reproduce the recompute so the columns match byte-for-byte. That
  imports the defect, the office-vs-organisation split, and the retype hazard — to make a diff quieter.
- **(c) rejected, and not taken.** It would narrow the graded domain (hard `user` gate) and it is not needed:
  the cells are reachable only via opt-in `runningBalance=true` / `fetchRunningBalance=true` that no vector
  need ever set, and one of the two routes is HTTP 500 on the only permitted database. The right instrument
  is a **positive rule on capture**, not a negative carve-out on grading.

**What the recommendation depends on** — if any of these turns out false, revisit it:

1. That no ledger vector ever sets `runningBalance=true` or `fetchRunningBalance=true`. If DEC-2 puts one of
   those cells in the graded domain, (b)-narrowed stops working and the gate reopens.
2. That the shadow-parity plan compares **behaviour at the contract boundary**, not raw table bytes. If it
   compares tables, the exclusion list in "What the tension costs" must be written and approved first.
3. That the Go port does not adopt Fineract's `GeneralLedgerReport Table` SQL verbatim — it carries R7's
   predicate, which is inert only because the column is `NOT NULL`.

## Follow-ups

1. **FU-1 (for G-11 / DEC-2, not decided here).** A ledger parity vector must not set `runningBalance=true`
   or `fetchRunningBalance=true`; if DEC-2 needs a balance cell it must be **derived** (summed from the
   vector's own entries, or captured from a deriving surface — the report's `openingbalance` /
   `cumulative_sum` were verified exact to the minor unit, `A2-472` / `A2-473`).
   `runningBalanceComputed: true` is **not** a correctness signal.
2. **FU-2.** `GET /glaccounts?fetchRunningBalance=true` is **HTTP 500 on PostgreSQL** — `group by
   account_id desc` at `GLAccountReadPlatformServiceImpl.java:127-131`. This is a broken oracle surface
   independent of G-12; any task planning to capture the GL-account list with balances must know it cannot.
3. **FU-3.** `GLAccountsApiResourceSwagger.java:74` declares `organizationRunningBalance` a `Long` and
   `LoanProductsApiResourceSwagger.java:1002,1025,1060,1095` declares the same field an `Integer`, over a
   `numeric(19,6)` column read with `rs.getLong`. A money field truncated to major units at a documented
   boundary. Worth a line in whatever records the contract's money-typing rules.
4. **FU-4.** The `LIMIT 10000` seed hazard (above) is untestable at this corpus size. If a scale/soak
   harness ever exists, it is a cheap and high-value probe.
5. **FU-5 — oracle state changed by this task.** 2 new GL accounts (**id 33 / glCode 19929, now INCOME**
   after the probe retype; **id 34 / glCode 19930, LIABILITY**), 3 manual journal entries (ids 59–62 plus the
