T253 could not execute the BSD arm and substituted a re-enacted getopt parse. **I executed the
real program instead.** `curl` reached `raw.githubusercontent.com` from this host, so I fetched

compiled it here and drove it: **12 OK / 0 FAIL**
(`.softhouse/reviews/t254-harness-portability/evidence/bsd-mktemp-proof.sh`, both C sources
committed beside it).

1. The new positional form is **accepted by the real BSD program**, file and `-d`, with a negative
   control that still fails so every `|| return 1` arm keeps firing.
2. **The template T253 chose is byte-for-byte the one BSD mktemp builds for itself** —
   `mktemp.c:166,168` construct `"%s/%s.XXXXXXXXXX"`, ten X's, into the same `mkstemp`. That closes
   the one gap my method leaves (glibc, not Darwin libc): if ten X's failed on Darwin, `mktemp -t`
   would never have worked there either.
3. **Every `#ifdef __APPLE__` block in that file sits on the `-t`/`-p` path** (`:94-98`, `:147-155`),
   which the new form never enters. The Mac-specific code is on the path T253 *removed*.

**D2 is safe on the Mac too, driven not reasoned** (my first probe was broken — a pipe subshelled
the `source`; P-72, the probe not the code): from a main checkout **and** from an isolated worktree
the derivation returns exactly the old hardcoded value, `pinned:…`, **zero substitution lines**.
On the Mac nothing changes. Negative control (dir present, `go/bin/go` not executable) falls back
loudly and exports **no** `GOROOT`.

*Stated plainly:* `zsh` is absent here, so go-env.sh's `${(%):-%x}` arm is unexecuted. It cannot
