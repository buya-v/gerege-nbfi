## My own reproduction (implementation, version, result)

**Apparatus** [VERIFIED, this session, this worktree]:
- `/usr/bin/grep --version` → `grep (BSD grep, GNU compatible) 2.6.0-FreeBSD` — the same version
  string T108/T154/T157 reported.
- `sw_vers`: `ProductName: macOS`, `ProductVersion: 26.5.1`, `BuildVersion: 25F80`. `arch` → `arm64`.
- Locale as inherited by this shell: `LANG=C.UTF-8`, `LC_ALL` unset — the same as T157's reported
  production locale.
- A `grep` **shell function** exists in this environment (visible via `type -a grep`) that routes
  interactive `grep` calls through a wrapper; I bypassed it throughout by invoking `/usr/bin/grep` by
  full path, and separately re-ran the same battery inside `env -i LANG=C.UTF-8 /bin/bash script.sh` (a
  clean, non-interactive environment where the function cannot be inherited) to rule it out as a
  confound. Both methods gave the same results.

**What I ran**: six invalid-byte spellings (`\xe2`, `\xff`, `\x80`, `\xc0`, `\xfe`, `\x81\x82`) inserted
into a synthetic `git status --porcelain`-shaped line, across three input shapes — file argument, `<`
redirection, and anonymous pipe — plus the poison placed directly on the `?? .softhouse/LOCK`-matching
line itself (the literal shape T154 described).

**Result: this build does NOT reproduce the blindness, in any of the 18+ combinations tried.** Every
case returned the correctly filtered output (non-LOCK lines kept, poison notwithstanding) with `rc=0` —
including the file-argument and `<`-redirection cases, which are exactly the shapes T157 drove red on
its own machine. I could not make `/usr/bin/grep` on this host go silent on invalid-byte input by any
method I tried.

**This is a stated negative, not a refutation of T157's or the driver's finding.** I have no reason to
doubt either of their reproductions — both are independently documented with byte-for-byte commands and
outputs in `T157.md`, and the driver's is on a *different* implementation (ugrep 7.5.0) entirely, so the
underlying behavior (seekable-input invalid-byte abort) is real and shared across at least two grep
implementations on at least one machine each. What my result adds is a **provenance caveat**: a grep
binary reporting the identical version string (`2.6.0-FreeBSD`) behaved differently on my machine than on
T157's. I did not determine why [UNVERIFIED beyond the observation]. The plausible explanation — Apple
patches `/usr/bin/grep` across OS updates without bumping its self-reported version banner — is a
hypothesis, not something I verified by, e.g., diffing binaries across two known OS builds.

Full session transcript of the reproduction commands and their raw output is not committed anywhere
(it was run in `/tmp/t171-repro`, outside the repo, and is not part of this branch); the exact byte
values and shapes tried are recorded above and in the `nonnegotiable-guard-audit.md` appendix so they
can be re-run.

## Reachability, stated exactly

**The corrected (fail-open) direction is NOT reachable through the live code as written today**, for two
independent reasons, both already established by T157 and re-confirmed by my own pipe tests:

1. `fire-program.sh:224` feeds grep via an **anonymous pipe** (`git status --porcelain | grep -v ...`),
   never a file argument or `<` redirection — and pipe-fed `grep -v` was not observed to go blind on
   either machine tested (T157's or mine), for any of the poison placements tried.
2. **APFS refuses to create a filename containing an invalid UTF-8 byte outright (`EILSEQ`)** [claim
   carried from T157's handoff; I did not re-run this specific filesystem test myself, so I mark my
   citation of it, not the underlying fact, as resting on T157's measurement rather than my own].

So this is a **latent mischaracterization sitting in merged evidence, not a live hole.** I did not
overstate it as more urgent than that in either file I edited — both explicitly say "not reachable
through the live anonymous pipe" and "APFS refuses ... EILSEQ" in the same terms as this section.

## Follow-ups

- **For whoever next touches `fire-program.sh` (T172 this fire):** if the line at 224 is ever refactored
  from a pipe to a seekable read (e.g. capturing `git status --porcelain` to a temp file before grepping,
  or inserting a `tee`+`<` stage), the fail-open behavior described here becomes live. The existing
  hardened spelling T154 recorded (`LC_ALL=C grep -av '...'`) is still the correct fix regardless of which
  direction the unhardened version fails in, and T157 verified it byte-for-byte on the real two ordinary
  (non-poisoned) `git status` scenarios that matter for normal operation.
- **A regex-boundary bug T157 noted in passing (F-1 in its handoff) is still open and out of my scope
  too:** `^?? \.softhouse/LOCK` has no trailing boundary, so it would also match a hypothetical
  `.softhouse/LOCKUP` or `.softhouse/LOCKED_backup/` path. No such path exists in the repo today; worth a
  follow-up task only if one becomes plausible.
- **The version-string-is-not-provenance lesson (P-55, rule 4) is general**, not specific to this bug —
  any future reproduction task that cites "same grep/tool version, different machine" as sufficient
  should also record the OS build.
