# T288 — the wrapper detected the exit-protocol violation and did nothing about it

**Branch** `softhouse/t288-exit-protocol-enforcement`
**Files touched** `.softhouse/bin/fire-program.sh`, `.softhouse/bin/ready-tasks.py`, plus a
drive harness and its transcripts under `.softhouse/reviews/t288-drive/`.
**Not touched, by scope declaration** `.softhouse/conformance.sh`, `.softhouse/LOCK`,
`.softhouse/tasks.json`, `.softhouse/RESUME.md`. Every drive below runs against a scratch
repo under `/tmp`, never the live one.

---

## 1. The defect, restated from the logs

Fire `20260822-140002` ended its turn with four workers live (`T271`, `T283`, `T285`,
`T286`). They died with it. It left all four `in_progress` and did not rewrite
`RESUME.md`. The 23:00 fire was refused by the five-hour quota twenty seconds in and
never got a turn. At `23:00:32` the wrapper printed:

```
WARN: exit-protocol violation — .softhouse/RESUME.md predates this fire's start;
      the next fire may act on stale state. Review it by hand.
```

It was right, and it changed nothing. Two fires later the state still lied, and the 08:00
fire reconstructed the truth by hand from six `rescued-agent-*` branch names and two logs.

**The rule this is an instance of, quoted rather than cited (P-86 — "every prompt wrote
out the full rule text beside the id rather than the id alone. The number was decoration;
the sentence carried the instruction"):**

> **P-45** — *"a guard that only works when someone remembers to run it enforces
> nothing."* (`.softhouse/patterns.md:1472`, and restated in STEP 0 of the
> softhouse-program skill.)

A `WARN` is that failure wearing a different coat. It **is** run, every fire, and it still
enforces nothing — because its only reader is a log file, and the only thing that reads a
fire log is the next fire, which reads `RESUME.md` and `tasks.json` instead.

The two facts the fix is built on, both from the skill:

> **STEP 5.5, section "NEVER exit with live workers", item 4** — there is no STEP 5.4 in
> the skill; the incident write-up called it that — *"A task whose worker you killed is
> **not** `in_progress` — mark it
> `needs_retry` with `note: worker killed mid-flight; rescued WIP on <branch>,
> completeness unverified`. Leaving it `in_progress` tells the next fire that work is
> happening when nothing is."*

> **P-85 / STEP 0** — *"a `HEAD` that says 'closed clean, zero live workers' while five
> are running is an **active lie to the next orchestrator**"*, and the authoritative
> liveness signal is push recency, *"because push recency is derived from doing the work
> rather than maintained beside it"* — never a `heartbeat` field, because in the
> 2026-08-22 incident the holder **did** commit its lock refresh and dispatch record and
> simply never pushed them, so a heartbeat would have been in those same unpushed commits.

## 2. What was built: REPAIR, not refuse — and what was rejected

**Decision: the wrapper REPAIRS the two artefacts the next fire actually reads.**

- `tasks.json` — every task still `in_progress` at fire exit is rewritten to
  `needs_retry`, with a `note` naming the fire that killed it, the WIP that was found,
  and the words *"Completeness UNVERIFIED"*.
- `RESUME.md` — when it was not rewritten this fire, the wrapper stamps a banner at the
  **top of the file itself**, carrying the driver's outcome and the reconcile verdict.

**Rejected: refuse loudly.** Two forms were considered and both fail for the same reason
the `WARN` failed.

1. *Exit non-zero.* The wrapper's exit code is read by launchd, which does nothing with
   it. The next fire still opens a `tasks.json` claiming four workers are busy.
2. *Drop a marker file the next fire is told to read.* This needs someone to remember to
   read it **and** someone to remember to clear it — two remembered obligations, which is
   P-45's exact shape reproduced inside the fix for P-45. It is also the shape `P-89`
   names — *"THREE ARTEFACTS SHIPPED WIRED TO NOTHING IN ONE FIRE … THE FIX IS A FILED
   TASK, NOT A SENTENCE"* (`patterns.md:2904`), restated in this file's own shorthand at
   `patterns.md:3008` as *"prose does not fire on the next fire."*

Both repairs are **self-clearing by construction**, which is the property that made repair
the right call: a demoted task leaves `needs_retry` when it is retried, and the banner
disappears the moment a driver rewrites `RESUME.md` per STEP 5.5.4. **Nothing new has to
be remembered by anybody, and no field has to be refreshed.**

**The refusal path still exists, but only where a repair could be wrong** — when a live
session might own those tasks. There the wrapper says so and leaves the state exactly as
found, because demoting a live worker's task would get it dispatched twice.

### Where the liveness answer comes from, and what it is NOT

`foreign_live_session_in_repo()` in `fire-program.sh`. Three-valued and fail-closed: only
"positively established that nobody is working here" authorises the rewrite.

The design follows a measurement, not an intuition
(`.softhouse/reviews/t288-drive/out/0-live-host-measurements.txt`, taken while fire
`20260823-080004` was live with six workers dispatched):

- **There is no process per worker.** A subagent is in-process. The whole fire is one
  `claude` (pid 28980) plus a caffeinate child. Any design that looked for a process per
  task would have found nothing and demoted everything.
- So worker liveness is **session** liveness, and a session is identified by its **cwd**:
  `lsof -a -d cwd -p 28980` → `/Users/buv/gerege-nbfi` (in the repo);
  `lsof -a -d cwd -p 1207` → `/Users/buv` (an unrelated interactive `claude`, not in it).
  **A blanket "any live claude ⇒ refuse" would have gone permanently inert against pid
  1207**, which is exactly a guard that never fires. Reading the cwd tells them apart.

By the time the guard runs, the fire's own driver has been `wait`ed on or killed by
`stop_driver`, so it is gone and is skipped by the `kill -0` leg. What remains is the only
case that must be protected: somebody else working in this checkout.

`ready-tasks.py --reconcile` adds a second, independent gate of its own: it refuses unless
`.softhouse/LOCK` is absent or names a pid that is an **ancestor** of the calling process,
walked out of `/bin/ps` so it cannot be asserted by the caller. **Ancestry alone turned out
not to be enough, and that was measured rather than reasoned:** run from a worker inside a
live fire the ancestry check *passed*, because a worker is a descendant of the wrapper that
holds the lock. So it also refuses when any ancestor is a `claude` — the wrapper reaches the
script through zsh only, and anything routed through a `claude` is a driver or a worker,
i.e. code running while the fire is live. Transcript:
`out/6-REFUSED-called-from-a-live-worker.txt`.

### Composition with what `ready-tasks.py` already did

`ready-tasks.py` already flagged *"an `in_progress` task with no `branch`"* as a suspected
isolation violation. The change **composes, it does not duplicate**:

- the `IN PROGRESS -- ALREADY DISPATCHED, do not dispatch again` block is where the lie
  was published, so the withdrawal lives in the same file;
- every `in_progress` line now carries **WIP evidence** beside the claim (branch absent /
  N commits ahead of main / no branch recorded), so a dead dispatch is visible at read
  time and not only at repair time;
- the no-branch case keeps its isolation-violation wording, and the reconciler's note for
  that shape repeats it rather than replacing it.

One fail-open was fixed in passing, of the P-77 shape already fixed twice elsewhere in
this file: `t.get("branch", "NO BRANCH RECORDED …")` applies its default **only when the
key is absent**, so `"branch": null` printed the string `None` and read as a branch name.

## 3. Driven, not argued

Everything below is a full end-to-end run of the **real** `fire-program.sh` against a
scratch repo built by `.softhouse/reviews/t288-drive/build-fixture.sh`. Transcripts are in
`.softhouse/reviews/t288-drive/out/`.

The fixture plants three shapes of dead dispatch, because they must produce three
different notes, plus a control that must not be touched:

| task | shape | control? |
|------|-------|----------|
| `T900` | branch exists, worker left **uncommitted** work in a live worktree | no |
| `T901` | branch has a **real commit** ahead of main (worker committed, then died) | no |
| `T902` | `"branch": null` — the isolation-violation shape | no |
| `T903` | `pending`, never dispatched | **yes — must be untouched** |

**The wrapper is driven ORPHANED** (`( cmd & ) &`, reparented to pid 1), because in
production launchd starts it. Started from an agent's shell its ancestor chain contains a
`claude` and the reconciler correctly refuses, so a terminal-run drive could only ever
exercise the refusal path. This was discovered by driving it.

## 4. Three defects this change introduced, found by driving it and fixed

Recorded because "it worked first time" would be the suspicious claim.

1. **A raw line of `lsof` output leaked into the fire log** (`l=n/Users/buv/gerege-nbfi`).
   Cause: `local l` inside a loop body. Measured under zsh 5.9 — `local x` for an `x` that
   already exists at that scope does not re-declare it, it **prints** `x=<value>`
   (`zsh -c 'f(){ local a; for a in x y; do local a; done }; f'` emits `a=x` / `a=y`). All
   locals are now declared once.
2. **The probe's evidence string was silently corrupted by the shell** into
   `pid=28980wd=lsewhere`. Unbraced `$pid:cwd=` applies zsh's `:c` history modifier and
   `$cwd:elsewhere` applies `:e`. Every expansion in that string is now braced. This one is
   worth the ink: it corrupted the **evidence line of a fail-closed guard**, which is the
   line a human would read to decide whether to trust it.
3. **A chain-loop regression of my own making.** The chain stops when an iteration
   produces no commits. A wrapper that now commits a repair on *every* exit satisfies that
   test forever — the banner carries a timestamp, so HEAD always moves, so a driver doing
   nothing eight times would be re-invoked all eight times. The chain is now handed
   `GUARD_HEAD_BEFORE_REPAIR`, the sha from before the wrapper's own correction, so it
   judges the **driver's** progress. Visible in the GREEN transcript:
   `chain: stopping — iteration produced no commits (nothing advanced)`.

Both zsh semantics are re-derivable from
`.softhouse/reviews/t288-drive/measure-live-host.sh`, §3 of its output.

## 6. What is proven, and what is not

**Proven, by driving the real bytes:**

- the pre-fix wrapper leaves three dead dispatches `in_progress` and prints one WARN;
- the post-fix wrapper demotes all three to `needs_retry` with distinct, evidence-bearing
  notes, leaves the `pending` control alone, stamps `RESUME.md`, commits and pushes;
- with a live session in the repo it refuses and leaves state **exactly** as found;
- with liveness unestablished (no `lsof`) it refuses and says why;
- a fire that never got a turn still performs the repair;
- called from inside a live session, the reconciler refuses (rc=4);
- the turn classifier separates *"never got a turn"* from *"worked, then hit the quota"* on
  three real event streams.

**NOT proven — read this before trusting the guard further:**

- **No drive has ever exercised this against a real killed `claude` worker.** Every drive
  uses a fake driver that exits immediately, and the negative case uses a `sleep` renamed
  `claude`. What is measured from the real thing is only the two fields the probe reads
  (argv[0] basename, `lsof` cwd), taken from the live fire in §2. Whether a *dying* real
  worker can leave a `claude` process alive with a cwd in the repo for a few seconds after
  the driver exits is **untested**; if it can, the wrapper will refuse that fire — the safe
  direction, but it would make the guard inert on precisely the fires it was written for.
  **First real fire after this merges should be read for the `reconcile:` line.**
- **The probe only sees processes named `claude`.** A hand-run orchestrator driven some
  other way is invisible to it and its tasks would be demoted. The lock is what is supposed
  to prevent that, and STEP 0 says a hand-run must honour it; this does not enforce it.
- **`ready-tasks.py --reconcile` does not judge worker liveness** — it only checks lock
  ancestry. If a future caller other than `fire-program.sh` calls it, that caller inherits
  the obligation to establish liveness first. This is stated at the function.
- **The banner is prepended to `RESUME.md` by a shell script.** If a driver *edits around*
  the banner instead of rewriting the file, the file stays flagged on the next fire. That
  is a false positive in the loud direction, and deliberate.
- No money math, no vectors, no oracle interaction: this task touches none of it. The
  integer-minor-units and PostgreSQL-only rules are not engaged by any line of this diff.
