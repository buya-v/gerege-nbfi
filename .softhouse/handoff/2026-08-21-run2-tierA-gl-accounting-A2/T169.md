### The fatal rule — stated, and the reasoning recorded

The brief asked me to say whether catching `Throwable` risks swallowing something that should kill
the process. It does, so the catch is **not** blanket:

* **RECORD AND CONTINUE** — `StackOverflowError`, every `RuntimeException`, every checked
  `Exception`. By the time the catch clause runs the overflowed frames have been popped, the heap is
  untouched, and the seam is a pure function of `(MathContext, LoanRepaymentScheduleModelData)` — so
  the *next* cell is still trustworthy, and the throw is the finding.
* **RECORD AND RE-THROW** — `VirtualMachineError` other than `StackOverflowError` (chiefly
  `OutOfMemoryError`), `ThreadDeath`, `LinkageError`. After these the JVM or the classpath is no
  longer in a state in which a later cell's numbers could be believed, and a rig whose numbers
  cannot be believed must stop loudly rather than keep emitting them. `announceFatal()` prints only
  strings that already exist (the cell id, the class name), because building JSON under
  `OutOfMemoryError` allocates.

The gain on the fatal path is **not** that the run survives — it does not. It is that the run now
**names which cell killed it**. Before T169 an `Error` produced a bare JVM trace and an exit code,
and the offending input had to be guessed.

**One implementation detail that would have broken every future run.** `t instanceof ThreadDeath`
compiles, but `ThreadDeath` is terminally deprecated on the image's Java 21 and javac writes a
removal note **to stderr** — and every runner refuses on non-empty stderr. My first `Post` run
emitted exactly that, 145 bytes, from that one line
[VERIFIED: `out/console-Post.txt` predecessor run, superseded; the current `out/stderr-Post.txt`
reads `stderr bytes on the POST run: 0`]. `isFatal()` now matches `ThreadDeath` **by name**. A fix
that makes every capture refuse itself is not a fix.
