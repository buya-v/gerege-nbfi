1. **New `GIT_PUSH_TIMEOUT_SECS` (default 10) and `git_push_bounded()`**, inserted between

   `rm -f "$LOCK"` is still the first statement.
3. **`DRIVER_STOP_GRACE_SECS` default changed from 3 to 5**, with a new comment block explaining
   the calibration (below) and its limits.
4. Two comments updated to stop saying "3s by default" (the `on_signal` block comment, and the
   `DRIVER_STOP_GRACE_SECS` declaration's own comment, rewritten).

## Follow-up 1 — what hangs, what I bounded, what I accepted

**What actually happens today, established by reading the code before changing it.** In
`release_lock()`, `rm -f "$LOCK"` is the *first* statement — the local lock file, the one STEP 0's
preflight (`[[ -f "$LOCK" ]]`) reads, is gone before any git call runs. So an unbounded `git push`
at the end of `release_lock` was **never a lock-safety hazard**: the next fire on this host is not
blocked either way, matching the task's framing exactly.

What it *does* threaten is the exit path. `release_lock` is reached two ways: the `trap
release_lock EXIT` at the tail of a normal run, or `on_signal`, which calls `exit $rc` only
**after** `release_lock` returns [VERIFIED: `on_signal`'s body, `stop_driver; release_lock; exit
$rc`, three statements in that order]. A push that never returns means `release_lock` never
returns, so `on_signal` never reaches its `exit` — the handler hangs forever, launchd's
SIGTERM→SIGKILL grace elapses, and the fire is SIGKILLed anyway. That is precisely the outcome
T211 built `stop_driver`/`wait`-in-background to avoid, reintroduced one call later. Since it's
the wrapper itself that gets SIGKILLed at that point (not merely the driver tree), a still-hanging
`git push` child dies with it — it doesn't survive as an orphan the way the pre-T211 driver child
did, but the handler itself never completing is a regression on its own: T211's whole point was a
handler that finishes inside the grace window and lets the fire log that it stopped cleanly.

**FAILURE MODE ACCEPTED:** the remote may not see the lock release promptly, or at all if the push
was always going to fail. The cloud fire's view can lag by up to `GIT_PUSH_TIMEOUT_SECS` (10s
default). This is strictly better than the prior unbounded hang and never re-strands the local
lock.

**FAILURE MODE PROTECTED AGAINST:** a hung push keeping a signal handler (or the EXIT trap) alive
past launchd's grace, turning a clean T211 stop back into a SIGKILL.

**Bound chosen:** `git_push_bounded` backgrounds the push, polls `kill -0` once a second up to
`GIT_PUSH_TIMEOUT_SECS`, and on timeout TERMs then KILLs the tree via `driver_tree` (a push spawns
`git-remote-https`/ssh children; killing only the top pid can leave those running). `wait "$job"`
always runs so the backgrounded job is reaped either way. I did not have a `timeout`/`gtimeout`
binary available to reach for [VERIFIED: `command -v timeout` and `command -v gtimeout` both
empty on this host] — this is a hand-rolled poll loop, not a wrapper around one.

## Follow-up 2 — what I actually measured, and against what

**I DID run a real `claude`, not only a stand-in.** Binary: `/Users/buv/.local/bin/claude` →
`/Users/buv/.local/share/claude/versions/2.1.233` [VERIFIED: `claude --version` → `2.1.233 (Claude
Code)`], the same binary `CLAUDE_BIN` defaults to in `fire-program.sh`.

**Method:** `.softhouse/reviews/t217-probe/calibrate-grace.py` spawns `claude -p <prompt> --model
haiku --output-format text` in a scratch cwd (`/tmp/t217-scratch/claude-cwd`, never the live
repo), own session, default dispositions (the same P-55 shape), sends **real** `SIGTERM` at a
chosen delay, and measures signal-to-exit latency, killing the session if it hangs past a 30s
ceiling. Full commands and raw output: `.softhouse/reviews/t217-probe/calibrate-grace-out.txt`.

**9 trials, 2 clusters:**
- **Cluster A — SIGTERM at 0.2–0.5s (still in startup, before the model call returns anything),**
  trivial prompt: **0.162s, 0.202s, 0.208s** (n=3). `rc=-15` — died directly by the raw signal, no
  handler yet.
- **Cluster B — SIGTERM at 3–8s into a ~9–10s call, while it is actively generating,** longer
  prompt: **0.826s, 1.055s, 1.141s, 1.156s, 1.194s, 2.591s** (n=6, mean ≈1.16s, max 2.591s).
  `rc=143` on every trial in this cluster — `claude` appears to install its own SIGTERM handling
  once its main loop is up and self-translates to `exit(143)`, unlike cluster A's raw kill; that
  is consistent with the higher, more variable latency here.
- **No trial hung** (`hung_past_30s=False` on all 9).

**Which cluster is the relevant one:** a real fire's `claude` spends essentially its whole
lifetime "mid-task" — a fire runs for hours of agentic work — so a stop signal overwhelmingly
lands in cluster B's regime, not cluster A's brief startup window. Max observed there is
**2.591s**.

**What I set and why:** `DRIVER_STOP_GRACE_SECS` default changed from 3 (T211's fake-child guess)
to **5** — roughly 2× the observed cluster-B max, not merely clearing it. The margin over "just
clear the measured max" is deliberate, not decorative: my calibration is a **single-turn,
tool-free `-p` text call**, and a real fire's `claude` runs `/softhouse-program` with Bash/Edit
tool calls and possibly MCP connections — none of which this calibration exercised, and any of
which could plausibly add shutdown latency (extra child processes, open sockets, in-flight tool
subprocesses) beyond what a bare text completion shows. **[UNVERIFIED for that heavier shape]** —
recorded honestly below rather than papered over. 5s still sits comfortably under launchd's ~20s
SIGTERM→SIGKILL grace even stacked with `GIT_PUSH_TIMEOUT_SECS`'s worst case (`stop_driver`'s ≤5s
+ up to ~2s of TERM/KILL overhead for the driver tree, well before `git_push_bounded` even starts
inside `release_lock`, which then adds ≤10s + ≤2s more) — and per follow-up 1, even the rare case
of exceeding the full grace at this late stage is benign: the driver tree is already dead and the
local lock is already gone by the time `git_push_bounded` runs, so a SIGKILL there loses only
logging, not safety.

I did **not** invent a number and did not merely validate 3s against a fake child — 5s is read
directly off the cluster-B trials with an explicit safety factor for the untested heavier-usage
gap, and the reasoning for the factor is written down rather than asserted.

## Unverified

- **`DRIVER_STOP_GRACE_SECS=5` against a real `claude` running WITH tool use / MCP connections /
  child processes**, as opposed to the single-turn, tool-free `-p` text call this calibration
  used. [UNVERIFIED] I judged this the honest limit of what I could measure without either
  running a full agentic session (expensive and itself hard to time precisely — "still working"
  vs "idle waiting on nothing" is fuzzy for a multi-tool session) or fabricating a number. The 2×
  safety margin over the observed max is my mitigation, recorded as a judgement call, not
  presented as itself measured.
- **`GIT_PUSH_TIMEOUT_SECS=10`'s adequacy for a real, slow-but-eventually-successful push** (e.g.
  a large lock-file diff over a congested link) vs a push that was always going to hang. [UNVERIFIED]
  I tested the pure-hang case (fake `git` that never returns) and the pure-fast-failure case (real

  real network fixture I don't have in this worktree. 10s is a judgement call, not a measured

- **Whether launchd's own `AbandonProcessGroup` default cleans up a KILL-stranded lock's driver.**

## Follow-ups

1. **`GIT_PUSH_TIMEOUT_SECS`'s value (10s) and `DRIVER_STOP_GRACE_SECS`'s value (5s) are both
   still on ONE machine, ONE day.** Neither is wrong on the evidence I have, but both would
   benefit from a second calibration pass after a few weeks of real fires, especially once a fire
   exercises heavier tool use before a stop lands mid-task.
2. **The lock-acquisition push at the top of the file** (`git push -q origin main 2>/dev/null ||
   log "WARN: could not push lock …"`, a few lines above `LOCK_RELEASED=0`) has the **same**
   unbounded-push shape `release_lock`'s did, and is not inside a signal handler's critical path
   so it's lower stakes, but it can still delay STEP 0 finishing (and therefore the driver
   starting) if a push there hangs. Out of scope for T217 — the task named `release_lock`'s push
   specifically — but worth a follow-up task naming it explicitly rather than leaving it as an
   unlabelled asymmetry between the two pushes in the same file. `git_push_bounded` is already
   general enough to reuse there directly.
3. **Cluster A vs cluster B's `rc=-15` vs `rc=143` split** in the calibration data (claude appears
   to only install SIGTERM handling once its main loop is up) is a real, reproducible-looking
   signal about claude's own startup sequence, observed as a side effect of this calibration and
   not investigated further — noted in case it's useful to a future task working on process
   lifecycle inside claude itself.
