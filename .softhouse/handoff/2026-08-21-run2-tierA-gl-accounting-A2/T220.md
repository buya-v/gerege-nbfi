### Route 2 — re-derived from the pinned Fineract SOURCE, and this explains family B

T116 wrote *"It does not explain family B. The cause remains `[UNVERIFIED]` by every task in this
program … I did not look for the cause either."* **I looked, and the cause is derivable.**

Replaying the pinned source's operation order in exact decimal at `(19, HALF_UP)`
(`/tmp/t220probe/derive_emi.py`):

- `rateFactorByRepaymentPeriod` ends in `.setScale(mc.getPrecision(), mc.getRoundingMode())` — that
  is **setScale(19), 19 DECIMAL PLACES, not 19 significant digits**
  [VERIFIED: `ProgressiveEMICalculator.java:1950-1963`]. At 600 % / 30 / 360 the rate factor is
  therefore `0.5000000000000000000`.
- `RepaymentPeriod.calculateRateFactorPlus1` adds with **no MathContext**
  [VERIFIED: `RepaymentPeriod.java:216-218`], so `rateFactorPlus1 = 1.5000000000000000000` — a
  BigDecimal of **precision 20**, one digit wider than the MathContext that will consume it.
- `calculateRateFactorPlus1NForEmi` accumulates `acc.multiply(rfp1, mc)` n times and
  `calculateFnResultForEmi` accumulates `1 + fn*rfp1` at mc, both at precision 19
  [VERIFIED: `ProgressiveEMICalculator.java:1816-1828`, `:1991-1993`].
- `calculateEMIValue` = `rateFactorPlus1N.multiply(balance, mc).divide(fnResult, mc)`
  [VERIFIED: `:1838-1841`], then `Money(...)` does
  `amountScaled.setScale(currency.getDecimalPlaces(), mc.getRoundingMode())`
  [VERIFIED: `Money.java:40-53`].

Result:

```
 n     EMI_raw at (19, HALF_UP)        Money.of -> scale 2 HALF_UP
102    0.005000000000000000002         0.01
103    0.005                           0.01
104    0.004999999999999999999         0.00   <-- EMI ROUNDS TO ZERO
105    0.004999999999999999998         0.00
108    0.004999999999999999998         0.00
```

**Family B is an EMI that rounds to zero at the currency scale.** With `emi = 0` every row has
`dueInterest = min(calculated, emi) = 0` and `duePrincipal = negativeToZero(emi - dueInterest) = 0`
[VERIFIED: `RepaymentPeriod.java:272-280, 345-350`], so nothing is repaid and the balance never
moves. `calculateLastUnpaidRepaymentPeriodEMI`'s **fallback** branch then fires — every period is
`isFullyPaid` when `emi == 0`, so the primary filter is empty and `totalPaidPrincipal` is zero, which
selects the last period with a positive balance [VERIFIED: `ProgressiveEMICalculator.java:1176-1181`]
— and sets `adjustedEmi = 0 + (totalDisbursed + totalDueInterest − totalEMI) = 0.01 + 0 − 0 = 0.01`
[VERIFIED: `:1200-1206`]. That last row then shows `interest 0.01, principal 0.00, balance 0.01`.

**That is the observed N104/N108 schedule, exactly**: 103 (resp. 107) rows of zeros, one final row
carrying MNT 0.01 of interest, principal column all zero, `totalPrincipalAmount 0.00`, balance 0.01
on every row. The derivation predicts the boundary at **n = 104**, and my own oracle probe measured
n = 102 and 103 clean, n = 104, 105 and 108 family B. Prediction and observation agree.

**Consequence worth carrying to G-8** (follow-up 3): the family-B condition is **not** "600 % p.a."
and **not** "n ≥ 104". It is `EMI_raw < half a minor unit`, i.e. the ratio
`rateFactorPlus1N / fnResult` dipping below `1/(1+i) · (1+i) = i/(1−(1+i)^−n)`'s exact value under
precision-19 accumulation of a precision-20 `rateFactorPlus1`. The boundary therefore moves with
principal, rate and term — which is exactly what T117's 14 principals / band structure and T159's
MNT 10.01-at-n-3000 were empirically mapping.

## Follow-ups

1. **PIN THE EXEMPTION COUNT.** The committed store's kill counts (113 / 106 / 7) and refused count
   (62) are pinned corpus-wide tripwires in `coverage_refusal_test.go`; **the exemption count is
   not** [VERIFIED: no test in `conformance/*_test.go` asserts an exemption total]. So a later task
   can add a fifth, sixth or twentieth exemption and no test moves — the only trace is a line in a
   report. A pinned `4` would make every future exemption an explicit, reviewed decision, exactly as
   the kill counts already do. **This is the single change that would most reduce the spread risk the
   brief was worried about**, and it costs one assertion.
2. **`admitVector` accepts an exemption on a vector that also withdrew the cell.** The only checks
   today are "names a known invariant" and "reason is non-empty"
   [VERIFIED: `conformance/admit.go:262-268`]. Two admissible-but-wrong shapes follow: (a) a
   **decoration** — exempting an invariant that would have held anyway, which T116 avoided *by hand*
   when it dropped `balance_roll_forward`; (b) a **double blindfold** — an exemption combined with
   `unrecorded_fields` withdrawing the same cells, which would silence the invariant *and* the cell
   comparison together. Candidate rule: refuse an exemption whose invariant HOLDS on the
   implementation's returned schedule (kills (a) mechanically), and refuse an exemption on an
   invariant whose input cells are withdrawn by that same vector (kills (b)).
3. **G-8's write-up says family B is unexplained. It no longer is.** The mechanism is above and is
   re-derivable from source in ~40 lines of exact decimal: `EMI_raw < half a minor unit ⇒ EMI rounds
   to 0.00 ⇒ nothing is ever repaid ⇒ the final-period fallback puts the whole residual into the last
   row as interest`. The material correction for the gate reader is that **family B is not a property
