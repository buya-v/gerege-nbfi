**What it proves — five things a porter cannot get from the DB dump:**

1. **The write field name and the read field name differ for every single slot.**
   `fundSourceAccountId` → `fundSourceAccount`, `interestOnLoanAccountId` →
   `interestOnLoanAccount`, `writeOffAccountId` → `writeOffAccount`, and so on for all
   nine. A port that reuses one name set on both sides breaks the contract.
2. **The read carries `{id, name, glCode}` and NOTHING ELSE — no `type`, no `usage`, no
   `disabled`, no `manualEntriesAllowed`.** The consumer of the product read cannot tell
   an INCOME account from an ASSET one without a second call to `/glaccounts/{id}`.
3. **An unmapped optional slot is ABSENT from the object, not present as `null`.**
   `goodwillCreditAccount` and `chargeOffExpenseAccount` simply do not appear. The
   collection-valued mapping fields behave the opposite way: they are present with the
   value `null`.
4. **Comparing `A2-211` (nine mapped) with `A2-212` (product 22, ten mapped) shows the
   object is sparse and slot-keyed, not a fixed record** — 22 has the extra
   `goodwillCreditAccount: {id:14, glCode:"50200"}` key and nothing else differs
   structurally.
5. `A2-213` (`GET /loanproducts/28`, HTTP 200) shows the **accrual shape**:
   `accountingRule: {"id":3,"code":"accountingRuleType.accrual.periodic"}` plus the three
   receivable keys `receivableInterestAccount`, `receivableFeeAccount`,
   `receivablePenaltyAccount` — thirteen keys in one object.

### The payment-channel override, at the boundary

`out/A2-212-read-product22-channel-override` (HTTP 200, sha256 `b2c0…71ce`) returns:

```json

  {"paymentType": {"id": 1, "name": "Money Transfer"},
```

The override is a **list of `{paymentType, fundSourceAccount}` pairs**, and the *default*

both as rows of the same table discriminated by a nullable `payment_type` column; the
contract splits them into two differently-shaped places. That is a real porting hazard and
it is only visible from this read.
