## What a corroboration MEANS here, argued from the registry

### The two claims have different truth-conditions. That much favours the revert.

A counterfactual is a claim about DISCRIMINATION whose antecedent is grading:
"grading this vector separates the oracle from this named wrong implementation by
margin *m*." `CounterfactualCoverage` says so in its own words — a refused vector
"separated no implementation from any other, so it kills nothing"
[VERIFIED: `capability.go:269-277`]. Refuse the vector and the antecedent is
false; the claim is unrealised, and crediting it is unsound.

A corroboration is **not** that shape. `Corroboration` is defined as "one claim
that a named cross-check source independently attests some of this vector's
columns" [VERIFIED: `vector.go:290-291`], and `CorroboratedBy` as "SECOND,
independent records of the same oracle output that this vector's values were
cross-checked against — and, per record, exactly which columns the cross-check
covered" [VERIFIED: `vector.go:274-277`]. Its truth-condition is entirely about
the RECORD: does a named second source print these columns for this row kind, and
did they agree with what this vector transcribed. It is validated offline at
ADMISSION, against the source's declared column list, touching neither the
implementation nor the seam [VERIFIED: `admit.go:480-529`,
`structural.go:138-170`].

And none of the five refusal reasons impugns that record. `RefusalFor` returns
`SEAM_BLIND`, `UNGRADED_CAPABILITY`, `UNKNOWN_CAPABILITY`, `UNKNOWN_SEAM` or
`UNGRADED_REQUEST` [VERIFIED: `capability.go:331-341` and the constants above it];
every one says *this harness will not compare this vector to an implementation*.
None says *this vector's transcribed values are doubtful*.

**So A2-22's sentence "a refused vector's cross-check claim is equally uncashed"
is doing more work than the definitions license.** A vector that graded nothing
kills nothing — literally true. A vector that graded nothing was still
cross-checked — also literally true. On truth-conditions alone, the revert wins.

### But the count is not a truth-value. It is a line in a RUN report, and the report has a consistent polarity rule.

`CorroborationsClaimed` is consumed in exactly one place: the printed line at
`report.go:192`. It feeds no fatal reason, no `UncoveredGradedCapabilities`, and
no exit code [VERIFIED: exhaustive grep — the identifier appears only at
`grade.go:157,458` and `report.go:193`; contrast `CounterfactualCoverage`, which
reaches `FatalReasons` at `grade.go:463-472` and thus the exit code]. So the
question is not "is the claim true" but "which population makes that PRINTED
SENTENCE least misleading."

The harness already answers questions of that form, and it answers them by
**polarity**, not by which struct the datum lives in:

- **Hazard disclosures take the widest population.** `RateFactorsRecorded` and
  `OverScaledCells` are accumulated in `gradeVector` **before any early return**,
  under the comment "Recorded-but-never-graded quantities, counted before
  anything else can return … a disclosure nobody counts is a disclosure nobody
  reads" [VERIFIED: `grade.go:504-513`; the refusal return is later, at
  `grade.go:549`]. A REFUSED vector therefore still contributes its rate factors
  and its over-scaled cells to the run totals. Same for `LoadErrors`,
  `InvariantAssertionsNotRun`, and `Refused`/`Inadmissible` themselves.
- **Support counts take the narrowest population.** `GradedCells`,
  `CounterfactualsNamed`, `MoneyKills`, `StructuralKills`, `ParityPass`.

The rule is conservative in one direction: never under-report a risk, never
over-report support. `ExitCode`'s own tiebreak states the same instinct — "the
louder of the two should win" [VERIFIED: `grade.go:183-185`].

A corroboration is unambiguously a **support** number. It exists to make the
corpus look better attested; it cannot make it look worse. It therefore belongs
on the narrow side of that rule, and it belongs there **independently of what
happens to kills**. That is the semantic argument the brief asked for, and it is
not the symmetry argument.

### The clinching case is the degenerate store the un-narrowed rule mis-describes.

Take a store in which every vector is refused — one blinded seam is enough.
Under the un-narrowed rule the report prints, in the same run:

```
cells compared: 0
corroboration claims made by ... vectors: 48
```

That is precisely the failure mode the section exists to prevent. Its own header
says the point is "so that a partial match is never read as a whole-row match"
[VERIFIED: `report.go:190-192`], and the T17-F2 finding it implements is stated
as "a partial cross-check reported as a match is how a corpus acquires confidence
nobody measured" [VERIFIED: `vector.go:281-286`]. A cross-check of columns that
were never compared to anything is the limiting case of confidence nobody
measured. Under the narrowed rule that store prints `0`, beside `a further 48 are
carried by REFUSED vectors and counted nowhere` — which is the true sentence.

### What the narrowing costs, stated honestly

It costs the "how well cross-checked is the STORE" reading, which is a legitimate
question and is now only answerable by ADDING the two printed numbers. I weighed
that and it does not overturn the result, for two reasons: the addend is printed
unconditionally, zero or not (P-35, `report.go:110-115`), so nothing is hidden;
and the store-quality question is a question about the corpus, which the store's
own README and the census answer, not a question about a run's verdict.

**Direction-of-error check.** `CorroborationsClaimed_narrow ≤
CorroborationsClaimed_wide` for every possible store, with equality exactly when
`Refused == 0`. There is no store on which the narrowing makes a run look better
supported than it is. The revert has no such guarantee.

## The divergent store I constructed, and what each version reported

**Construction** (P-36-safe: nothing was executed from the repo root, no
promote/rewriter script was touched, and no `/tmp` copy of anything script-like
was run). The probe is a **sibling `_test.go` file in
`nexus/internal/apps/loanschedule/conformance/`** — T161's shape, adopted by T180
— so it compiles in the package under test and resolves the same roots the real
run does. Source archived verbatim at
`A2-24-evidence/corroboration-population-probe_test.go.txt`.

It does three things:

1. `copyStore(t, storeRoot(t))` → a `t.TempDir()` copy. **The pristine store is
   never opened for writing.**
2. Injects one admissible corroboration
   (`embeddable-readme-ci-stdout` / `REPAYMENT` / `["principal","interest"]`) into
   `provenance.corroborated_by` of **every** vector in the copy, via a
   `json.Decoder` with `UseNumber()` so no money or rate literal ever passes
   through a float.
3. Blinds `monthend.reanchor` on `path_a_embeddable` in the copied
   `capabilities.json` — A2-22's own one-word perturbation — which refuses 14
   vectors.

**Why a store change was unavoidable:** the committed store carries **zero**
`corroborated_by` entries — `grep -rn corroborated_by .softhouse/vectors` hits
only `README.md:494` and `:724` [VERIFIED]. With no corroboration anywhere, both
rules read 0 for any refusal pattern. The divergence needs corroborations AND
refusals in one store, and neither exists today.

**Fixture bite, asserted before any conclusion (P-35 / P-64):** the probe
`t.Fatal`s if it injects 0 corroborations, if the perturbation refuses 0 vectors,
or if the injection makes anything INADMISSIBLE. It reported
`vectors=48 injected_corroborations=48 refused=14 inadmissible=0` — so the arm
demonstrably RAN and measured a non-empty population.

**Measured, same store, one line of `grade.go` apart:**

| | `CorroborationsClaimed` | `RefusedCorroborationsClaimed` | printed line |
|---|---|---|---|
| **ARM A — narrowed (HEAD, `ee2c532`)** | **34** | 14 | `corroboration claims made by GRADED vectors: 34 (a further 14 are carried by REFUSED vectors and counted nowhere)` |
| **ARM B — un-narrowed (A2-22's revert)** | **48** | 14 | `corroboration claims made by GRADED vectors: 48 (a further 14 are carried by REFUSED vectors and counted nowhere)` |

Both arms: `refused=14`, `counterfactuals named=48`, `refusedNamed=62`,
`unbacked=[monthend.reanchor]` — identical, confirming only the corroboration
population moved. 34 + 14 = 48 = the injected total, so ARM A's two numbers
partition the corpus and ARM B's overlap it.

**ARM B's transcript also shows why A2-22 called it a TWO-line revert, and it is
the stronger half of my case.** In ARM B the printed sentence is FALSE on both
clauses: 48 claims were not "made by GRADED vectors" (only 34 were), and the 14
are not "counted nowhere" (they are inside the 48). A revert that changes only
`grade.go` ships a report line that lies; the second line is
`report.go:192-193`, which must go back to "made by admissible vectors: %d (of
which %d are carried by REFUSED vectors)". **That the revert cannot be done
without also weakening a report sentence is itself evidence about which
population the sentence wants.**

ARM B was produced by adding exactly one line inside the `case OutcomeRefused:`
block at `grade.go:446` and rebuilding; the line was removed with
`git checkout --` immediately after, and the tree is proven clean below.
