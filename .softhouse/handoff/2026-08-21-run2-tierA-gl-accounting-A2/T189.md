## Verdict — what the discriminator actually is

**The discriminator is WHICH PROGRAM THE TOKEN `grep` NAMES.** Not the byte class, not the locale,
not the OS build, not seekable-vs-pipe on its own.

On this host `grep` resolves to a **shell function** (`/Users/buv/.claude/shell-snapshots/snapshot-zsh-1787317182354-elwb1c.sh`)
that re-execs the `claude` binary as **`ugrep 7.5.0`** with **`-I` hard-coded** — ugrep's
*ignore-binary-files* flag, which **skips the whole file and exits 1**. `/usr/bin/grep` is BSD grep
2.6.0-FreeBSD and never does this. [VERIFIED: `type -a grep`; `declare -f grep` shows
`exec -a ugrep "$_cc_bin" -G --ignore-files --hidden -I --exclude-dir=… "$@"`;
`exec -a ugrep "$CLAUDE_CODE_EXECPATH" --version` → `ugrep 7.5.0 aarch64-apple-macosx`.]

**All four prior attempts measured correctly. Two measured one program, two measured the other, and
the record compared them as four measurements of the same thing.**

- **T157's reproduction is real** — its own committed transcript shows bare `grep`, i.e. the wrapper,
  i.e. ugrep. Its *Apparatus* paragraph, two sections earlier, names `/usr/bin/grep`. Nobody
  cross-checked the two. Measurement correct, **attribution wrong**.
- **The "independent reproduction on ugrep 7.5.0" was the SAME program.** It is not a second
  implementation. **The two positives are one program measured twice.**
- **T171's negative is real**, and so is the driver's — both called `/usr/bin/grep` by absolute path.
- **T154's "fail-closed" was never measured at all** — reasoned by analogy. It is not resurrected.

**"Two positives vs two negatives" was a miscount of programs, not a disagreement about behaviour.**
The driver's own caveat — *"the binary actually invoked may differ between measurements"* — was
exactly right and is the answer.

**Neither "fail-open" nor "fail-closed" is a property of this line.** Both were attempts to give one
direction to a behaviour with **three** outcomes that depends on an axis none of the four
measurements pinned.

It reproduced **accidentally, in vivo**, mid-task: `grep -c "^IMPL=" matrix-out.txt` → nothing, rc=1,
while `/usr/bin/grep -c` on the same file → `124`, rc=0. The output file contained the poison bytes
echoed back, so `-I` classified it binary and skipped it whole.

## Is `fire-program.sh:224` safe today?

**YES — but the reason recorded in the register is the wrong one, and one genuinely live fail-open in
the same line has been missed by everyone.**

Live line, extracted (P-46):
```
DIRTY=$(git status --porcelain | LC_ALL=C grep -av '^?? \.softhouse/LOCK$' || true)
```

Safe for four independent reasons, strongest first:

1. **`-a` is present.** 27/27 correct under **both** implementations, every shape, every byte class
   **including NUL** (A1 and A4). **This is the load-bearing defence.** T157's edit was correct; only
   its stated rationale was wrong (P-11 — right fix, wrong reason, for the second time on this line).
2. **The real fire never runs ugrep** — verified four ways (provenance table above).
3. **The input is ASCII by construction** — three independent barriers (reachability table above).
4. **The pattern is anchored at column 0** against a fixed ASCII literal the script itself creates.

**It is NOT safe "because it is a pipe."** That reachability argument — which T157 stated and T171
inherited — is **refuted**: NUL defeats a pipe under **both** implementations (A2 pipe → third mode;
A3 pipe → zero bytes, exit 1).

### The one genuinely LIVE fail-open here has nothing to do with bytes

`DIRTY=$(git status --porcelain | … || true)` — **if `git status` fails, `DIRTY` is empty and the
guard silently concludes the tree is clean and skips the rescue.** Measured: outside a repo,
`git status --porcelain` → **rc=128**, `DIRTY=[]`. The script runs `set -uo pipefail` **without
`-e`** [VERIFIED: `fire-program.sh:17`], and the trailing `|| true` discards the status regardless, so
**nothing observes it**. This is the exact failure direction the whole dispute was about, arriving
through a door nobody was watching — and unlike the byte scenarios it needs no exotic filesystem, just
one bad `cwd`, a `.git` lock contention, or an interrupted index.

**Recommendation: the line is safe enough to leave running this fire. Harden it next fire.**
