## D-1 re-derivation (my own reading, not T183's)

**T183 is right about the defect, and its argument for the fix is right too — but its
description of the asymmetry is imprecise, and getting it precise makes the case stronger.**

What I read in the merged file, line by line:

1. `ConstResolver.__init__` harvests names from `ast.Assign` nodes only. A **parameter** is
   not an `Assign`, so it enters neither `consts` nor `partial`.
2. `probe()` therefore returns, for `ast.Name('path')`, nothing but the unparsed text `path`.
3. `scope_of("path")` matches no `TARGET_RX` and no `SCRATCH_RX` → **`UNKNOWN`**.
4. `main()`'s `--enforce` block selects `s["scope"] == TRUSTED and s["verdict"] == UNGUARDED`.
   `UNKNOWN` is not `TRUSTED`. **`--enforce` returns 0.**

So the fail-open is structural, not incidental: it is the exact composition of (1) and (4).

**The asymmetry, checked with my own eyes.** `indirectly_guarded_funcs(tree, parents)` walks
every `ast.Call` in the file, matches it to a local function by bare name, and propagates
what the CALL SITES prove (`enclosing_try_finally(n, parents) is not None`) INTO that
function's body. That is a callee-looks-up-its-callers walk, and the classifier already
performs it — **for guards**. The parameter step is the same walk over the same call sites,
asking what the callers PASSED instead of whether the callers were guarded.

**Correction to T183:** T183 calls the two steps "mirror-image", one FORWARD and one
BACKWARD. They are not mirror images — they are the **same direction** (gather this
function's call sites; propagate into its body) applied to **two different facts**. That
makes the case for the fix *stronger*, not weaker: this is not a new analysis being
introduced, it is one existing analysis being asked a second question. I would not have
applied a patch that needed a new capability to justify itself.

**Reproduced, not inferred.** Pre-T187 bytes of `edit18/20/21` at `16d5252`, copied into
scratch and only parsed [VERIFIED: PROBE A]:

```
BASE --enforce exit = 0   <-- the FAIL-OPEN
  edit18.py:17  io.open(mode='w')   target: path
  edit20.py:21  io.open(mode='w')   target: path
  edit21.py:17  io.open(mode='w')   target: path      (all three UNKNOWN)
T196 --enforce exit = 1
  edit18.py:17  tags=PORT,RIG,ADR
  edit20.py:21  tags=ADR
  edit21.py:17  tags=PORT,RIG,ADR
```

One detail T183 states loosely and I checked: `edit18.py` calls `patch("docs/adr/DEC-1-….md", …)`
with a **string literal**, not a module constant [VERIFIED: source at `16d5252`, `:21`, `:42`].
So the defect is not "module constants are too shallow" — it is the **parameter boundary
itself**. Even a literal handed straight to the helper was invisible.

### What I changed about T183's patch before applying it, and why

**(a) Scope. T183's block is keyed by BARE PARAMETER NAME and feeds the flat `self.partial`.**
That leaks a parameter's binding onto every same-named variable in the file. **Measured, on
real repo files:** it tags the vector-store write at `T64-promote-vectors.py:401` **`CAPTURE`**
— off the argument of an entirely unrelated `def sha256(path)` twelve functions away. The real
target there is `os.path.join(VECTORS, FILENAMES[cid])` = `.softhouse/vectors/loanschedule`,
which is **`STORE`**. Right scope, **wrong reason**, on four files.
[VERIFIED: PROBE H, `BASE -> T183` shows `tags=['CAPTURE']`; `T183 -> T196` shows the four
moving `['CAPTURE'] -> ['STORE']`]

**(b) A NEW FAIL-OPEN inside T183's patch, which I consider the material finding of this
task.** The patch merges the actual arguments of **every** call site into one probe text, and
`scope_of` tests `SCRATCH_RX` **before** any target tag. So a helper called once with
`/tmp/…` and once with the ratified DEC-1 scores **SCRATCH → SANDBOX**, and the site vanishes
from *both* finding lists — it is not even in the UNKNOWN list the baseline put it in. **One
harmless call site launders a gate bypass.** [VERIFIED: PROBE B, fixture
`red_union_scratch_mask.py.txt`]

```
BASE --enforce exit = 0    (UNKNOWN — printed, not excused)
T183 --enforce exit = 0    <-- SCRATCH/SANDBOX: silently excused
T196 --enforce exit = 1
```

T196 applies **worst-case-wins per call site**: if any single call site resolves `TRUSTED` on
its own, only the `TRUSTED` call sites describe the parameter. That mirrors the tool's own
`VERDICT_ORDER` worst-first roll-up and `indirectly_guarded_funcs`' own conservatism (there,
one unguarded call site disqualifies the function).

**[UNVERIFIED] whether this channel is exercised by any file on `main` today.** It is not:
`T183 -> T196` over `.softhouse` shows **zero** scope/verdict moves, only the four tag
corrections. The fixture is constructed. The channel is **prospective**, and I am not claiming
it bit anything.

**(c) Two smaller corrections.** `posonlyargs + args`, so the positional index is right on a
function with positional-only parameters (T183's `f.args.args` would have been off by the
number of posonly params — a **mis-attribution**, not a conservative miss); and keyword actual
arguments (`patch(path=P, …)`) are now read.

**(d) The ATOMIC test is deliberately left UNSCOPED**, i.e. parameter bindings never reach it.
Letting them in would let an actual argument make a *source* look like a temp file and promote
a site to `ATOMIC` — an **excuse**. Withholding them means a genuinely atomic
`os.replace(tmp, dst)` inside a helper is reported UNGUARDED: it cries wolf, which is the
direction this instrument is allowed to be wrong in. Commented at the point of decision.

## D-3 re-derivation

**T183 is right, and right about which direction fires.** Read for myself:

- `local_restoring_cms(tree)` reads `@contextmanager`/`__exit__` from **this file's AST**;
- `RESTORING_CM_NAMES` is a hardcoded stdlib set;
- `process_handlers(tree, …)` scans **this file's** `atexit`/`signal` calls;
- `ast.Import`/`ast.ImportFrom` appeared **once** in the whole 855-line file, in
  `module_reachable_funcs`, and only to **skip** imports when seeding reachability.

So a mutation that is **local** with a guard that is **imported** could only score UNGUARDED.
T179's docstring disclosed the cross-file **mutation** case and not the cross-file **guard**
case — and the guard case is the one that trips `--enforce`. Reproduced on T183's fixtures
[VERIFIED: PROBE C, `BASE --enforce exit = 1` on `green_imported_cm.py` and
`green_imported_atexit.py`, both of which are genuinely guarded].

**Why this is not a cosmetic complaint.** The idiom it punishes is this program's own: T178
factored the write and the guard into `t178_guard.py`, and T187 put all 25 `t41-probe`
rewriters onto it. An instrument that calls the fix broken gets worked around, and then it
protects nothing.

**I fixed it, and an excuse mechanism needs its own RED.** T196-3 follows **exactly one**
import hop, and only for the two things the tool already recognises locally: a restoring
context manager that **encloses** the site, and a module-scope `atexit`/`signal` registration
(including one made by calling an imported registrar on a module-live path — the
`mylib_guard.install_restore(P)` shape, which is how T179 already treats a *local*
registration inside a module-reachable function). Imported-handler excuses get their **own
verdict**, `GUARDED-PROCESS-IMPORTED`, ranked **weakest** in `VERDICT_ORDER`, and every excuse
granted plus every import **not** followed is printed in a dedicated report section.

RED for the fix itself [VERIFIED: PROBE D] — two fixtures that import a real guard module and
are still unprotected must **still fire**, and do:

```

  red_dead_registrar.py:33     (registrar called only from a function nothing calls)
  red_import_not_covered.py:28 (the CM is used — but not around the write)
```

Following an import has **not** degenerated into "this file imports a guard module, therefore
it is guarded". `red_dead_registrar` in particular checks that the import hop inherited
`process_handlers`' own conservatism rather than being more permissive than the local rule it
mirrors.

**Measured blast radius on the real tree: ZERO.** Over the whole of `.softhouse`, the import
hop excuses **0 sites** — 0 files import a module defining a restoring CM, 0 import a module
with a module-scope handler [VERIFIED: PROBE H, T196 import-hop disclosure].

**And I checked that this zero is a real answer and not a resolution failure**, because those
are indistinguishable from the report alone. `t178_guard` **does** resolve — from

`.softhouse/reviews/t47-probe/t178_guard.py` — and `_guards_of_module` returns

to excuse. [VERIFIED: direct call to `_resolve_module` / `_guards_of_module` on `edit18.py`]
