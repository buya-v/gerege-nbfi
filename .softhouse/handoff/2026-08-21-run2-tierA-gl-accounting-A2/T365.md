## Money-math notes

No money is computed here — this is the lock path — but the arithmetic discipline is the same
and the non-negotiables apply to every path.

* **Integers only, still.** Every value the change introduces is `local -i` / `typeset -i` and
  every operation is inside `(( ))`. Grepping the added lines for
  `float|double|decimal|mysql|mariadb|ojdbc|oracle.jdbc|:1521|first_name|last_name|Stripe|Plaid|Lithic|Persona`
  returns **nothing**, and for any `N.N` literal returns **nothing** [VERIFIED: `git diff | grep`].
  The one division added (`LOCK_RELEASE_SKEW_SECS / 2`, in the z07 control fixture) is integer
  division — checked directly: `zsh -c 'print $(( 3601 / 2 ))'` → `1800` [VERIFIED].
* **No database, no hard-coded UTC offset.** The parser accepts only `Z`.
* **The five epoch constants in group H were derived independently of the code under test** —
  python's `calendar.timegm`, not `_iso8601_epoch` [VERIFIED: `1970-01-01T00:00:00Z`→`0`,
  `1970-01-02T00:00:00Z`→`86400`, `2000-02-29T00:00:00Z`→`951782400`,
  `2099-12-31T23:59:59Z`→`4102444799`; and python rejects `2100-02-29` with "day is out of
  range for month"]. Grading a function against its own output is the failure this task exists
  to avoid.

### The finding this task made while proving C5, and it is a real one

**Condition C1 makes the century non-leap rule unreachable through a lock body, so T361's
proposed `released_at: 2100-02-29T00:00:00Z` row would have shipped blind.** If the century
rule breaks, `2100-02-29` decodes to `2100-03-01` — which C1 then refuses as far-future. The
row stays `HELD` and the mutation is invisible. And **no substitute date exists**: Feb 29 of a
non-leap century year is 1900 or earlier (negative epoch, refused by `_e > 0`) or 2100 or later
(future, refused by the skew bound). Routing it through `started_at` does not help either —
both signs yield a negative age, which is `HELD` regardless.

[VERIFIED by driving it: `out/07` rows **r07** and **r07b**. On the same mutated file, the body
route returns `HELD-live` while `_iso8601_epoch` happily returns `4107542400`.]

That is why group **H** asserts the parser directly rather than through `lock_decide`. It is
more than T361 asked for, and I would rather say plainly that I added it than let a condition
land in a shape that satisfies the letter of the review and grades nothing.

### A second, smaller one — the sign of an epoch error is not symmetric

My first red driver asserted that an epoch drifting **high** fires arm 3. **It does not**: a
high epoch makes the instant later, so `now - e` reads *smaller*, and every `want=HELD` row
stays green. The direction that fires arm 3 against a live holder is an epoch reading **low**.
The driver caught my own claim (`CHECKS=15 WRONG=2` on the first run,
`out/06-red-drives.txt`), both signs are now driven separately as r05 / r05b, and the row note
in the source was corrected. `out/06` is kept rather than overwritten, because the transcript
of a control catching its author is the evidence that the control works.

The other WRONG in that first run was mine too: an unescaped `&&` in a `sed` replacement (`&`
is the whole match), which landed a mangled mutation. Both are recorded in comments at the
mutation sites so the next reader does not repeat them.
