## 2. My own re-measurement of the two `git grep` counts (R3)

Measured by me on this branch at `93e82869`, not carried over from T379:

```
git grep -c -E '\bmain\b'   summed over the whole repository  =  109
git grep -c -E 'bmainb'     summed over the whole repository  =  109      <- IDENTICAL
git grep -c -E '\bmain\b'   -- .softhouse                     =  109
git grep -c -E 'bmainb'     -- .softhouse                     =  109      <- IDENTICAL
git grep -c -F 'bmainb'     -- .softhouse                     =  109      <- the SAME 109
```

**They still agree, so the hazard is live — and the third line says *what* they agree on**, which
is stronger than T379's derivation and than T238's. The `-F` fixed-string count is the same 109:
`git grep -E '\bmain\b'` is not merely "returning something odd", it is being compiled down to the
literal string `bmainb`, and it then matches the 109 lines in this repository that literally
contain `bmainb` — every one of them a *document about this hazard*, written by T234, T238, T239
and their reviewers. The failure mode is self-documenting and self-confirming.

T379 measured `97 / 97`; I measure `109 / 109`. **The two are not in conflict**: the number is a
count of how many times this program has written the string `bmainb` down, and it grows every
time someone records the finding. That is also why the number must never be pinned anywhere.

**What this licenses, and what it does not.** It does *not* license a calibration that demands the
two disagree — on this host they are *expected* to agree, and such a calibration would abort the
sweep on every run for the right reason at the wrong time. So R3 is closed by calibrating what the
selectors actually rely on (ERE metacharacter interpretation: brackets, groups, alternation,
bounded quantifiers) and by **refusing** the construct that is known broken. The measurement is
printed on every run as `SWEEP OBSERVE`, so a host where the hazard has gone away shows up in the
transcript instead of being assumed in either direction.
