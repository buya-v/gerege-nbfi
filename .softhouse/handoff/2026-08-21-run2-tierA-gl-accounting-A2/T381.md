## 2. My own re-measurement of the two `git grep` counts (R3)

Measured by me on this branch at `93e82869`, not carried over from T379:

```
git grep -c -E '\bmain\b'   summed over the whole repository  =  109
git grep -c -E 'bmainb'     summed over the whole repository  =  109      <- IDENTICAL
git grep -c -E '\bmain\b'   -- .softhouse                     =  109
git grep -c -E 'bmainb'     -- .softhouse                     =  109      <- IDENTICAL
git grep -c -F 'bmainb'     -- .softhouse                     =  109      <- the SAME 109
```

**They still agree, so the hazard is live — and the third line says *what* they agree on**, which
is stronger than T379's derivation and than T238's. The `-F` fixed-string count is the same 109:
`git grep -E '\bmain\b'` is not merely "returning something odd", it is being compiled down to the
literal string `bmainb`, and it then matches the 109 lines in this repository that literally
contain `bmainb` — every one of them a *document about this hazard*, written by T234, T238, T239
and their reviewers. The failure mode is self-documenting and self-confirming.

T379 measured `97 / 97`; I measure `109 / 109`. **The two are not in conflict**: the number is a
count of how many times this program has written the string `bmainb` down, and it grows every
time someone records the finding. That is also why the number must never be pinned anywhere.

**What this licenses, and what it does not.** It does *not* license a calibration that demands the
two disagree — on this host they are *expected* to agree, and such a calibration would abort the
sweep on every run for the right reason at the wrong time. So R3 is closed by calibrating what the
selectors actually rely on (ERE metacharacter interpretation: brackets, groups, alternation,
bounded quantifiers) and by **refusing** the construct that is known broken. The measurement is
printed on every run as `SWEEP OBSERVE`, so a host where the hazard has gone away shows up in the
transcript instead of being assumed in either direction.

## 3. What the four calibration arms now are

```
SWEEP CALIBRATE+F: -F POSITIVE   a known-present string must be findable                (P-72)
SWEEP CALIBRATE-F: -F ANTI       a run-time sentinel must return zero AND the search must have RUN
SWEEP CALIBRATE+E: -E POSITIVE   a DISCRIMINATION PAIR: the same pattern under -E and     [NEW, R3]
                                 under -F must DISAGREE.  Measured here: -E 2, -F 0.
SWEEP CALIBRATE-E: -E ANTI       an ERE-shaped run-time sentinel must return zero         [NEW, R3]
SWEEP OBSERVE   :  the T238 hazard, re-measured every run, reported and NOT gated         [NEW, R3]
```

**Why the `-E` arm is a PAIR and not a single search.** The obvious form — one `-E` search for a
metacharacter-bearing pattern that must return at least one hit — was written first and **the red
drive refuted it** (§5.1). Read as a *fixed string*, such a pattern matches **the line of
`casualty-sweep.sh` that defines it**, so under a literal-minded engine the arm returned 1 and
passed. Two changes followed, both from that measurement:

- `CALIB_POS_ERE` is now **assembled at run time** from `_ere_alt` and `_ere_dig`, so its literal
  spelling exists in no file and `-F` can find it nowhere;
- the arm runs the same pattern under **both** modes and requires the counts to **differ**. An
  engine that has stopped interpreting ERE answers identically in both, whatever the number, and
  the comparison catches it **without depending on either number being any particular value** —
  which also means it cannot rot as the corpus grows.

`C[A]SUALTY` still guards the `-E` direction (the pattern demands a literal `CASUALTY`, so the
definition line cannot match it under `-E`); the pair guards the `-F` direction. Both were
needed, and only one of them was obvious.

### 5.1 The drives refuted T381 twice, and that is recorded rather than tidied away

**The first run of this suite failed on two of its own arms, and both failures were real.**

1. **My first `-E` calibration arm was defeated by its own source.** A single
   `git grep -c -E 'C[A]SUALTY SW(EEP|OOP) for the T3[0-9]{2}'` **PASSED under the D-R3a shim**,
   returning 1 — because read as a *fixed string* the pattern matches **the line of
   `casualty-sweep.sh` that defines it**. A calibration a broken engine satisfies by reading the
   calibration's own source is not a calibration. Repaired two ways: the pattern is now assembled
   from parts at run time so its literal spelling exists in no file, and the arm is a
   **discrimination pair** — `-E` and `-F` on the same pattern, which must disagree. Measured at
   this head: `-E` = **2**, `-F` = **0**.
2. **D-R3b was measuring the wrong input.** It inserted the probe selector with
   `awk -v ins="$PROBE_SEL"`, and **`awk -v` expands escape sequences**, so the `\b` reached the
   file as an actual BACKSPACE. The RED arm therefore printed `MEASURED ZERO` for the wrong
   reason and the GREEN arm did not refuse at all. Insertion now goes through
   `t381-insert-probe-selector.py`, which **refuses unless the backslash-class survives the round
   trip**.
3. **D-R3a's discriminator was also wrong**, and its replacement is the more interesting finding.
   It counted `MEASURED ZERO` lines, assuming a literal-minded engine falls silent. **On this
   corpus it does not**: the selectors' own ERE patterns appear verbatim in `.softhouse/` — in the
   sweep script, in handoffs, in transcripts that quote them — so a literal search returns
   **self-referential hits** rather than zeros. Measured under the shim: **0** `MEASURED ZERO`
   lines. That is a *worse* failure than silence, not a milder one. The discriminator is now
   divergence of per-selector `hits total` against the control.
4. **A three-line verdict window read the noise instead of the result.** D-R5's first run
   reported `DID NOT REPRODUCE` for a defect that **had** reproduced: the erroring check prints
   one `grep: invalid character range` **per argument** before the selector reaches its result,
   so `grep -A3` never saw it. A verdict predicate whose window depends on how much noise the
   failure emits is not a predicate about the failure. Widened to 12, and the *display* widened
   with it so a reader sees the same bytes the predicate read.
5. **I corrupted a running drive by editing the script under it.** `bash` reads a script
   incrementally, so an edit mid-run produced `syntax error near unexpected token` at line 332
   and killed the run at D-R4. The final run is executed from a **frozen copy** taken from the
   clean committed tree; the drive still extracts BEFORE and AFTER from git, so P-22 is intact.

Points 1–4 are the drive doing its job — three of them are defects **in T381's own repair or in
T381's own instrument**, found because the drive was run rather than described. Point 5 is my
process error and is recorded because a green run that hides a red one is worth less.
