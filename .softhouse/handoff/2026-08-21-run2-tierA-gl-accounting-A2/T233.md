## 1. T222's F-4 — what is enforced, and why NOT T222's own proposal

T222 proposed: *"require an `evidence` / `capture_ref` field on `Exemption`,
validated like a counterfactual's."* **I did not do that, deliberately, and the
reason is the finding itself.**

A counterfactual's `Evidence` is **itself free prose**, checked only by
`statesBothValues` — crudely, for the presence of the words *"observed"* and one
of *"instead / rather than / wrong / emits"*. Adding a second prose field to
`Exemption` would have moved the defect one field over and called it closed: an
uncited reason would have become an uncited reason **plus an uncheckable evidence
line**. It also could not have been adopted without editing four committed
vectors — which the BAR's pinned store digest forbids.

**What is enforced instead: the harness MINTS the citation and requires it to
RESOLVE.** Three components, each checked against something outside the sentence
that claims it:

1. **THE ARTEFACT.** `provenance.capture_ref` must resolve to a regular,
   non-empty file **in this repository**.
2. **THE OBSERVATION INSIDE IT.** `provenance.capture_case_id` must **occur in
   that artefact's bytes**. *A Path A capture is a BUNDLE; a case id that names no
   case in the bundle it cites is a page that is not in the book.*
   **[VERIFIED: nothing checked this before.]** `admitParityProvenance`
   (`admit.go:624-629`) requires the id to be non-empty and **never opens the file
   looking for it** — I read the function and then drove it red.
3. **THE RECORD'S OWN SENTENCE.** The grounding verdict's `Detail` — the exempted
   invariant re-run against the captured schedule — must be non-empty. This is the
   half **no author can write**, because it is generated by re-running the
   invariant.

`reason` is untouched and still required non-empty: it is the human half; the
citation is the machine half, and only the machine half is evidence.

Citations are minted **only for otherwise-admissible exemptions** (`GROUNDED` or
`UNDETERMINED-ON-THE-RECORD`), so a `DECORATION` still reports the one precise
defect it has rather than that defect plus a derived echo.

**Verbatim, from the final green run:**

## 2. The census gate — and `main_grade` now READS the report

`.softhouse/conformance.sh` previously exec'd the graded binary and returned its
exit code. It parsed **nothing**. So neither the exemption count nor the
GROUNDED/UNDETERMINED split was read by anything that decides a verdict, and the
corpus could drift in **either** direction silently.

`gate_exemption_census` compares **five figures for EQUALITY**:

```
conformance:   exemption census READ: exempted assertions (graded) = 4 == pinned 4
conformance:   exemption census READ: declared exemptions (loaded) = 4 == pinned 4
conformance:   exemption census READ: GROUNDED                     = 4 == pinned 4
conformance:   exemption census READ: UNDETERMINED-ON-THE-RECORD   = 0 == pinned 0
conformance:   exemption census READ: UNGROUNDED                   = 0 == pinned 0
```

Equality, not a floor and not a cap, **because only an equality closes both
directions**. Growth stays legal — it just has to happen in a commit that also
edits `EXEMPTION_PIN_*`, where a reviewer sees the two together.

Fail-closed three ways, each driven red: an **absent** figure is an ERROR (never a
0, never a skip); a figure matching **more than one line** is an ERROR (an
ambiguous match's value is whichever line `sed` reached last, which is not a
measurement — the T201/T197-F-1 defect, one census over); and the **NIL-COVERAGE**
arm is a real corpus state that is still COMPARED, not an excuse to skip.

**P-57 obeyed, and no pipeline restructured.** `main_grade` writes the binary's
output to a `mktemp` file and `cat`s it; every read in the gate is a `sed`/`grep`
over that **file**, so there is no early-exiting consumer for `set -o pipefail` to
invert. `"$CONF_BIN" | tee` would have handed `$?` to `tee` — the exact hazard.
The full output is printed unmodified. `--prove`'s pipelines are untouched.

Pinned **in `conformance.sh`, not `PIN.json`**, for two reasons stated in the
file: (a) `GROUNDED`/`UNDETERMINED` is a classification the **harness** computes,
not a property of the vector files — T230 *invented* `UNDETERMINED-ON-THE-RECORD`,
which under a store-side pin would have forced a vector-tree edit for a pure
harness change; (b) `PIN.json` is **inside `.softhouse/vectors/`**, and an expected
value should not live in the tree it describes. **This is not theoretical: I could
not have edited `PIN.json` in this task at all** — the BAR pins that tree.

## 4. T230's tail — the PORT conjunct is now asserted

The report has claimed since T116-N1 that an exemption *"is admissible only for a
shape where the REFERENCE ORACLE ITSELF violates the invariant **and the
implementation reproduces it**"*. `exemption.go` asserts the first conjunct and
refuses when it fails. **The second was asserted by nothing.** T222 raised it
(F-3); T230 re-raised it (F-4) and made the omission *explicit in the report's
prose* — *"nothing here asserts it"* — rather than closing it.

`CheckInvariants` now runs an exempted invariant **anyway**, against the schedule
the implementation returned, and carries the verdict on the result. The exemption
still stands: `Status` is `EXEMPT` and nothing in this path can fail a vector.

**Reported, never refused, and the asymmetry is argued rather than assumed:** the
oracle conjunct is decidable **offline from the vector file alone**, so failing it
is an admissibility defect in the store (exit 2). The port conjunct is a statement
about **a run**; a port that satisfies an invariant the oracle violates has
diverged, and a divergence is a parity finding **the cell diff already owns**.
Refusing here would give one divergence two graders that can disagree, and would
turn an exemption — whose whole purpose is to let a legitimate shape through —
into a second way for that shape to be rejected.

`COULD NOT SAY` is counted apart from `REPRODUCED`, for the same reason
`UNDETERMINED-ON-THE-RECORD` is counted apart from `GROUNDED`: finding T58-N2,
now applied at three levels.

```
--- PORT CONJUNCT (every exempted invariant re-run against the schedule THE IMPLEMENTATION RETURNED) ---
    INSPECTED 4 exempted assertion(s) on the graded vectors.
    4 REPRODUCED (the returned schedule violates the exempted invariant too), 0 DIVERGED, 0 COULD NOT SAY.
```

and beside every exemption in the section above it:

```
    T116-G8-FAMB-N104 — principal_portions_sum_to_disbursed [EXEMPT]
        REASON: …
        PORT CONJUNCT: REPRODUCED — the schedule the implementation RETURNED violates
            this invariant too, which is the second half of the sentence above: principal advanced 1 minor units, principal repaid 0 minor units, difference -1
```

## One mechanism or two? — the T160 judgement

Read T160's brief (`tasks.json`, status **`pending`**, dependencies `T155`/`T158`
— **the mechanism does not exist yet**, verified, not assumed).

**Same diagnosis. Two mechanisms. And they must not share an artefact.**

**The diagnosis is one, and it should be written down once.** T160's store census
and T233's exemption census are the *same* defect wearing two costumes:

> **An artefact and its enumerator agreeing is not evidence of completeness.**
> `StoreFileCensus` and `CaseIDIntegrity` walk *what is there*, so a deleted vector
> is walked by nothing and both enumerators agree it is absent. `InspectExemptions`
> walked *the exemptions that are there*, so a deleted exemption was absent from the
> only walk that could have missed it. Both refuse **inflation** by construction and
> are structurally blind to **deflation**. The only thing that distinguishes *"this
> is COMPLETE"* from *"this is SELF-CONSISTENT"* is **an expected value committed
> apart from the thing it describes**.

That shared doctrine is why my gate is an **equality** and not a floor, why absence
is an **error** and not a zero, why it **prints what it compared**, and why the pin
may **never** be regenerated from the store. Those four rules are T155's three
constraints plus P-35, and they belong to both tasks.

**But building one MECHANISM for both would be wrong, for three reasons I can
point at rather than argue:**

1. **They compare different KINDS of thing, and only one of them is a count.**
   T160's brief is explicit: a missing vector must be **NAMED** (*"a case_id in the
   manifest with no file on disk is a REFUSAL (exit 2) naming the missing ids"*).
   Only the Go side knows which ids it loaded, so T160 needs an **identity
   manifest read by the binary**. My census is five **integers the grader
   computed** — `GROUNDED` is not a property of any file, it is a verdict — so
   there is no id set to manifest and nothing for the binary to name. A count-pin
   in the shell would catch T160's measured deflation at the count level and
   would still not tell anyone **which vector went missing**, which is the actual
   required action.
2. **They fail-close at different layers, and that is a feature.** T160's must
   refuse **before grading**, because a store that is not the store is not worth
   grading. Mine must run **after**, because the figures it reads are produced by
   the run. Forcing both into one place would make one of them wrong.
3. **They cannot share a HOME, and I have the receipt.** T160 proposes `PIN.json`,
   which lives **inside `.softhouse/vectors/`**. That is right for an identity
   manifest of vectors and **wrong for the exemption census**: `GROUNDED` /
   `UNDETERMINED-ON-THE-RECORD` is a classification the *harness* owns — T230
   invented the second one — so a store-side pin would force a vector-tree edit
   for a pure harness change. **This is not hypothetical: I could not have edited
   `PIN.json` in this task at all**, because the BAR pins that tree at
   `73c3ea7b…`. A pin I am forbidden to touch is a pin that gets worked around.

**Concrete recommendation to the driver, for T160:**

- Keep T160 as specified — an **identity manifest** in `PIN.json`, read by the Go
  binary, refusing and **naming** missing case_ids before grading.
- **Reuse `_census_one` / the fail-closed reading discipline**, not the pin. Those
  three functions are already generic over `(report, sed-expression, name)`; a
  second caller costs three lines.
- **Do not** fold the exemption figures into `PIN.json`, and **do not** fold the
  store manifest into `EXEMPTION_PIN_*`.
- **I deliberately did NOT pin the parity-vector count (46) or the cell count
  (7884) in `conformance.sh`, though it is one line each and my gate's machinery
  would take them today.** That is T160's surface, T160 is `pending` with

  rediscovering it. **My gate already catches one specific form of store deflation
