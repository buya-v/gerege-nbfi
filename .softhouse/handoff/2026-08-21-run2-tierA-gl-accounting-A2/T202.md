## T-a — the worktree sweep read a failing git as a clean worktree

### The defect

`.softhouse/bin/fire-program.sh:262` (pre-fix), inside `run_exit_guard()`:

```zsh
WD=$(git -C "$W" status --porcelain | wc -l | tr -d ' ')
(( WD == 0 )) && continue
```

`wc -l` prints `0` on empty input, so a *failing* git is byte-identical to a *clean* worktree. The
guard `continue`s — abandoning exactly the stranded deliverables the comment three lines above it
was written for (`Observed 2026-08-18 17:22: three workers killed, 4,482 insertions stranded`).
**Polarity: fail-OPEN.**

### The fix, and one thing T200 did not name

Two changes, both **fail-CLOSED**:

1. **The enumerator.** `for W in $(git worktree list --porcelain | awk … | tail -n +2)` discarded the

## T-c — the signal trap. What each signal should do, why, and what it now does

### RED, measured past the handler (which is the whole point)

Real `release_lock` + `trap release_lock EXIT INT TERM` bytes extracted verbatim
(`sed -n '122,132p'`, 523 bytes), wrapped in a body that models the chain loop: a foreground child
then guard work, ticking 40 times and logging whether the lock it claims to hold still exists.

**A correction to my own method first, because it changed the answer.** My first driver backgrounded
the subject from a non-job-control zsh, which sets SIGINT and SIGQUIT to **SIG_IGN in the child**
(the POSIX background-job rule) and made zsh look as though it ignores SIGINT. That is a P-55 trap in
my own probe — the shape of the launcher confirmed a claim about the subject. `setopt MONITOR` could
not fix it (no controlling terminal here: `can't change option: MONITOR`), so I re-drove everything
through `/usr/bin/python3` `subprocess.Popen(..., start_new_session=True)`, which gives the subject
its **own session and default dispositions — what launchd gives it**. All numbers below are from that
driver [VERIFIED: `.softhouse/reviews/t202-probe/tc-spawn.py`, `tc-signal-matrix.txt`].

| signal | PRE rc | PRE lock | PRE ticks after release | PRE reached end of body |
|---|---|---|---|---|
| **INT**  | **0** | absent | **38 of 38 remaining** | **YES** |
| **TERM** | **0** | absent | **38 of 38 remaining** | **YES** |
| HUP  | 1 | absent | 0 | no |
| QUIT | 0 | absent | 0 | **YES — the signal did nothing at all** |
| KILL | −9 (137) | **PRESENT — stranded** | 0 | no |

**T200's claim reproduces, and the magnitude is worse than reported.** T200 saw *5* further ticks;
I see the fire release its lock at tick 2 and then run **every remaining tick** — each logging
`lock_present=NO` — and **exit rc=0**, i.e. report SUCCESS. A fire that has been interrupted, has
deleted its own lock, and then works on for hours reporting success is precisely the two-orchestrators
state that STEP 0 of `/softhouse-program` exists to prevent.

**Two dispositions T200 did not test, one of which is a live hole:**

- **SIGQUIT is IGNORED.** zsh 5.9 ignores SIGQUIT in a non-interactive script. Confirmed on a
  minimal, independently-shaped subject (no traps, no borrowed structure): `SIGQUIT: rc=7`,
  reached END, while `SIGINT: rc=-2`, `SIGTERM: rc=-15`, `SIGHUP: rc=1` all terminated. **Today a
  SIGQUIT cannot stop a fire at all.** An explicit trap *does* fire (measured), so this is fixable.
- **SIGHUP already terminated and already ran the EXIT trap** (rc=1, lock released). So HUP was
  *safe* pre-fix; trapping it only replaces a misleading `rc=1` — indistinguishable from a driver
  failure — with a truthful 129.

### The finding that reframes the whole thing: **zsh defers the trap until the foreground child exits**

[VERIFIED: `.softhouse/reviews/t202-probe/zsh-trap-deferral.txt`, `defer.py`]

```
foreground child = sleep 0.2s;  signal sent 0.6s in
  wall time from signal to wrapper exit = 29.88s     <- it waited out the NEXT child, sleep 30
foreground child = sleep 6s;    signal sent 0.6s in
  wall time from signal to wrapper exit = 5.43s      <- exactly when that child finished
```

The fire's foreground child is **`claude`, which runs for hours**. launchd's stop path is SIGTERM
then SIGKILL after a short grace. **Therefore, in production, the SIGTERM handler will usually never
run at all — the fire is SIGKILLed with the lock still on disk.** The stranded lock is the *normal*
outcome of stopping a fire, not the exotic one, and every fire for the next `LOCK_MAX_AGE_SECS`
(6 h) then exits at "another orchestrator holds the lock". That reorders the value of the fix:
the SIGKILL recovery is the most valuable part, not the footnote.

### Disposition argument — what each signal *should* do

- **SIGINT (130).** A human asked for it to stop. It must stop. Spending three more hours of driver
  time after an interrupt is wrong on its own terms, and doing it lock-less is the failure mode the
  lock exists to prevent. Release, then exit 130.
- **SIGTERM (143).** launchd unload/shutdown, `launchctl kill`, plain `kill`. Same reasoning, plus:
  launchd will SIGKILL shortly after, so anything not finished promptly will not finish. Release,
  exit 143.
- **SIGHUP (129).** Session or login shell gone; the `-lc` invocation makes this reachable
  interactively. Already terminated safely, but with a misleading rc. Release, exit 129.
- **SIGQUIT (131).** Today a dead letter. There is no good reason for a signal whose default
  disposition is "terminate and dump core" to leave a repo-mutating orchestrator running. Release,
  exit 131.
- **SIGKILL.** Untrappable by construction — **nothing in-process can help, and any design that
  pretends otherwise is a vacuous guard (P-22).** It must therefore be handled **out of process**,
  at the next fire's lock acquisition. The lock already records `"host"` and `"pid"`; if that pid is
  gone on *this* host, the holder is dead and the lock is stale *now*, whatever its age.

I deliberately did **not** add a `kill -TERM 0` process-group sweep to the handler. The reason is
measured, not assumed: because the trap is deferred until the foreground child exits, **the driver
has already exited by the time the handler runs**, so there is no orphan to kill. A heartbeat probe
(a child appending a timestamp every 0.2 s; count the appends after the wrapper is gone) confirms it:
`heartbeats at wrapper-exit: 100, 3s later: 100 — driver died with the wrapper`
[VERIFIED: `orphan-heartbeat.txt`]. A group kill would be blast radius bought with no defect closed.

### The fix

```zsh
LOCK_RELEASED=0
release_lock() { (( LOCK_RELEASED )) && return; cd "$REPO" || return; rm -f "$LOCK"; LOCK_RELEASED=1; … }
on_signal() { local sig=$1 rc=$2; log "SIG$sig received — releasing the lock and TERMINATING (rc=$rc)…"; release_lock; exit $rc }
trap 'on_signal INT  130' INT
trap 'on_signal TERM 143' TERM
trap 'on_signal HUP  129' HUP
trap 'on_signal QUIT 131' QUIT
trap release_lock EXIT
```

plus `lock_holder_is_dead()` at acquisition, **fail-CLOSED in every leg**: it returns "dead" only
when the lock is readable, `"host"` *and* `"pid"` both parse, the host is **this** host, the pid is a
positive integer, it is not our own pid, and `kill -0` fails. Anything else returns 1 and leaves the
6 h age rule in sole charge. It can make takeover happen **sooner**; it can never make a live lock
look free.

`exit` from a `trap '…' SIG` handler genuinely terminates zsh 5.9 — measured before relying on it
(rc 130/143/129/131 for INT/TERM/HUP/QUIT). Note `trap - EXIT` inside the handler function did **not**
suppress the EXIT trap under zsh, which is why `release_lock` carries an explicit `LOCK_RELEASED`
re-entry guard instead of depending on trap-scoping semantics.
