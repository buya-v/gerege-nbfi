### THE ANTI-HIJACK PROPERTY — **SURVIVES.** I attacked it three ways.

The resolver is a `for _c in /usr/bin/mktemp /bin/mktemp` over two **literal absolute paths**, with
`FIRE_MKTEMP=""` assigned unconditionally first, so an inherited value is discarded before the loop
runs. `$PATH` is never consulted and there is no environment variable, array, or config file that
can reorder, extend, or relativise the list — the candidates are source text
[VERIFIED: reading `fire-program.sh` at the resolver block; and driven below].

I planted a hostile `mktemp` that announces itself on stderr and creates a marked directory, and
drove `--probe` three ways [VERIFIED: `bin/t380-attack-knobs-and-mktemp.zsh`, `out/02-knobs-and-mktemp.txt`]:

| case | attack | result |
|---|---|---|
| `h01` | `$PATH` replaced so the hostile `mktemp` is found first | **rc 0**, marker never printed, no `/tmp/t380-hijacked.*` created |
| `h02` | `FIRE_MKTEMP` **exported** by the attacker | **rc 0**, ignored — the unconditional `FIRE_MKTEMP=""` discards it |
| `h03` | both at once, **with the T301 snapshot re-exec LIVE**, so the *second* `mktemp` call site is exercised too | **rc 0**, marker never printed, no directory created |

`h02` is the case worth naming: `FIRE_MKTEMP` is a **plain, non-exported, non-readonly** variable
that the file overwrites before use, so the environment cannot inject a path into it. That is the
property that had to hold and it holds. The `${FIRE_MKTEMP:-/usr/bin/mktemp}` fallback at the end of
the block reads like an env-honouring default but is not one, because the preceding `FIRE_MKTEMP=""`
guarantees the parameter is empty unless the loop set it.

Both call sites use the resolved value — the C2 self-test scratch dir and the T301 snapshot
[VERIFIED: `grep -n 'FIRE_MKTEMP' fire-program.sh` returns the resolver plus exactly those two uses;

every other mutation in the corpus; the failing line is still **in the fire log** for a human; and
