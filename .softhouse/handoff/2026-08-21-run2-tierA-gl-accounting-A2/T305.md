## THE FINDING NOBODY ASKED FOR: THE REFUSAL RULE IS NOT WHAT THIS STORE SAID IT WAS

`capture2.sh`'s first arm was named `OB-REFUSE-02` and **predicted HTTP 403**. It got **HTTP 200**.

`findNonContraTransactionIds(contraId)` EXCLUDES every transaction that touches the contra account,
and **every entry an opening balance writes touches it** (`:796`). **So opening balances do not
block each other.** Measured, on one instance, with byte-identical request bytes each time

| `OB-ACCEPT-01` | empty | **200**, 6 entries |

| `OB-REFUSE-03` | one NON-CONTRA transaction exists | **403**, `errors[0].args` = exactly that one transaction id |

**THE RULE IS "AFTER A NON-CONTRA JOURNAL ENTRY", NEVER "AFTER ANY JOURNAL ENTRY".** The oracle's
own message at `:814` says the wrong thing and this store repeated it in `LDG-REFUSE-03`'s title
and `_note`, in `impl.go`'s STEP 1.5 comment, and in the capability row. **All three are corrected
here. Nothing GRADED changes** — LDG-REFUSE-03's three cells are the status, code and message the

## Money-math notes

**Every monetary value in this task is an integer count of MNT minor units, and the only decimals
anywhere are the ORACLE'S OWN CHARACTERS, transcribed.**

- The capture body is **balanced by construction**, checked as integers:
  `25000025 + 10000037 = 35000062` minor units. It must be — `:724` refuses an unbalanced opening
  balance before any write, so an unbalanced body could not have produced an accept.
- The oracle stored at **scale 6** (`250000.250000`) and the currency has **2** minor digits.
  `build-vector.py` converts by splitting on `.`, and **REFUSES a non-zero digit beyond the second**
  rather than rounding it — DEC-2 §4.3 consequence 2, the residue rule. It does not import
  `decimal` either: a `Decimal` would be correct and would also hide the residue rule, which is the
  thing worth refusing loudly. **`float()` is never called on a money value anywhere in this rig**;
  the one place `json.load` produces a Python float is the request body's `amount` literal, which is
  used **only** to cross-check an account id, and the code says so at the line.
- **STEP 4's arithmetic is three `int64` additions.** Each request leg contributes one debit and one
  credit of its own amount, so both totals equal the sum of leg amounts: **70000124** each. The
  captured entry balances at 70000124 = 70000124 over six legs, and the harness's
  `double_entry_balances` invariant asserts it independently on what the PORT returned.
- **The margins are measured, not computed by me**: −35000062 (no-contra) and −124 (truncating) are
  the harness's own `maxMargin`, read out of the run and then written into `graded_against`.
- **The contra expansion is the reason this vector has 8 money cells instead of 5**: six leg
  amounts and two totals, and `ledger-wrong-truncating` dies on all eight.
