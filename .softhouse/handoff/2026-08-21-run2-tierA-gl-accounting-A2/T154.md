## Unverified

- **`[UNVERIFIED]` — that an invalid byte could actually reach a committed vector `.json` in
  practice.** T108 marked this open and I did not close it: what is measured is that the guard goes
  blind on such a file, not that the capture pipeline can produce one. Fail-closed does not depend on
  the answer, and the store-root case (M-5) needs no capture pipeline at all — a file placed there by
  hand is enough.
- **`[UNVERIFIED]` — behaviour on any host but this one.** Every `grep` claim is BSD grep
  2.6.0-FreeBSD, `LANG=C.UTF-8`, invoked from inside a `bash` script, on the input shapes in the
  committed corpus (P-33: binary, version, locale, invocation, input shape). ugrep's half of the
  two-token argument is inherited from T108's matrix; I did **not** re-run it, because the Bash tool's
  `grep` function is not what these guards get.
- **`[UNVERIFIED]` — filesystem sensitivity of F-3 and F-5.** Both were driven red on APFS, which is
  case-insensitive and normalisation-preserving. On a case-**sensitive** filesystem `UPPER.JSON`
  behaves the same for these guards (the glob and the suffix test are both case-sensitive in
  software), but I did not run either row on one. The census's rules are filesystem-independent by
  construction — it matches the extension case-insensitively and compares names bytewise — which is
  why they are written that way, but the *measurement* is single-platform.
- **`[UNVERIFIED]` — that the sweep found every load-bearing grep in the program.** It covered
  `conformance.sh` (24 sites, all hardened) and `.softhouse/bin/` (2 sites, 1 hardened, 1 deliberately
  not — see Blockers). **What it structurally could not have found** (P-26): greps inside the
  ~90 historical evidence scripts under `.softhouse/reviews/*-evidence/` and
  `.softhouse/handoff/*-evidence/`, which I did **not** modify because they are committed transcripts
  of past measurements and editing them would falsify the evidence they record; greps in Python
  (`attest.py` and friends) and in `perl`/`sed`/`awk` stream filters, which have their own encoding
  behaviour and were not audited; any grep on an unmerged sibling branch; and a grep constructed at
  runtime from a variable, which a lexical sweep cannot see.
- **`[UNVERIFIED]` — the census's behaviour on a hard link.** A hard link presents as an ordinary
  file with a second path, so it would arrive as a `.json` the harness did not load and be refused —
  but I did not test it. (`DuplicateCaseIDs`' doc comment already claims to catch this case via the
  duplicate id; that claim is also untested by me.)

## Follow-ups

- **F-1 (for the orchestrator).** Mark `T143`, `T132`, `T120` closed in `obligations.md` and
  `tasks.json` — see Blockers 2.
- **F-2. `guard_gofmt` is still phrased negatively and is still vacuous on starved input.**
  `unformatted="$(gofmt -l … 2>/dev/null | grep -v …|| true)"` then `[ -n "$unformatted" ]`: if
  `gofmt` is absent or dies, stderr is discarded, the variable is empty, and the guard **passes having
  formatted-checked nothing**. This is T134's row C-2 and it is the same shape as the two I fixed. I
  hardened its grep but did **not** rewrite the guard, because that is a different non-negotiable
  (G-3) and the brief scoped me to the no-float surface. It should be phrased positively: assert
  `gofmt` ran, assert N files were checked, and assert the unformatted set equals exactly
  `{contract.go}`.
- **F-3. The no-float census reads the source tree at run time.** `Run` scans
  `<RepoRoot>/nexus/internal/apps/loanschedule`. That is fine for this harness — `FindRepoRoot` walks
  up for `.softhouse/vectors`, so the repo is present by construction — but a future binary shipped
  away from its source would report `THE NO-FLOAT GUARD COULD NOT RUN` and be exit 2. That is
  fail-closed and deliberate; it is written down here so nobody "fixes" it into a skip.
- **F-4. Eight non-negotiables still have no executable guard at all** (append-only ledger,
  holds→available, `Idempotency-Key`, the never-insured/protected/guaranteed string rule, three-part
  names, the national-ID shape, the RTGS threshold, deposit-activation-disabled). T134 measured this
  and T154 changed none of it. `ABSENT` is still the biggest bucket and the quietest.
- **F-5. The register's own remaining vacuous rows** — D-1/D-2/D-3 (PostgreSQL-only preconditions
  vacuous on zero input), R-5/R-6 (the rounding canary), X-1, X-2, Z-2 — are untouched.
- **F-6. A guard that can be *removed* is not covered by any of this.** Every check T154 added lives
  in files a future worker can edit. `--prove` demonstrates the harness goes red on doctored
  **vectors**; nothing demonstrates it goes red on a doctored **guard**. The three `regen-*-red.sh`
  scripts are the closest thing, and they compare against a pinned sha rather than against the current
  tree — so they would not notice a guard deleted tomorrow. A `--prove` case that deletes the census
  from a scratch copy of the source and requires the run to change would close it.
