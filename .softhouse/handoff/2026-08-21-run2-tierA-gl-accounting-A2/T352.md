### 3.1 THE HEADLINE: the oracle ACCEPTS AND PERSISTS a sub-minor-unit residue

`POST /journalentries`, MNT, debit gl 16 `100.125` / credit gl 21 `100.125`.

* **HTTP 200**, txn `a29bca0816a7` — `out/T352-A01-residue-3dp.json`, request wire bytes
  `out/T352-A01-residue-3dp.req` sha256 `6a6f389538808d1e…`.
* Read back at the contract boundary as **`"amount":100.125000`** on both legs, with the
  response's own currency block still saying **`MNT, decimalPlaces: 2`** —
  `out/T352-A09-residue-3dp-readback-cited.json`, sha256 `7163378b7ab73e9d…`.
* At the database: `amount 100.125000`, `scale(amount) = 6`, column confirmed
  `numeric(19,6)` — `out/T352-A06-residue-db.txt`.

**So the oracle neither refuses a sub-minor-unit residue nor rounds it away. It stores it
and serves it back.**

Three consequences, kept separate because they are different claims:

1. **money.go's `[UNVERIFIED]` is now partly VERIFIED.** It asked "whether the oracle can
   produce one at all on a money column" — the column can hold one and the reader serves
   one. **What is still NOT observed is the oracle's own arithmetic *generating* residue:
   I supplied the third decimal, it was not computed.** I will not overstate this.
2. **The port and the oracle demonstrably diverge on this input.** Run against the
   captured bytes:
   `MinorUnitsFromDecimalText("100.125000", 2)` →
   `ledger: monetary text "100.125000" carries sub-minor-unit residue at scale 2 … This
   port applies NO truncation rule **because no captured vector establishes one**;
   refusing rather than silently inventing an amount`.
   The refusal is still the right default — 10012 and 10013 are both inventions — but the
   stated *reason* is now false, and it is the reason the error text itself gives.
3. **The vector schema cannot represent the observation at all**, and I DROVE this rather
   than arguing it (§4).

### 3.2 The balance check runs at FULL SCALE — observed, then confirmed in source

Debits `0.125 + 0.125` against a single credit `0.25`. **HTTP 200**, txn `a29bca9bf813`
(`out/T352-A03-residue-balance-scale.json`; psql shows `0.125000 + 0.125000 = 0.250000`).

Had the oracle rounded each leg to the currency's minor unit before summing, HALF_UP gives
`0.13 + 0.13 = 0.26` against `0.25` and the entry is refused as a sum mismatch. It was not.
Source agrees: `checkDebitAndCreditAmounts` sums raw `BigDecimal`s and compares with
`compareTo`, no scaling on the path
[VERIFIED: `JournalEntryWritePlatformServiceJpaRepositoryImpl.java:306-326`; and
`grep -rn 'setScale\|RoundingMode' fineract-provider/src/main/java/org/apache/fineract/accounting/journalentry/`
returns **nothing** at the pinned commit].

**A rounding observation, with its attribution stated rather than assumed.** A leg posted
at seven decimals, `100.1234565`, was accepted and stored as **`100.123457`** (txn
`a29bcaa6a41b`, `out/T352-A04-overscale-7dp.json` / `out/T352-A05-overscale-readback.json`).
That is round-half-**UP** into the column's scale 6; HALF_EVEN and truncation both give
`100.123456`.

**It may NOT be cited as witnessing MoneyHelper's ratified HALF_UP.** The JE write path
applies no Java-side rounding at all (the grep above), so what I observed is
PostgreSQL's `numeric(19,6)` coercion, whose half-away-from-zero coincides with Java
HALF_UP for positive amounts. A positive-amount probe cannot separate them and this corpus
posts no negative leg. Recorded as the *system's* behaviour at the boundary, not the
tenant rounding mode. (The report's own "T55 witnessed no shape separating … HALF_UP from
HALF_EVEN" is therefore still standing for the *engine*.)

### 3.3 `ledger.multi.currency.entry` — the row's reason was wrong in both halves

* **A multi-currency entry is NOT EXPRESSIBLE at this seam, structurally.** A journal-entry
  leg has no currency field: `SingleDebitOrCreditEntryCommand` carries exactly
  `glAccountId`, `amount`, `comments` [VERIFIED: `SingleDebitOrCreditEntryCommand.java:33-35`],
  and `currencyCode` is a single scalar on the enclosing command [`JournalEntryCommand.java:40`].
  No capture campaign will ever close this row here. The current reason ("UNTOUCHED …
  there is NO OBSERVATION") implies a probe would help. It would not.
* **The ledger is currency-general; the STORE is not.** The tenant has two selected
  currencies, MNT and USD (`out/T352-P01-currencies.json`), and a **USD** journal entry on
  the same two GL accounts was **accepted, HTTP 200**, txn `a29bcb5d6fcf`, read back as
  `currency USD, decimalPlaces 2, amount 12.340000`
  (`out/T352-A07-usd-entry.json`, `out/T352-A08-usd-readback.json`).
  G-07's MNT pin is a **store policy** enforced at `admit.go:156-162`, not a constraint the
  oracle imposes. The row's sentence *"there is NO OBSERVATION … so G-07 pins MNT"* inverts
  cause and effect: the pin came first.

This is the **first non-MNT journal entry in the tenant**, so A2-15's
`sql/q4-a2-26-ledger-state.sql` assertion that every row is MNT is now false as a matter of
moved baseline, not of query defect.

### 3.5 A free rig finding: FILE-NAME-ONLY citations are avoidable at capture time

The corpus pins **3 FILE-NAME-ONLY** citations, and a fourth is inadmissible. A citation
falls to FILE-NAME-ONLY when the capture's `.http` sidecar contains the case id nowhere —
which happens for every **GET**, because cap10/cap11 write `body-wire-bytes-artefact: NAME.req`
only when there is a body.

**Fix, requiring no script change: pass the case id as the `Idempotency-Key`.** I proved it
by re-capturing the same readback that way: `T352-A09-residue-3dp-readback-cited` has
`Idempotency-Key: T352-A09-residue-3dp-readback-cited` in its sidecar and resolves as
**HTTP-SIDECAR**, and its body digest is **identical** to the badly-keyed `T352-A02`
(`7163378b7ab73e9d…`), so the fix costs nothing and the readback is stable. Recommended as
standing capture discipline for GETs.
