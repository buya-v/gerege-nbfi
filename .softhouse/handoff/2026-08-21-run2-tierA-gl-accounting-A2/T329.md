## 1. What T327 saw, and what it actually was

T327 observed `/glclosures` → `createdDate: "2026-08-27"` (string) and `/journalentries` →
`createdDate: [2026,8,28]` (array), same instance, seconds apart, and marked the cause
`[UNVERIFIED]`. **The cause is two independent defects stacked, and the second is worse than the
first.**

**The two fields are not the same quantity and never were.**

- `/glclosures.createdDate` — an **audit row-insertion timestamp** truncated to a date, stamped from
  `ZoneId.systemDefault()` (the **JVM/container** zone).
- `/journalentries.createdDate` — **a plain alias for `submittedOnDate`**, i.e. the **business
  date**, which comes from the **tenant** zone. There is no created-date column in that query at all.

`[VERIFIED: JournalEntryData.java:211]` `this.createdDate = submittedOnDate;`

**A port that "fixes the timezone" fixes nothing** — the two fields would still disagree with both
clocks in the same zone, because they measure different things.

## 2. The two serialisation paths, cited

| | `/glclosures` | `/journalentries` |
|---|---|---|
| stack | **Jackson** (resource returns the POJO) | **Gson** (resource returns a serialized String) |
| entry point | `GLClosuresApiResource.java:91-95` (`return glClosureReadPlatformService.retrieveAllGLClosures(officeId);`) | `JournalEntriesApiResource.java:93, :166` (`apiJsonSerializerService.serialize(...)`) |
| shape decided by | `JacksonLocalDateBeanSerializerModifier.java:39-48` — class-level `@JsonLocalDateArrayFormat` present? | `GoogleGsonSerializerHelper.java:107` → `core/api/LocalDateAdapter.java:38-47` |
| `GLClosureData` / `JournalEntryData` annotated? | **NO** `[GLClosureData.java:34-35]` | n/a — Gson never reads the annotation |
| writer | `LocalDateJsonConverter.java:44-48` → `ISO_LOCAL_DATE` **string** | `JsonArray` of year/month/day → **int array** |

**The Gson adapter's own class comment is the smoking gun** `[core/api/LocalDateAdapter.java:30-33]`:
*"returns the date in array format **to match previous Jackson functionality**."* It imitates an
**old** Jackson config; the **current** Jackson config emits strings. That is how they drifted.

**Clock chain, both sides fully cited:**
- closure: `GLClosure.java:44` extends `AbstractAuditableCustom` → `AbstractAuditableCustom.java:46-47`
  (`created_date`, `LocalDateTime`) → `CustomAuditingHandler.java:63-69` picks `INSTANCE` (not the
  UTC base) → `CustomDateTimeProvider.java:42-44` → `DateUtils.java:101-104`
  `LocalDateTime.now(ZoneId.systemDefault())`.
- journal entry: `JournalEntry.java:136` `submittedOnDate = DateUtils.getBusinessLocalDate()` →
  `DateUtils.java:238-240` → `BusinessDateReadPlatformServiceImpl.java:74-75`
  `getLocalDateOfTenant()` → `DateUtils.java:70-72, :65-68` `ZoneId.of(tenant.getTimezoneId())`.

I re-derived T327's `BusinessDateReadPlatformServiceImpl:74` citation independently; it holds.

**The window.** Its width is `tenantOffset − jvmOffset`, **not a constant**. On T327's instance
(container `TZ` unset = UTC, tenant `Asia/Ulaanbaatar` +08) it is 8h/day, 16:00Z–24:00Z. T327 landed
at 17:33:40Z, 93 minutes in. For `Asia/Hovd` (+07) it would be 7h.

## 3. Blast radius — table size and headline

**16 rows**, each `endpoint x field x stack x shape x kind x clock`, in `blast-radius.md`. Covers all
**7** `*ApiResource.java` under any `*/accounting/*` path, plus `BusinessDateApiResource`.

- **ARRAY**: all four `/v1/journalentries` read endpoints (Gson) + `/v1/businessdate` (Jackson +
  annotation).
- **STRING**: `/v1/glclosures` (3 date fields) and `/v1/provisioningentries` (`createdDate`).
- **NO dates at all**: `/v1/glaccounts`, `/v1/accountingrules`, `/v1/financialactivityaccounts`,
  `/v1/runaccruals`, `/v1/provisioningentries/entries`.

**Three findings a coder must not miss:**
1. `/journalentries` is the **only** accounting resource still on the Gson response stack — a
   migration in progress, not a design. It will move.
2. **Three distinct `createdDate` fields, three distinct meanings** (JVM wall clock / business date /
   provisioning run date). The name is not the meaning.
3. If `JournalEntriesApiResource` is migrated to Jackson and `JournalEntryData` is left unannotated,
   `submittedOnDate` **silently flips array → string**. Nothing in the codebase guards this.

**Only 9 DTO classes program-wide carry `@JsonLocalDateArrayFormat`; none is in accounting.**

## 5. Rules for the next coder (full text in README §4–§5)

**PORT:** never infer a date's meaning from its name (P-1); model calendar date / business date /
audit instant as three different types (P-2); the business date is an **input**, never `time.Now()`
(P-3); tenant zone from the tenant row (P-4); the audit zone is a **third** zone, the deployment's
(P-5); the deserialiser must fail loudly on an unexpected shape, never fall back (P-6).

**VECTOR:** carry each date's provenance, not just its value (V-1); never grade an
audit-timestamp-derived cell without pinning the JVM zone — `/glclosures.createdDate` is **not
gradeable as a stable value** (V-2); assert relations, not literals (V-3).

**V-4 is live and imminent.** T327's `B1-ACCEPT-06` / `B2-ACCEPT-01` readbacks are the next queued
promotion and they contain `createdDate`. **Grading it as a literal would bake the 8-hour window
into the corpus and make the vector pass or fail depending on what time of day CI runs.** Grade
`transactionDate` (safe); grade `submittedOnDate` only as a *relation* to `request.business_date`.

**I did not propose hard-coding `+08` anywhere.** That is the rule this finding threatens.

   Source-derived; worth a probe before any port consumes `changes`.

**One item RESOLVED during the task:** `acc_gl_closure.created_date` is `datetime`
`[0001_initial_schema.xml:93]` → PostgreSQL **`timestamp without time zone`**, and the `datetime(6)`
widening is gated `context="mysql"` `[0117_set_datetime_precision.xml:25]`, so it never runs for us
(CLAUDE.md: PostgreSQL only). The column carries no zone, so Postgres performs **no** conversion on
read — **the JVM zone is the whole story, with no second database-side effect layered on top.**
