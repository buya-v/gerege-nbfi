**One sentence.** T172's committed probe scripts (`run-pre-fix.sh` / `run-post-fix.sh`) replay

pathspec instead of a piped grep — `grep -c` for either transcript's pattern against the current

**New:**
- `check-lock-exclusion-anchor.sh` — the live regression gate. Extracts the current `DIRTY=$(git status
  --porcelain ...)` guard line from a TARGET file (default: the live `.softhouse/bin/fire-program.sh`,

## What the old anchor asserted vs the new

**Old (T172, pre-T190, was `fire-program.sh:224`):**
```
DIRTY=$(git status --porcelain | LC_ALL=C grep -av '^?? \.softhouse/LOCK' || true)   # pre-fix (buggy)
DIRTY=$(git status --porcelain | LC_ALL=C grep -av '^?? \.softhouse/LOCK$' || true)  # post-fix (T172's fix)
```
Asserted: piping full `git status --porcelain` through a `grep -av` that excludes the literal `?? .softhouse/LOCK`
line, anchored with a trailing `$` so it does not also swallow lines merely *prefixed* by that path (e.g.
`?? .softhouse/LOCKED_STATE.md`).

**T190 removed this construct entirely** (not merely edited it) — see the block comment immediately above
the guard in the live file, `.softhouse/bin/fire-program.sh:299-310`: a pipeline through `grep -av '...' ||
true` cannot, under `set -uo pipefail` without `-e`, distinguish "clean tree" from "git status itself
failed" (`git rc=128` + filter `rc=1` → pipeline `rc=1`, indistinguishable from a genuinely empty match).
T190's fix drops the pipeline and the grep entirely, replacing them with git's own pathspec exclusion and a
checked `$?`:

**New (live, `.softhouse/bin/fire-program.sh:313`):**
```
DIRTY=$(git status --porcelain -- ':(top)' ':(top,exclude).softhouse/LOCK')
GS_RC=$?
```

**Same property, different mechanism.** The thing under test — *does `.softhouse/LOCKED_STATE.md` survive
being merely a path-prefix sibling of the excluded `.softhouse/LOCK`, while `.softhouse/LOCK` itself is
excluded* — is unchanged. What changed is where the exclusion logic lives: a regex anchor inside a piped
grep (T172's fix), replaced by git's own `:(exclude)` pathspec matching (T190). I verified empirically, in
a scratch repo built by `setup-scratch-repo.sh`, that the live pathspec `:(top,exclude).softhouse/LOCK`
does the exact-match (not prefix-match) exclusion git's pathspec semantics promise here — output below.
This is the same property T172 fixed, re-scoped to the new mechanism; I did not need to invent a new
property, only re-point at where it now lives.

**Sibling-file shape used, and why (T161's trap):** `fire-program.sh` does **not** derive its repo root
from `$0`/`__file__` — `REPO="${GEREGE_NBFI_REPO:-/Users/buv/gerege-nbfi}"` is hardcoded

found elsewhere. What **is** `$0`-relative is `check-lock-exclusion-anchor.sh`'s own default-target
resolution (`HERE="${0:A:h}"` → `../../bin/fire-program.sh`), so `run-red-demo.sh` writes its mutant

explicitly as the `TARGET_FILE` argument, matching the sibling-file shape T161 measured rather than
assuming it wasn't needed here.

## Zero-match demonstration

`run-zero-match-demo.sh` writes a decoy file that deliberately has no `DIRTY=$(git status --porcelain
...)` line, then runs `check-lock-exclusion-anchor.sh` against it:

```
$ zsh .softhouse/reviews/t172-probe/run-zero-match-demo.sh
=== decoy file contents (anchor pattern absent by construction) ===
#!/bin/zsh
echo "this file deliberately has no DIRTY=... guard line at all"

=== running check-lock-exclusion-anchor.sh against the DECOY (expect ERROR, nonzero exit, not a vacuous pass) ===
ERROR (P-35, patterns.md): anchor pattern matched ZERO times -- this is not a pass.
  pattern: DIRTY=$(git status --porcelain
  file:    .../t172-probe/decoy-no-anchor.RED-scratch-copy.sh
The guard line this probe checks no longer exists at that text in the target file. Investigate and re-point the anchor by hand; do NOT treat a zero-match as green.

exit code: 1
ZERO-MATCH DEMONSTRATION CONFIRMED: probe refused with a non-zero exit (1) and named the pattern + file, never a vacuous pass.
```
[VERIFIED: ran directly, real zsh 5.9, this worktree. Also independently confirmed the underlying premise
of this whole task: `LC_ALL=C /usr/bin/grep -Fac "grep -av '^?? \.softhouse/LOCK'"
.softhouse/bin/fire-program.sh` and the same for the `$`-anchored post-fix variant both return `0` against
the live file — the exact "grep -c returns ZERO" measurement the task description states.]

**grep binding (P-58):** `check-lock-exclusion-anchor.sh` hardcodes `GREP=/usr/bin/grep` and refuses to run
if it is not executable, rather than trusting a bare `grep`. Measured directly in this environment: in this
agent's interactive shell, `grep` is a function that re-execs as `ugrep 7.5.0` with `-G -I
--exclude-dir=...`; but that is a shell **function**, not exported, and does not survive into a fresh `zsh
script.sh` child process — a standalone `#!/bin/zsh` script invoked as its own process resolves bare `grep`
to `/usr/bin/grep`, BSD grep 2.6.0-FreeBSD, both under plain `zsh script.sh` and under `zsh -lc '...'` (the
shape launchd uses to invoke `fire-program.sh`) [VERIFIED: ran `type grep; grep --version` inside a
`#!/bin/zsh` script both ways, both resolved to `/usr/bin/grep` / BSD 2.6.0-FreeBSD]. All greps inside the
new probe use `LC_ALL=C` and `-a` for the same byte-determinism reasons T157/T172 established for the old
guard.
