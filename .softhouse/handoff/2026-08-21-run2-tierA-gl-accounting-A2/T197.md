### Is it the hard-coded-floor trap in disguise? **No — and here is the precise reason.**

The disguised-hard-code failure would be a floor that **silently** stops bounding. This one
cannot go silently vacuous in the dangerous direction:

- floor `0` (git derivation failed, or corpus untracked) → `[ "$floor" -lt 1 ]` → **ERROR**.

  mitigation for graceful degradation is that the number is on the screen, and it genuinely is.

defect in T194, but it should not be remembered as something the floor covers.

## Findings (all NON-BLOCKING)

**F-1 — the census extraction regex is greedy and would take the LAST `inspected N` on a line.**
`sed -n 's/^CENSUS .*inspected \([0-9][0-9]*\).*$/\1/p'` — the leading `.*` is greedy, so on
`CENSUS x inspected 320 bodies, 5 not inspected 7 more` it returns **7**, not 320
[VERIFIED: run directly]. **Latent, not live**: both real census lines contain exactly **one**
occurrence of `inspected` today [VERIFIED: `grep -oc 'inspected'` = 1 on each]. Polarity of the
hazard is *unknown* — it depends on which figure is larger — so it is not safely fail-closed.
T194 documented the *first-line-of-many* degradation but not the *last-match-within-a-line* one.
Worth a follow-up; not worth a number change today.

**F-2 — the gate reads the FIGURE but not the ROOT.** Stub E printed
`... .java files across 20 directories under x ...` and the harness accepted it, printing
`census figure READ: inspected 57 >= 57`. The census line already carries the walked root, and
the harness already knows `$REPO_ROOT`; asserting they match is a cheap available hardening T194
did not take. It raises the impersonation cost slightly and, more usefully, would catch a guard
walking the *wrong tree at the right size* — which is a near neighbour of T173 merge defect A.

**F-3 — stale line numbers in the doc that warns about staleness.** `softhouse-program/SKILL.md:110`
cites *"`run_guards` is called at `conformance.sh:281`; the probe prints at `:296`"*. Actual on
merged main: `run_guards` defined at **938**, called at **982**, probe printed at **997**. The
*rule* is correct and load-bearing; only the citations have drifted ~700 lines.
**Pre-existing — not introduced by T194** — but it is the exact hard-coded-number decay T194's
own reasoning is about, sitting in the driver's rulebook.

**F-4 — CONSTRUCTIVE: T194's technique answers T160 more directly than T160's brief allows for.**
T160 argues the deflation asymmetry is structural because *"a vector that has been REMOVED is
absent from BOTH enumerators, so `find` and LoadStore AGREE"*. That is true of the two
**filesystem** enumerators and **false of a third one: the git index.** A vector deleted from the
worktree is still listed by `git ls-files` — which is precisely how T194's case-2 fail-closed
works. A floor of
`git ls-files -- '.softhouse/vectors/**/*.json' | grep -c` on `guard_no_float_in_vectors`'s `seen`
would refuse the green 42/5617 I measured above, at roughly three lines, for the failed-checkout
/ bad-merge / stray-`rm` / worktree-prune causes T160 enumerates. It is **weaker than T160's
committed manifest** — it pins a count, not the `case_id`s, and a deliberate `git rm` lowers both
together — so it is a complement, not a substitute. Recommend T160's implementer read T194 before
starting.

**F-5 — cry-wolf cost of case 2, accepted.** `rm` of a tracked `.java` without `git rm` takes the
whole harness to exit 2. The window is narrow (a legitimate rig retirement uses `git rm`, moving
both numbers together) and the message is self-diagnosing (`git tracks 57 file(s) it must open`).
