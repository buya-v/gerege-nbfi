### The minor-unit arithmetic, RE-DERIVED

The oracle stored `250000.250000`, `100000.370000`, `350000.620000` — `acc_gl_journal_entry.amount::text`
at **scale 6** — and returned `250000.25`, `100000.37`, `350000.62` on REST at **scale 2**. The
builder converts each independently: split on `.`, **REFUSE** a non-zero digit beyond MNT's two
minor digits, `int(whole)*100 + int(keep)`.

```
250000.250000 -> 25000025      100000.370000 -> 10000037      350000.620000 -> 35000062
debits  25000025 + 10000037 = 35000062
credits                       35000062        EQUAL — the builder refuses to emit otherwise
```

**No float touches a money path, including intermediate calculation.** `guard_no_float_money()`
refuses outright any money value that did not arrive as the oracle's own decimal **string** — which
matters because `json.load` turns the `.req` wire literal `250000.25` into a Python float, and the
only fields the builder takes from a request body are integers (`officeId`, `glAccountId`) and
strings. The amount text always comes from the **readback**. The residue rule's `NONE` is T327's
measurement, red-driven there on `250000.250001`, `0.005`, `1.239`, `100.00000001`.

## 3. `createdDate` — the per-field gradeability decision, and its argument

**Decision: `createdDate` and `submittedOnDate` are NOT GRADED, by construction, on both vectors.**

**The finding, and this capture verifies it independently.** T329 established from the pinned source
that `/journalentries` `createdDate` is **a plain alias for `submittedOnDate`** —
`JournalEntryData.java:63` declares it a `LocalDate`, `:211` assigns `this.createdDate =
submittedOnDate`, and the read query has no created-date column — while `/glclosures` `createdDate`
is an audit row-insertion timestamp on the **JVM** zone. **T327's bytes show both quantities at the
same instant**:

| endpoint | field | value | what it is |
|---|---|---|---|
| `GET /glclosures` | `createdDate` | `"2026-08-27"` | JVM/UTC day of row insertion |
| `GET /journalentries` | `createdDate` | `[2026,8,28]` | tenant business day |
| `GET /journalentries` | `submittedOnDate` | `[2026,8,28]` | the same quantity, the same value |

**Two different quantities sharing one name**, on one instance, seconds apart.

**Why grading either as a literal is a defect and not a choice.** The value is the **wall-clock day
at insertion**. Re-running the committed recipe on another day — *or the same day either side of
16:00Z* — emits a different number, so the vector would **pass or fail on what time of day CI ran**.
That is an up-to-eight-hour window baked into a parity vector. The fix is **not** to normalise with
an offset: `CLAUDE.md` forbids hard-coding one, and that rule is precisely what this hazard
threatens.

**The exclusion is structural, not editorial.** Both vectors are built from the **database**
readback (`acc_gl_journal_entry` joined to `acc_gl_account`), which **has no created-date column at
all**, and the vector schema has no field that could hold one. The REST bytes are committed beside
the capture and graded by nothing. The hazard is sharpest on LDG-07, whose `transactionDate` and
`submittedOnDate` **coincide** (both `2026-08-28`) — a reader who assumed they were one field would
find them agreeing there and be wrong; LDG-06's arm, four seconds later, has `2026-08-27` and
`2026-08-28`, and that is the pair that separates them. Argued in full in both `_note`s.

**The date that IS gradeable and IS used: the DB's `entry_date`.** It is the caller's transaction
date — a business fact, not a clock reading — and the builder **asserts** it on every row rather
than copying it, which is what turns `request.transaction_date` from a transcription of the request
into an observation of what the oracle stored.

## 4. The capability widening — and T306's prescribed edit would have admitted NOTHING

### The door was closed, and I have the transcript

`out/40-RED-door-is-closed-inadmissible.txt`: with the pre-T328 predicate, **both vectors are
INADMISSIBLE** and the run is exit 2, with the gate's own message ending *"PROMOTE THE CAPTURE
FIRST, then widen this rule"*. T296's standing instruction — widen *"deliberately and with the
capture in hand, instead of finding the door already open"* — is satisfied by measurement.

### What T306 prescribed, and why it was wrong

`openingbalance_test.go` and `admit.go` both said: *"drop `v.Expect.Kind == \"refusal\"` from the
date arms in the same change."* **That alone admits neither vector.** `preClosureInputs` is
`!isoBefore(closing, txn)` — true only when the transaction date is **on or before** the closing
date, the **REFUSING** region. T327's B-1 is dated one day **after** the closing date, so it is
`false`; the same asymmetry holds for `futureDatedInputs` against B-2, dated **on** the business
date. **Both promoted vectors sit in the ACCEPTING region of their comparison — which is the only
place an acceptance can be observed — and the old predicate had no term that could ever be true for
them.** The instruction was right about *when* to widen and wrong about *what*.

### What the rule is now

```go
closureInputs   := latest_closing_date != "" && transaction_date != ""
businessInputs  := transaction_date  != "" && business_date != ""
refusingRegion  := (closureInputs  && !isoBefore(closing, txn)) || (businessInputs && isoAfter(txn, business))
acceptingRegion := ((closureInputs && isoBefore(closing, txn)) ||
                    (businessInputs && !isoAfter(txn, business))) && !refusingRegion
observedShape   := openingBalanceCommand ||
                   (Expect.Kind == "refusal" && refusingRegion) ||
                   (Expect.Kind != "refusal" && acceptingRegion)
```

**T306-F-2 survives**: the region is computed from the vector's own two dates by *the same comparison
the oracle makes*, and `expect.refusal.code` is still never read here. Requiring the expectation to
**agree with** the region is not keying on the answer — it is refusing a vector that claims coverage
of a shape nobody captured. The refusing region **wins when both apply**, because the oracle refuses
as soon as either guard fires.

### Default-deny, checked by construction in three directions (P-89 — *"PROSE DOES NOT FIRE ON THE NEXT FIRE"*)

- **no date inputs, no command** → refused (pre-existing arm, unchanged, still passes);
- **an ACCEPTANCE in a REFUSING region** → refused (the arm T306 wrote, **renamed and not one line
  changed** — it still passes, now for the sharper reason that the oracle refuses on those inputs);
- **a REFUSAL in an ACCEPTING region** → refused. **This arm is new (T328).** Before the widening
  this direction was covered *by accident*, because the gate refused every accepting-region shape
  outright; now that the accepting region is claimable, it is the arm that shows the gate did not
  simply open. It uses the exact dates the store observed being **accepted**, so it cannot be
  satisfied by a date the oracle was never asked about.

**Why it could not fire.** Its predicate was `preClosure || futureDated` — the **REFUSING**-region
comparisons. An acceptance sits in the **ACCEPTING** region by construction, so the predicate is
`false` on exactly the vectors it was built to notice. It could only ever have caught an acceptance
claiming a shape the oracle *refuses*, which the mutation arm above it already refuses as data. The
store was **not** unprotected — `Admit` refused both vectors and the bar was exit 2 — but the bell
built to ring did not ring, and the message that *did* fire said *"the store moved"* rather than
naming the edit.

**Fixed here.** Re-keyed to assert what the rule actually says: **every dated claimant's
`expect.kind` must AGREE with the region its own dates put it in**, re-derived from the committed
store independently of `Admit`, with an anti-vacuity floor of 4 dated claimants (both sides of both
rules) and a message that names the vector, the region, and the one-diff-not-two edit.
**Red-driven in both directions** [`out/80-red-drive-tripwire.txt`]: acceptance dragged into the
refusing region → RED; refusal dragged into the accepting region → RED; committed store → green;
store restored byte-identical and verified.

### `FU-T328-2` — MEDIUM. A red-drive that perturbs the vector store and omits `-count=1` measures the go test cache.

The first run of `80-red-drive-tripwire.sh` reported **BOTH ARMS GREEN**. The perturbation is to a
data file outside the module and no package source changed, so `go test` replayed a cached result —
a vacuous control of exactly the kind the script exists to prevent. `-count=1` is now load-bearing
there and the trap is documented in the script. **Any future arm that perturbs the store inherits
this**, and no lint in this repo catches it.

### `FU-T328-3` — MEDIUM. `LDG-REFUSE-04` / `LDG-REFUSE-05` carry a DERIVED business date; T328's carry a BRACKETED one.

T329 named `request.business_date` in both refusal vectors as ambiguous. They were lifted out of
T287's prose. `LDG-06`/`LDG-07` carry a value **measured by a two-sided bracket** and the builder
refuses to emit if the bracket does not close. **The store now holds two provenance grades for the
same field.** I did not touch the refusal vectors: changing a graded input on a committed vector is
a re-observation question. The cheap route is a throwaway re-capture of both refusals on the T327
rig, which would bracket them the same way.

### `FU-T328-4` — LOW, and it is a documentation gap in a guard, not a defect.

`census_dead_paths.py`'s `LITERAL_RE` only extracts a `.softhouse/` path that sits **inside single
or double quotes**. An unquoted `# see .softhouse/no/such/file` is invisible to the dead-path
census. That is a defensible selector — an unquoted path in a comment is usually prose — but it is
**not stated in the four-bucket table** the module docstring prints, and a red-drive that omits the
quotes silently measures nothing (which is how I first hit it). One sentence in that docstring would
close it. **The file is `.softhouse/capture/t316-dead-path-guards/census_dead_paths.py`, outside my
scope, so I did not edit it.**

### `FU-T328-5` — LOW. The top-level `parity vectors` count excludes the ledger, and a brief mis-derived from it.

See §6. `46 / 7884` is the loanschedule schema alone; the ledger is counted separately and always
has been. The T328 brief predicted a landing state of *"48 parity vectors"*. The report's own header
says *"SECOND SCHEMA, SECOND COMPARATOR, SEPARATE COUNTS"*, so the number is correct and the
expectation was not.

### `FU-T328-6` — MEDIUM, and it is the honest limit of what T328 bought.

**Nothing in the store grades the refusal PRECEDENCE between the two date rules.** `:630` runs
before `:636`, but no capture sends a request that violates **both**, so a port evaluating them in
either order scores identically — which is exactly why the registered mutant can invert the order
and still reproduce both refusals (§1, arm W-1 vs W-2). Closing it needs one capture: an entry dated
**both** after the business date **and** on or before the closing date, which must return
`future.date`. `admit.go` already refuses a vector claiming `accounting.closed` with those dates —
correctly — so the gap is a **missing observation**, not a missing rule. Recorded in the
`ledger.refusal.parity` row.
