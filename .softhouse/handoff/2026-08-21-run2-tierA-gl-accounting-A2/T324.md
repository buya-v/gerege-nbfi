# T324 — FU-T318-2: three "independent" clean checks, one blind spot, work destroyed

Branch `softhouse/T324-worktree-prune-skipbit`. Role `coder`.
Raised by T318 (merged `2f1ba61c`) as FU-T318-2, HIGH, live in committed code.

**Headline.** The kill chain is closed **on the wrapper's automated prune path**, and the
word that caused it is corrected where it was written. `wt_prune_check` still answers
PRUNE on a skip-bit-hidden worktree — its file is outside my edit set — so the refusal is
placed at the **call site in `fire-program.sh`**, between the verdict and
`git worktree remove`, which is the only place in this repo where that verdict becomes a
deletion.

**Two things T318's prescription did not cover, both found by experiment rather than
taken on trust, as the brief required:**

1. **`--skip-worktree` and `--assume-unchanged` destroy work identically but print
   DIFFERENT LETTERS.** `--assume-unchanged` → **`h`** (lowercase). `--skip-worktree` →
   **`S`** (UPPERCASE). Both bits set at once → **`h`**. So the natural-looking rule
   *"flag lowercase tags"* would sail straight past `--skip-worktree`. The rule shipped is
   **`tag != H`**. [VERIFIED: `evidence/10-taxonomy.txt`, shapes B/C/D, git 2.50.1
   (Apple Git-155).]
2. **`ls-files -v` alone is NOT sufficient.** Two further shapes reach status=CLEAN,
   `git worktree remove` rc=0, content destroyed, with `ls-files -v` reporting `H-only`:
   `status.showUntrackedFiles=no` (shape H, 56 bytes lost) and gitignored content
   (shape G, 35 bytes lost). Shape H is **closed here**; shape G is **not**, deliberately,
   and the reasoning is below and in the code. [VERIFIED: `evidence/10-taxonomy.txt`.]

### 1. `.softhouse/bin/fire-program.sh` — the fix (+213 / −5)

**a. New function `wt_prune_blindspot_check()`**, top level, between
`reconcile_tasks_json()` and `run_exit_guard()`, delimited by the literal markers
`T324-PRUNE-BLINDSPOT-GUARD BEGIN` / `... END` so instrument 20 can extract and drive
**the shipped bytes** rather than a copy of them.

- **TERM 1 — `git -C "$W" ls-files -v -- ':(top)'`; REFUSE if any entry's tag is not `H`.**
  This is the only genuinely independent term in the chain: it reads *the index bits
  themselves*, i.e. the state that switches git's working-tree comparison off. A term
  cannot be silenced by the mechanism it is looking at.
- **TERM 2 — `git -C "$W" status --porcelain -uall -- ':(top)'`; REFUSE if non-empty.**
  Not a restatement of `wt_prune_check` rule 2: worktree-set
  `status.showUntrackedFiles=no` makes a bare `--porcelain` report CLEAN with live
  untracked files present, and `git worktree remove` inherits it. `-uall` is a
  command-line override and is immune.
  `git -c status.showUntrackedFiles=normal` was measured to work equally well and was
  **deliberately not stacked on top** — it defends the same threat by the same mechanism
  (config precedence), so the pair would be one term wearing two hats, which is the exact
  error this task exists to name.
- Fail-closed on every git failure: an unreadable index is never read as an unmarked one.
  No pipeline in the load-bearing path (T190's rule in this file: under
  `set -uo pipefail` without `-e`, a pipeline reports the rightmost status, so
  *git-broke* and *nothing-found* become byte-identical); the tag filtering uses the zsh
  array subscript `${LINES:#H *}`.

**b. The call site** now asks TERM 1/TERM 2 **after** a PRUNE verdict and **before**
`git worktree remove`. On refusal it folds into the existing verdict variables so the
single `keep:` line reports it once, prefixed `T324 BLIND-SPOT OVERRIDE (wt_prune_check
said PRUNE)` — the disagreement between two checks is the fact worth logging, and a silent
downgrade would hide it.

**c. The false claim is corrected in place, at the comment that made it.** The old text
said `git worktree remove` "is itself a **THIRD, independent** clean check". It is a third
check; it is **not an independent one**. It asks git to compare working tree against
index — the same question, of the same oracle, as `wt_prune_check` rule 2 — and a skip bit
moves no ref, no HEAD, no config and no commit, so rule 1 cannot see it either.
**One bit blinds all three simultaneously.** The comment now says so, and says why that is
*worse* than having one check: three checks that fail independently agree only by
coincidence, so their agreement is evidence; three checks sharing an oracle agree by
construction, and their agreement gets read as corroboration when it is only repetition.
The redundancy added confidence it had not earned, and the confidence is what let the
removal proceed. `git worktree remove` is still called without `--force` and is still
worth having — it is the term that catches a plain untracked file and a worktree locked
between the check and the call (instrument 10 shape F, instrument 20 R5) — it is simply
not a second opinion about a tree git has been told to stop looking at.

**Shape E is flagged on purpose and the reason is a race, not tolerance of a false
positive.** TERM 1 keys on **the bit**, never on whether a difference happens to exist at
the instant it looks. Once the bit is set git has been told to stop comparing that path,
so a write can land between this check and the `git worktree remove` that follows it and
nothing in git will report it. A version of TERM 1 that asked *"is it modified yet?"*
would have to ask the very oracle the bit switched off — the whole defect restated one
layer down. The instrument scores E as PASS-when-flagged and **FAILS if the flag ever
disappears**, because that would mean TERM 1 had become content-dependent and racy.

## Direction: why fail-closed, and why it is not fail-closed-everywhere

Refusing to prune a worktree that was in fact disposable costs a directory on disk and a
reader's patience, and the next fire re-evaluates it. Pruning one that was not destroys
work that exists in **no ref, no reflog, no stash and no remote**. The two errors differ
by orders of magnitude **and by reversibility**, so this is not a symmetric tie and it
breaks toward KEEP.

**T319's counter-consideration is honoured, not waved at.** Its F3a note rejects a repair
that would *"replace a fail-OPEN with a permanent fail-CLOSED, which is the failure T288
exists to remove"*, and `patterns.md:66` records what inert cleanup produced: *"On 21 Aug
2026 the tree held 121 worktrees / 12 GB"*. A prune check that refuses everything has
traded a rare catastrophe for a permanent one. So the refusal here is **narrow by
construction** — it fires only on evidence that git's comparison has been switched off, or
that something untracked is really there — and its cost is **measured** (0 of 55), not
asserted, with a control row (R6) that proves the chain still prunes.
