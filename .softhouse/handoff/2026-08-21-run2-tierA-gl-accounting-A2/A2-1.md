## What I established

**The mapping-resolution order (priority 3 of the brief, the highest-value output).** Traced end to
end in `fineract-provider/.../journalentry/service/AccountingProcessorHelper.java` — note that this
code is in **A1's** package, not in any of A2's four scope paths; A2 owns the storage and the finder
queries only. Four steps: a pre-emptive **financial-activity branch** when the placeholder id is one
of `{100,101,102,103,200,201,300}` (`:1187`, `:1340-1342`), which ignores the product entirely; then
the **core row** keyed on `(product_id, product_type, financial_account_type)` with all six
discriminator columns NULL (`ProductToGLAccountMappingRepository.java:38-40`); then a
**payment-type override** applied only when the placeholder is the family's fund-source/reference
placeholder — value 1 in all three families (`:1199`, `:1285`, `:1309`); then the miss. Charges are a
separate entry point with **three different precedence chains** across loan / savings / shares, and
savings uniquely lets the `m_charge` row's own GL account outrank every mapping (`:1255-1258`).
Reason and classification mappings bypass the core row entirely and ignore `financial_account_type`
(`:194-208`). Full trace, tables and one-paragraph summary in §4 of the document.

**The GL account tree (priority 1).** Hierarchy construction and its exact string shape with a worked
example; the two-flush create sequence; the fact that re-parenting does **not** cascade to
descendants; that `hierarchy` drives only display indentation and **no money decision anywhere**; and
a complete refusal table — 14 create refusals, 9 update, 4 delete — each with its error code and
`FILE:LINE`. Established that update evaluates U3/U4 **before** loading the account, so a request
against a non-existent id reports the wrong error; that is observable and vector-worthy.

**Enums as persisted (priority 2).** Every persisted value is the enum's own `getValue()`; there is no
`ordinal()` call anywhere in the four scope paths or in `AccountingConstants.java`. Tabulated
`GLAccountType` (1–5), `GLAccountUsage` (DETAIL 1 / HEADER 2), `FinancialActivity` (100/101/102/103/
200/201/300 — declaration order deliberately not value order), and all five placeholder enums.

**Financial activity accounts (priority 4).** Table, single-column unique constraint on
`financial_activity_type`, tenant-global with no office dimension, the type-pairing validation, and
a clean create/update asymmetry.

**The two money questions the brief called out.**

- *Sign convention:* **A2 does not fix one, and I said so plainly.** No table in the slice carries a
  sign or normal-balance flag, and nothing derives one from `GLAccountType`. The only sign the slice
  *consumes* is the trial balance's, defined in A1's `JournalEntryRepository.java:52-66` +
  `JournalEntryType.java:23-24` (CREDIT=1 negated, DEBIT=2 positive). A1 must re-derive it from
  those files, not from my document.
- *`BigDecimal`:* exhaustive grep. **Zero `BigDecimal` and zero floating-point in
  `producttoaccountmapping`, `financialactivityaccount` and `productaccountmapping`.** Every hit is
  in the trial-balance code: `TrialBalance.amount` and `TrialBalance.closingBalance`, both with **no
  `precision`/`scale` on the annotation**, both persisting to `DECIMAL(19,6) NOT NULL`
  (`0001_initial_schema.xml:4669-4678`). And `m_trial_balance.closing_balance` is a **written stored
  balance** — in direct tension with our derived-balances non-negotiable. Flagged as decision D-9.

## Findings a reviewer should attack first (highest value, highest risk if I'm wrong)

1. **`PortfolioProductType.fromInt` permutes 3/4/5 relative to `getValue()`.** Declared
   `CLIENT(5), PROVISIONING(3), SHARES(4)` at `PortfolioProductType.java:26-31`; `fromInt` maps
   `3→CLIENT, 4→PROVISIONING, 5→SHARES` at `:51-59`. Writes use `getValue()` so storage/retrieval is
   self-consistent and posting is unaffected — but a port that transcribes `fromInt` inherits an
   off-by-permutation bug on shares.
2. **`CashAccountsForLoan` and `AccrualAccountsForLoan` collide at 22, 24 and 25 with different
   meanings**, and cash puts receivables at 25/26 where accrual puts them at 8/9. So a stored
   `financial_account_type` is **not decidable from the row alone** — you need the product's
   accounting rule. A Go schema modelling it as one enum is already wrong.
3. **The `financial_action` unique constraint does not exist in the database.** It is a JPA
   `@UniqueConstraint` (`ProductToGLAccountMapping.java:42-43`) with **zero** occurrences in
   `fineract-provider/src/main/resources/db/` (my own grep, re-run independently of the subagent that
   first found it). Duplicate mapping rows are physically possible.
4. **Share product create writes advanced mappings under the wrong `product_type`.**
   `ProductToGLAccountMappingWritePlatformServiceImpl.java:386-387` calls the **savings** helper,
   which hard-wires `PortfolioProductType.SAVING` (`SavingsProductToGLAccountMappingHelper.java:113,
   :124-125`), while the update path uses the shares helper. This one is source-derived, **not
   observed** — see the UNVERIFIED list.
5. **Savings and shares resolution has no null check** before `accountMapping.getGlAccount()`
   (`:1293`, `:1317`, and all three charge paths). A missing mapping is an NPE, not a typed
   not-found. Only loans and working-capital loans raise
   `ProductToGLAccountMappingNotFoundException`.

## What I marked `[UNVERIFIED]`, and why

Twelve items, §11 of the document. The reason in every case is that the pinned source cannot settle
it — never that I ran out of budget. Grouped:

- **Needs a live PostgreSQL / running oracle (5 items).** The literal type of
  `acc_gl_account.account_usage` (declared `TINYINT`, which Postgres lacks — the mapping is inside
  the Liquibase library); the auto-generated constraint names; **which error code a duplicate
  `glCode` and a duplicate financial-activity row actually return** (both handlers substring-match a
  constraint name the DDL never assigns — these decide two contract refusal codes and are the
  cheapest, highest-value captures this slice produces); whether
  `GET /glaccounts?searchParam=x` errors, since `GLAccountReadPlatformServiceImpl.java:154` emits the
  literal `%?%`; the `rs.wasNull()` mis-ordering at `:98-99`.
- **Needs a trace outside the four scope paths (4 items).** Where
  `manual_journal_entries_allowed` is enforced (nothing in scope reads it); whether anything forbids
  posting to a HEADER account (nothing in scope does); what the four reason/classification finders'
  callers do with `null`; whether `PortfolioProductType.fromInt` is ever reached with a stored 3/4/5
  via its two call sites.
- **Reachability, not existence (2 items).** The two `fromInt(...).toString()` NPEs inside the
  not-found exception messages (`:1210`, `:1026`) — the null return is proven, the reachability is
  not. And the DDL default `account_usage = 2`, which every code path should shadow.
- **Derived but not observed (1 item).** The share-product `product_type` mis-filing above.

I also **withdrew** one over-strong sentence during the correction pass: I had asserted flatly that

## Backlog (§12 — nothing outside scope was modified, only read)

Nine items. The three that change how the program should be planned:

- **B-1 — the slice's own core types are not in the slice.** `GLAccount`, `GLAccountType`,
  `GLAccountUsage`, `GLAccountData`, `GLAccountJsonInputParams`, `AccountingConstants` and
  `PortfolioProductType` all live in **`fineract-core`**, under the same Java package names. And
  `LoanProductToGLAccountMappingHelper` lives in **`fineract-loan`** in a **split package** shared
  with `fineract-provider`. **A Go package boundary drawn on the Fineract directory boundary leaves
  A2 with no account entity and no enums** — it must be drawn on the Java package, which spans four
  Gradle modules. This has an obvious knock-on for how `program.json` scopes future slices.
- **B-3 — the resolver is duplicated four times in `AccountingProcessorHelper` with three different
  miss behaviours and three different charge-precedence chains**, plus a fifth partial copy in
  `fineract-investor`'s `InvestorAccountingHelper.java:92, :123`. A single parameterised Go resolver
  is the obvious shape, but unifying them **changes behaviour** — it must be a recorded decision.
- **B-5 — Fineract ships no default chart of accounts.** Zero rows inserted into `acc_gl_account` by
  `0002_initial_data.xml` / `0003_postgresql_specific_initial_data.xml`; the only mentions are report
  parameter SQL. A Mongolian NBFI / FRC-aligned COA is therefore a **product decision to be made**,
  with nothing upstream to reconcile against. Per CLAUDE.md's answering gates that is a PRODUCT gate
  the driver decides, not a RESERVED one.

Remaining: B-2 (A1/A2 ownership of the resolution path), B-4 (`DECIMAL(19,6)` vs MNT minor unit 2 —
one program-level decision, not one per slice), B-6 (no index on `acc_product_mapping.gl_account_id`
despite the disable-check scanning it), B-7 (no index on `hierarchy`), B-8
(`write_off_reason_id` added with no FK and a mismatched width), B-9 (`m_charge`'s own GL account is a
precedence level shared with the charge context).
