## The defect, restated

T169 found that running `build_harness_t159.py` into a mirrored scratch tree emits the seam-call
handler as `catch (RuntimeException e) { ... e.printStackTrace(System.err); ... }` — the shape it
copies unmodified from the committed `CaptureT100.java` — while the **committed**

source template, 474/489 of the committed output) were applied **by hand** after generation and
never folded back into the generator. So the generator did not reproduce the artefact it is
supposed to produce.

## Which outcome and why

**Outcome 1 — the hand hunks were correct; the generator was fixed to emit them.** Not outcome 2
(committed Java is wrong). Reasoning:

- `java.lang.StackOverflowError` is a `java.lang.Error`, not a `RuntimeException`. The *original*
  handler (`catch (RuntimeException e)`) cannot catch it at all — it would propagate, uncaught,
  out of `run()` and out of `main()`, killing the JVM before a byte of JSON is printed. T159's own
  `WHY THIS PASS EXISTS` paragraph (unchanged by this task, still emitted verbatim by the
  generator) states the pass exists to probe the region **above n = 1000** — and T169 later showed
  (`.softhouse/handoff/2026-08-21-run2-tierA-gl-accounting-A2/T169.md`) that this is exactly the
  region where the reference oracle's `ProgressiveEMICalculator` can `StackOverflowError`. A
  handler that cannot catch the one failure mode the pass exists to probe would defeat the pass's
  own purpose. Catching `Throwable` is therefore not an incidental hardening — it is required for
  T159 to be able to do what it says it does.
- `run-t159.sh` (`.softhouse/capture/t159-review-t117/src/run-t159.sh:67`, unchanged by this task)
  refuses any run whose stderr is non-empty (`[ -s "$ERR" ] && { printf 'RUN FAILED: stderr NOT
  empty:\n' ...; exit 1; }`). Under the *original* `e.printStackTrace(System.err)` line, a single
  cell throwing would write to stderr and cause `run-t159.sh` to refuse the **entire** sweep — so
  a throwing cell could never be recorded as data, only as a rig failure. The committed code keeps
  the frames in `errorStackTop` (already part of the JSON payload the un-hand-edited code emits)
  and never touches stderr — exactly the behavior `run-t159.sh`'s own refusal rule requires of a
  probe that expects some cells to throw.

Both hand hunks are therefore **necessary for T159 to function as designed**, not defects in the
committed evidence. T169's own handoff independently reaches the same conclusion ("T159 applied
its two hunks by hand afterwards... Nothing T159 reported is affected... the builder is not a
reproduction of the harness"). This task closes that gap: the generator now emits the artefact
T159 committed, mechanically, from its own committed inputs (`CaptureT100.java` and
`/tmp/t159-cases.java`, the latter shown byte-reproducible from the committed
`gencases_t159.py` — see next section).

No committed `CaptureT159.java` byte was changed. The prohibition against repairing the evidence
to fit the tool was not violated because the tool needed no such repair to be made to fit — it
needed a repair to fit the evidence, which is what outcome 1 is.
