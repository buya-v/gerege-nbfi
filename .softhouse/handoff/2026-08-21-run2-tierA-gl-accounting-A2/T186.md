## The ruling (a) / (b) / (c)

The non-negotiable and Fineract's REST API do **not** conflict — they are about different objects.
The non-negotiable governs **the numbers Gerege owns**. The capture wire carries **the oracle's
numbers in the oracle's own shape**, and a capture that reshaped them would stop being an
observation.

**(a) The oracle-facing capture wire — major-unit decimal is ADMISSIBLE and in fact MANDATORY.**
Fineract reads `principal` as a major-unit decimal. Sending `116250250` instead of `1162502.5`
would not "comply" — it would ask the oracle about a MNT 116,250,250 loan and label the answer as a
MNT 1,162,502.50 one. The non-negotiable is not suspended; it binds as a **byte-fidelity**
obligation (the bytes must be exactly the decimal intended, and must not have passed through a float
on our side) rather than a **representation** obligation.

**(b) The Go module's own adapter/API surface — BINDS ABSOLUTELY, no exception.** Already ratified,
not new: `contract.go:120-121` ("no float32, float64, big.Float, decimal string or float-backed"),
`contract.go:219` ("a float rate is prohibited on any money path"), and DEC-1:829 — *"the doubles in
the Java source are an artefact of the reference implementation, never a licence to introduce one
here."* Corollary this task exists to close: finding a `double` in Fineract is **never** a licence to
introduce one in Go. Reproduce the oracle's observed **output**; never import its arithmetic **type**.

**(c) The stored vector — REJECTION, and it is already clean.**
**`.softhouse/vectors` = 50 JSON files, exactly ZERO float-typed JSON tokens of any kind.**
Money is a JSON string of integer minor units (`"principal_minor": "116250250"`), the oracle's own
characters ride alongside as a string cross-check (`"principal_major_text": "1162502.50"`), and rates
are exact rationals.

**A fourth category the trichotomy does not name:** the **response** leg. 9 of the 38 files are
oracle responses carrying `"principal":1200000.000000`. They are observations, equally unamendable,
and their scale-6 form is itself information (it witnesses `DECIMAL(19,6)`).

**T173's choice, re-justified upward.** T173 called byte-preservation "the weaker, defensible
property." It is in fact **the exactly correct property** — see the next section.

## Fineract's declared wire type, with source citations

**The declared type is `BigDecimal`, and the JSON-number branch parses the ORIGINAL TOKEN TEXT.**
Re-verified by hand, not taken on the sub-agent's report:

- Resource method takes a **raw `String`** body, so Jackson never sees the numbers
  [VERIFIED: `LoansApiResource.java:570-572`; `JerseyJacksonObjectArgumentHandler.java:62-63`].
- `if (primitive.isNumber()) { value = primitive.getAsBigDecimal(); }`
  [VERIFIED: `JsonParserHelper.java:151-152`] — **not** `getAsDouble()`.
- `BigDecimal` at every layer: `LoanScheduleAssembler.java:267` / `:252`,
  `LoanApplicationValidator.java:637-638`, entity `LoanProductRelatedDetail.java:61-62` / `:64-65`
  (`scale = 6, precision = 19`), DDL `DECIMAL(19, 6)` [`0001_initial_schema.xml:2040`, `:3117`],
  Swagger `LoansApiResourceSwagger.java:1343` / `:1357`.
- Gson is a bare `new Gson()` with **no** BigDecimal/Double/Number adapter registered anywhere
  [VERIFIED: `FromJsonHelper.java:57-60`; `GoogleGsonSerializerHelper.java:105-115`], pinned at
  `gson:2.14.0` [VERIFIED: `…dependencies.gradle:55`].

**This matters exactly as the task said it would.** A `BigDecimal` parsed from a JSON number literal
is a far weaker exposure than a `double` — which makes the whole loans corpus safe.

### Two findings that invert the intuition

**1. Quoting a money value would move it ONTO a `double` path, not off one.**
A **quoted** value takes the `else` branch [`JsonParserHelper.java:154-157`] into `convertFrom`,
which ends `else { number = BigDecimal.valueOf(parsedNumber.doubleValue()); }`
[VERIFIED: `JsonParserHelper.java:732-738`, the `doubleValue()` at `:737`]. It also makes `locale`
mandatory [VERIFIED: `:704-715`]. The naive "fix" for a JSON float is the dangerous form.

**2. There IS one genuine `double` on a Fineract request path — `POST /charges`.**
`private Double amount;` [VERIFIED: `ChargeRequest.java:41`], and unlike `PostLoansRequest` this DTO
is **actually deserialized**, because the resource method declares the DTO type rather than `String`
[VERIFIED: `ChargesApiResource.java:139-142`], with `USE_BIG_DECIMAL_FOR_FLOATS` not enabled
[VERIFIED: `JerseyJacksonConverterConfig.java:48-54`]. `minCap`/`maxCap` on the same class are
`BigDecimal` — it is an inconsistency in one DTO, not a design.

> **This is why T173's guard property is the right one.** A value survives the
> Jackson→`double`→Gson→`getAsBigDecimal()` chain **exactly iff** its token text is already the
> shortest round-trip repr of its double — which is precisely `repr(float(tok)) == tok`, T173's
> property. It is the **necessary and sufficient** condition, not a convenient weaker one.

Two further oracle `double` sites, downstream of the wire, recorded as porter's hazards:
`LoanProductRelatedDetail.java:344-346` (the rate getter launders `BigDecimal` through
`Double.parseDouble` on every read) and `FinanicalFunctions.java:44-55` (the `pmt` EMI kernel).

`MoneyHelper.PRECISION = 19` [VERIFIED: `:34`] and `new MathContext(PRECISION, getRoundingMode())`
[VERIFIED: `:89-92`] re-confirmed.

## Dyadic analysis: which tokens do NOT round-trip

**Not overstating it:** `1162502.5` major = `116250250` MNT minor **exactly**, and `0.5` is dyadic,
so it round-trips a binary double byte-identically. **The defect, if any, is REPRESENTATIONAL, not a
measured arithmetic error.** Nothing measured here is an arithmetic error.

Three properties, kept apart — conflating them is how this stayed open:
**P1** exactly representable as binary64 · **P2** bytes preserved (`repr(float(t))==t`, T173's guard)
· **P3** value preserved through a double.

### Request bodies — T173's derived set reproduced digit for digit

320 request bodies, 0 unparseable, 221 carrying a float-shaped token: **214 `interestRatePerPeriod`,
53 `amount`, 11 `principal`.** Those 278 occurrences are **only 15 distinct tokens**:

| non-dyadic (9) | `0.001875` `0.009375` `0.021875` `0.1` `1.2345` **`21.6`** `333.33` `7777.77` `12345.67` |
|---|---|
| **exactly binary64 (6)** | `0.5` `1.25` `2.5` `3.75` `12.0` **`1162502.5`** |

- **Which are NOT dyadic? Nine of fifteen — including `21.6`, which is 211 of the 214 rate tokens.**
  So the great majority of rate tokens are non-dyadic, and `1162502.5` — the flagged one — is **not**.
- **Is any a value where a double round-trip would change the bytes the oracle received? NO — zero,
  across the entire request corpus.** Each of the nine is already the shortest round-trip repr of its
  nearest double. **The guard is green for a reason, not by luck.**

### Where the `amount` tokens actually go — the decisive split

- **7** are `POST /charges` bodies → `ChargeRequest.amount`, a real Java `Double`. Values `1.2345`×4,
  `3.75`×2, `0.5`×1 — and **all 7 carry `chargeCalculationType` ∈ {2,3,4}**, i.e. percentages.
- **46** are `charges[].amount` nested in a loan body → the `String` path → `getAsBigDecimal()`.

> **ZERO money-valued tokens in the corpus traverse Fineract's `Double`. All seven that do are
> PERCENTAGES**, and the one non-dyadic among them (`1.2345`) is byte-stable, so even that is lossless.

### Whole corpus, including responses

| | distinct | occurrences | P1 fail | P2 fail | **P3 fail** |
|---|---|---|---|---|---|
| MONEY | 1,539 | 70,594 | 1,372 | 235 | **0** |
| RATE | 4 | 321 | 2 | 2 | **0** |
| OTHER | 427 | 612 | 409 | 8 | **0** |

**All 245 P2 failures are trailing-zero forms** (`1200000.000000`→`1200000.0`, `21.600000`→`21.6`) —
Fineract's own scale-6 emissions on the **response** leg. Value intact in every one; only scale would
be lost.

### Headroom — the honest reason P3 is zero

Binary64 loses decimal **value** above 17 significant digits. **MONEY tokens: max 10 significant
digits, max scale 6. RATE tokens: max 3.** The only 17-sig-digit tokens in the tree are `gap_float` /
`*_display_only_float` analysis diagnostics in exactly two files. **The margin is ~7 orders of
magnitude — enormous, not marginal.** That is also why P3 must **not** become the guard property: it
would pass a corpus that had already drifted badly, right up until it didn't.

### Does the non-negotiable bind a rate?

**A rate is not money**, so the non-negotiable's letter (*"no floating-point in any **monetary** code
path…"*) does not reach `interestRatePerPeriod`. It binds by two other routes to the same end:
**P-25** (the rule binds anything whose output reasons about money — a rate multiplies a principal),
and **`contract.go:219` already rules explicitly**: *"a float rate is prohibited on any money path"*,
with `Rate{Numerator, Denominator int64}` [`contract.go:230-233`]. Wire `21.6`, vector `{27, 125}` —
already correct.

**Method (P-25):** all arithmetic exact via `Fraction`/`Decimal`; the single `float()` **simulates**
the defect and every conclusion compares strings or `Decimal`s. Detection via
`json.load(..., parse_float=hook)` on original token text, never a regex (P-48 rule 1).

## The enforcement boundary, mechanically stated

**Path decides the rule.**

**Zone A — `.softhouse/capture/**` (oracle-facing wire).** Float-shaped major-unit money tokens
**ADMISSIBLE**. Enforce instead:
- **A1** byte preservation (P2) on every request body — **already implemented and wired**:
  `.softhouse/capture/lib/check_wire_float_roundtrip.py` from `conformance.sh:784`.
- **A2** a blanket "no float-shaped token in a request body" rule is **WRONG** and must be rejected
  in review — it refuses 221 of 320 bodies and pins `conformance.sh` at exit 2.
- **A3** never quote a money value to avoid a JSON float (it moves it onto `:737`'s `doubleValue()`).
- **A4** responses are observations — never rewrite, re-emit through a float, or normalise scale.

**Zone B — `nexus/**`.** Any float type on a money/rate path is a **REJECTION**. Money `int64` minor
units; rates `Rate{Numerator, Denominator int64}`. Mechanical test: reject a diff where `float32`,
`float64`, `big.Float` or a float-backed decimal shares a declaration/field/signature/expression with
a money or rate identifier.

**Zone C — `.softhouse/vectors/**`.** A float-typed JSON token of **any** kind is a **REJECTION**.
Total test, no key list needed (current count is zero):
`json.load(path, parse_float=<hook that raises>)` — any hit rejects.

> **One line:** *a float-shaped money token is admissible exactly where it is a faithful transcription
> of bytes the ORACLE defined, and is a rejection everywhere GEREGE defines the bytes.*

## What I did NOT establish

1. **Gson 2.14.0's `getAsBigDecimal()` internals — UNVERIFIED against source.** No Gson jar or source
   on this host. The loans path's freedom from `double` rests on library behaviour for its final
   link; everything upstream is verified from repo source.
2. **Spring's `NumberStyleFormatter.parse` return type — UNVERIFIED.** So whether
   `JsonParserHelper.java:737`'s `doubleValue()` is **reachable** is **open**. The line's existence is
   verified; its reachability is not. Latent, not live, since our corpus sends unquoted numbers.
3. **No live-oracle experiment.** I did not POST `1162502.5` vs `"1162502.5"` and diff. That would
   settle 1 and 2 empirically.
4. **29 of 749 capture `*.json` were not parsed** (concatenated/NDJSON raw transcripts). Every
   corpus-wide count excludes them. I did **not** verify they contain no value-losing token.
5. **44 of 53 `amount` tokens have unresolvable `chargeCalculationType`** (a loan-attached charge
   carries only `chargeId`). My money-vs-percentage split for those 44 rests on **magnitude
   inference, not verified type.** The 7 `POST /charges` bodies are verified.
6. **I did not sweep the `capture-prod3*` request generation.** Those bodies are produced inline by
   `src/run-pass3*.sh`, not committed under `req/`, so they are outside both T173's derived set and
   my census — and **42 of the 43 parity vectors descend from them.** Largest coverage gap here.
7. **No claim about arithmetic correctness of any vector.** Representation and transit fidelity only.
