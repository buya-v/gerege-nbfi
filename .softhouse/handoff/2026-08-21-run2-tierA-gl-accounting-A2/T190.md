Three decisions, each of which I re-derived rather than inherited:

**1. The PIPELINE had to go, not just the `|| true`.** This is stronger than T189 argued and it is the
core of the fix. Under `set -uo pipefail` without `-e` [VERIFIED: `fire-program.sh:17`], when git fails
it prints nothing, so the filter selects nothing and exits 1, and **zsh's pipefail reports the
rightmost non-zero status** — so the pipeline returns **1**, which is *byte-identical to what a
genuinely clean tree produces* (clean tree → git rc=0, no output → filter rc=1 → pipeline rc=1).

```
$ /bin/zsh -c 'set -uo pipefail; sh -c "exit 128" | sh -c "cat >/dev/null; exit 1"
                print "pipeline rc=$? pipestatus=${pipestatus[*]}"'
pipeline rc=1 pipestatus=128 1

$ /bin/zsh -c 'set -uo pipefail; V=$(sh -c "exit 128" | LC_ALL=C /usr/bin/grep -av "^?? x$"); print "V=[$V] rc=$?"'
V=[] rc=1
```
[VERIFIED: run above, zsh 5.9 arm64-apple-darwin25.0.] **Consequence: simply deleting `|| true` and
testing `$?` would NOT have closed the fail-open** — rc=1 cannot distinguish "git broke" from "clean".
Only removing the pipeline exposes git's own 128. A reviewer should check this, because it is the
argument that makes the minimal-looking alternative wrong.

**2. `:(top)`, not T189's `-- .` — T189's exact pathspec form has a cwd-dependent fail-open of its
own.** T189 proposed `git status --porcelain -- . ':(exclude).softhouse/LOCK'` and drove it from the
repo root only. Measured from a subdirectory of the same tree:

| form | from repo root | from `some/other/` |
|---|---|---|
| **F1** `-- . ':(exclude).softhouse/LOCK'` (T189's) | correct 3 lines | **silently drops everything outside cwd** — `?? .softhouse/LOCKED_STATE.md` vanishes |
| **F2** `-- ':(exclude).softhouse/LOCK'` (exclusions only) | correct 3 lines | **LOCK exclusion stops working** — `?? .softhouse/LOCK` and `D  .softhouse/LOCK` reappear (the exclusion is resolved relative to cwd) |
| **F3** `-- ':(top)' ':(top,exclude).softhouse/LOCK'` (**adopted**) | correct 3 lines | **identical** to root |

below.] In production cwd *is* the repo root [VERIFIED: `cd "$REPO" || { … exit 1; }` at

## Blast radius — why this cannot break the running fire

**This edit takes effect on the NEXT fire, not this one.** `fire-program.sh` is the wrapper that
launched the fire I am running inside. A running shell reads its script from the **already-open file
descriptor / inode** it was started with; my edit is a new write to the path in an isolated worktree,
which is not even the same file as `/Users/buv/gerege-nbfi/.softhouse/bin/fire-program.sh`. Two layers
of separation therefore:

1. **Worktree isolation.** I edited
   `/Users/buv/gerege-nbfi/.claude/worktrees/agent-a73424a6001f745ae/.softhouse/bin/fire-program.sh`.
   The live wrapper is at `/Users/buv/gerege-nbfi/.softhouse/bin/fire-program.sh` and is **untouched**.
   Until the orchestrator merges this branch to `main`, the live path does not change at all.
2. **Inode/fd semantics.** Even after the merge writes the live path, the *currently executing* zsh
   keeps reading the bytes it already has. The running fire will finish its chain loop, run the **old**
   `run_exit_guard`, and release its lock with the **old** `release_lock`. The new guard first executes
   on the next launchd fire (08:00/11:00/14:00/17:00/20:00/23:00 per the plist).

**So the worst case of a mistake here is a fire that fails at start, not a fire that loses work
mid-flight** — and `zsh -n` rc=0 plus a successful `--probe` (below) exclude the parse-error class.

**What the merger must know:** the merge itself is safe at any time; the *behaviour* change lands at
the next fire boundary. Nothing in this diff touches the lock protocol, the chain loop, exit codes, the
driver prompt, or the worktree sweep.
