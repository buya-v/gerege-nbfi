## Changes Made

All in `.softhouse/handoff/T61-mutations.py` (306 → 495 lines; pre-fix blob
`394dbeddec49044a95d8369ba73288aead77b3f9d904201712baf8ba3e500b5c` at commit `60109a4`,
which is what my throwaway clone's HEAD held before any edit — see "Restore shape reused"
for why that made a separate sibling-file trick unnecessary here).

* **`_install_signal_traps()`** — `signal.signal(signal.SIGTERM, _handler)` and
  `signal.signal(signal.SIGHUP, _handler)`, where `_handler` raises `_Signalled(signum)`, a
  `BaseException` subclass. CPython's default disposition for SIGTERM and SIGHUP is
  immediate termination with **no** Python bytecode running and **no** `finally` firing;
  installing a handler that raises turns both into ordinary Python exceptions that the
  pre-existing `try/finally` in `main()`'s mutation loop already knows how to unwind
  through. `_Signalled` is a `BaseException`, not `Exception`, on purpose: an
  `except Exception` added anywhere else in this file later must not accidentally swallow
  it and skip the restore. **SIGINT was already covered before this task** — CPython turns
  it into `KeyboardInterrupt`, which the existing `finally` already caught — and I did not
  add a redundant explicit handler for it; see "The BENIGN classification, re-checked"
  below for the empirical check of that claim, not just the reasoning. SIGKILL and SIGSTOP
  cannot be trapped by any process; there is no handler for either, by design — see the
  start-up mechanism instead.
* **`_write_marker(mid, originals)`** — called **before** any mutation is written, for
  every mutation, not only the ones that later get interrupted. For each path it pins the
  file's *current, pre-mutation* bytes into the git object store with
  `git hash-object -w --stdin` (content-addressed: pinning the same bytes twice is a no-op)
  and records `{path: {blob, sha256}}` plus the mutation id in
  `.softhouse/handoff/.t61-mutation-inprogress.json`, written atomically
  (`.tmp` + `fsync` + `os.replace`). This is the ORIGINAL working-tree bytes at mutation
  time, not `git show HEAD:path` — a locally-modified `rounding.go` (uncommitted before the
  script even ran) would be pinned and restored exactly, not silently reverted to HEAD.
* **`_recover_startup()`** — runs as the **first** thing `main()` does, before the baseline
  conformance call. If the marker exists, for each path it: (1) checks whether the file is
  *already* at the recorded bytes and, if so, says so plainly ("nothing to restore") rather
  than claiming a repair that didn't happen; (2) otherwise verifies the named blob exists
  in the object store and hashes to the recorded sha256, and only then restores it, with a
  `RECOVERED: …` message naming the mutation, the path, the digest and the blob. Two ways
  it can fail are both **fail-closed**: an unreadable/malformed marker, or one naming a
  blob that's absent or that doesn't hash to what was recorded — both `SystemExit(1)`,
  marker left in place, file left untouched, "repair by hand" printed. An empty `files`
  dict in the marker is also refused (P-40: an empty census is a refusal, not a pass).
* **`_write_verified(path, text)`** — every write (the mutation loop's restore, and
  start-up recovery's restore) is followed by a re-read and a byte comparison; a write that
  "succeeds" but doesn't land raises rather than being trusted.
* **The mutation loop's `finally`** now: writes each original back through
  `_write_verified`, tracks whether *all* paths verified, and clears the marker **only**
  if every path did. A partial restore leaves the marker in place so the *next*
  invocation's start-up check still catches it, instead of reporting false confidence.
* **`if __name__ == "__main__":`** now catches `_Signalled` and `KeyboardInterrupt` at the
  top level and translates them to the conventional `128+signo` exit code (`143` for
  SIGTERM, `129` for SIGHUP, `130` for SIGINT) — the restore itself already happened inside
  the `finally` by the time control reaches here; this only sets the process's own exit
  status honestly.

Money-literal note: the only `json.load`/`json.dump` in the new code is the marker file,
whose schema is `{"mid": "<str>", "files": {"<path>": {"blob": "<hex>", "sha256": "<hex>"}}}`
— no numeric field, no money value, nothing `parse_float` would touch.
[VERIFIED: `grep -n "json\." .softhouse/handoff/T61-mutations.py` — both call sites read;
schema has no numeric field]

## Restore shape reused (and any divergence)

Reused from **T161** (`.softhouse/capture/pathb/t80/prove-f1.sh`, same fire): trap-and-exit
signal handling that funnels into one restore path; the restore is **verified**, not
assumed; **start-up recovery** for the SIGKILL case, checked before anything else runs;
the restore source is an **immutable git blob**, pinned into the object store rather than
kept as a plain dotfile copy that a stray `rm -rf` could take with it; idempotent restores
that say honestly when there was nothing to restore; and **fail-closed** refusal — never
guess bytes — when the marker can't be verified.

**Divergences, and why, for the driver to reconcile against T168/T180:**

1. **No "background + `wait`" restructuring.** T161's shell script had to background the
   attester and `wait` it, because bash defers a trapped signal until the current
   *foreground* child finishes — measured there as 8.8 s of pure deferral. I measured the
   equivalent case here (signal delivered while `subprocess.run(conformance.sh)` — a
   foreground child from Python's point of view — was in progress) and found **no**
   deferral to work around: 0.052 s from signal to restored-and-exited. This is a genuine
   CPython/bash difference (CPython's signal-checking loop interrupts a blocked
   `waitpid` promptly; POSIX shell job control does not), not a shortcut — I looked for the
   deferral before deciding not to build around it. [VERIFIED: `/tmp/t162/timing.log`]
2. **`_pin_blob` always calls `git hash-object -w`, unconditionally**, rather than T161's
   "reuse the index blob if the file is clean, else pin" branch. Since git blobs are
   content-addressed, pinning bytes that already match an existing object is a no-op (git
   deduplicates), so the unconditional form is behaviourally identical to T161's branch but
   simpler. Not forced on me — a simplification I chose; flagging it in case a reconciled,
   single shared helper (if the driver wants one) should pick T161's explicit-branch form
   instead.
3. **No directory-wide census.** T161's target (`t36/out/emiloop`) is a directory of
   captured evidence with an open-ended file set, so it needed a whole-tree census
   (path + size of every file) to detect collateral damage. My target is exactly two named
   Go files, enumerated by the `patches` list that defines the mutation — a census over a
   two-element, statically-known set would be redundant with the per-file verified
   read-back I already do. If T168/T180 also target a small, statically-known file set,
   the same simplification likely applies; if either targets an open-ended directory, T161's
   census is the right shape, not mine.
4. **Coverage matches the letter of this task, not T161's full signal list.** I added
   SIGTERM and SIGHUP (as asked) plus SIGKILL start-up detection; I did **not** add SIGQUIT
   (explicitly T168's territory per the task text) or SIGPIPE (T161 added it because its
   script is plausibly read through `| head`; this driver's own long-running stdout is not
   typically piped that way, and I did not invent a scenario to justify it). If the driver
   wants a uniform signal set across the family, SIGQUIT and SIGPIPE are the two to
   consider adding here to match T161's list — not done in this task to avoid guessing at
   T168's scope.

## Unverified

* **Only CPython 3.x on darwin 25.5.0 was exercised.** `signal.signal` for SIGTERM/SIGHUP
  and the `waitpid`-interruption timing are both CPython/POSIX behaviour; not tested under
  any other Python implementation or OS. [UNVERIFIED]
* **A second signal arriving *during* the restore itself** (i.e., inside the few
  milliseconds between `_write_verified`'s `write()` and its own re-read, or between two
  paths in a multi-file mutation's restore loop) was reasoned about, not driven: the marker
  is only cleared after every path verifies, so even a restore interrupted by a second
  signal leaves the marker for the next invocation's start-up recovery to catch — but I did
  not attempt to time a second signal into that sub-millisecond window. [UNVERIFIED —
  reasoned from the code structure, not measured]
* **A hung `conformance.sh`** (e.g. a wedged `docker exec` to the oracle) was not driven
  here; T156 measured the shell-script analogue (a hung driver held the pre-fix rig open at
  a 25 s timeout, restored in 1.5 s post-fix) but I did not reproduce a hang for this
  Python driver specifically. Given the 0.052 s measured deferral against a live 16 s
  conformance run, I'd expect the same responsiveness against a hang, but that is inference,
  not a measurement. [UNVERIFIED]
* **Concurrent invocations** (two `T61-mutations.py` processes racing on the same marker
  path) were not tested; nothing about the original script was concurrency-safe either, and
  this task did not change that. [UNVERIFIED, not this task's scope]
* **SIGSTOP-then-SIGKILL, disk-full during a write, and machine power loss** were not
  tested — the same class of gaps T156 and T161 both recorded as out of scope for a
  reasonable single task. [UNVERIFIED]
