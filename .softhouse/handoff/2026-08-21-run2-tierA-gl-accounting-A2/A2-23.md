## StoreFileCensus vs Admit — which layer, and why

**This belongs in `StoreFileCensus`, and I did not put anything in `Admit`.** The two functions
answer two different questions about two different things:

- **`Admit` (admit.go) answers: is this FILE's declared claim admissible?** It runs per-vector, after
  a file has been read and decoded into a `Vector` struct. Its `context` check (`:139`, A2-20) asks
  "does `v.Context` name a context this schema grades?" — a question that can only be asked of a
  file that EXISTS and DECODED. An empty directory produces no `Vector`, so there is nothing for
  `Admit` to be asked about. This is exactly A2-20's own diagnosis (its handoff §6): "a directory
  containing no vector makes no claim and grades nothing, so there is no vector to declare
  inadmissible."
- **`StoreFileCensus` (census.go) answers: does the STORE'S SHAPE make sense, independent of any
  one file's content?** It already refuses a symlink and a directory nested inside a context
  directory — both are properties of the *tree*, checked by walking the tree, never by decoding a
  vector. A top-level directory with an unrecognised name is the same kind of fact: it is true or
  false about the directory NODE itself, checked by `os.ReadDir`/`WalkDir`, before (and whether or
  not) anything inside it is ever handed to a decoder.

The task's own framing states this correctly and I am restating it as the thing I actually verified,
not assuming it: an unknown EMPTY directory can never reach `Admit`, because `Admit` is only ever
called on a `*Vector` that `LoadVector` successfully produced from a `.json` file, and `LoadStore`'s
loop over an empty directory's entries performs zero iterations — no file, no `LoadVector` call, no
`Vector`, no `LoadError`, nothing appended to any of the three inputs `StoreFileCensus` is given.
[VERIFIED by reading `LoadStore`, `nexus/internal/apps/loanschedule/conformance/vector.go:922-985`,
this task — the inner `for _, f := range files` loop simply does not execute when
`os.ReadDir(dir)` returns an empty slice.]

A rule placed in `Admit` cannot see this shape by construction — there is no vector to admit or
refuse. Putting the check there would have meant inventing a second, unrelated mechanism (e.g.
having `LoadStore` itself walk directory names and synthesize a fake refusal) that duplicates what
`StoreFileCensus` already does for every other store-shape fact. Putting it in `StoreFileCensus`
means one function states one property — "every top-level directory under the store root is a
context some schema recognises" — using the same `WalkDir` pass that already states the symlink and
nested-directory properties, at the same layer, with the same before-or-after-the-comparator timing
this file's own doc comment already argues for regarding contract-refusal vectors.

## Does A2-20's argument survive? (argue it, do not just overturn it)

**Yes, and I did not need to overturn any part of it.** A2-20's claim, stated exactly in its
handoff: *"a directory containing no vector makes no claim and grades nothing, so there is no
vector to declare inadmissible... it matters less than it looks: an empty directory cannot inflate
a number."*

That is a claim about **NUMBERS** — parity count, cell count, the two figures every `RESUME.md` and
gate write-up in this program quotes as evidence of coverage. It is true, and my fix does not
change it: `StoreFileCensus`'s new check is a **store-wide refusal**, exactly like the symlink and
nested-directory checks that already existed before this task. A refusal aborts the run before any
grading happens (`LoadStore` returns the joined `refusals` error and `Run` exits 2 without printing
a parity count at all) — so there is *still* no path by which an empty directory inflates a NUMBER,
because there is no longer a path by which it produces a PASS verdict at all.

What A2-20 did not claim, and what I am not attributing to it, is that an empty unknown directory is
harmless in every sense. Its own handoff already named the residual, already proposed the fix
("closing it would be a store-shape check — `StoreFileCensus` refusing an unrecognised directory —
which is a different guard with a different failure mode"), and explicitly recommended it as a
follow-up rather than doing it itself, because it was out of that task's scope. This task is that
follow-up. So the relationship between the two is not "A2-23 corrects A2-20" — it is "A2-20 correctly
scoped its own fix to vector admissibility, named the adjacent store-shape gap by name, and this
task closes the gap it named." Nothing here required arguing A2-20 was wrong about anything it
claimed.
