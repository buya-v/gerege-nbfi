### The fix, and why `head -1` was never a candidate

Exactly one summary line is admissible. Zero → REFUSE (P-84 presence-before-value,
`patterns.md:2813` — **P-84, not P-83**; P-83 at `:2806` is the reconcile-by-running rule, and the
source comment now says so in-line). One → behave exactly as before. Two or more → REFUSE, not
because either line is wrong but because the wiring cannot say **which run** either describes.

`head -1` only moves which line wins. Case **m04** drives the mirror ordering (clean first,
failing second): under `tail -1` it happens to refuse, under `head -1` it would start the fire.
Both orderings now refuse for the same reason, and the m04 grade explicitly FORBIDS the
`this is the READERS` sentence, because no reader has been graded when the population is ambiguous.

**How the five defeat attempts are answered, and it is the ANCHORS doing the work, not a new rule.**
The selector is anchored at both ends, so only whole lines that are nothing but a summary join the
population. Trailing whitespace (m06a/m06b) and substring containment (m10) therefore fall OUT of
it — which is the SHUT direction in both roles: as an impostor such a line cannot silence a real
one, as the only summary it refuses under the zero arm, and as narration it cannot manufacture a
false multiplicity. That last matters more than it looks: the wiring's own `lockselftest| ROWS=…`
echo is a substring line, and a naive `grep -c ROWS=` fix would have refused every healthy fire.
Stderr **is** in the population because the capture is `2>&1` (m08 — which the old `tail -1` let
through at rc 0). A split across a write boundary is still one line (m09a, green); a split across a
line boundary matches nothing and refuses (m09b).

### A bug of my own, caught by my own control, recorded rather than tidied away

My first implementation counted with `_ST_NSUM=${#${(f)_ST_SUMS}}`. In an **assignment** context
that nested form is scalar and `${#…}` is a **string length**: it read **41** — the character count
of `ROWS=45 FAIL_OPEN=0 FAIL_SHUT=0 SKIPPED=0` — and refused the healthy control m00 with
*"printed 41 TALLY LINES"*, i.e. it turned the multiplicity fix into a control that refuses every
fire. The m00 control caught it before it left the worktree. It is counted through a real array now
(`_ST_SUMLINES=( ${(f)_ST_SUMS} )`), and the reason is written into the source so it is not
re-introduced. **This is the case for insisting a multiplicity fix ship with a fire-must-still-START
control**; without m00 the file would have been committed refusing everything and passing every
"does it refuse?" test I wrote.

## 2. F-T380-2 — the ceiling has no structural MAXIMUM. **CLOSED, and it is derived, not typed.**

`_knob_int` bounds each threshold from below and by an int64 round-trip, but nothing bounds one
from above — while the C, G and Z fixtures are DERIVED from the thresholds. So an accepted-but-
absurd threshold breaks the **fixture** and the run is graded as a **reader** fault.

Reproduced against the shipped file [`out/05-red-evidence-thresholds.txt`], and it is worse than
one case:

* **f01** `LOCK_CEILING_SECS=9223372036854775807` (T380's k12) — c01/c02 FAIL-SHUT, and the log
  says *"The thresholds validated at startup, so this is the READERS."* It is not the readers.
* **f06** `LOCK_RELEASE_SKEW_SECS=9223372036854775807` — **new here.** `SKEW*2+60` wraps to `58`,
  so z06's *"past the skew bound"* fixture lands 58 s in the future, z06 reads `ok` **for the wrong
  reason**, and its own control z07 goes FAIL-SHUT. A row passing while grading the opposite of its
  claim, next to a control that fails — again reported as the readers.
* **f02** `LOCK_CEILING_SECS=1800` — **the fire STARTS, rc 0, all 45 rows `ok`.** g01 prints its own
  vacuity: `started_at -1800s old, INSIDE the 1800s ceiling`. `_NEAR_AGE` is negative, `_NEAR` is a
  FUTURE instant, the age reads negative and arm 6 answers `HELD-default`; the row wants HELD, so it
  passes while grading nothing. P-22.
* **f05** `LOCK_CEILING_SECS=3600` — the exact boundary: `_NEAR_AGE` = 0, an "inside the ceiling"
  fixture that is NOW. Fire starts.

**The fix** is a gate immediately after the fixtures are derived, inside `--self-test-lock-readers`,
that re-runs the fixture arithmetic and asserts each derived value has the property the row
consuming it depends on. Six tests, **no new cardinal and no restated one** — they ARE the fixture
expressions (P-83, reconcile by running):

```
_OLD_AGE  > LOCK_CEILING_SECS                 # c01/c02: CEILING*2+60 did not wrap
_NOW_E - _OLD_AGE >= 0                        # c01/c02: the past-ceiling instant is post-epoch
_NEAR_AGE > 0 && _NEAR_AGE < LOCK_CEILING_SECS# g01: an age genuinely INSIDE the ceiling
_SKEW_FAR > LOCK_RELEASE_SKEW_SECS            # z06: SKEW*2+60 did not wrap
_NOW_E + _SKEW_FAR  > _NOW_E                  # z06: the far-future instant is representable
_NOW_E + _SKEW_NEAR >= _NOW_E                 # z07: the inside-bound instant is representable
```

It exits **78 (`EX_CONFIG`)**, so the wiring's existing `rc == 78` branch names it a THRESHOLD and
never a lock-reader regression — and **this makes that branch genuinely reachable in a
single-process run**, which is the property T377 flagged `[UNVERIFIED]` because the outer process
validates the same environment first. These are faults `_knob_int` structurally cannot see.

**It is a BOUND, not a BAN — graded two-sided.**
`capture/t383-t380-conditions/bin/t383-threshold-drive.zsh`, 9 cases, nothing mutated (the
environment IS the input):

| | | shipped | fixed |
|---|---|---|---|
| f00 | defaults | rc 0 | **rc 0** |
| f01 | ceiling = int64 max | rc 2, blames READERS | **rc 78, THRESHOLD** |
| f02 | ceiling = 1800 | **rc 0, vacuous g01** | **rc 78**, `inside-ceiling age=-1800` |
| f03 | ceiling = 604800 (legitimate 7 d) | rc 0 | **rc 0** |

RED **`CHECKS=9 WRONG=4`** [`out/04-red-thresholds-shipped.txt`]; GREEN **`CHECKS=9 WRONG=0`,
`RESULT: PASS`** [`out/06-green-thresholds-fixed.txt`]. f04/f05 straddle the boundary exactly, which
is what makes it a comparison against the fixture and not a typed cardinal. f07 pins that the skew
minimum is still 0 — the z07 test uses `>=`, deliberately, because a skew of zero makes z07's

**STATED COST, direction SHUT and NEW: `LOCK_CEILING_SECS <= 3600` now refuses the fire** where it
previously ran with a vacuous g01. Both halves are measured (f02/f05 before and after). I judge it

written into the source as a stated cost, not left to be rediscovered.

**I did not adopt the alternative** of re-deriving `_NEAR_AGE` as `LOCK_CEILING_SECS / 2` to make it
always positive: it would move g01's fixture from 3600 s inside the ceiling to half the ceiling
away, and g01's sensitivity to an epoch drifting LOW is proportional to how CLOSE to the boundary it
sits. That would have silently weakened the row to avoid a refusal. Recorded so the option is not
re-proposed as an improvement.
