**`_lock_json_field <key> <str|int>`, new.** Reads one field out of `$LOCK` with

### Why not the one-liner — measured, not argued

T280's `v="${v%%\}*}"` is correct and it fixes case 1b. It fixes **one row of the seven**
(and half of a second, 4d, whose other half is a separate guard bug it cannot see):

| # | body | old verdict, live holder on this host | why the one-liner cannot reach it |
|---|---|---|---|
| 1b | `"released_at": null` **last key** | `FREE-released` | — this is the one it fixes |
| 4d | compact separators, no space after any colon | `FREE-released` | it repairs the `null}` half, but the `"host": "` / `"pid": ` / `"started_at": "` guards each hard-code one space and still all miss |
| 1e | `released_at` twice, timestamp then null | `FREE-released` | `${body#*…}` takes the **first**; `json.load` takes the **last**. Taking the first is what `#*` *means*. |
| 1f | body not JSON, contains `"released_at":` | `FREE-released` | a substring test is not a syntax check |
| 1g | write truncated mid-value | `FREE-released` | same |
| 2c | `pid` twice, dead then live | `TAKE-dead-pid` | first-wins again — and this one doesn't involve `released_at` at all |
| 4b | `started_at` twice, 105 h then now | `TAKE-ceiling` | same |

A repair per row would still leave this file **disagreeing with `ready-tasks.py`**, which
reads the same lock with `json.load` and **REFUSES** when it will not parse. The old readers,
on that same input, answered FREE. Two components of one program reading one lock file with
opposite polarity is verbatim the P-85 shape STEP 0 exists to prevent
[`.softhouse/patterns.md:2822`]. That is the argument for the parser, and it is not an
aesthetic one.

**Cost, in seconds.** ~104 ms per `/usr/bin/python3` fork; a fire start reads four fields, so
**0.42 s once per fire** [VERIFIED: `out/06-cost-json-parse.txt`]. `/usr/bin/python3` is already
an unconditional dependency of this wrapper (two `branch_sweep.py` calls in the preflight, the
`ready-tasks.py` call in `reconcile_tasks_json`), so this adds forks, not a dependency class.
**Rejected:** `jq` (not a dependency of this repo; adding one *on the lock path* is worse than
the bug) and `plutil` (macOS-only, and silently tolerant of duplicate keys — the case we most
need refused).

**Duplicate keys REFUSE rather than resolve.** `json.load`'s last-wins would have been enough
to match `ready-tasks.py`, but refusing is strictly more fail-closed *and* it makes the
first-wins/last-wins question moot instead of merely answered in one place.

### Why the "obvious" fix does not work, and the correction to how T280 said it

T280 says adding `{}` to the strip class **"does not compile under zsh."** Not quite, and the
difference is the interesting part [VERIFIED: `out/03-why-brace-class-fails.txt`]:

```
A1 naive: add {} inside $'...' in the class      parses; RUNTIME FAIL rc=1: bad pattern: [$' \t\r\n\"{
A2 naive: add } only                             parses; RUNTIME FAIL rc=1
A3 backslash-escaped braces outside the quote    parses; result [null]
A4 braces via $'\173\175' octal escapes          parses; result [null]
B  T280 proposal: cut at first } then strip      parses; result [null]
```

`zsh -n` returns **rc 0** on the naive form. The `}` inside the bracket expression **closes the
`${…}` substitution** — zsh's parameter-expansion scanner has no notion of a glob character
class — so the expansion silently becomes `${v//[$' \t\r\n\"{}` with an unterminated pattern,
and that is only diagnosed when the *pattern* is compiled, at runtime.

So the accurate statement is **"it parses and then fails at runtime"**, which is *worse* than
"does not compile": `zsh -n` is the natural syntax guard and it would have waved it through.
Two spellings (A3, A4) do work; I used neither, because the parser removes the whole class of
question.

## Money-math notes

**None, and that is a statement about the diff, not an omission.** T342 touches the fire
wrapper's lock protocol. No monetary value, no currency, no rounding, no ledger row, no
schedule is read, written or computed anywhere in it. Checked explicitly against the
non-negotiables:

- **No floating point introduced.** The only arithmetic in the diff is `now - e` on integer
  epoch seconds (unchanged from T279). The new python reads `pid` as an `int` and explicitly
  **rejects** a float or a bool where an int is required.
- No ledger, no balance, no hold, no `Idempotency-Key` path, no DB of any kind. No SQL, no
  driver, no dialect — the PostgreSQL-only rule is untouched.
- No name fields, no national ID, no timezone arithmetic (the one date parse is `TZ=UTC` on a
  `Z`-suffixed ISO stamp, unchanged).

The nearest thing to a money consequence is indirect and worth naming: a double-holder
incident is what corrupts in-flight state, and P-85's 2026-08-22 instance destroyed four
worker branches. This fix is upstream of that, not of any arithmetic.

## On severity — where I agree with the brief and where I don't

The brief asked for judgement rather than agreement. Here it is.

**Where the filed argument is weaker than stated.** It says *"the most natural way to
hand-write that file — `released_at` last — triggers it."* I went and read what STEP 0
actually instructs, and it says:

> "Otherwise write it (`holder`, `host`, `pid`, `started_at`, `heartbeat`) and delete it
> before you finish."
> [VERIFIED: `.claude/skills/softhouse-program/SKILL.md`, STEP 0]

**`released_at` is not in that list, and release is by DELETION.** So a hand-runner following
STEP 0 *literally* never writes the field at all, and the "most natural hand-write" claim
requires an author who goes **beyond** the documented instruction. That is a real weakening
and the brief does not carry it.

**Where it is stronger than stated, and this is the half that decides it.** The document
*reads* a field four lines below the place it declines to tell anyone to *write* — arm 1,
"`released_at` is non-null → free." A field that is read-significant and write-unspecified is
exactly the condition under which an author invents a write, and the write they invent is
`"released_at": null` meaning *"not yet released"*. **The field written to say HELD was read as
FREE.** That is not a corner case; it is the inversion of the field's only plausible hand-use.

**And the reachability argument is not needed at all for part of the census.** Cases 2c and 4b
defeat arms 2 and 3 with **no `released_at` anywhere**, and 1f/1g fire on a body that is not
JSON — which the shipped writer can produce, because it is a `cat > "$LOCK"` heredoc
**whose return code is not read** (a fact this program has already written down, in
`ready-tasks.py`'s own comment about that exact `cat >`). A disk-full or interrupted write
does not need a human.

**Verdict: I agree with BLOCKING, on a partly different basis.** The severity is not
overstated. The *justification* filed with it leans on a hand-write claim that STEP 0's text
does not support, and would have been stronger leaning on the read/write asymmetry and on the
`fire-program.sh` ↔ `ready-tasks.py` polarity split. I have written the stronger version into
the source comment so the next reader inherits it. I did **not** downgrade it, and I would
have said so plainly if I thought it should be.
