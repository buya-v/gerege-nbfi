## The three questions I was sent to answer

### 1. Does the inherited-IFS null-control finding hold? — **YES.**

Verified from first principles with my own probe, not T130's script, on **bash 3.2.57
(host) and bash 5.3.9 (alpine)**, and then via `ifs-routes.sh` on **bash 4.4.0 built by me
from the GNU tarball**:

```
exported IFS=z, then:
  bash script            -> IFS = the 3-char default        DELIVERS NOTHING
  bash --posix script    -> default                          DELIVERS NOTHING
  bash -c                -> default                          DELIVERS NOTHING
  argv[0]=sh             -> default                          DELIVERS NOTHING
  POSIXLY_CORRECT=1      -> default                          DELIVERS NOTHING
  BASH_ENV=<IFS=z>       -> IFS=[z]                          DELIVERS
  sourced (IFS=z set)    -> IFS=[z]                          DELIVERS
```

**Every `IFS=…` row in T97's matrix, T106's review, T113's refutation and T121's 448-value
brute force was a null control.** Four rounds of argument about the `IFS=` prefix ran over
an experiment that could not fail. T130's relabelling and its `[SUPERSEDES:]` note are
correct.

Two completeness notes, neither weakening it: `BASH_ENV` does **not** deliver to a
POSIX-mode non-interactive bash (which reads neither `BASH_ENV` nor `ENV`), and an
interactive `--rcfile` shell is an 8th delivering route. Both irrelevant to the branch,
because `interpreter-matrix.sh` **asserts the route before relying on it** rather than
assuming it.

### 2. Is the fourth stripping rule right? — **RIGHT WHERE IT IS USED, WRONG WHERE IT IS STATED.**

- Inside the swept domain it is **correct**: my own independent implementation of the
  sentence agrees with `read` in **960/960** cases; T130's 3,282 reproduce at 0
  disagreements on 3.2.57, 4.4.0 and 5.3.9.
- T130's sharpening of T121 (*"ANY IFS delimiter"*, not *"that character"*) is a **real
  correction**: `abcze` survives `IFS=ze`, which T121's phrasing predicts would be
  truncated. Third statement wrong, fourth better.
- But the sentence shipped in `conformance.sh:208-215` **drops the "IFS containing no
  whitespace" scope that T130's own rig header keeps**, and it is false without it:

```
IFS=[ a]  line=[bb a]  read=[bb]   -- the shipped rule predicts [bb a]
IFS=[ a]  line=[a ]    read=[]     -- the shipped rule predicts [a]
(identical on 3.2.57, 4.4.0, 5.3.9)

  81 of 960 cases disagree once IFS may contain a space or a tab. → **F-T150-2, P3.**

- **The `[6b]` implication it is used to justify is nevertheless TRUE**, and I proved that
  separately rather than deriving it from a rule I had just found over-scoped:

```

### 3. Ruling on assert-vs-restructure — **T130's reasoning is SOUND, and I measured both of its reasons.**

- **Structural change to the probe's SHAPE.** I applied the doubling option to a copy of the
  harness and ran T106's **unmodified** rig: `the probe redirection is not in … any more —

  and worse than stated, since the comparison line would have to change too.
- **Change to the token's VALUE.** T106's rig hard-codes and seeds `conformance-psub-live`.
  Against a *post-fix* harness with the token renamed, the rig reports **7 passed, 1 failed

- **Not going through `read`** needs `cat` or `read -N` (4.1+); the host is 3.2.57.

**Uphold.** Asserting the invariant catches strictly more than a structurally-immune token
