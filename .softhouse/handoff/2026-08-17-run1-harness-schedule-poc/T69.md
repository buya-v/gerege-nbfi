## The rule, and why it is now true

Stated compactly, the way I would defend it:

> The memo is a map from a period index to a money pair. It can be wrong two ways:
> the **value** at a key can be stale, or the **key** can be a lie.
>
> **(a)** fixes what a value depends on: nine per-period stored fields, plus two
> model-wide ones (`minorDigits`, `precision`) that no index expresses.
>
> **(b)** keeps values fresh. The true requirement is `m.chainValid <= j` at the next
> chain read after a write to period `j`. The *rule* — "precede the write with
> `invalidateFrom(j')`, `j' <= j`, with no chain read between" — is a **sufficient**
> discipline for establishing that requirement, and it is the discipline every
> live-model write site follows. It is **not necessary**: construction already
> satisfies the requirement with `chainValid == 0`, which is why
> `newScheduleModel`'s and `deepCopy`'s writes are sound with no guard and are not
> defects to be "fixed".
>
> **(c)** keeps the key honest: `m.periods[i].idx == i` for all `i`, and `m.periods`
> never reordered. (b) says nothing about `idx`, so (b) alone is not sufficient.

Why each half is true rather than merely plausible:

- **(b) sufficiency.** If every write to a fold-input field of period `j` is preceded
  by `invalidateFrom(j')` with `j' <= j` and no intervening read, then at the next
  read `chainValid <= j' <= j`, so `interestChainUpTo` will not trust `m.chain[k]`
  for any `k >= j` and will recompute every step from `chainValid` onward, reading
  the post-write fields. Entries below `chainValid` were computed from fields of
  periods `< j` (by (a), step `k` reads only periods `0..k`), which this write did
  not touch.
- **(b) non-necessity.** `chainValid` starts at 0 and only `interestChainUpTo`'s own
  store ever raises it. Before the first chain read on a model, `chainValid == 0`,
  nothing is trusted, and the requirement holds for **every** `j >= 0` with no call
  made. That is exactly the state at `generator.go`'s build loop (where `m.chain` is
  not even allocated yet) and at the top of `deepCopy` (fresh empty chain).
- **(c) necessity.** `interestChainUpTo(p.idx)` returns `m.chain[p.idx]` /
  `m.periods[p.idx]`'s step. If `p.idx != position(p)`, the answer is another
  period's money, and no amount of write-ordering repairs it, because nothing was
  written.
