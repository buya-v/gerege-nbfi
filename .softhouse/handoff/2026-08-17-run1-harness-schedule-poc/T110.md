## 1. The defect

The two numbers this program quotes as its evidence of coverage — **"N parity vectors"** and **"M graded cells"** — are both computed by summing over the vectors `LoadStore` returns. Nothing rejected a store in which two files declared the same `case_id`, so the same case was graded twice and **both** headline numbers moved, with every other check still green.

Not the defect: T90 added `path` as a third comparator key so a tie *orders* deterministically, and T104 measured that the tie-break never went red. Ordering was never the problem. **The problem is that duplicates were not REFUSED.**

## 3. The fix

**`vector.go` — new exported `DuplicateCaseIDs(vectors []*Vector) error`,** called from `LoadStore` *after* the sort (so the refusal names its files in a deterministic order) and returned as `LoadStore`'s **third** value:

```go
if err := DuplicateCaseIDs(vectors); err != nil {
    return nil, loadErrs, err
}
```

**`grade.go` — `s.LoadErrors = loadErrs` moved above the `err != nil` check**, so a store that is both malformed *and* duplicated reports both. Behaviour is identical when `err == nil`. `Run` then does what it already did with a `LoadStore` error: appends a fatal reason and `return s, nil` — and **the grading loop is below that return**.

### Which error channel, and why

| candidate | rejected because |
|---|---|
| a new exit code | Exit 3 = wrong-interpreter refusal, 2 = unusable, 1 = FAIL, 0 = PASS. Adding a fifth would break every caller and every gate write-up that reads these four. |
| `Summary.Errored` — the counter the report prints as **"harness errors"** | It is a **per-vector** outcome (`OutcomeError`, `grade.go:319`), incremented **inside the grading loop**. Routing the refusal through it would (a) misattribute a relationship between two files to one of them, and (b) require grading to have already run — which is the exact thing that must not happen. |
| `LoadError` | A `LoadError` is a property of ONE file ("this one could not be read"). No single file here is at fault. |
| **`FatalReasons` → exit 2** ✅ | The existing "the harness, the corpus or the oracle is unusable" channel, documented on `Summary.ExitCode`. It is the same channel that already carries **ZERO VECTORS FOUND** — the other way a store lies about its size — so a duplicate and an empty store are now reported the same way, at the same point, with the same code. |

### Refusal, not warning, not dedup

A warning leaves 43/5623 printed and quotable. A silent de-duplication is worse: the two files are **not known to agree** — the copy may carry a different expectation, provenance or capture reference — so dropping one is the harness choosing which claim is true, invisibly. That is the same class of lie in the other direction. The code says so, in the doc comment, and a de-dup mutation is driven red in §5 (M2).

### The key is `case_id` alone, store-wide

Not `(context, case_id)`. The report's first column prints CASE **without** CONTEXT, so two rows with one `case_id` in different directories are indistinguishable to a reader and still add to the same totals. This also catches a symlinked or hard-linked copy, which arrives as two distinct paths carrying one `case_id`. Driven red as M4 in §5.

## 5. Attacking my own guard (P-22)

*What is the observation, and could it be produced by the check never running?* The observation is "the run was refused". It could be produced by a harness that refuses everything, by a check that fires after grading, or by a check keyed too narrowly. So: a **control** sub-test asserts the unperturbed store still loads 47 vectors, grades 5,576 cells and exits 0 (it fails loudly if the committed store ever acquires a duplicate, or if it grades zero cells — which would make every "graded 0" assertion below vacuous); and four mutations were applied to the **fixed** tree, each built and run:

| # | mutation | result |
|---|---|---|
| **M0** | none (sanity) | `ok ... 12.495s` — all 5 sub-tests green |
| **M1** | `DuplicateCaseIDs` returns `nil` unconditionally — *the check never runs* | **RED** (4 sub-tests) |
| **M2** | silently de-duplicate instead of refusing | **RED** — `it loaded 47 vectors and the run would have graded P-00 TWICE`; the dedup restores the *count* and is still caught |
| **M3** | **warn only**: record the duplicate as a `LoadError`, keep grading | **RED** — and this is the decisive one. M3 gets the **exit code right (2)**, so an "exit 2" assertion alone would have passed it. The guard fails with `the refusal must fire BEFORE grading: got 48 results, 5623 graded cells, 43 parity passes ... these numbers were computed and could be quoted` |
| **M4** | key on `(context, case_id)` instead of `case_id` | **RED on exactly one sub-test** — `duplicate_across_context_directories_is_refused` — the other four stay green. Precise, not blanket |

**M3 is the proof demanded by step 6:** the refusal provably executes *before* grading, because a variant that runs *after* grading and still yields exit 2 is caught. This run has already found five guards structurally incapable of failing (a sha256 printed but never compared, an abort writing FAIL to stderr while the gate grepped stdout, a precondition table built by looping over the ids it then checked); M1–M4 are the corresponding evidence for this one.

One further self-inflicted catch worth recording: the first draft of `refusal_message_is_deterministic` hard-coded three vector filenames and **`t.Skip`ped** when one had been renamed — it read green and checked nothing. It now derives its three files from `LoadStore`'s own output and `t.Fatal`s if the store has fewer than three vectors.

**A second, independent divergence found while measuring E2–E4:** `conformance.sh`'s `guard_no_float_in_vectors` enumerates the store with `find "$STORE_ROOT" -name '*.json' -type f`, which is **recursive** and does **not** follow symlinks, while `LoadStore` is **one level deep** and byte-suffix-matched. The two components therefore disagree about which files are in the store: E3's nested file is float-scanned but never graded, and E4's `UPPER.JSON` is neither. Nothing compares the two counts. This is the shared root of F-T110-1/2/3 and is the shape a follow-up should take: **make the harness's own file census explicit and refuse any `.json` under the store root that it did not load.** That is a bigger change than this task and belongs in its own diff.

## 7. Findings raised

* **F-T110-1 (P2)** — a symlinked context directory is silently skipped; a whole context can be present and ungraded with no signal. `[VERIFIED: E2]`
* **F-T110-2 (P2)** — vectors in a nested subdirectory are silently skipped. `[VERIFIED: E3]`
* **F-T110-3 (P3)** — a `.JSON`-cased (or any non-exact-suffix) file is silently not a vector. `[VERIFIED: E4]`
* **F-T110-4 (P3)** — `case_id`s differing only by letter case are accepted and both graded. Recommended fix is *not* case-folding (it would reject legitimate ids by policy) but the rule in F-T110-5.
* **F-T110-5 (P2)** — `case_id`s differing only by Unicode normalisation are accepted, both graded, and render **identically** in the report. All 47 committed `case_id`s are pure ASCII today, so the cheap, dependency-free fix is to **refuse any `case_id` outside `[A-Za-z0-9._-]`** — which closes F-T110-5 outright and F-T110-4's realistic form — rather than importing `golang.org/x/text/unicode/norm`. Recommended as one small task together with F-T110-1/2/3.
* **F-T110-6 (P3)** — on any fatal early return the report still prints `INVARIANT ASSERTIONS THAT COULD NOT RUN → NONE — every invariant assertion ran`, over a run that graded nothing. Pre-existing on every early-return path (`LoadPin` failure, capability-registry failure), not introduced here, but it is a true-sounding sentence about a run that did no work.

## 9. `[UNVERIFIED]`

1. **Any toolchain, OS or architecture other than `go1.26.6 darwin/arm64`.** `os.ReadDir` ordering, symlink `DirEntry` typing and case-sensitivity in E4/E5 are filesystem and runtime properties. macOS here is case-**insensitive**; on a case-sensitive filesystem E4/E5 may behave differently, and I did not test one.
2. **T104's own 43/5623 transcript.** I reproduced the *numbers* on my own tree with my own binary; I did not re-run T104's scripts and did not compare byte-for-byte with its output.
3. **That the enumeration in §6 is complete.** It is what I could construct and measure in one task. I have no argument that no ninth way exists — F-T110-1/2/3 were found only because I went looking for the *under*-count direction after the brief asked, which is exactly how many were missed before.
4. **Behaviour on a store where the two duplicate files DISAGREE.** Both duplicates I built were byte-identical copies. The refusal does not read the contents, so the outcome is the same by construction — but I did not measure a store whose two `P-00` files carry different expectations.
5. **Hard links** specifically. E1 used a symbolic link. A hard link presents as two ordinary files with one `case_id`, which is the same input to `DuplicateCaseIDs`, but I did not run it.
6. **`--self-test` beyond `--prove`'s use of it,** and every other branch of `conformance.sh`. I ran the default mode and `--prove`.
7. **Whether any *historical* run in this program's record was taken on a duplicated store.** I did not audit past reports; the committed store is clean today and the control sub-test now fails loudly if that ever stops being true.
