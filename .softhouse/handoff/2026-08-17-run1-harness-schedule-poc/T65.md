### P1-1(b) — the cost test

`TestGenerationCostIsNotQuadraticInTheTerm` → **`TestGenerationCostIsLinearInTheTerm`**.
It no longer takes a ratio between two points; it measures **allocations per
period** at `n ∈ {90, 180, 360, 720, 1000}` and asserts that figure does not grow
by more than 2.00x off the `n=90` baseline. Per P-7 that is a property, not
today's constant: a linear generation holds it at any constant.

Two named constants carry the declared domain — `gradedCostCeiling = 1000` and
`costSampleTerms` — with a doc block giving the measured cliff table, the
recursion mechanism, the Java citation, and T63 F-4's rate axis.

**The wall-clock assertion is removed entirely.** Every assertion in the test is
now machine-independent, which is the flakiness objection T59 raised, taken to its
conclusion. Justification for not keeping a crude timing net: I measured the only
defect it could plausibly have caught (the `installmentNumberOf` scan) at 2.12 ms
inside a 230 ms generation at `n=1000` — under 1%, unseparable from noise anywhere
inside the graded ceiling. A cap that cannot catch the defect it is kept for is
not a net.

New **`TestInstallmentNumbersAreDenseOverPayableRowsOnly`**, the guard for the
carried counter. It is a correctness test in a liveness file and the doc says why:
the scan was self-evidently consistent, a carried counter is not, and no cost
metric here can see the class of defect the change introduces.

Both test docs now carry an explicit "what this cannot see" section.

## Money-math notes

**No money value moved and none could have.** Neither change touches an arithmetic
expression:

- P1-2 is comment-only. `git diff` on `emi.go` shows only comment lines outside
  the one-line `chainStep` struct, which is unchanged.
- P1-1(a) replaces one pure function of the already-emitted rows with a counter
  that computes the same function incrementally. The old `installmentNumberOf`
  returned `1 + |{emitted rows of kind DownPayment or Repayment}|`; the new
  counter starts at 1 and increments once per such row appended, so it holds the
  same value at every read by induction on the loop. Proved empirically by the
  51,888-row byte-identity above and by 32/32 conformance, not asserted.
- `InstallmentNumber` is `int32`, not money. The money cells on the same rows
  (`PrincipalMinor`, `InterestMinor`, `OutstandingPrincipalMinor`) are `int64`
  minor units throughout and are untouched.

Float scan over the three files —
`grep -nE '\bfloat(32|64)\b|math\.(Floor|Ceil|Round|Pow|Abs|Log)|ParseFloat|%f'` —
returns **nothing**. The new test's ratios are computed in hundredths with integer
division (`int64(got) * 100 / int64(base)`), the same convention T59 used.

**On the cliff and why I did not fix it.** The `applyFinalPeriodResidual`
self-recursion is a faithful port of `calculateLastUnpaidRepaymentPeriodEMI`'s
self-call [VERIFIED: `ProgressiveEMICalculator.java:1211-1215` — the guard at
:1211-1213, the call at :1214]. On an unpaid schedule `getTotalPaidAmount()` and
`getTotalCreditedAmount()` are both zero, so the Java condition reduces to
`emi < 0` and `setEmi(0)`, which is exactly the port's arm. **The reference oracle
has the same quadratic.** Removing it would be a divergence from the oracle
introduced to make a cost test pass, with no vector covering the shape — precisely
the trade this program does not make. T59 refused it and was right to.

## Follow-ups

Discovered but deliberately **not** in this diff (scope guard):

1. **The `applyFinalPeriodResidual` quadratic is still there, and it is the
   oracle's too.** Any fix is a divergence from `ProgressiveEMICalculator
   :1211-1215` and must be vectored first. The capture wanted is a **long-term OR
   high-rate** shape — T63 F-4 is right that rate reaches "many rows amortize zero
   principal" at a quarter of the term, which makes the capture far cheaper to
   take from the oracle. Until such a vector exists, `gradedCostCeiling` is the
   honest statement of the domain.
2. **`gradedCostCeiling` is stated for one rate only.** A second cost sample at a
   higher rate would either raise or (more likely) sharply lower the declared
   ceiling. Worth one task once (1) has a vector; the constant should probably
   become a (rate, term) pair.
3. **T63 F-5 stands:** `memoiseInterestChain` is a mutable package-level global in
   production code, and its comment is a discipline claim rather than an
   enforcement. A build-tag or a test-only seam would close it. Not touched here.
4. **`generate` emits no `PeriodKindDownPayment` row at all** —
   `grep PeriodKindDownPayment` finds it only in `contract.go`, the conformance
   package, and (formerly) the deleted helper's predicate. The new counter is
   written to handle one, and `TestInstallmentNumbersAreDenseOverPayableRowsOnly`
   asserts the numbering over both kinds, but **neither is exercised today**, so
   the down-payment arm of the numbering rule is ungraded. Worth a line in
   whichever task first enables `DownPaymentPercentage`.
5. **Naming.** `costSampleTerms` and `gradedCostCeiling` are package-level
   identifiers declared in a `_test.go` file, so they are invisible outside tests;
   if a future task adds a second cost test they should move to a shared
   testing-support block rather than being duplicated.
