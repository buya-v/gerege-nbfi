## 1. The defect

`prove-guards-go-red.sh` extracts three files from a pinned baseline commit and runs every COUNTERPROOF row
against them. T102 pinned that commit to a **literal sha** in `FORK-POINT-SHA` and added four loud refusals —
missing file, non-hex, abbreviated, not-a-commit. All four test the pin's **shape**. None tests whether it
names the **right commit**.

So a **wrong-but-valid pin is silently accepted.** T103 measured it (case 5i): pin `main`'s own tip — a real,
reachable, 40-hex commit — and the rig scores a green **25/25** against a baseline that already contains the
fix, i.e. every counterproof compares the fixed code against itself and prints a green row for a comparison
that never happened.

T102's write-up concluded this *"cannot be detected — **nothing can**"*. That was **false**, and its own
disproof was printed on screen on every run for three tasks:

```
BASE run-pass3i.sh     sha256 d84ec7bf…
BASE promote-vectors   sha256 27bb20b4…
```

Computed, printed, **never compared to anything**. That is verbatim the canary shape **P-22** was written
about — the sha256 printed but never compared, which certified `HALF_UP` on a `HALF_EVEN` JVM (T77→T80) — and
it was the **third occurrence of that one shape in this run**.

## 2. The fix

| file | change |
|---|---|
| `FORK-POINT-SHA` | **Format changed to keyed.** `commit <40-hex>` plus one `sha256 <64-hex> <repo-relative path>` per extracted file, **each required exactly once**. The T102-era bare-sha form is **refused deliberately** — it carries no digest pins, which is the hole. Order-independent; leading/trailing whitespace and CRLF tolerated. |
| `prove-guards-go-red.sh:44-208` | Keyed parser replacing `grep -v … \| tail -1`. **The three extracted baseline files' sha256s are compared against the pins** and a mismatch is `exit 2` naming the file, the expected value and the observed value — **before the header prints and before the first proof row runs**. Each `git show` extraction is checked (T103's **F-4**). New refusals: missing / duplicate / unknown directive (which closes T103's **F-6** last-line-silently-wins). |
| `prove-guards-go-red.sh` (header) | The three baseline digests print `[MATCHES PIN]`. The **capture under test is now pinned too** — it was printed and never compared, and the CONTROL row and every capture-side mutation are built from it. The three shipping-code digests are relabelled `[provenance — code under test, unpinned on purpose]`, with the reason in a comment. **Every digest on that screen is now either compared or labelled as not compared and why.** |
| `run-precondition-block.sh:43` | The sha256 of the heredoc **sliced out of `run-pass3i.sh`** — the one value that would reveal a mis-slice — was printed and never compared. Now pinned, with the pin **suspended when `$T82_SCRIPT` names a mutated copy**, because a moved digest is the point of those rows. |
| `mutate.py:13`, `prove-promote-guards.py:11,205` | T103's **F-2**: the documented recovery command `git show $(cat …/FORK-POINT-SHA):<path>` never worked — `cat` emits the comment header and git dies on it. Replaced with the literal sha at all three sites, including the operator-facing `SystemExit`. |
| `sweep-census.py` | T103's **F-1**: the census output now **stamps the commit it measured**, and shouts if the working tree was dirty. |
| `T82.md`, `T102.md`, `T102-merge-acceptance/README.md` | The false sentence corrected in place, plus its restatements (§5). |

**Why the digest pin closes the hole rather than narrowing it.** The property the counterproofs actually need
is *"these three files hold the pre-T82 bytes"*. Until now the rig asserted a **proxy** for it (a commit id)
and never checked the thing itself. It now checks the thing itself, and the commit sha is demoted to a
locator. A different commit carrying byte-identical files is not a defect — the counterproofs would be
running against exactly the right code.

## 6. Attacking my own comparison

**The observation is:** a wrong-but-valid pin produces exit 2 and no proof rows. **Could that be produced by
the check never running** — e.g. by the rig failing early for an unrelated reason, or by the refusal living on
a branch nothing reaches?

- **A rig that simply cannot run would refuse everything.** It does not: the *same* rig, *same* invocation,
  with the *correct* pin, runs to **25/25, exit 0** (leg B below). The refusal discriminates.
- **The refusal is not one branch.** Five independent inputs reach it by different routes — a wrong commit
  (R1), each of three individually-altered digests (R3, R3b, and R1's first-file trip), a bare-sha file (R2),
  a duplicate directive (R5), a commit lacking the paths (R6). If any single comparison were dead, R3 or R3b
  would have gone green; both refuse, naming their own file.
- **Ordering is proved by absence, not by reading.** On every refusal **stdout is 0 bytes** — the header,
  which is the first thing the rig prints, had not run — and `scratch/` contains **no** `att-*` / `cf-*`
  artefact, which is what an `expect` row writes. Zero rows ran, measured two ways.
- **Every way it is actually invoked.** `prove-guards-go-red.sh` has exactly one documented usage
  (`bash prove-guards-go-red.sh`) and one caller in the repo (`T82.md:557`, a human instruction). I ran it
  **ten ways** with the wrong pin — absolute path from repo root, relative path from repo root, bare name from
  the rig dir, `./name` from the rig dir, absolute path from `/tmp` and from `$HOME`, direct exec via the
  shebang, `sh`, `zsh`, and piped (`bash < script`, where `$0` carries no path at all):

  ```
  LEG A — WRONG-BUT-VALID PIN: all 10 forms   exit=2  stdout_bytes=0  proof_rows=0
  LEG B — CORRECT PIN:          3 forms       exit=0  stdout_bytes=46573  25 as expected, 0 not
  ```
  [VERIFIED: `T109-digest-compare/every-invocation.txt`.]
- **`BASE` cannot be supplied from the environment.** `FORK_SHA_FILE="$HERE/FORK-POINT-SHA"` and every pin
  variable is an unconditional assignment — no `${…:-}` default, no `export`, no argument parsing. `ROOT` is
  derived from the script's own location.

**What this does not prove:** that the *pinned digests themselves* are the fork point's. That rests on three
independent measurements agreeing (T102, T103, me) and on the fact that the counterproof rows only score 25/25
against genuinely pre-fix bytes — see §7.

## 7. The residual hole, measured rather than asserted

Someone could edit the pin **and** recompute the digests from the wrong commit. I built that case (**R1b**):
pin `main`'s tip, digests recomputed from it. Result: **not a false green** — `18 as expected, 7 not as
expected, exit 1`, the seven being exactly the seven COUNTERPROOF rows. The counterproofs themselves go red
when the baseline contains the fix, which is the signature this whole family of bugs produces and which the
run's own history teaches an operator to read.

So the honest statement is: **adjusting the digests to match a wrong pin does not buy a green.** For a false
green you would need a commit whose three files are byte-identical to the fork point's — in which case the
counterproofs are running against exactly the right code, and nothing is wrong.

   with no digest skips the check silently. `nexus/` is another worker's this fire.

   not compared and why.* Three occurrences in one run; the census in §8 says there are ~90 more candidates.

   message — deliberate, but worth knowing before someone "fixes" it back.
