## Remedy chosen and why (call-through vs delete vs other)

**Chosen: call-through, for BOTH twins.** Each file is now ~50 lines of provenance comment plus:

```sh
RIG=$(cd "$(dirname "$0")/../.." && pwd)/pathb/t36/preconditions.sh    # ../../.. for audit-t44
[ -f "$RIG" ] || { echo "  FAIL  … rig is missing …" >&2
                   echo "PRECONDITIONS NOT RUN. DO NOT CAPTURE — nothing was asserted about the oracle." >&2
                   exit 2; }
. "$RIG"
```

Rulings the brief asked for, explicitly:

* **Is call-through possible? Yes, and nothing had to change to make it so.** Same single optional
  argument (tenant, default `gerege`); no working-directory dependence in the rig (verified: it
  resolves no path relative to itself and reads `CANARY_REQ` from the environment); the one caller
  that supplies `CANARY_REQ`, `bin/run-preconditions.sh:8`, already supplies exactly the
  digest-pinned file (`sha256 2a6621be…352154`, measured equal to the rig's `PIN_CANARY_SHA256`).
  No committed artefact pins the copy's bytes as a *dependency* — the only digest reference is a
  prose sentence in `AUDIT-CHARGES.md`, handled below.
* **Dot-source, not `exec`.** `exec sh "$RIG"` would pin the interpreter and destroy the `sh`-vs-
  `bash` invariance T85 required of T80. Sourcing preserves the caller's shell and inherits `"$@"`.
  Verified by running the whole suite under both (13/13 identical, all four labels).
* **Why not delete the named copy?** `AUDIT-CHARGES.md` names it as the provenance of a committed
  transcript (`out/PRECOND-default.txt`). A dangling name in an audit report is its own hazard.
* **Why not leave the named copy's bytes alone as "evidence"?** Considered and rejected. It is a
  *recipe*, not a capture — and the project's own precedent is that recipes get corrected after
  they have produced transcripts (T76 and T80 both edited `t36/preconditions.sh` after it had
  produced committed `preconditions.txt` files). The bytes are not lost:
  `git show e6c1795a172168105d788321a71ee4ca62b73e36`.
* **The one committed claim this falsifies, named so nobody trips over it.**
  `AUDIT-CHARGES.md:190` says this file, `charges/bin/preconditions.sh` and
  `pathb/t36/preconditions.sh` were "all three sha256 `9256b881…a46b54`". That was true when T44
  wrote it; it was **already false for the third** the moment T76 landed, and T91 makes it false
  for the other two. I did **not** edit `AUDIT-CHARGES.md` — it is another task's committed report.
  Instead the shim header states the change, the old blob id, and the reproduction result, so a
  reader who checks the digest finds the explanation in the file they are checking.
* **T44's finding survives.** Measured, not assumed: re-running the T44 control through the shim —
  `CANARY_REQ=<pinned> sh preconditions-COPY.sh default` — gives the **same 5 breaches** and the
  same exit 1. The transcript differs in exactly two places: one **added** `PASS  canary request
  pinned by DIGEST COMPARISON …` line, and a longer wording on the HTTP-404 FAIL line.
  [`.softhouse/capture/t91/out/happy/T44-control-reproduced-POSTFIX.txt`]
* **Net effect on the codebase: three divergent copies become one rig.** A third patched copy was
  never created, per T80's recommendation.
