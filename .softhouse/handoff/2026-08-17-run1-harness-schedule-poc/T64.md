## Derivation from source (with citations)

Every line was re-opened in `/Users/buv/fineract` at the pinned commit `426a23544`, clean tree.

**1. A repayment row's principal is `max(0, installment − due interest)`, full stop.**

```java
public Money getDuePrincipal() {
    // Due principal might be the maximum paid if there is pay-off or early repayment
    return MathUtil.max(MathUtil
            .negativeToZero(getEmiPlusCreditedAmountsPlusFutureUnrecognizedInterest().minus(getDueInterest(), getMc()), getMc()),
            getPaidPrincipal(), false);
}
```
[VERIFIED: `RepaymentPeriod.java:345-350`]

On the Path A origination seam nothing is paid and nothing is credited, so the first term is just
the period's installment and `getPaidPrincipal()` is zero. There is no "final principal := remaining
balance" rule — pattern P-6 settled that already.

**2. Both quantities are quantized to the currency scale before they meet.**
The installment is built through `Money.of(...)` [VERIFIED: `ProgressiveEMICalculator.java:1731-1733`],
the interest likewise [VERIFIED: `RepaymentPeriod.java:252-265`], and every `Money` quantizes in its
constructor: `amountScaled.setScale(currency.getDecimalPlaces(), getMc().getRoundingMode())`
[VERIFIED: `Money.java:52`]. For MNT that is 2 decimals under the ratified `HALF_UP`.

**3. The exact installment/interest gap never reaches zero.** The oracle folds the EMI rather than
using `pow` [VERIFIED: `ProgressiveEMICalculator.java:1725-1726`, `:1816-1827`, `calculateEMIValue`
at `:1838-1840`], and the closed form of what it folds gives, with `B` the principal in **minor
units** and `r` the per-period rate factor,

```
exact interest₁ = B·r
exact EMI       = B·r·(1+r)ⁿ / ((1+r)ⁿ − 1)
exact gap       = B·r / ((1+r)ⁿ − 1)      > 0 for every finite n
```

So **the two can only quantize onto the same minor unit when the gap closes below half a minor
unit.** That needs `B ≥ ceil(0.5/r)` (so the interest itself quantizes to ≥ 1 minor unit) and a long
enough term.

**4. The EMI smoothing loop must not undo it.** With every row amortizing zero the balance never
moves, so the final period absorbs the whole principal as residual
[VERIFIED: `ProgressiveEMICalculator.java:1202-1205`], and the smoothing loop then sees a
last-vs-penultimate gap of `B`. Its guard is

```java
public boolean shouldBeAdjusted() {
    double lowerHalfOfRelatedPeriods = Math.floor(numberOfRelatedPeriods() / 2.0);
    return lowerHalfOfRelatedPeriods > 0.0 && !emiDifference.isZero() && emiDifference.abs()
            .multipliedBy(100).isGreaterThan(originalEmi.copy(lowerHalfOfRelatedPeriods));
}
```
[VERIFIED: `EmiAdjustment.java:31-36`]

and **`Money.copy(double)` REPLACES the amount rather than scaling it**
[VERIFIED: `Money.java:216-222`], while `multipliedBy(100)` takes the `long` overload
[VERIFIED: `Money.java:380-390`]. In minor units the guard is therefore

> **`|emiDifference|_minor > floor(n/2)`**, i.e. on this shape **`B > floor(n/2)`**

so the loop stops firing at **`n ≥ 2·B`**. `uncountablePeriods` is identically zero at origination
[VERIFIED: `ProgressiveEMICalculator.java:2027-2031`].

### The derived bound, and the finding inside it

> **A repayment row can amortize exactly zero principal with non-zero interest only at the ROUNDING
> FLOOR: `B ≥ ceil(0.5/r)` and `n ≳ 2·B`, with `B` in MINOR UNITS.**

**That is the unflattering half of this task and it is a real result.** At a commercially realistic
Mongolian principal the term required is astronomical — MNT 10,000 at 21.6 % would need
`n ≈ 2,000,000`. **The path T59 profiled is reachable only in the dust region**, so a vector that
grades it has to live there, and the four promoted below are dust-principal loans on purpose rather
than by accident. Anyone reading `T64-ZP-A` and thinking "MNT 0.28 is not a loan" is right, and §3
is the reason there is no alternative inside the graded domain.

**Ten-rate check of the bound, run against the Go port BEFORE the oracle was asked** (the port as a
search device only, T61's precedent; `src/t64predict_test.go.txt`): `B_min` exact on **10 of 10**,
`n_min` exact on **8 of 10** and an over-estimate at 24 % and 60 %. `n ≥ 2·B` is therefore
**sufficient, not necessary** — the loop has four exits and those two shapes leave by a different
one (`hasLessEmiDifference` rejects the trial, which discards it and leaves the pre-trial
zero-principal schedule live [VERIFIED: `EmiAdjustment.java:45-47` applied at
`ProgressiveEMICalculator.java:1288-1290`]).

**Graded-domain check — no gate needed.** `GradedDomain` in `admit.go:999-1058` constrains currency
digits, the three rounding fields, disbursement cardinality, `repayment_every`, frequency unit,
interest method, day count, down payment, installment rounding, and the disbursement window. It
places **no bound on principal, term or rate**, and `NumberOfRepayments` was *deliberately removed*
as a graded-domain predicate in DEC-1 revision 4 (P2-T26-1) as "continuous or unbounded… graded by
sampling" — the same clause T59 cited when it declined to bound it. All four shapes are strictly
inside the ratified domain. **I did not widen anything and there is no gate to raise here.**

### FINDING — right answer, wrong reason (pattern P-11)

**`PREDICTION.md` §2.4 attributes the `n ≥ 2·B` threshold to the wrong mechanism.** It says the
smoothing *adjustment* `B/n` quantizes to zero and the loop breaks at
`ProgressiveEMICalculator.java:1270-1273`. It does not. The gate is `shouldBeAdjusted()` returning
**false** at `:1267-1269`, per the derivation above:

| | `\|emiDiff\|` minor | `floor(n/2)` | guard | outcome |
|---|---|---|---|---|
| `T64-ZP-A` (n=56) | 28 | 28 | `28 > 28` → **false** | loop never runs; 55 zero-principal rows |
| `T64-ZP-B` (n=55) | 28 | 27 | `28 > 27` → **true** | loop runs; pays off at period 15 |

Both readings yield `n ≥ 2·B`, **which is exactly why the wrong one survived a ten-rate check**.
Agreement on the answer is not agreement on the mechanism.

* The misreading is now a **named, measured counterfactual in the store**:

### A defect in my own measurement, found and fixed mid-task

The first red/green run reported identical BEFORE and AFTER for every mutation. Cause:
`conformance.FindRepoRoot(".")` walks up from the **process's working directory**, not from the
script's location [`registry.go:291-306`], so running the scratch copy's `conformance.sh` from
elsewhere silently graded the scratch's mutated binary **against the real store**. The second run
then reported exit 2 everywhere, because `admit.go` re-reads and re-digests every vector's
`provenance.capture_ref` and the 121 MB capture tree was not reachable in the scratch. Both are
fixed in `src/run-harness-mutations.sh`, with the reasons written where they bit. **A red/green rig
that cannot go red is decoration** — the control line exists precisely so this is caught, and it is
what caught it.

## Follow-ups

1. **F-1 — `ZP-PRINCIPAL-NOT-CLAMPED` is still ungraded at 36 vectors.** `MathUtil.negativeToZero`
   in `getDuePrincipal` [`RepaymentPeriod.java:345-350`] is a provable no-op on every promoted
   shape. To grade it the corpus needs a row where the installment falls **strictly below** the
   interest, which needs a *negative* residual large enough to push the final installment under its
   own interest. `applyFinalPeriodResidual`'s own clamp-and-recurse branch is the candidate region.
   Mark `TO_BE_CAPTURED`.
2. **F-2 — T59's backlog item is dischargeable now.** "Capture a long-term / near-interest-only
   vector from the reference oracle, then revisit the residual iteration" — the first half is done
   and `ZP-RESIDUAL-NO-RECURSION` goes red, so a future change to `applyFinalPeriodResidual` has an
   oracle. Note the vectors are at **n ≤ 72**, not n ≈ 1100, so they grade the *behaviour* and not
   the *cost cliff*.
3. **F-3 — the rounding-floor regime is a product question, not only a test one.** The oracle will
   happily emit a 56-period MNT 0.28 loan that accrues 0.56 in interest — twice the principal — and
   nothing in the graded domain forbids it. Whether the adapter should refuse a principal below some
