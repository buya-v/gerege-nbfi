### `CONTRACT_REL` — deleted, not wired up

`CONTRACT_REL="nexus/internal/apps/loanschedule/contract/contract.go"` was assigned
and never read anywhere in the script [VERIFIED: `grep -n CONTRACT_REL` returned the

I deleted it rather than wiring it up, for two reasons, and the second is the
binding one:

1. **The enforcement it looks like already exists, in Go.** The frozen DEC-1
   artefact's path is `PIN.json.contract_file` and its bytes are checked against

   not to do silently. Every use I could invent for it (a shell-side digest guard,
   a "contract.go is unmodified" HARD guard) is a new refusal condition, not a
   restatement of an existing one. Raised as follow-up F-1 instead.

The line is now a comment that states the above, so the next reader does not
re-add it thinking they are closing a hole.

## The proof, and the mutation it catches

### What it withdraws, and how

In a `mktemp -d` copy of the store (the live store is never written), on the
hand-authored `_selftest/SELFTEST-01-two-period-zero-rate.json` only, the **final
REPAYMENT row's** `outstanding_principal_minor` is withdrawn **through the store's
own mechanism**, not a side channel — the three things `admit.go:722-818` demands of
an honest withdrawal, all at once:

* `"outstanding_principal_minor": "0"` → `""`
* `"outstanding_principal_major_text": "0.00"` → `""`
* `"unrecorded_fields": []` → `["outstanding_principal_minor"]`

`assert_mutated` (already in the script) refuses to run the proof if that
perturbation did not apply, so it cannot go vacuous.

That cell is the right one because `registry.go`'s `contractFixesCellAtZero`
returns **false** for `outstanding_principal_minor` on a `REPAYMENT` row, so the
replay's stand-in `0` is a **placeholder, not the contract's own value**
[VERIFIED: `registry.go`, `contractFixesCellAtZero` returns true only for
`installment_number` / `interest_minor` on `DISBURSEMENT` / `DOWN_PAYMENT`]. It is
also the exact cell whose withdrawal produced T60's **silent false green**: the
placeholder is `0`, and `0` is precisely what `principal_amortizes_to_zero` looks
for, so the pre-fix rig printed `HOLD  final outstanding == 0` and `exit 0` over a
number nobody observed.

### What it asserts

Two runs, one verdict.

**Run A — the mutated store, scoped `-context=_selftest`:**

| # | Assertion | Which wrong answer it catches |
|---|---|---|
| A1 | exit code is `0` | FALSE VIOLATION |
| A2 | output does **not** contain `INVARIANT principal_amortizes_to_zero VIOLATED` | FALSE VIOLATION |
| A3 | output matches `SELFTEST-01-two-period-zero-rate .* principal_amortizes_to_zero \[N/A\]` | FALSE HOLD |
| A4 | output contains the `NOT ASSERTED: row 2: final outstanding == 0 cannot be asserted (outstanding_principal_minor never recorded by the capture` line | FALSE HOLD |
| A5 | summary matches `invariant assertions +[1-9][0-9]* NOT RUN` | FALSE HOLD |

A3 is the load-bearing one and it is **per-vector**: an invariant has exactly one
status per vector, so asserting `[N/A]` on this vector excludes `HOLD` on this
vector without counting anything.

**Run B — the PRISTINE store, unscoped, the anti-no-op control:**

| # | Assertion | What it catches |
|---|---|---|
| B1 | exit code is `0` | the fix broke the ordinary run |
| B2 | coverage line matches `principal_amortizes_to_zero +hold [1-9][0-9]* +violated 0` | the fix became a no-op — "not asserted" turned into a way to switch a check off |

**Pattern P-7 compliance.** No literal vector count appears anywhere in the proof.
A3/A4 are per-vector strings. A5 and B2 are `>= 1` regexes that grow with the
corpus. The corpus is 32 parity vectors today; nothing in this proof has to be
edited when it is 40. The two counts that *do* appear in the proof's echoed output
(`n/a 1`, `not-asserted 1`) are **printed, never asserted**.

**Failure messages are distinguishable by construction.** Each failed assertion
appends its own named reason to the `PROOF FAIL` line, prefixed `FALSE VIOLATION:`,
`FALSE HOLD:` or `control:`. The three mutations below produce three different
reason lists.

### The mutations, and which wrong answer each produces

Applied one at a time to the real Go source, `--prove` run, then reverted with
`git checkout --`. Verified reverted after each (`git status --porcelain` showed
only `M .softhouse/conformance.sh`).

| Mutation | Where | Wrong answer | Proof verdict |
|---|---|---|---|
| **M-A** — replay stops declaring placeholders (drop `placeholders.Add(i, f)`); this **is** the pre-T60 rig | `registry.go:207-209` | **FALSE HOLD**, silent | FAIL, exit **0/0**, three `FALSE HOLD:` reasons |
| **M-B** — the placeholder branch grades instead of declining (`InvariantNoData` → `InvariantViolated`) | `invariants.go:312` | **FALSE VIOLATION** | FAIL, exit **1/0**, two `FALSE VIOLATION:` reasons |
| **M-C** — the invariant never asserts anything, ever (`if true \|\| ph.Has(…)`) | `invariants.go:301` | **over-correction / no-op** | FAIL, exit **0/0**, the `control:` reason |

**M-A is the whole point of the task.** Its exit code is `0/0` — *the proof is what
catches it, not the exit code*. That is exactly why a green `--prove` run was not
evidence before this change, and why a Go package test alone was not enough: the
driver re-runs `--prove`, and `--prove` was blind here.

M-C is the guard in the other direction. Without it, "report N/A" could be
satisfied by an invariant that reports N/A always, which would silently retire a
check that currently holds 33 times.

## Follow-ups

1. **F-1 — a shell-side or Go-side guard that `contract.go` is byte-frozen at every
   run, not only when a store is loaded.** `VerifyContractDigest` runs inside
   `Admit`, so the digest is checked when there is a corpus to admit. Whether it
   should also be a HARD guard that fires before anything else — so that an edited
   contract is refused even on `--prove` or an empty store — is a real question and
   a NEW enforcement. That is why `CONTRACT_REL` was deleted rather than wired up.
   Cheap to add; needs a decision, not a silent edit.
2. **The other five invariants have no `--prove` proof of their placeholder
   behaviour.** This task added one, for `principal_amortizes_to_zero`, because
   that is the one whose placeholder value coincides with the value it looks for and
   therefore the one that fails *silently*. `balance_roll_forward`'s partial-hold
   path is exercised incidentally by the same proof (its NOT ASSERTED line is
   echoed) but not asserted. `contract_row_ordering`'s "one unkeyable row makes the
   whole ordering unkeyable → N/A" path is covered only by the Go test.
3. **Still open from T60 and untouched here:** `Result.PlaceholderCells` is
   populated and never printed (item 2); `DOWN_PAYMENT` rows remain unasserted by
   `balance_roll_forward` (item 3); the `.softhouse/vectors/README.md` store-count
   fact has no mechanical guard against going stale (item 5). The README's count is
   stale **right now** — it says 29 parity vectors and the corpus is 32
   [VERIFIED: the plain run reports `parity vectors PASS 32`]. Out of scope for T62
   (the README is not in my file scope); worth a one-line fix in the next task that
   touches the store.
4. **Pattern candidate for `.softhouse/patterns.md`** (not edited — out of scope):
   *a property proven only in a language-level unit test is not proven to the
   driver.* `--prove` is the artefact the orchestrator re-runs independently at
   every fire; a defect class that lives outside it can escape a green fire even
   with a green `go test`. This is the corollary of T60's own pattern candidate
   ("a guarantee enforced at one consumer and not another is not a guarantee") one
   level up, at the harness/driver boundary.
