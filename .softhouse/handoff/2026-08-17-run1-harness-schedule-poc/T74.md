## Headline

The Path A harness could not tell `CurrencyData.inMultiplesOf` from
`installmentAmountInMultiplesOf` — one field fed both, in three places, for six capture passes
(T21 P1-8, which is T19 required change 10). Pass 3i separates them and puts a 2×2 factorial to the
oracle at both currency scales.

**All of the money movement belongs to `CurrencyData.inMultiplesOf`. None of it belongs to
`installmentAmountInMultiplesOf`. And at the production `MinorUnitDigits = 2` neither input moves a
single cell.** So: **nothing was promoted from any of it**, for four independent reasons, and that is
the correct outcome rather than a shortfall.

What *was* promoted is the other half of the task — T21 P1-11's `36 × 16.8 %` small-principal shape,
six vectors, which turn out to be the first in this store that meaningfully grade the arithmetic
precision seam.

### The one refutation, in full

**S2 predicted** that `T74-D1-DP0-SMALL-CUR1000`'s final repayment row would carry
`principal 1000, interest 0, total 1000, balance 0`.

**The oracle emitted `balance 1000`.** Every one of the six rows carries `balance 1000`, including
the row that repays the whole principal. The other four cells of the claim were right.

**Why, verified from the pinned source** — and this matters more than the prediction did, because
pattern P-11 says the reason is the part the next contributor reuses:

`RepaymentPeriod.getOutstandingLoanBalance()` (`:389-402`) is a `Memo` whose dependency array is
`{paidPrincipal, paidInterest, interestPeriods, totalDisbursedAmount}`. **`emi` is not in it** —
unlike `getDueInterest()`'s memo at `:288-289`, which does list `emi`. With every EMI quantized to
zero by channel 1, every period is *vacuously* `isFullyPaid` (`:371-372` is
`emi + credited + FUI == totalPaid`, i.e. `0 == 0`), so `calculateLastUnpaidRepaymentPeriodEMI` takes
its `:1178-1181` fallback branch — whose last filter is
`rp.getOutstandingLoanBalance().isGreaterThanZero()`, **which populates the memo on the last
period**. `:1210` then raises that period's EMI to 1000 through a plain Lombok `@Setter` that
invalidates nothing, and nothing recomputes the balance afterwards: the smoothing loop breaks at
`:1267` because `shouldBeAdjusted()` is false, so `:1306` never runs.

**The guard that selects the target period is what stales that period's balance.**

I got the answer right about principal, interest and total by deriving the EMI path correctly, and
wrong about the balance by assuming it was derived after the residual absorption. It is not; it is
memoized before.

## Vectors promoted or NOT, and why

### NOT promoted: everything from groups A, B, C and D

Four reasons, each independently sufficient, and all four asserted in code by
`.softhouse/handoff/T74-promote-vectors.py` rather than only written down:

1. **The frozen contract has no field for it.** `contract.go`'s `Currency` struct carries `Code` and
   `MinorUnitDigits` and nothing else. A vector varying `CurrencyData.inMultiplesOf` **cannot be
   expressed as a contract request at all**. The binding promotion rule — promote only for a field
   the frozen contract actually returns — refuses it at the first step.
2. **`Currency.MinorUnitDigits == 2` is a graded-domain predicate.** Groups A, C and D all run at 0.
3. **`capabilities.json` records `currency.zero.decimals` with `in_graded_domain: false`**, and
   `contract.go:190-192` says the channel is one "this contract deliberately does not expose".
4. **`installment.rounding.multiple` is `blind` on `path_a_embeddable`** — and this capture is what
   PROVES it. An implementation honouring it and one ignoring it score identically, so a vector over
   it grades nothing. That is the T66 lesson applied.

Group B is the sharpest of the four and worth stating on its own: at the production
`decimalPlaces = 2` the observed blocks of `T74-B1`, `T74-B2` and `T74-B3` are **byte-identical to
the already-promoted `P-MNT-5M`**. A vector there would duplicate an existing vector while claiming
to grade an input it cannot move.

**`capabilities.json` was updated instead**, which is the mechanism the store provides for exactly
this: `installment.rounding.multiple` now records that its blindness is OBSERVED and not only
derived, and `currency.zero.decimals` now records the full measured gate, rule and consequences.

## Money-math notes

Money handled as **integer minor units** end to end. No float appears in `Capture3i.java` (`BigDecimal`
only), in `check-prediction.py`, `build-counterfactuals.py` or `T74-promote-vectors.py` (exact
integer-string scaling, and each refuses a significant digit beyond the currency scale rather than
rounding a transcription). At `decimalPlaces = 0` the "minor unit" is one whole tugrik, which is what
that currency record itself declares.

### The rule, pinned rather than merely observed

**Channel 1 — `Money.java:44-52`, the private constructor.** Gate is **four** conjuncts, not three:
`inMultiplesOf != null && decimalPlaces == 0 && inMultiplesOf > 0 && MathUtil.isGreaterThanZero(amountScaled)`.
Observed: `inMultiplesOf` of 0 and −100 are inert (`T74-C2`, `T74-C3` identical to baseline); 1 is
arithmetically inert at scale 0 (`T74-C1`); 7 and 1000 both move money, and 7 rules out any
implementation that "rounds to multiples" by shifting a decimal scale.

Rule: round to the **nearest** multiple, `existingVal.divide(m, 0, MoneyHelper.getRoundingMode()).multiply(m)`
(`Money.java:150-157`). `T74-A1` period 1 emits interest **77100** for an exact 77,083.33 — nearest,
not floored (which would be 77,000).

**Channel 2 — `ProgressiveEMICalculator.java:1761-1776`.** Gated on the *schedule model's* field,
touches the *installment only*, and carries a zero-guard (`safeRoundingForEMI`, `:1772-1774`) that
channel 1 does not have. **It never fires on Path A**: `LoanApplicationTerms.assembleFrom(LoanRepaymentScheduleModelData, MathContext)`
(`:579-607`) builds only through `Builder`, contains zero occurrences of `MultiplesOf`, and the
`Builder` has no setter — the field's only assignment is at `:828`, in a positional constructor this
path never reaches.

### Two consequences a port must not miss

**(a) Channel 1 rounds the DISBURSED PRINCIPAL.** `T74-C4-DP0-CUR7` requested MNT **5,000,000** and
the oracle emitted `totalDisbursedAmount` **5,000,002**, with the `DISBURSEMENT` row's principal and
balance both `5000002`. `assembleFrom` opens with `Money.of(modelData.currency(),
modelData.disbursementAmount(), mc)` (`:580`), straight through the leaking constructor. The borrower
is lent two tugriks nobody asked for, and the schedule amortizes them correctly. A port that
quantized only the output columns and not the input principal would diverge on every total.

**(b) Channel 1 has no zero-guard, and that is the observation that tells the two channels apart.**
`T74-D1` (MNT 1,000 / 6 × 21.6 %, `inMultiplesOf = 1000`) comes back with five of six EMIs at zero,
total interest `0`, and the balance-memo staleness described above. `safeRoundingForEMI` exists
precisely to stop a positive EMI rounding to zero — and it does not fire, because it belongs to the
channel this seam never reaches. **A mechanism identified by the absence of the guard that would have
stopped it.**

defeat, and it cannot be defeated by editing a file.

## Follow-ups

- **F-1 — separate the tenant rounding mode from the threaded one for channel 1.** Needs a capture
  whose threaded `MathContext` mode differs from `tenantRoundingModeValue`. That breaches
  `run-pass3i.sh`'s precondition 9, so it belongs in a **purpose-built probe** (the
  `run-rc6-rounddown-attestation.sh` pattern), never by weakening a parity recipe. The distinction is
  live for any port: `Money.java:154` reads the tenant mode while `:167` reads a parameter.
- **F-2 — is the stale-balance mechanism reachable inside the graded domain?** Candidate, fully
  specified: **MNT 0.01 / 6 × 21.6 %, `decimalPlaces = 2`, `(19, HALF_UP)`, start = disbursement =
  2024-01-01, no multiples-of anything.** The level installment is ≈ 0.0017, which quantizes to
  `0.00`, which should make every period vacuously `isFullyPaid` and drive
  `calculateLastUnpaidRepaymentPeriodEMI` into its `:1178-1181` fallback — the branch that poisons the
  memo. If it reproduces, the oracle emits a **graded-domain** schedule whose `balance` column does
  not amortize to zero, and the Go port (which derives the balance) would diverge: a promotable money
  kill on `schedule.core`, and a shape the corpus currently has no power over. **Register the
  prediction first.**
- **F-3 — a whole-FILE never-promotable mark has no home in `PIN.json`.** `Pin` uses
  `DisallowUnknownFields` (`admit.go:60-66`) and `NeverPromotable` is matched against
  `provenance.capture_case_id` (`:603`). Adding `never_promotable_capture_files` is a small Go change
  plus an admissibility check; worth doing the next time the harness is opened, so that "this
  artefact is superseded" is enforced rather than documented.
- **F-4 — the store README's "the MathContext is provenance, not a graded claim" section is now
  partly stale.** It says T55 witnessed no shape separating precision 19 from 12. The `T74-E-*`
  family does separate them, and `P-01` already did. I updated the "what this store holds" paragraph,
  which that file's own rule requires; I did **not** rewrite the section, because it is making a
  narrower point about T55's own shapes and rewriting it is a judgement the next author of that file
  should make with the harness's `WHAT THIS RUN DOES NOT GRADE` output in front of them.
- **F-5 — `installment.rounding.multiple` still has no vector, and now provably cannot get one on
  Path A.** It is `exercised` on `path_b_server` (capture B-02). If DEC-1 ever admits
  `InstallmentRoundingMultipleMinor` to the graded domain, the vector must come from Path B, and
  `capabilities.json` already says so.
- **F-6 — a Go port must decide what to do at `MinorUnitDigits == 0`.** Today the contract refuses it
  and the graded domain pins 2, which is correct and should stay. Pass 3i is the record of what the
  oracle does there if that is ever revisited — including lending two tugriks that were not
  requested.
