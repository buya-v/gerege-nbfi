### The refusal logic, and why there is no fallback

`prove-guards-go-red.sh` aborts with **exit 2 before any proof row runs** if the file is missing, is
not hex, is not 40 chars, or names an object that is not a commit here. All four exercised — see
`T102-merge-acceptance/no-fallback.txt`:

```
FATAL: …/FORK-POINT-SHA is missing.
       The counterproof baseline is a LITERAL sha and this rig has NO computed fallback:
       `main:`, `merge-base main HEAD` and every other moving ref resolve to code that
       CONTAINS THE FIX once this branch is merged. Restore the file; do not substitute a
       computed ref. See T102.
FATAL: …/FORK-POINT-SHA does not contain a 40-hex commit sha (read: 'not-a-sha').
FATAL: …/FORK-POINT-SHA must hold a FULL 40-hex sha; got 7 chars ('8da4b83').
FATAL: deadbeefdeadbeefdeadbeefdeadbeefdeadbeef is not a commit in this repository.
```

A silently-wrong baseline is worse than a missing one: it prints a **green** COUNTERPROOF row for a
comparison that never happened. The abbreviated-sha check is there because `8da4b83` (the form this
brief and T98 both used in prose) is exactly the kind of value someone would paste in, and a 7-hex
prefix can become ambiguous as the repo grows.

I chose the file over a hard-coded literal because the sha would otherwise have had to appear in the
shell rig **and** in two Python message strings, which is a drift surface. One file, one parser, one
loud failure mode.

### What this sweep could NOT have found

Stated plainly, because a sweep's limits are part of its result:

1. **Semantic moving refs with no textual match.** A baseline reached via `git describe`, a tag, a
   `.git/` file read, `git log -1 --format=%H`, a branch name in a variable, or a ref assembled from
   string fragments would not match any pattern I grepped. I read all five rig scripts end to end and
   saw none, but the *grep* is not what rules them out.
2. **Anything outside `.softhouse/` and this branch's 17 files.** I did not sweep `.claude/skills/`,
   `docs/`, `nexus/` or the repo root. Untouched by this branch, but a moving-ref baseline could
   exist there.
3. **The reverse defect.** I looked for refs that move. I did **not** systematically look for places
   that *should* track main and are now wrongly frozen. `FORK-POINT-SHA` is correct for this rig
   because the rig's baseline is definitionally "before this branch"; a literal sha would be a defect
   in a rig whose job is to compare against current main.
4. **Whether the pin stays meaningful after a rebase or history rewrite.** If this branch is rebased
   or `main` is rewritten, `8da4b83…` may become unreachable — at which point the rig **aborts with
   exit 2** ("not a commit in this repository") rather than silently mis-baselining. That is the
   designed behaviour, and it is exercised, but it is a *loud failure*, not immunity.
5. **The three-way and octopus merge cases.** I reproduced the two-parent merge the driver actually
   performs. A different merge topology could resolve computed refs differently; the literal pin is
   insensitive to all of them by construction, but I only *measured* the one.

## Follow-ups

1. **Re-measure the pin if this branch is rebased** before merge. `FORK-POINT-SHA` records the
   command; re-run it and update the last line. The rig will refuse loudly rather than mis-baseline,
   so this cannot fail silently — but it can block a run.
2. **A candidate pattern for `patterns.md`, if the driver agrees** — *"A proof that a fix works must
   be run in the state the defect occurs in."* This defect shipped twice because both repairs were
   verified on the branch, where the moving-baseline bug is dormant by construction. The corollary is
   sharper than P-22: **a rig whose result depends on the repository's merge state must be run in
   both states**, and the strongest form of the claim is not "the score matches" but "the transcripts
   are byte-identical".
3. **A second candidate** — *"A scratch worktree is not a scratch merge."* `git worktree add --detach
   <tmp> main` leaves `main` pointing at the pre-merge commit and hides exactly this defect class.
   Reproducing a merge-state bug needs a clone whose own `main` is the merge. A future worker told to
   "verify on a scratch merge" could pick the worktree and report a false green.
4. **Consider whether other rigs carry the same time bomb.** My sweep covered this branch and
   `.softhouse/`. `.claude/skills/`, `docs/` and any future proof harness were not swept, and the
   defect is invisible until the day something merges.
5. **T87's prediction was correct twice over and cheap to act on.** It named the class before either
   repair attempt. Worth noting in the postmortem that the reviewer's prediction, not the two
   subsequent fixes, is what identified the defect both times.
