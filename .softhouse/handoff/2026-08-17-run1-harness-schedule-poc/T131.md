## F-T108-1 — LATENT, not live

Confirmed at `.softhouse/conformance.sh:184` and `:201`: bare `grep -Eq`, reading **stdin from a pipe**, and
`conformance.sh` **sets no locale anywhere** — so it inherits ambient `LANG=C.UTF-8` and runs BSD grep in a
UTF-8 locale, the blind combination. My own demonstration on the pipe shape (T108's matrix only used file
arguments): a lone `0xE2` before a float on the same line → **`clean - PASSES`**, with `-a` inert and
`LC_ALL=C` fixing every cell. The clean control fires. This guards the first non-negotiable in CLAUDE.md.

**Latent** — measured with a detector I drove **red** first:

```
vector json files scanned: 49
files with any byte outside TAB/LF/CR/0x20-0x7e: 5
ANY INVALID UTF-8 BYTE ANYWHERE IN THE COMMITTED VECTOR STORE: False
```

Four qualifications the driver should carry forward:

1. **The store is NOT ASCII.** 5 vectors carry `e2 80 94` (U+2014), 15 line-occurrences —
   `capabilities.json` (9), `_selftest/SELFTEST-01-…:17`, `REFUSE-01-…:17`, `REFUSE-02-…:17`,
   `REFUSE-03-…:6` (2). **18 of 21 `.go` files** in `nexus/internal/apps/loanschedule` likewise.
   **T119's "all 47 `case_id`s are ASCII" does not extend to file contents.**
2. They are all **valid** UTF-8, which is the only reason the guard is not blind today.
3. **An undocumented second layer exists for JSON:** all 15 occurrences sit inside string literals, which the
   `perl -0pe 's/"(\\.|[^"\\])*"//g'` prefilter deletes before grep runs; and valid JSON can carry non-ASCII
   only inside strings. **That layer does not exist for `guard_no_float_in_harness`**, which strips comments
   only — there the Go compiler's UTF-8 requirement is the accidental substitute.
4. **One corrupted byte away:** truncating an existing `e2 80 94` to `e2 80` outside a string makes the guard
   silently pass (measured). Nothing enforces ASCII or validates UTF-8 on the way in.

**Latent by accident of content, in a guard that fails OPEN. Fix it — the fix does not depend on the answer.**
