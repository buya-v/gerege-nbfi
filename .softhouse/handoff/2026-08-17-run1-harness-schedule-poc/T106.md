### F1 — the required fix, exactly

```diff
   conformance_psub_seen="$(
     builtin eval '
+      _conformance_psub_line=
       IFS= builtin read -r _conformance_psub_line \
            < <(builtin printf "%s\n" "$CONFORMANCE_PSUB_TOKEN")
       builtin printf "%s" "$_conformance_psub_line"
     ' 2>/dev/null
   )"
```

A plain assignment, deliberately: it is not a command word, so unlike
`builtin unset -v …` nothing can shadow it. Mechanical, no number, no money logic.
Recommended in the same edit: add `_conformance_psub_line` to the trailing `unset`
list (it is the only probe variable omitted), and replace the two false
fail-closed sentences per F2.

Measured, on real bash 5.3.9 with `/dev/fd` removed and again on the host with the
redirection rewritten to a path that fails `open()`:

| | clean env | `_conformance_psub_line` pre-seeded |
|---|---|---|
| healthy psub, as shipped | 0 admitted | 0 admitted |
| healthy psub, **fixed** | 0 admitted | 0 admitted — no false refusal introduced |
| broken psub, as shipped | 3 refused | **0 admitted** ← the forge |
| broken psub, **fixed** | 3 refused | **3 refused** ← closed |

**Why it matters beyond tidiness.** A wrongly admitted run on a psub-dead shell reaches
the HARD guards, and both are `while IFS= read -r f; do … done < <(find …)` loops that
`return "$bad"` after the loop. With psub dead the redirection fails, the body never
runs, `bad` stays 0, and the function returns **0 having inspected zero files**
[VERIFIED: T106 — a guard-shaped function in that container returned 0 over an empty
set]. That is `guard_no_float_in_vectors` certifying "no floats" without opening a
file — the P-22 failure mode the harness's own line 53 cites. So unlike the residual
hijacks, this one **can** turn a red check green.

### F2 — ruling on the residual `builtin()` hijack (the review question)

T97 asked to be judged on: *no fixed point exists; the trade is one hijackable name
instead of three; it is fail-CLOSED; no fail-closed refusal can turn a red run green.*

- **"No fixed point" — correct**, and for a reason T97 did not give: in bash, function
  lookup precedes builtin lookup for **every** command word, and the only bypasses
  (`builtin`, `command`) are themselves command words. I could construct no
  command-free way to move a byte through `< <(…)`. The `builtin eval` change should
  stand; it closed a genuine false refusal (exported `eval()`), reproduced both ways.
- **"One name instead of three" — false.** `[` is a second one and the guard uses it
  four times [VERIFIED: T106, bash 5.3.9].
- **"Fail-CLOSED" — false.** The hijack does whatever the attacker's function body
  says; two bodies I wrote make the guard ADMIT a shell it correctly refuses when
  clean.
- **Therefore:** the honest statement, which is also simpler, is that **an environment
  able to export shell functions into this harness has already won** — it can shadow
  `find`, `perl`, `grep`, `sed` and `go` further down the file where nothing is checked
  at all. This guard defends against a **wrong invocation**, never against a hostile
  environment, and the comment should say that instead.
