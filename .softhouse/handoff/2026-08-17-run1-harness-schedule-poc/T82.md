### The proof rig, and why it is the real code under test

`run-pass3i.sh` cannot be re-run without docker, the pinned image and the pinned checkout — and
re-running it would produce a *new capture*, which is not what a defect fix has to demonstrate. What
it has to demonstrate is that the **precondition block goes red on an input built to break it**.

So `T82-guard-proofs/run-precondition-block.sh` **slices the `python3 - … <<'PY' … PY` heredoc out of
`run-pass3i.sh` byte for byte** (`sed` between the two anchors) and runs that exact text with the same
21 `argv` the script passes it, against a chosen capture JSON, writing its attestation to a scratch
path. Nothing is transcribed or paraphrased: change the block and the next proof run executes the
changed block. The pinned constants are read **out of the script** by `grep`, so they cannot drift
from it either.

**Control:** the committed capture through the corrected block is **exit 0**, and the sidecar it
produces is **byte-identical** to the one the *pre-edit* block produced [VERIFIED: `diff` clean].
So the corrections changed which inputs are refused and changed **nothing** about what a good run
emits.

## E-1: which option I took, and the guard firing

**I took option 1 — the table is written by hand — so an unregistered id is genuinely possible.**
The claim now stands over a guard that fires.

**Why not option 2 (delete the claim).** The claim is worth keeping: pass 3i deliberately carries
precision-12 companions, so a defaulted precision is the exact mechanism by which a discrimination
probe gets validated as a parity candidate. Deleting the claim would have left the *defaulting*
in place and merely stopped advertising it. The script already carries a 15-entry hand-written
`FIELD_SEPARATION` table for the same reason, so a literal table is the established idiom here, not a
new one. Cost: 36 lines.

**What was actually wrong, stated precisely.** The old form was

```python
CASE_PRECISION = {'P-CAL': 12}
for _id in EXPECTED_IDS:
    if _id not in CASE_PRECISION:
        CASE_PRECISION[_id] = 12 if _id.endswith('-p12') else 19
_unregistered = [i for i in EXPECTED_IDS if i not in CASE_PRECISION]
```

The loop's post-condition is exactly the predicate the next line tests, so `_unregistered` is `[]`
**for every possible `EXPECTED_IDS`**. It is not a weak guard; it is a guard with an empty domain.
And the replacement rule — `endswith('-p12') → 12, else 19` — is pass 3h's `.get(id, 19)` default
moved one layer down and keyed on a string suffix. **A P-15 violation inside the check advertised as
curing P-15**, exactly as T75 named it. [VERIFIED: read from the pre-T82 bytes, and reproduced by
running them — see the counterproof below.]

**The fix also closes the other direction.** A hand-written table can go *stale* — an entry for a case
the run no longer captures — so `_stale` is checked too. A table that outlives the cases it describes
has stopped being a check.

## E-3: the predicate, and it biting

**The old predicate was dead in BOTH directions — a stronger statement than the brief makes, and I
verified it before changing anything.**

```python
if ia["mathContextRoundingMode"] != ib["mathContextRoundingMode"] != "HALF_UP":
```

Python expands this to `(ia != ib) and (ib != "HALF_UP")`.

* **Both arms share a non-ratified mode** → first conjunct **False** → guard passes. This is the hole
  the brief names, and it is precisely the case the `varying` check above cannot see, because a value
  common to both arms does not vary.
* **The arms differ** → the guard *would* fire, but it never gets the chance: differing modes put
  `mathContextRoundingMode` into `varying`, `allowed` is `{"mathContextPrecision", "tenantId"}`, and
  the run already died at `raise SystemExit(... differ in more than the precision ...)` **two checks
  earlier**. [VERIFIED: observed in the E-3 one-arm proof below, which dies with the *varying*
  message, not the mode message.]

So the chained comparison could not fire on any input at all. The fix states the requirement
positively, per arm, with no chaining — each arm must be at the ratified `HALF_UP` of
`MathContext(19, HALF_UP)`.
