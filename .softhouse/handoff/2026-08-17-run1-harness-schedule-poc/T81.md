### The guard, and why it is not "is this bash?"

```sh
EXIT_WRONG_INTERPRETER=3
conformance_shell_why=""
if [ -z "${BASH_VERSION:-}" ]; then
  conformance_shell_why="BASH_VERSION is unset, so this shell is not bash at all."
elif ! ( eval 'while read -r _conformance_probe; do :; done < <(printf %s "")' ) >/dev/null 2>&1; then
  conformance_shell_why="this IS bash ${BASH_VERSION}, but process substitution '< <(...)' does not work in it."
fi
```

**A `BASH_VERSION`-only guard would have closed nothing on this machine.**
[VERIFIED: `/bin/sh --version` → `GNU bash, version 3.2.57(1)-release (arm64-apple-darwin25)`;
`/bin/sh /tmp/t81/psub_test.sh` printed `BASH_VERSION=3.2.57(1)-release` **and then**
`syntax error near unexpected token '<'`, exit 2.] `sh conformance.sh` and
`bash --posix conformance.sh` are *bash by every name test* and still cannot parse
the file, because bash 3.2 switches process substitution off in POSIX mode and
enters POSIX mode both ways. So the guard feature-tests the **capability**. A future
bash where POSIX mode keeps process substitution (5.1+) passes the test and is left
alone; I could not exercise that case — see `## Unverified`.

The `eval` runs in a subshell so a shell that aborts on a syntax error in a special
built-in kills only the subshell, and it is reached only once `BASH_VERSION` is known
to be set, so that `eval` is always bash's own.

The two branches report **different** reasons on purpose: zsh *has* process
substitution and is still fatal here (`BASH_SOURCE` unset → wrong `SCRIPT_DIR`), so
claiming a missing feature it actually has would send the next reader to the wrong
place.

## Which exit code I picked and why it is free

**Exit 3.**

Free, and I grepped rather than assumed:

- `grep -E 'exit [0-9]+|exit "?\$' .softhouse/conformance.sh` → every `exit` in the
  script is `0`, `$?`, or `"$EXIT_UNUSABLE"` (=2). There is no literal `exit 3`.
  [VERIFIED: grep output in this session.]
- The graded verdict comes from the Go binary, whose only codes are 0/1/2:
  `cmd/conformance/main.go` has four `os.Exit(2)` plus `os.Exit(summary.ExitCode())`,
  and `grade.go:154-172 ExitCode()` returns exactly `1`, `2`, `2`, or `0` — no other
  value is reachable. [VERIFIED: read `grade.go:154-172`, `main.go:41,76,85,105,108`.]
- `prove()` returns 0 or 1. [VERIFIED: `conformance.sh` `[ "$fail" -eq 0 ] || return 1`.]

Free of shell convention too:

- **0/1/2** are this harness's own verdict codes and are untouched. 3 is deliberately
  *not* 2, because 2 is simultaneously "oracle unreachable" and `/softhouse-program`'s
  oracle-is-down stop condition — the collision that created the defect.
- **126** = "found but cannot execute", **127** = "not found", **128+n** = death by
  signal (129–165 in practice), **255** = exit status out of range. 3 collides with
  none of them. It is inside the 3–125 range conventionally left to the application.
- **2** is also bash's own "builtin misuse / usage error" code, which is the *other*
  reason the old behaviour was unreadable: bash's syntax-error 2 and the harness's
  deliberate 2 were the same number. 3 has no such second owner.

3 also keeps the table dense and readable (0,1,2,3) and the header states plainly that
**3 is not a verdict, it is a refusal to start** — 0/1/2 remain the only three verdict
codes.
