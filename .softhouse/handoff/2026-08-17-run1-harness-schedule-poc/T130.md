## 1. F-T121-1 (P2) — the false `read` rule, corrected at three sites

T121 is right: T113 correctly withdrew T106's `IFS=e` claim and then shipped a **different**
false statement of bash `read` semantics in its place — in `conformance.sh`, in
`interpreter-matrix.sh` and in `T113.md`. P-11 exactly: the disposition is right and the
reason is wrong, and the reason is what the next contributor checks.

### 1a. I re-derived the rule rather than transcribing T121's phrasing

T121 states it as *"strips one trailing non-whitespace IFS delimiter, when it occurs exactly
once and is the final character"*. I did not take that on report; I turned it into a
**predicate** and brute-forced `read` against it:

> With IFS containing no whitespace, a single-variable `read -r` returns the line unchanged
> **unless** the line's LAST character is an IFS delimiter **and** that is the **only**
> position in the whole line holding **any** IFS delimiter — in which case exactly that one
> character is removed.

| sweep | cases | agree | disagree |
|---|---|---|---|
| every string of length 1..6 over `{a,b}` × IFS ∈ `{a, b, ab}` | 378 | 378 | **0** |
| every string of length 1..5 over `{a,b,c}` × IFS ∈ `{a, b, c, ab, bc, abc, :, a:}` | 2,904 | 2,904 | **0** |

**3,282 cases, 0 disagreements, on bash 3.2.57, 4.4.0 and 5.3.9 alike**
[VERIFIED: T130, `T130-evidence/read-ifs-predicate.sh`, committed and run on all three].

Note the sharpened part: the count is of **any** IFS delimiter, not of the final character.
`abcze` survives `IFS=ze` (two delimiter positions, different characters) while `abcz` does
not. T121's single-character phrasing is right on its own domain; the predicate is what the
comment now states, because a future editor may well use a two-character IFS.

Spot checks reproducing T121 exactly, identical on all three versions:

```
IFS=[z] abcz  -> abc   MANGLED       IFS=[z] abczz -> abczz INTACT
IFS=[z] zabc  -> zabc  INTACT        IFS=[z] zabcz -> zabcz INTACT
IFS=[z] abzc  -> abzc  INTACT        IFS=[ze] abcz  -> abc   MANGLED
IFS=[e] abce  -> abc   MANGLED       IFS=[ze] abcze -> abcze INTACT
conformance-psub-livz under IFS=[z] -> conformance-psub-liv  MANGLED
conformance-psub-live under IFS=[e] -> conformance-psub-live INTACT
```

## 2. **Removing the accident of spelling** — the assertion, and the red proof

The brief's harder half: *do not leave the guard's correctness resting on a coincidence
nobody will notice when they rename a string.*

### 2a. Why not "make the token structurally immune"

I costed the structural options first and rejected them for a reason I can state:

- **Doubling the emitted line** (`printf "%s%s\n"`) would make the last character repeat for
  *any* token, which is genuinely structural. But T106's rig greps the harness for the
  literal `< <(builtin printf "%s\n" "$CONFORMANCE_PSUB_TOKEN")` and for
  `      IFS= builtin read -r _conformance_psub_line`; changing either makes that rig
  **INERT (exit 1)**, and the brief requires it to reproduce **7/1** and forbids modifying
  it.
- **Changing only the token's VALUE** keeps both greps matching, but T106's rig seeds the
  literal `conformance-psub-live`. Post-fix row `[1]b` would then go red for **two** reasons
  at once — the fix, and a seed mismatch — destroying exactly the discrimination T121
  checked so carefully. An evidential downgrade for a cosmetic gain.
- **Not going through `read`** needs an external command (`cat`) or `read -N` (bash 4.1+),
  and the IFS trimming applies to `read -d ''` just the same. There is no version of this
  that keeps the probe self-contained.

So: **assert the invariant.** That is the brief's own second option, and it catches strictly
more than a structural token would — it also fires on whitespace in the token, and on a
future rename that breaks for some reason I have not thought of.

### 2b. What is asserted — `interpreter-matrix.sh` section `[6b]`, new

The token is now **read out of the harness** (`sed -n 's/^CONFORMANCE_PSUB_TOKEN="\(.*\)"$/\1/p'`),
never hard-coded in the rig, with an INERT refusal if that line is missing. It used to be a
literal, which is why a rename would have gone unnoticed. Then:

1. **Structural, spelling-independent.** (i) the token contains no whitespace; (ii) the
   token's last character occurs **earlier** in the token. Together these imply, from the
   measured predicate, that the token round-trips through a single-variable `read` under
   **every** IFS — because any IFS containing the final character finds at least two
   delimiter positions, and any IFS not containing it does not touch the last character.
2. **Empirically against `read` itself**, once per distinct character of the token's own
   alphabet, plus the whole alphabet at once and the doubled final character.
3. **End to end**, through a **prefix-deleted** copy of the harness, over **`BASH_ENV`** —
   the route that delivers. Run over `env IFS=` this leg would be a null control and would
   stay green straight through the defect.

Section `[6]` also now **asserts the routes themselves** before relying on them: an exported
IFS must arrive as the 3-character default, and a `BASH_ENV` one must arrive as `z`. So
"null control" is a measured statement rather than an excuse, and if a future bash starts
inheriting IFS the rig says so instead of quietly mislabelling twelve rows.

## 6. A defect T130 found in the rig it was sent to correct

**`interpreter-matrix.sh` produced a FALSE FAILURE on Alpine, and would on any host whose
`/bin/sh` is a non-bash shell with process substitution.**

T113 asserted `agree "/bin/sh" /bin/sh` unconditionally. `agree` means *"the guard's decision
must track the psub CAPABILITY"* — which is only the right rule for a shell that is bash.
Alpine's `/bin/sh` is **busybox ash, and it HAS process substitution** (capability `yes`),
while the guard correctly refuses it at 3 on `BASH_VERSION` being unset, before capability is
ever consulted. The rig reported:

```
FAIL  /bin/sh
      psub capability=yes but guard exit=3 — the decision does not track the capability
```

on a **correctly behaving harness**. That is the mirror of P-22: not a check that cannot
fail, but one that **fails on a correct system** — just as corrosive, because the next reader
learns to discount a red row. Fixed by asking what `/bin/sh` *is* first (`bashver`) and
routing it to the `[1b]` "not bash → must be refused at 3" rule otherwise. Both branches are
graded; neither is skipped.

Only T121's ad-hoc container matrices had ever run in an environment where this fires; the
committed rig had only ever been run on macOS and on the temurin image, where `/bin/sh` is
`dash`.
