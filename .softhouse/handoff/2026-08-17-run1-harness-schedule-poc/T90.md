### The order, and why it is total

* **Keys** (capability names, row kinds, seam-status capability names): they are keys of a
  Go map, therefore **pairwise distinct**. `sort.Strings` orders them by Go's byte-wise `<`
  over the UTF-8 encoding, which is a *strict total order on distinct strings*. No tie can
  arise, so the printed sequence is a function of the map's **contents alone** — not of
  insertion order, hash seed, map size, or toolchain version. This is why the answer is not
  "whatever `sort.Strings` gives on today's key shape": the argument does not depend on the
  shape, only on uniqueness, which the map type itself guarantees.
* **Values within a key** (counterfactual ids): these **repeat** — one entry per vector
  naming that counterfactual — so the line is a *multiset*, not a set. A sorted multiset of
  strings is unique, so byte-wise ascending is total here too, and `sort.Strings` being
  unstable cannot show, because equal strings are interchangeable by definition.
  `CapabilityRegistry.CounterfactualCoverage` already sorted them; `report.go` now sorts a
  copy as well, so the report's determinism is checkable **without leaving the file** and
  does not depend on a function three files away continuing to sort. Sorting an
  already-sorted slice is a no-op — proved, not assumed, by the byte-identity below.
* **Vector rows**: `(context, case_id, path)`, ascending byte-wise, with `path` unique ⇒ no
  ties ⇒ total.

## Sweep: what I searched for and what it could not find

**Searched (all over `nexus/internal/apps/loanschedule/**`, non-test unless stated):**

* `grep -rn 'map\['` — every map declaration, field and literal in the tree; each one traced
  to whether it is ever ranged.
* `grep -rn 'for .*range '` — **every** range loop in the tree (≈130), each ranged
  identifier resolved to its declaration to decide map vs slice. That is the net that found
  sites 2 and 3, neither of which the brief named.
* `grep -rn 'time\.Now|math/rand|rand\.|go func|goroutine|sync\.Map|os\.Getenv|filepath\.Glob|%p|unsafe'`
  → **zero hits**. So: no clocks, no randomness, no concurrency (hence no scheduler order),
  no environment reads, no pointer printing in the harness.
* `grep -rn 'sort\.'` — every comparator read for **tie-freedom**, not just for presence.
  That is what surfaced site 4; `sort.SliceStable` at `invariants.go:765` is stable and its
  input order is a slice, so it is fine.
* Directory iteration: `LoadStore` uses `os.ReadDir` twice, which Go documents as **sorted by
  filename**, and then re-sorts. `filepath.Glob` (also sorted) is not used.
* Output surfaces enumerated: `report.go` is the only writer of the report;
  `cmd/conformance/main.go` writes the `-list-implementations` list and three error strings.
  The harness **writes no files** (`grep -rn 'os.Create|WriteFile'` → none in non-test code).
* `_test.go` files, for map ranges — none (the three `range` hits there are slice ranges).

**What this sweep could NOT have found, stated plainly:**

1. **Order-dependence in sections no live run exercises.** Today's store produces 0 load
   errors, 0 fatal reasons, 0 refusals, 0 inadmissible vectors, 0 not-asserted invariants.
   The `FILES THAT COULD NOT BE READ`, `WHY THIS RUN CANNOT BE TRUSTED`, refusal-detail and
   `NOT ASSERTED` blocks were therefore **read**, not **measured**, in the 30-run
   experiment. I read them: each ranges a slice built in vector order. Reading is weaker
   evidence than measuring, and I am not claiming otherwise.
2. **Environment-shaped differences that are not bugs.** The report prints the **absolute
   store path** and the oracle probe result, so two runs from different worktrees, or one
   run while the oracle is down, produce different bytes *by design*. Byte-identity claims
   here are for one checkout, one store, one probe outcome.
3. **Data-shaped ties I do not have data for.** A future corpus with two vectors sharing a
   `case_id` would have been ordered by an unspecified rule; site 4 removes the tie, but no
   test in the store exercises that shape, and nothing yet *rejects* it (follow-up F-T90-1).
4. **Other Go versions / OS / arch.** Everything below is go1.26.6 darwin/arm64. Map
   iteration randomisation is a runtime property; a different runtime could hide the defect
   entirely and would make the pre-fix measurement look green.
5. **Nondeterminism in the shell layer.** I checked `conformance.sh` for clocks and durations
   and found none, and measured 3 full-script runs byte-identical — but I did not audit every
   branch of that script (its `--prove` mode builds binaries and copies stores).
6. **A grep cannot prove a negative about code paths added later.** `sortedKeys` is a
   convention, not an enforcement; nothing stops the next contributor from ranging a map
   directly (follow-up F-T90-4).

## Follow-ups

* **F-T90-1.** Nothing rejects two vectors sharing a `case_id` inside one context. The
  comparator no longer ties on it, but such a store is a corpus defect that would go
  unreported. A `LoadStore`/admit check would make it a fatal reason — deliberately **not**
  done here, because it can turn a 0 into a 2 and this task must not change any outcome.
* **F-T90-2.** The report embeds the **absolute** store path, so runs from two different
  worktrees can never be byte-identical. If reviewers are to diff a worker's run against a
  `main` run, the report needs a repo-relative path or a normalising flag. That changes report
  *content*, so it is out of T90's remit and needs its own task.
* **F-T90-3.** `sortedKeys` is a convention, not an enforcement. A token-aware test that fails
  on any `range` over a map type in this package would close the class the way
  `TestNoFloatInTheLoanScheduleTree` closes floats. Not added; it needs type information the
  existing scanner-based guard does not have.
* **F-T90-4 (for the driver, P-21).** `.softhouse/RESUME.md:94` still describes T90 as
  "`report.go:102` ranges an unsorted map … measured 27/3". After merge both halves are stale:
  the line number has moved and the defect is fixed. I did not edit it — that file is fire
  state owned by the orchestrator, and editing it would have been an unannounced out-of-scope
  change.
* **Carried, untouched, not mine:** `report.go`'s standing text that "no vector separates
  HALF_UP from HALF_EVEN" is the backlog item T61 falsified. It is prose in a section I did not
  open, and correcting it moves report bytes, which would have destroyed this task's proof.
