### 2. THE COUNT, MEASURED FROM `information_schema` — the T513 correction applied here

T513 found T510's "three" was really seven because it had been counted from the Liquibase XML. I
counted from the live schema. **The two figures are different things and both are reported:**

```sql
SELECT count(*) FROM information_schema.columns
WHERE table_schema='public' AND table_name='acc_gl_journal_entry'
  AND is_nullable='NO' AND column_default IS NULL;   -->  13
```

| measurement | value |
|---|---|
| NOT NULL columns with no default on `acc_gl_journal_entry`, **total** | **13** |
| of those, omitted by the (name-corrected) statement | **4** — `id`, `created_on_utc`, `last_modified_on_utc`, `submitted_on_date` |
| of those four, supplied by the server | **1** — `id` is `GENERATED BY DEFAULT AS IDENTITY` (`is_identity='YES'`, `identity_generation='BY DEFAULT'`), so omitting it is correct |
| **columns the statement actually had to gain** | **3** |

The 13 in full: `id`, `account_id`, `office_id`, `currency_code`, `transaction_id`, `entry_date`,
`type_enum`, `amount`, `created_by`, `last_modified_by`, `created_on_utc`, `last_modified_on_utc`,
`submitted_on_date`. **So T503's "three" is right for this table** — but it is right as an
*omission* count, and the table's NOT-NULL-no-default count is 13. The T513 failure mode was
counting one and reporting the other; both are stated here so no later reader has to guess which.

Two columns that look like the missing ones and are NOT: `reversed` and `manual_entry` are NOT NULL
**with** defaults (`false`), so they carry no obligation. The running-balance pair
(`office_running_balance`, `organization_running_balance`) are NOT NULL with default `0` and stay
untouched — G-12 / I-3 forbid this port writing them, and defaults are how they stay unwritten.

### 3. The fix

| column | before | after | authority |
|---|---|---|---|
| `createdby_id` | named, does not exist | **`created_by`** | `AuditableFieldsConstants.CREATED_BY_DB_FIELD = "created_by"` + information_schema |
| `lastmodifiedby_id` | named, does not exist | **`last_modified_by`** | `AuditableFieldsConstants.LAST_MODIFIED_BY_DB_FIELD` + information_schema |
| `created_date` | written `CURRENT_TIMESTAMP` | **dropped** | the oracle leaves it NULL — see §Money-math notes |
| `lastmodified_date` | written `CURRENT_TIMESTAMP` | **dropped** | same |
| `created_on_utc` | absent | **added**, `$12::timestamptz` | `DateUtils.getAuditOffsetDateTime()` |
| `last_modified_on_utc` | absent | **added**, the SAME `$12` | oracle writes one instant to both on insert |
| `submitted_on_date` | absent | **added**, `$13::date` | `DateUtils.getBusinessLocalDate()` |

Placeholders 11 → **13**; columns 13 → **14** (`$12` is selected twice). The statement is still ONE
fixed string literal, still an `INSERT`, still writes no balance column. T503's readability property
is preserved and re-verified (§Vectors run).

New knobs on `PostgresJournalEntryRepository`, all defaulting to something that cannot be silently
wrong:

- `SetAuditClock(func() time.Time)` — default `time.Now`; the value is `.UTC()`-normalised inside
  `Append` regardless of what the clock returns.
- `SetTenantLocation(*time.Location)` — a **zone**, never an offset. No default.
- `SetBusinessDate("yyyy-MM-dd")` — the COB override. No default. Validated by parsing and
  re-rendering, so `2026-2-3` and `2026-02-30` are both refused before reaching Postgres.
- `Append` **REFUSES** when neither is set, naming the reason and the source line. Rationale in
  §Money-math notes.

## Money-math notes

**No arithmetic changed. Not one line of money math is in this diff.** Amounts are still integer
minor units in Go, rendered to exact decimal text by `FormatDecimal`, and cast to `numeric` by
Postgres. There is no float anywhere on this path, in Go, on the wire, or in a fixture.

**The one money fact this diff newly proves, end to end.** `amount` is `numeric(19,6)`
`[VERIFIED: information_schema]`, so `25000025` minor units stores as `250000.250000` and reads back
through `amount::text` as `"250000.250000"`. `MinorUnitsFromDecimalText` accepts the trailing zeros
past scale 2 and returns `25000025`. The round trip **integer minor units → numeric(19,6) → integer
minor units** is now asserted against the real column type rather than assumed
`[VERIFIED: TestAppendExecutesAgainstTheRealSchema, live]`. Nothing had ever exercised it.

**`type_enum` is confirmed on both sides.** `JournalEntryType`: `CREDIT(1)`, `DEBIT(2)`
`[VERIFIED: fineract-core/.../journalentry/domain/JournalEntryType.java:23-24]`, and the live rows
carry `type_enum=2` on the debit leg and `1` on the credit leg. Go's `EntryCredit = 1`,
`EntryDebit = 2` (`money.go:214-215`) match. Now asserted through a real write and read-back.

**Where each new value comes from.**

`created_on_utc` / `last_modified_on_utc` — `JournalEntry` extends
`AbstractAuditableWithUTCDateTimeCustom`, whose `createdDate`/`lastModifiedDate` map to
`created_on_utc`/`last_modified_on_utc` and are stamped by `CustomAuditingHandler`, which selects
`CustomDateTimeProvider.UTC` for exactly that base class → `DateUtils.getAuditOffsetDateTime()` =
`OffsetDateTime.now(ZoneOffset.UTC)` `[VERIFIED: source, four files, plus the live rows]`. So: pure
UTC, no tenant zone, and equal on both columns at insert.

*One deliberate simplification, stated rather than hidden.* The oracle stamps each entity
separately at flush, so its two legs differ by microseconds — **observed**, `.289487` vs `.294834`.
This port uses ONE instant for the whole batch. That difference carries no information, is not
deterministic, and no vector can pin it; what the capture does pin — UTC, and
`created_on_utc == last_modified_on_utc` — holds here structurally, because one array feeds both
columns. A shadow-parity comparator must treat these two columns as **wall-clock, compare-by-
tolerance**, never byte-equal, on either implementation.

`submitted_on_date` — `this.submittedOnDate = DateUtils.getBusinessLocalDate()`
`[VERIFIED: fineract-accounting/.../journalentry/domain/JournalEntry.java:136]` →
`ThreadLocalContextUtil.getBusinessDate()` `[DateUtils.java:238-240]`, whose map is built by
`BusinessDateReadPlatformServiceImpl.getBusinessDates()` `[:72-83]`:

```java
LocalDate tenantDate = DateUtils.getLocalDateOfTenant();     // LocalDate.now(tenant zone)
businessDateMap.put(BusinessDateType.BUSINESS_DATE, tenantDate);
if (configurationDomainService.isBusinessDateEnabled()) { ...overwritten from m_business_date... }
```

Two branches, and the port has exactly two: `SetTenantLocation` (today in the tenant's zone) and
`SetBusinessDate` (the COB override). **`enable_business_date` is absent from `c_configuration` on
this instance** `[VERIFIED: live query]`, so the capture exercised the first branch only; the second
is implemented from source and is `[UNVERIFIED: not observed against a business-date-enabled tenant]`.

**WHY THERE IS NO DEFAULT, and why refusing is the right answer.** Every available default is wrong
in a way no error message would ever reveal:

- *default to the UTC date* — hard-codes an offset in all but name. For a `+08` tenant every posting
  made after 16:00 UTC would be stamped with **yesterday's** date. The unit test
  `TestSubmittedOnDateComesFromTheTENANTZone` fixes an instant at `2026-09-03T17:30:00Z` — still
  3 September in UTC, already **4 September** in both `Asia/Ulaanbaatar` (+08) and `Asia/Hovd` (+07),
  the only two zones CLAUDE.md permits — and pins `2026-09-04`.
- *default to `entry_date`* — writes a value the oracle demonstrably never writes; red drive (c).
- *default to the host's local date* — the port's host zone is not the tenant's zone.

So `Append` refuses, naming the column, the constraint, the oracle source line, and the two methods
that fix it. Classified **ENGINEERING** under CLAUDE.md § Answering gates and decided here
(`chosen_by: agent`); reversible, and nothing downstream depends on the default's absence.

**Why `created_date` / `lastmodified_date` were DROPPED, which is the least obvious change here.**
Three independent lines agree: (i) `JournalEntry`'s auditable base class maps only the `_on_utc`
pair — there is no mapping to the legacy columns at all; (ii) the oracle's own hand-written
journal-entry INSERT names 27 columns and **neither** of them
`[VERIFIED: fineract-savings/.../SavingsSchedularInterestPoster.java:164-170]`; (iii) the live
capture wrote **NULL** to both. Keeping the `CURRENT_TIMESTAMP` writes would have made **every**
Go-written row differ from **every** oracle-written row, on two columns carrying no information —
i.e. it would have poisoned a shadow-parity window before one was ever run. Both columns are
nullable, so dropping them is legal `[VERIFIED: information_schema]`.

**I-3 and I-4 hold.** Still exactly one statement; still an `INSERT`; no `UPDATE` or `DELETE` against
`acc_gl_journal_entry` anywhere in the diff; corrections remain reversing entries. No balance column
is written — `office_running_balance` and `organization_running_balance` keep their schema default
of `0`, which is how they stay derived. The DB-backed test **rolls back** and never commits, so it
does not itself append to a ledger.

  `submitted_on_date` is resolved per `Append` call, which is what a single posting means; a batch
  held open across midnight would stamp them all with the earlier date. The oracle would too, since
  its business date is per-request, but that was not tested.
- `[UNVERIFIED]` **That the write path is now correct for any caller.** It still has **no callers.**
  This task made the statement *executable* and *tested*; it did not wire it into the posting path.
- `[UNVERIFIED]` **That `created_by = 1` is right for production.** The default is the oracle's
  `ADMIN_USER_ID = 1L` `[VERIFIED: AppUserConstants.java:35]`, which `AuditorAwareImpl` also falls

4. **Audit the other three statements T503 made readable** for the same defect class. T508 examined

   family, not an incident. A cheap sweep: `PREPARE` every literal in the tree against the live
   schema. **`PREPARE` alone is not enough** — it passes a statement that omits a NOT NULL column;
   it takes an `EXECUTE` inside a rolled-back transaction to find those, which is exactly why the
   first defect here was visible and the second was not.
5. **A shadow-parity comparator must special-case the two `_on_utc` columns** as wall-clock
   (compare-by-tolerance), and must expect `created_date` / `lastmodified_date` to be NULL on both
   sides for this table.
6. **The T503 backlog item is still open**: the guard's argument heuristic skips a leading context
   only when it is a bare identifier, which is why `Append` still assigns `ctx := r.ctx` before the
   call. Teaching it to skip a ctx-named selector would remove a workaround from money code.
